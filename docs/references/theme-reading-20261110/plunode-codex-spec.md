改訂日：2026年11月10日 JST

## 今回の改訂点

この版は初版の全文改訂版。次の指摘を、追記だけでなく本文・表示規則・受入条件にも反映した。

- 「範囲」という語を禁止したり「※」へ置換したりする話ではない。補足文の視覚的な強さ・位置・面積が、主軸の魅力を奪っていることを直す。
- 情報を残すことと、すべてを前面に同じ強さで並べることを分ける。情報保持だけでは合格にしない。
- 引きのある導入とテーマ画像を本実装の対象にする。その導入に応えるデータを集める編集方針を持ち、「既存データにないので魅力を削る」で終えない。
- テーマ詳細への明示的な導線を上部に置き、テーマのSEOまで同じ実装範囲に含める。
- 年表を展開しても右の詳細と同じ情報が出る構成をやめる。流れをつかむ表示と深く読む表示の役割を分ける。
- 種別・状態はバッジで記号化する。情報をすべて無装飾の文章に戻して平坦化しない。
- 「テーマの情報6件」は主導入と分離し、グラフ・年表の下へ移す案を基本試作とする。上部で閉じる案も比較対象として残す。

## 0. 目的と判断基準

完成させたいのは、検索から来た人が「何が面白いのか」を導入と画像でつかみ、年表・図を辿り、気になったところを詳細で深く読める画面。情報の残存だけでなく、読む順番と視線の主従を成立させる。

生成案の引きのある導入、画像、種別バッジ、見出し、余白、本文と補足の差を実装対象にする。「あくまでイメージ」としてこれらを省いた実装を完成扱いにしない。画面内の文章を全部同じサイズ・色・重さにそろえる方向へ戻さない。

判断の順序：
1. テーマの魅力と中心となる内容が最初に目に入り、何を読む画面かが分かる。
2. 次の操作で得られる情報が分かり、年表と詳細が別の役割を持つ。
3. 詳細・出典・補足へ辿れ、元の読書位置へ戻れる。補足は主内容を押しのけない。
4. この体験を実現するための構成を選ぶ。実装の容易さを理由に上記を省かない。
5. 全件手作業や閲覧ごとのAI生成など、継続的な運営負担を増やしすぎない。

不変条件：
- 事実、対象、関係の方向、肯否、時間の意味、適用範囲を見た目のために改変しない。ただし、同じ強さで表示する義務はない。
- 本文・出典・引用・該当箇所・版参照・翻訳・訂正入口を保持する。移設した項目には到達先を定める。
- scopeは補足であり、主文と同じ温度感の見出し・カード・バッジ・注意枠にはしない。「範囲」の文字列を変えるだけで解決したことにしない。
- 生成案の編集方向・視覚設計は具体化する。一方、生成された解説文・商品名・書影・科学的主張は未検証のまま事実として公開しない。
- 商品がない地域での表示は未決定。非表示を一律の確定要件にしない。
- グラフ操作を購入リンクへ置き換えない。出典と商品推薦を混ぜない。
- 既存の公開／非公開、内容版、構成版、資料版、翻訳版を保持する。

## 2. 画面の役割と視覚的な主従

### 2.1 テーマ上部：読む理由を先に伝える

ここでの「上部」は、テーマを開いた中央コンテンツの先頭を指す。サイト全体のヘッダーを大型化する話ではない。

構成：
- テーマ名。
- テーマ画像と、引きのある導入文。見た人が「何を知れるのか」「なぜ続きを見たいのか」をつかめる。
- 短い説明と、文字で読める「このテーマについて」へのリンク。小さな本アイコンのみを入口にしない。
- 関係図・年表は直後に続き、既存の探索と別サービスのように分断しない。

導入例「Webbが赤外線で見た宇宙は、私たちの宇宙観をどう広げたのか。」は編集の方向として維持する。既存の収録が開発史だけなら、導入を機械的に弱めるのではなく、観測・発見まで何が不足しているかを収集計画へ落とす。未収集の答えを捏造せず、導入と内容の対応まで作る。単に生成案から既存descriptionを流し込んで完了にしない。

既存のtheme.descriptionは詳細本文として再利用可能。短い導入と同一でよいテーマは兼用できるが、必ず長文から先頭N文字を切り取る設計にはしない。独立した導入が必要なら、対象の版・言語と結びついた編集用情報を持つ（第4章）。

「このテーマについて」は右欄のテーマ詳細を開く。年表・グラフの位置と選択中の記録は保持し、「読んでいた記録へ戻る」で復帰できる。スマートフォンでも同じ目的の入口を使う。

### 2.2 年表：流れをつかむ

通常のカードは、日付、具体的な見出しまたは短い主文、必要な種別・状態バッジで構成する。詳細の全文・scope・引用・版情報をコピーした展開領域は設けない。

- 例：1996年／「赤外線宇宙望遠鏡の開発をNASAへ提言」／出来事バッジ。
- 見出しは編集済みの短文または適切な時間ラベルを用いる。未整備の記録は既存assertionを使えるが、読みづらい全件を放置して完成扱いにはしない。
- カード選択で詳細欄を更新する。折りたたみの山形アイコンで「年表内にもっと本文がある」と誤認させない。選択色・枠・接続点で現在位置を示す。
- 「根拠を見る」は同じ詳細欄の出典位置を直接開く。年表内にもう一組の引用を作らない。
- 年表内の開閉は、子年表・下位の出来事など本当に別の情報が増える場合に使う。内容と操作名を一致させる。
- 時点／継続期間／発生時期の幅、年・月・日の精度は表現上も保持する。毎カードに同じ説明文を繰り返すのではなく、時間表現と共通の凡例で伝える。
- scopeは年表カードから外し、同じ記録の詳細に一度だけ置く。期間表示そのものの意味はscopeの長文に依存させない。

### 2.3 詳細：選んだ先で理解が進む

同じ見出しや対象名を繰り返して位置を示すことと、全文を丸ごと二重表示することを分ける。詳細では、年表の短文から先に進める本文、必要な補足解説、関係する対象、根拠・引用を読む。

| 対象 | 読む順番と役割 |
|---|---|
| テーマ | タイトル・導入 → このテーマが辿る問いと流れ → 収録内容・関連テーマ → 出典への入口 → 関連する本・作品 → 記録情報 |
| 人物・作品等のEntity | 種別バッジ・名前 → 説明 → このテーマとの関わり → 他の関係やテーマ → 関連する本・作品 → 別名等の補助情報・記録情報 |
| 出来事・関係・説明のRecord | 種別／状態バッジ・具体的な見出し → 本文 → 必要な場合のみ背景・重要性 → 出典 → 関連する対象 → 関連する本・作品 → 記録情報 |

scopeの短い注記は本文直下へ小さく添える。長いものは詳細下部の補足群にまとめる。いずれも独立した主セクション・強調枠にしない。

すべての記録に「なぜ重要なのか」「わかること」の2区画を埋める必要はない。同じ内容を3種類の言い方で水増ししない。本文と出典の詳しい確認だけでも追加の価値になる。新しい解説が必要な代表テーマには、実際に根拠付き解説を用意する。

右欄の先頭を「詳細」「出来事・説明」という汎用見出しの重複にしない。具体的な見出しを主役にし、その種別は小さなバッジへ移す。

### 2.4 関係図と下部のテーマ情報

グラフは対象と関係を理解する場所。ノードはEntity詳細、線は関係の詳細へ結ぶ。選択フィードバックと現在読んでいる情報を一致させる。購入ページへ直接移動させない。

「テーマの情報6件」は、テーマ画像・導入の代わりに上部を占有しない。基本試作では年表／図の下に、開いた状態の読みやすい一覧として配置する。中央コンテンツの縦スクロール内に置き、固定高さの図のさらに内側に埋め込んで到達困難にしない。

比較候補は「上部に閉じた小さな入口」。いずれも確定済みデザインとはせず、主導入の邪魔をしないことと本文への到達性で比較する。「開いた下部一覧」の候補を実装都合で除外しない。

下部一覧は、日時のない記録を全件保持する。説明文をクリックすれば右欄で本文・出典を読める。単一の紹介文へ潰さない。件数や管理用の種類を主役にせず、何の説明があるかが読める項目名にする。件数が多い場合の追加表示は明示し、黙って数件で打ち切らない。

### 2.5 文字・バッジ・余白の設計

以下の数値は実画面比較の開始値であり、全画面一律の文字拡大を指示するものではない。

| 階層 | 対象 | 表現の案 |
|---|---|---|
| 主役 | テーマ名、引きのある導入、テーマ画像 | タイトル24〜32px、導入16〜18px程度。太さと余白で最も目に入る位置を作る |
| 内容 | 年表の主文、詳細の見出しと本文 | 見出し18〜22px、本文14〜16px程度。読み進める順が分かるまとまり |
| 記号 | 出来事・関係・人物等の種別、否定・不確実等の状態 | 短いラベル＋小さなアイコン＋淡い地色／境界。定位置に置き、文章行を増やさない |
| 補助 | scope、原文情報、版など | scopeは11〜12px程度の非強調注記が候補。本文より落ち着いた色・小さな余白。独立した背景、太字、アイコン、カード枠を使わない。版・内部情報は下部の記録情報へ |

補足は小さくするだけでなく、重複を取り除き、必要な場所にまとめ、画面占有を抑える。小さい文字で画面を埋める方向にも、全部を大きくして目立たせる方向にも寄せない。

バッジの規則：
- 種別と状態は別の意味として扱い、配置・形・色の役割を固定する。画像の「出来事」バッジを実装対象にする。
- 状態バッジは否定・不確実などを短く示す。単なる「肯定」を「検証済み」「確実」の認証マークへ変えない。
- 色だけに意味を任せず、ラベル／アイコンでも区別する。クリックできないバッジはボタンの見た目や挙動にしない。
- scope、すべての版番号、すべてのメタデータをバッジ化しない。記号の過剰増殖で主文の視認性を落とさない。
- 出典の支持／反証／背景は出典に属する表示。記録の肯否と混同しない。

小さな注記にも可読性は残す。WCAGの通常文字の最低コントラスト4.5:1を確認し、主従はサイズ・太さ・位置・余白も使って作る。これは補足を主役と同じ見た目へ戻す理由にはしない。[W4]

## 3. 情報の移設表

| 現在の情報 | 新しい通常表示 | 移動先・保持方法 |
|---|---|---|
| テーマ名・説明 | 上部の引きのある導入、詳細への明示リンク | 詳しい説明はテーマ詳細。導入と説明は必要に応じ分離して管理 |
| テーマ画像 | 導入と組にして上部に表示 | 第4章の画像管理。TOPカードとOG画像にも共通の編集資産を利用 |
| 日時のない複数記録 | 基本案は図／年表の下の開いた一覧 | 全件を辿れ、選択で記録詳細へ。上部折りたたみ案も比較 |
| assertion／relation | 年表は短い主文、図は関係の言葉 | 詳細に全文・説明・根拠。年表の全文展開を重複実装しない |
| scope | 年表では繰り返さない。詳細本文下の小さな非強調注記 | 長文は詳細下部の補足群へ。専用の「範囲を開く」操作を新設しない |
| 肯定／否定／不確実 | 種別と区別された状態バッジ | 機械的な肯定ラベルは通常表示から外せる。否定・不確実の意味は保持 |
| 時間・精度・期間と発生幅 | 読みやすい日付と時間の記号 | 複雑な時間注釈と共通凡例。毎カードの説明文重複を削減 |
| 資料名・リンク | 詳細の出典欄 | 年表からは対象を指定して同じ出典欄へ移動 |
| 支持・反証・背景 | 出典に添える小さな表示 | 一律「根拠あり」に統合しない |
| 引用・該当箇所・書誌 | 詳細の出典ごとに短い入口 | 「引用と該当箇所を読む」で同じ場所に展開。押した出典を直接開ける |
| 原文言語・翻訳 | 人が分かる言語名と翻訳の入口 | 原文・訳文・参照版を保持。単独の言語コードを主文の途中に差し込まない |
| 内容版・資料版・構成版 | 主文から離す | 記録情報に種類別でまとめる。閲覧版の切替は黙って行わない |
| 意味対応・旧版対応 | 通常は読書の前面に出さない | 記録情報。検索条件に影響する場合は当該条件に結びついた説明を使う |
| 投稿者・訂正・編集 | 目的の分かる控えめな入口 | 既存権限と文脈を保持し、閲覧用と管理用を混ぜない |
| 別名・同一対象・関連テーマ | Entityの本文・文脈に続ける | 同名を推測で統合しない。テーマ内と全体の情報を区別 |
| 保存・戻る・共有等 | 操作の目的と選択状態が分かる表示 | Undo、Capsule、言語、共有・復元を維持 |
| 既存広告 | 購入カードとは別の判断対象 | 生成画像から消えているという理由だけで削除しない |

### scopeの扱い：語句ではなく視覚的な優先順位

対象例：
> 範囲：次世代宇宙望遠鏡の開発提言。提言と完成機の仕様・完成時期を同一視しない。

この文は補足。「範囲」というラベルは保持してよい。「※」への置換も必須ではなく、それで視覚的なノイズが解決したことにはしない。本文と同じ文字サイズ、濃さ、独立した段落余白で表示する状態をやめる。

短い注記は、詳細の本文下に小さく・落ち着いた色・短い間隔で一度だけ置く。年表側にも同文を繰り返さない。長い補足は、同じ詳細の下部にある補足情報へまとめ、主役の見出しや解説より先に目立たせない。

scope専用のカード、警告帯、バッジ、新しい開閉ボタンを作らない。本文の短い見出しから削った重要語をscopeで説明して帳尻を合わせない。本文は本文として誤解なく成立させ、その後に補足を添える。

この変更では原文の言い換えを必須にしない。別途文章を編集するときは、UIの配置変更とは分けて既存の訂正・版管理へ載せる。

## 4. 引きのあるテーマ・解説・画像を実データにする

### 4.1 導入に沿って収集する

テーマの理想形を「現在あるデータを一覧にしてから無難な説明を付ける」に限定しない。読む理由となる問い／切り口を決め、その問いに応える資料と記録を集める。

Webbの導入例を採る場合の編集・収集設計：
1. 「宇宙観をどう広げたのか」を読者に約束する問いとして明示する。
2. その問いに答えるには何を知る必要があるかを整理する。例：なぜその観測方法を選んだのか、開発・展開をどう乗り越えたのか、どの観測・知見につながったのか。
3. 既存の記録で説明できる部分と、資料収集・解説追加が必要な部分を対応表にする。
4. 収集した根拠から本文と補足を整える。画像だけ魅力的で実画面では答えがない、という状態を完成にしない。

上記は収集方針の具体化であり、今回の文書更新で収集計画の登録・公開・自動実行を行ったという意味ではない。既存のスケジュールや登録内容は変更しない。

### 4.2 読みやすい見出しと補足解説

「なぜ重要なのか」「わかること」は既存フィールドを並べ替えるだけでは生まれないが、だから実装から除外するのではない。必要な代表記録には、根拠付きの解説を用意して実際に表示する。

- 既存のnoteとaboutRecord／aboutThemeで原記録に結びつけることを基本候補とする。
- 「背景」「重要性」「次に読む」など表示上の役割は、編集用の指定として管理する。noteという種類だけから重要性と決めない。
- 短い記録見出し、年表向けの主文、テーマのhook／leadは任意の編集用情報として持てる。参照する対象ID・版・言語を明示する。
- 自動生成する場合は収集・編集時の候補生成にとどめ、確認済みの公開版を表示に使う。閲覧ごとの生成と追加コストを前提にしない。
- 解説がない記録でも、原文と出典で読める形を作る。全件を同じ解説テンプレートで埋めない。
- 元の内容が更新された場合、解説・短文・翻訳の対象版を確認する。古い主張を新しい版の確定解説として黙って載せない。

表示用情報の案：target(kind/id/revision)、locale、shortTitle、timelineSummary、hook/lead（theme）、explanationRefs（参照先の版と表示役割）、imageRef、編集状態。最終の保存形は既存の版・翻訳・承認モデルに合わせる。事実の本文を上書きする別データベースを作る意図ではない。

### 4.3 画像は納品・検証対象

生成案の望遠鏡画像に相当するテーマビジュアルを、本番UIの構成要素として作る。画像の調達・保存・配置・代替状態・クレジットまでを仕様に含める。「権利確認が必要なので省略」で終わらせない。

基本案：導入の横にテーマ固有の写真またはイラストを配置する。PCではおおむね幅160〜220pxから比較し、導入全体がグラフを押し下げすぎないよう高さを調整する。スマートフォンでは同じテーマ画像の小さいトリミングを使い、中心の被写体が切れないようにする。細部は生成案と実データの並列比較で決める。

画像データ：asset ID、画像ファイル、種別（写真／イラスト等）、alt、短いcaption、作者／提供者、source URL、利用条件と確認日、トリミングの焦点位置。表示用画像とOG画像は同じ編集資産から作るが、表示サイズに合わせた派生画像を用意する。

調達経路：
- 個別の権利を確認できる公式画像、または自作・利用許諾のあるイラストを登録する。
- NASA資料も一律に自由使用とみなさず、画像ごとの第三者クレジットと公式の利用案内を確認する。NASAの推薦・提携と誤認させない。[W5]
- 生成案にある一般的な望遠鏡をJWSTの実機写真と誤認させない。概念的なイラストならその役割を保つ。科学的な対象の表示と、テーマの雰囲気を伝える表現を区別する。

技術条件：HTMLのimg／picture等で表示し、サイズを先に確保する。画像だけでタイトルや導入文を描画しない。内容画像は適切なalt、純装飾は空alt。画像なし・読み込み失敗のレイアウトも用意するが、代表テーマは実画像込みで検証する。画像なしの代替状態だけを実装して画像対応完了としない。[W3]

TOPのテーマカード、テーマ上部、共有用OG画像を同じテーマ編集情報から構成し、三か所を手作業で別々に更新する運用を避ける。

## 5. 操作と復帰

### 年表 → 詳細 → 根拠 → 年表

1. 年表の短いカードを選択する。カード内に詳細のコピーは展開しない。
2. PCでは右欄に本文・解説・根拠を表示し、選択中カードを強調する。スマートフォンでは同じ詳細内容を読めるペインへ移る。
3. 出典を確認する操作では、その資料の引用・該当箇所を直接開く。汎用の詳細先頭に戻して再検索させない。
4. 「年表に戻る」で元のカード・スクロール・フォーカスへ復帰する。図の倍率・座標を維持する。

詳細で新しく得られる情報がなく、年表と同じ文を再表示するだけの導線は合格にしない。追加の解説が不要な記録でも、全文、具体的な出典、該当箇所など確認の価値を明示する。

### 記録 → テーマについて → 記録

上部の「このテーマについて」でテーマの詳細を開く。探索の終了・選択解除・グラフのリセットは行わない。「読んでいた記録へ戻る」で以前の詳細対象と表示位置に戻る。テーマ詳細は既存の右欄の用途として整え、商品専用モーダルの入口にしない。

### 図／年表の下にあるテーマ情報 → 詳細 → 元の位置

一覧の項目名から該当記録の説明と根拠を開く。閲覧後は下部一覧の同じ項目・位置へ戻れる。上へ自動スクロールして導入から読み直させない。

### 実装上の状態

グラフ／年表の選択を一つの基準として保ち、詳細欄の表示対象・展開中出典・戻り先をその上で管理する。記録選択とテーマ詳細の一時表示を区別し、勝手に二つの選択状態が食い違わないようにする。

参照は表示中スナップショットのIDと版を使用する。根拠を見る操作で無条件にlatestへ切り替えない。最低限保持するものは、テーマID・版、記録ID・版、時間注釈ID、evidence ID、出典の開閉、年表と下部一覧の位置、図の座標と倍率、戻り先。

公開テーマURLから直接開いても、TOPから開いても、同じ導入・本文・選択体験を提供する。URLへ保存する状態と、セッションで戻す状態は既存の共有・復元契約に合わせる。

## 6. 商品カードとOneLink

### 6.1 役割分担

- カードのレイアウト、説明、掲載理由：Plunode。
- 商品情報・画像の取得：Creators APIなど、利用が認められた取得元。
- クリック後の地域別のAmazonへの誘導：OneLink。

OneLinkは画像カードを返す機能ではない。Amazon公式FAQでは通常のアソシエイトリンク／Amazon短縮リンクへの対応が案内されている。Plunodeがそのリンクをボタンとして表示する設計にする。商品画像取得にはCreators APIのImagesリソースがある。OGPが読めることだけを画像の利用許諾として扱わない。

Creators APIには利用資格があるため、実アカウントの資格と商品画像の利用条件は着手時に確認する。未確認のまま、画像付きカードを本番で実現できたことにしない。一方、画像の調達条件とUIの情報整理は別の依存関係として扱う。

### 6.2 紐づけと表示

必要なデータは、次の三つを区別する。

| データ | 内容 |
|---|---|
| 商品・版の識別 | 書名／作品名、著者等、形式、言語、巻・版、ISBN等。作品と特定の版を混同しない |
| 掲載理由と対象 | theme／entity／recordのIDと必要な版、商品参照、掲載理由、表示順、公開状態 |
| 国別の販売先と画像 | Marketplace、ASIN、アソシエイトURL、画像と取得元・期限、確認状態と日時 |

商品情報をテーマごとに複製せず、同じ商品を再利用できるようにする。掲載理由はテーマ・対象ごとに持つ。商品推薦は公開知識の「根拠付き関係」と別にし、購入リンクの有無がKGの事実を変えないようにする。

表示規則案：
- テーマ詳細：テーマへの直接の推薦と、収録Entity／Recordに紐づいた推薦を、由来を明示して集約。同じ商品は重複表示しない。関係グラフ全体を辿って無制限に商品を混ぜない。
- Entity詳細：当該人物・作品との関連が説明できる商品。
- Record詳細：当該記録に直接対応する商品。テーマ全体の本を載せるなら「テーマ全体を知る本」と分ける。
- 初期表示は少数のカードで候補比較できるようにし、追加分への明示的な入口を置く。件数は実画面で調整する。
- 専用の商品タブを増やす案は採用前提にしない。詳細内で普通に読める区画を基本候補とする。

カード：画像、書名、言語・形式・版、掲載理由1文、販売先が分かるボタン、広告を含む旨の表示。画像内の書名・書影は未検証のダミーとして扱い、本番へ流用しない。

### 6.3 商品・画像がない場合

「存在しない」と「調べられていない／一時エラー」を分ける。取得失敗を不存在と判定しない。

地域別の商品がない場合の候補は、(A)その販売先のボタンを出さない、(B)確認済みの別地域・別版への案内だと分かる表示で残す。ユーザーの最新の発言では表示次第のため、どちらも確定しない。対象言語・版が変わる場合に、表紙や説明は元の商品、リンクだけ別商品という状態を許さない。

画像取得失敗時に壊れた画像アイコンや架空の表紙を見せない。画像なし状態も部品として定義し、画像が必要な採用デザインの代わりとして無断で確定しない。

購入可能性を未確認のまま「購入できます」「在庫あり」と表示しない。価格・在庫を表示する場合は、確認方法と更新条件を別途持つ。

## 8. 表示サイズ・性能・公開境界

PCでは詳細欄を読みやすい幅にしつつ、中央の年表・図の可読幅を確保する。本文を無理に縮めて三列を維持しない。補足を小さくする情報階層の設計と、狭幅を全部の文字縮小でしのぐことを混同しない。既存の年表／図／詳細の切替を活かし、商品専用タブを増やして解決しない。

スマートフォンでは、根拠や商品を見た後に同じ記録へ戻れることを重視する。折りたたみはキーボード操作でき、見出し・開閉状態・対象が支援技術にも伝わるようにする。ツールチップだけに情報を退避させない。

商品情報の遅延で年表や図を待たせない。閲覧のたびにAIを呼ばず、登録済みの本文・解説を使う。商品情報と画像は提供元の保存・更新条件を守り、失敗状態も独立させる。権限のない解説・商品管理情報・非公開の記録を公開DTOへ混ぜない。

検索向けのテーマURLとサーバーからの本文提供は第12章の実装対象。画面だけ完成させてSEOを外さない。Googleの実際の登録・順位は別の観測結果として報告する。

## 9. 実装の区切りと完了条件

### A. 読む体験と公開テーマの入口を一巡で作る

代表テーマに実際の導入、テーマ画像、明示的な詳細入口、種別・状態バッジ、年表の短いカード、右欄の本文・根拠、下部テーマ情報、主従をつけた補足を載せる。公開テーマURL・本文HTML・metadata・サイトマップを同じ作業範囲に含める。

完了：検索対象にできるURLを直接開いて主題が分かり、年表から詳しく読む操作で理解が進み、scopeや版情報が主軸より目立たず、元の位置へ戻れる。代表テーマは画像と実文面を含めて比較する。

### B. 導入に応える内容と再利用可能な表示データを整える

引きとなる問いから不足する記録・資料・解説を整理する。収集・編集する内容は承認範囲に従う。短い見出し、導入、解説参照、画像などの保存と版・翻訳対応を整える。

完了：生成案だけにあった魅力が、公開可能な実内容として存在する。本文の更新と編集情報の対応が取れ、全記録の毎回手書きを必須にしない。AとBは相互に確認し、見た目だけの仮データで最終完了にしない。

### C. 商品カードを文脈と結ぶ

実商品・画像・掲載理由・地域別案内を詳細欄に接続する。出典・人物・関係・テーマとの違いが分かる表示を作る。

完了：実商品が適切な文脈に出て、本文の読書を遮らず、出典と混同せず、言語・版・地域の不一致を黙って隠さない。地域未対応時の見せ方は比較して判断する。

### D. 実機・本番で確認する

広い画面、ノートPC、スマートフォン、日本語・英語で読む順序と戻りを確認する。公開URLのHTTPヘッダー・HTML・リンク・サイトマップを確認し、利用できる権限の範囲でSearch ConsoleのURL検査を行う。

完了：実装確認、公開反映、検索エンジンによる登録確認を混同せず、それぞれの実測結果を示せる。検索順位が上がるまで実装未完了とするわけではないが、SEOの実装を省略して画面刷新完了とはしない。

## 10. 受入テスト

| 分類 | 合格条件 |
|---|---|
| 第一印象 | 最初に目に入るのがテーマ画像・主題・導入。scope・版・コードが主役を押しのけていない |
| 主従 | 「範囲」を「※」へ変えただけでは不合格。補足のサイズ・色・余白・位置・重複が実際に変わり、主文が先に読める |
| 種別・状態 | 出来事等がバッジで識別できる。否定・不確実も見分けられ、色だけに依存せず、バッジだらけにはならない |
| 導入・データ | 引きのある問いに応える記録がある。不足は収集・編集の対象として明示され、仮文章で事実を補わない |
| テーマ詳細 | 上部の文字付き導線から迷わず開ける。読んでいた記録の選択・スクロールを失わない |
| 年表と詳細 | カード選択が全文の二重展開にならない。詳細で説明・根拠等の追加情報を得られる |
| 実際の開閉 | 子年表など開くと別の情報が増える操作は残る。選択しか起きない箇所に展開アイコンを付けない |
| scope | 詳細の小さな注記か下部の補足群に一度だけある。年表と詳細の重複、強調枠、専用の開閉はない |
| 情報保持 | 全項目の移動先が確認できる。ただし情報が残っているだけでは全体を合格としない |
| 時間 | 年・月・日精度、時点・期間・発生幅・未分類・境界の不確実性・複数時間・周期・段階を区別できる |
| テーマ情報 | 下部の開いた一覧案と上部の閉じた入口案を比較。主導入を妨げず、全件に到達できる |
| 閲覧往復 | 年表→詳細→根拠→年表、図→詳細→図、記録→テーマ→記録、下部一覧→詳細→一覧で位置・版を保持 |
| 複数出典 | 押した出典が開く。支持・反証・背景、引用・書誌・該当箇所を取り違えない |
| 内容更新・翻訳 | スナップショットに別版の本文・訳文・解説を黙って混ぜない |
| 画像 | 代表テーマで画像が実表示される。クレジット・alt・トリミング・寸法を確認。画像なしだけで完了にしない |
| 公開テーマSEO | 公開URLがログインなしで200、意図したindex、自己canonical、テーマ固有title/description、可読本文、画像、内部リンクを返す |
| SEO境界 | 非公開・非表示・管理画面・限定共有を公開サイトマップに混ぜない。任意の探索状態を無制限にindexしない |
| 検索への到達 | TOP・一覧・関連Entityから通常のHTMLリンクで到達でき、サイトマップに公開テーマが載る |
| 言語 | 実在する翻訳ページだけを言語別の検索対象として扱う。見かけだけ英語URLを量産しない |
| 商品 | 同一商品・別版・別言語・地域未対応・画像/API失敗・商品0件で、知識本文と独立して破綻しない |
| 既存操作 | 保存、Capsule、共有、編集・訂正、Undo、戻る、翻訳、図の切替が動く |
| 実画面 | PC／狭いPC／スマートフォン、日英、長い見出し・引用で視線の主従と可読性が保たれる |
| 内容品質 | 架空の書名・書影、未検証の解説、実機と誤認させる画像が本番へ混入していない |

before/afterで、主題が最初に伝わるか、補足がどれだけ画面を占めるか、開く前後で何が増えるか、元の記録へ戻れるかを確認する。生成案と似たスクリーンショット、または項目保持チェックだけでは完成としない。

## 11. Codexへ渡す場合

推奨モデル：Sol  
推論レベル：高  
理由：情報保持、複数の選択状態、版参照、時間表現、翻訳、公開境界をまたぐ実装のため。切り分け後の局所的なスタイル修正はSol・中が候補。

指示本文の前提：
- この文書は仕様案であり、この文書を作ったこと自体は実装・本番反映の許可ではない。
- 実装依頼を受けた際は現行AGENTS.md、作業ロック、既存作業の差分を先に確認する。
- 最初に主題・導入・バッジ・本文・補足の階層と、年表／詳細の役割を確定し、情報の移動先と往復操作を合わせて実装する。
- 生成案の導入・画像・視覚的な主従・バッジを実装対象にする。「イメージだから対象外」としない。一方、生成文面・商品・図の関係は根拠確認なしで事実として投入しない。
- scopeの語句変更や「※」への置換を主目的にしない。小さな補足としての視覚的な位置づけと重複解消を実装する。
- 年表と詳細で同じ本文・根拠を開き直す構造を残さない。解説の水増しで差を作らない。
- テーマSEOを今回の範囲から外さない。既存の管理用 `/themes/[id]` を不用意に公開ページへ転用しない。
- 運用者の新しい毎回作業やAIコストを、未承認で必須にしない。
- レイアウトのみの変更と、データ／解説／商品掲載を伴う変更を区別して報告する。
- 本番配置、外部アカウント登録、実課金、データ公開等は別途承認の範囲に従う。

## 12. 公開テーマのSEOと入口の実装

### 12.1 読む画面と検索対象を同じ内容にする

公開テーマごとに安定したURLを設ける。案は `/t/{themeId}` と、実在する英訳を持つ場合の `/en/t/{themeId}`。パスは着手時のルート確認で決める。既存の `/themes/[id]` は編集・管理側の用途を確認し、衝突や権限の変更を避ける。

公開URLも既存のExplorer／KnowledgeReadingにつなぐ。SEO用の別記事、別の説明サイト、既存探索から切り離されたランディングページを手作業で二重運用しない。公開されたテーマの内容・導入・画像を、検索入口でもサイト内閲覧でも同じ意味で提供する。

### 12.2 URLと公開状態の契約

| URL／状態 | 方針案 |
|---|---|
| 公開テーマの正規URL | 200、index可能、自己参照canonical、テーマ固有のtitle・description・OG情報 |
| 同じ内容の表示切替だけを持つURL | 正規URLへのcanonicalと、状態の保持方法を整理。無関係なトップURLへまとめない |
| 現行 `/?ktheme=…` 等 | 既存の共有・復元を壊さない互換入口。テーマ・版・表示状態を解決して正規URLへ接続する |
| 過去版を固定した共有 | 最新版へ無条件転送しない。旧版として復元し、indexの扱いは正規公開ページと分離 |
| 管理・非公開・限定共有 | 認可を保持し、公開本文・画像・metadata・サイトマップへ漏らさない |
| 公開を取り消したテーマ | 本文や検索向けキャッシュを残さない。存在・公開方針に合った404等とサイトマップ除外を行う |

クエリパラメータがあること自体がSEO不可なのではない。前段で見つかった「すべて状態付きとしてnoindex」の条件に、公開テーマの正規な入口まで巻き込まない。

`noindex`はGoogleでの検索掲載を止める指定であり、canonicalはランキングの優先順位指定ではない。別の内容のEntityページをテーマへcanonical化して順位を上げようとしない。テーマが常にEntityより上位になる保証もしない。[W1][W6]

### 12.3 サーバーから返す内容

初回HTMLに、テーマ名、導入、画像、説明、公開している年表の主文／関係の読める説明、出典へのリンクを出す。その内容を利用者にも表示し、検索ロボット専用の隠し文章を増やさない。

操作後は既存のグラフ・年表・詳細へ自然につながるようhydration／初期データ受け渡しを整える。`use client`だけを理由にSEO不可と断定せず、実際のHTTPレスポンスとレンダリング結果を検査する。JavaScript後の取得にしか主要本文がない構成は、この実装で改善する。[W2]

`title`は「テーマの具体的な内容 — Plunode」、descriptionは導入から内容に合う短い説明を用意する。検索用文面だけ誇張しない。OG画像はテーマ画像とタイトルから生成できるようにし、文字・商品カードを含む画面全体のスクリーンショットで代用しない。

Googleが最終的に表示するタイトル・抜粋・順位を固定できるとは扱わない。実装できるのは、内容と整合した情報、辿れるURL、読める本文を提供するところまで。

### 12.4 見つけてもらうための導線

TOPのテーマカード、テーマ一覧、関連するEntity／記録から、正規テーマURLへhrefを持つ通常のリンクを置く。ボタンのonClickだけに依存しない。リンク文にはテーマ名を使い、関連する理由も必要に応じ短く示す。

サイトマップには公開テーマのみを追加する。lastmodは実際の公開内容の更新を反映し、閲覧のたびに現在時刻へしない。順位を上げる目的でpriority属性だけを調整する作業にはしない。[W7]

英語版は実在する公開内容のあるページだけを言語別URL・hreflangの対象にし、存在しない翻訳の組合せを出さない。表示言語と商品の購入地域は別々に扱う。

画像はimg／picture、alt、実際の周辺本文と結びつける。SEOに必要なテーマ画像をCSS背景だけへ追いやらない。[W3]

### 12.5 完了確認

未ログインで正規URLを直接開き、HTTPステータス、meta robotsとX-Robots-Tag、canonical、title、description、実本文、画像、内部リンク、サイトマップを確認する。TOP側の共通noindex、管理ガード、認証、配信ヘッダーが公開テーマに混入していないかも確認する。

権限がある場合はSearch ConsoleのURL検査でクロール可否・検出canonical・レンダリングを照合する。Search Consoleへアクセスできなければ、未確認と具体的に記録する。Googleでの登録と検索順位は、実装反映とは別の観測結果として報告する。
