# 公開パイプライン「まとまり2」更新の連続停止調査

2026-10-29。調査基準は **99ae8a3c653f57ef463723ceafb42a92e366fed8**。以下の時刻は2026-10-28の日本時間。改善案への判断資料であり、今回の変更はこのレポートと検証索引だけである。

## 1. 結論と調査範囲

**推定する主因は、承認済みの実行版・データの互換性を確かめる検証と、それを実環境へ設置する更新補助処理の検証が分離し、後者の前提を十分に照合せず運営者へ渡したこと。** ジョブ形式の誤認、初期導入snapshotの分類漏れ、退避名衝突は、当時すでに存在したコード・固定判断票から事前に発見できた。必要な安全検査が厳しすぎたために起きた失敗ではない。

一方、ロック競合は正常な排他動作である。手戻りを増やしたのは、それを一度の実行内で待機・限定再開する処理が後から追加されたこと。PowerShell失敗は、子処理のstderrを捨てたため直接原因を確定できない。最後に成功した事実から、権限・競合・照合のどれが原因だったかを逆算してはいけない。

推奨するのは、**完了版にすでに入った修正を再利用し、更新作業用の短い参照導線と「運営者へ渡す前に残りの更新工程まで確認する」基準を整える小規模な改善**である。汎用installerや公開基盤の刷新、全テストの増量、モデル変更を先に行う根拠はない。文書だけではコード上の誤りを防げないため、既存の隔離試験を、次の更新処理とその実入力に接続することを伴う。

### 根拠の扱い

- **事実**：固定commitのコード、運営者返却ログ、記録JSON、セッションの実ツール入力・出力・利用者向け応答で確認した内容。
- **推定**：それらを結ぶ原因解釈、改善効果の見込み。
- **未確定**：欠けたログや比較実験が必要な内容。記録がないことを、行為がなかった証明には使わない。

[検証索引](evidence.json) の S番号はローカルCodexログの行番号に対応する。終了報告だけでなく、初回引渡し前から完了までの実操作を確認した。索引には時刻・記録種別・履歴照合用hash・要約を収録し、生ログ、非公開の推論、認証情報は転記しない。セッションは継続追記されるため、完了報告までの先頭11,106行を固定した。

記録された担当設定は **gpt-6.1-sol / xhigh**。高速モードは記録から確認できない。同じ作業を別モデルで比較した記録はなく、今回の失敗をモデル固有の傾向とは判定しない。

## 3. 各停止の原因、事前情報、再実行判断

### 3.1 nonce別backupをジョブstateと誤認

**事実**：初版 current_jobs() は jobs/*.json の全件に state['phase'] を要求した。しかし既存executorは同じディレクトリへ、phaseを持つnonceのstateと、checksum/payloadを持つ nonce-backup.json を保存する。[初版consumer](https://github.com/isinxnisi/graph-knowledge/blob/26ce52cd/ops/apply-publication-bundle2-update.py#L105)／[既存producer](https://github.com/isinxnisi/graph-knowledge/blob/26ce52cd/scripts/publication-executor.py#L327)

初回引渡し前にAIはexecutorを読んでいる。ただしS9004は55〜275行の読取で、backup生成の327〜333行を含まない。S9007の出力にもその生成箇所はない。初期試験は手作りの単一state fixtureであり、実producerのディレクトリ構成を再現していなかった。[初期試験](https://github.com/isinxnisi/graph-knowledge/blob/26ce52cd/tests/test_publication_bundle2_rollout.py#L58)

**推定**：ジョブ棚卸しの仕様をproducerから確定せず、ディレクトリ名と想定形式から再実装したことが直接の設計上の前提だった。「既存executorを参照した」という事実だけでは、保存形式まで確認したことにならない。

**再実行判断**：fix1は未知形式を無視せず、対応state、終端状態、監査待ち、予約nonceを確認し、旧stage/imageを保持した。この安全性は妥当。ただし、最初の形式誤認を見つけた時点で同じディレクトリの全producerを確認せず、nonceの2形式に修正を閉じたまま次の権限操作を依頼した判断は不十分だった。実際に次の停止を招いた。

### 3.2 初期導入snapshotの分類漏れ

**事実**：初期導入コードは jobs/install-readonly-backup.json を作り、trusted/installation.json にそのSHA、root/export先、scope、観測revisionを記録していた。[導入producer](https://github.com/isinxnisi/graph-knowledge/blob/26ce52cd/ops/install-publication-disabled.py#L218)

この情報は初版作成時にもrepoに存在した。確認できた更新ターンのツール履歴では、writerの横断検索・導入producerの該当箇所の読取は2回目の停止後（S9439/S9449）。以前の全セッションを通じて一度も読んでいない、とは断定しない。

**再実行判断**：fix2は名前だけで除外せず、保護された導入記録とsnapshot全bytesのSHA・識別情報を照合した。既存ジョブ3件、nonce別backup3件、導入snapshot1件、未完了0件は、次のVPS実行内で確認された。[診断・照合条件](../publication-pipeline-bundle2-20261028/rollout/installation-inventory-fix.json)／[VPS結果](../publication-pipeline-bundle2-20261028/rollout/vps-installed-result.json)

この段階では棚卸しの原因調査がproducer全体へ広がり、Web停止前の実image・KG・会員schema/ledger検査も追加された。VPSの再実行依頼は合理的。ただし残るWSL更新全体の隔離完走はまだ確認しておらず、VPS側の修正成功を一括更新全体の完成根拠にはできなかった。

### 3.3 ロック競合、待機期限、取得直前の競合

**事実**：WSL更新は共通lock→preparation lock→Worker lockをnonblockingで取得し、途中で失敗するとExitStackが全て解放する。既存Workerは収集attemptがなくても、通常のonce処理全体でworker.lockを保持する。したがって state.activeAttemptなし・preparation idle は、更新用の3ロックが同時に空いている証明ではない。[初版更新](https://github.com/isinxnisi/graph-knowledge/blob/26ce52cd/ops/apply-publication-bundle2-update.py#L241)／[Worker](https://github.com/isinxnisi/graph-knowledge/blob/99ae8a3c/scripts/collection-worker.py#L841)

AIは初回依頼直前に3ロックの存在とWorker側のlock箇所を確認していた（S9199）。しかし初版には競合からの待機・WSLのみの再開がなく、一括コマンドがエラーで運営者へ戻った。

再開処理は待機中に取得済みロックを全解放し、更新前の既知のBlockingIOErrorだけを再試行する。VPS成功工程、更新途中の失敗、署名やapplyは再実行しない。これは妥当な限定である。ただし非特権probeの解放から、HTTPS確認・sudo認証・root stage照合を経て実取得するまでには競合余地がある。最後のprobe追加でも予約にはならず、最終成功時にも競合が一度発生した。[完了版再開処理](https://github.com/isinxnisi/graph-knowledge/blob/99ae8a3c/ops/resume-publication-bundle2-wsl.py#L88)

**評価**：15分で停止することやロック競合そのものを修正対象にはしない。初回から待機と更新前限定再開をまとめて渡せた点は改善対象。永久的なデッドロック、特定プロセスだけが15分保持したこと、待機時間の全量をAIの手動holdが生んだことは証明できない。保持PIDの入替えが観測されており（S9673ほか）、正確な内訳には連続した取得・解放時刻が必要である。

手動holdは開発中には必要で、運営者への各引渡し前に解放された。更新後の通常運転検証では手動holdによりwaiting-local-lockが生じ、解放後の通常スケジュールで終了0になった。待機中のTaskのLastResultを終端エラーと扱わなかった判断は妥当。[通常運転記録](../publication-pipeline-bundle2-20261028/rollout/normal-operation-verification.json)

### 3.4 同名ファイルの退避先衝突

**事実**：初版はWorkerファイルを 'worker-' + path.name + '.before' へ退避した。固定判断票に初めから含まれた lib/domain/contribution.ts と lib/i18n/contribution.ts が、どちらも worker-contribution.ts.before になる。before SHAは7bb75f38…とdcbf6996…で異なる。二つ目の保存を既存backup上書き禁止が拒否した。[初版退避処理](https://github.com/isinxnisi/graph-knowledge/blob/26ce52cd/ops/apply-publication-bundle2-update.py#L262)／[固定5ファイル](../publication-pipeline-bundle2-20261028/update-decision-request.json)

**推定**：固定入力から分かるパスの対応を、各ファイルのhash照合とは別の検証対象にしていなかった。これは稼働環境へアクセスしなくても発見できる不具合である。初版の6試験にも、fix2までの11試験にもWSL更新全体を通すケースはなかった。

**再実行判断**：fix3は相対パスを保持し、全退避先を先に確認し、元の所有者/mode/存在有無も記録する。旧部分backupを固定SHAで照合・保全し、新stageから進めた。実Workerのbefore bytes、173ファイルのpolicy、12 receipt、承認済みsource/設定を使う私有treeで更新と差戻しを通したため、この不具合に対する再実行根拠は十分だった。[実入力の隔離実証](../publication-pipeline-bundle2-20261028/rollout/wsl-backup-real-input-proof.json)

ただしroot所有権・実Windows Task setter・実approverはmock等で置き換えていた。S10245で残るTaskコードも読み直したが、Task XMLの退避が変更成功後にしか行われない点と、子のstderr欠落はこの時点では残った。「27件成功」はこれらの境界の成功を意味しない。

### 3.5 PowerShell失敗と診断情報の欠落

**事実**：fix3実行はsource設置まで進み、windows_task()→run()が Fixed command failed: powershell.exe を返した。PowerShellが非ゼロ終了したことまでは確認できる。run()はstderrをPIPEへ取得しながら保存せず、終了コード値と具体的な子例外を返さずにプログラム名だけを例外にした。Task XMLのroot退避も、変更を含むwindows_task()の成功返却後だった。[失敗時のrun](https://github.com/isinxnisi/graph-knowledge/blob/30d795ef/ops/apply-publication-bundle2-update.py#L57)／[診断記録](../publication-pipeline-bundle2-20261028/rollout/wsl-task-diagnostics.json)

Task Action、Worker、delivery/approver、12 receiptの事後読取は旧固定値。新sourceの403ファイルは承認archiveと一致した。このため「全て変更前に止まった」とは言えない。またTaskが一時的に変更されてから戻ったかは、残ったgeneric errorだけでは区別できない。

初回からPowerShell構文検査と旧source→同じ旧sourceの実読取照合は行っていた。この経路では Set-ScheduledTask を実行しない。通常ユーザーの同CLEAN環境で読めることも、sudoからWSL interopを通した実変更・事後照合が成功する証明にはならない。失敗後の読取成功と関連イベントの不検出も、当時の直接原因を確定しない（S10409/S10412）。

**既存機能の再利用評価**：同じbundle2で、approverには子のstdout/stderr/return codeを保持するChildFailureとprivate診断を実装済みだった。一方、以前のWeb-only helperも子のstderrを捨てる方式だった。更新補助処理は後者と同様の弱点を持ち、改善した診断の考え方を設置側へ適用できていなかった。[既存の子結果保持](https://github.com/isinxnisi/graph-knowledge/blob/26ce52cd/ops/plunode-publication-approve#L34)／[診断保存](https://github.com/isinxnisi/graph-knowledge/blob/26ce52cd/scripts/publication-diagnostics.py#L44)

完了版でも共通run()自体のgeneric errorは残り、PowerShell専用呼出しだけが詳しい子結果を保持する。Docker等の別の子処理まで同じ改善が入ったとは扱わない。[完了版の共通run](https://github.com/isinxnisi/graph-knowledge/blob/99ae8a3c/ops/apply-publication-bundle2-update.py#L57)

ただし公開診断はnonceを必須とする。更新に架空nonceを作ってそのまま流用するのではなく、子結果保持・秘匿・工程識別の部分を再利用すべきだった。

**再実行判断**：fix4は変更前Task XML/SDDL snapshot、更新直前の一致、工程・原例外・HRESULT・差戻し結果を保持した。7シナリオのPowerShell試験は実setterをmockしたもので、実変更成功を先取りしていない。旧固定状態、既存権限、再適用しない境界を確認し、「原因未確定」と明示して運営者へ一度の観測可能な実行を依頼した判断は合理的。成功を約束できる根拠ではなかったが、原因情報を増やさない同じ再実行とは異なる。

**未確定**：元失敗がTask実行競合、CIM/権限、更新後保全比較、その他のどれだったか。確定にはその時点の子stderr/例外、変更前後Task XML/SDDL、実行tokenとTask状態が必要。今回の最終成功だけでは補えず、原因を確かめるための本番再更新も不要である。

「AIが何も調べなかった」は誤り。既存Web-only/画像検証helper、executor、固定判断票を実際に読み、hash・receipt・権限境界を確認していた。S8980などで新コードも読み直した。しかし、参照したファイル名の多さは、今回の更新が使う全形式・変更分岐を確認した証拠にはならない。

### 開発・承認・運用の評価

固定対象、署名境界、旧stage、receipt、既存imageを保持し、不明な状態から新nonce・再署名・再applyへ進まなかった点は適切だった。確定した3不具合は実行先の書換え前で停止し、退避衝突では上書き禁止が作動した。承認契約を緩める理由はない。

新helperを作る必要性自体はあった。旧Web-only更新はWebに限定され、旧image updaterはWorker/Task/gate2ファイルの今回の一括更新を扱わない。disabled導入用readiness入口も、稼働中の今回の更新をそのまま実行する入口ではない。既存コードの無条件実行や、過去の承認を広げる方が危険だった。

問題は「一回限りの補助」を低い検証単位で扱ったこと。複数ホスト、root保護ファイル、Windows Task、既存運用の排他に触れる実行物であり、対象bytesの固定とは別に、**設置手順・中間状態・失敗結果の説明可能性**も引渡し前の成果に含める必要があった。人間による更新承認は、AIが省いた機械確認を代替しない。

副次的な同種の例として、最終記録commit直前に git diff --cached --check がCRLF由来の違反でexit 1になったのに、次のcommitを実行した履歴がある。push前にLF化・amend・再検査で直しており、本番停止や人間再操作は増やしていない。これは「確認コマンドを実行した」と「失敗結果で後続を止めた」の違いを示す（S11059/S11065/S11069）。更新後probeのCLI envelope誤認、beta CLIのCloudflare 403、並列生成検査のtimeoutも、運営者更新の不具合件数へは加えない。

### 推奨する次回の進め方

次の実装で子処理の呼出しを再利用する際は、PowerShell専用の診断だけで終えず、共通run相当にも子exit code・秘匿した出力・原例外を残す小さい変更を含める。履歴の固定包を遡って書換えず、次の更新補助に接続する。別の状態管理基盤を作る必要はない。

初めに、対象を「データ追加」「実行版更新」「初期導入」「同nonceの公開復旧」のどれかへ分類する。実行版更新では、既存の公開・受入フローを再構築せず、次の4点を一組で確認してから運営者へ渡す。

1. **入力とproducer**：設置元commit/image、固定対象、全journalの種類と生成元、Taskの実行主体・参照先。権限が足りない情報は未確認と明示し、既存のSSH/sudo操作の最初でまとめて取得・照合する。
2. **更新全工程**：変更前確認→全退避先の一意性/既存backup一致→source設置→Task→Worker/config→self-check→実設置検証を、固定入力を使った隔離経路で通す。副作用境界をmockした箇所を一覧にし、読取成功と変更分岐を分ける。
3. **失敗結果**：少なくとも停止工程、子exit code、秘匿された子エラー、変更済み対象、差戻し結果、再開できる境界が分かる。正常待機、変更前拒否、変更途中、完了をgeneric errorへ潰さない。
4. **引渡し**：同じ固定資材と既存権限で、可能な機械処理を次の人間判断まで継続する。既知の変更前競合は一実行内で待つ。対象drift・未知エラー・変更途中は安全停止し、成功工程を繰り返さない。

再利用先は [journal/資材検査](https://github.com/isinxnisi/graph-knowledge/blob/99ae8a3c/tests/test_publication_bundle2_rollout.py)、[待機・限定再開](https://github.com/isinxnisi/graph-knowledge/blob/99ae8a3c/tests/test_publication_bundle2_resume.py)、[退避とWSL全工程](https://github.com/isinxnisi/graph-knowledge/blob/99ae8a3c/tests/test_publication_bundle2_wsl_backup.py)、[Task変更・例外](https://github.com/isinxnisi/graph-knowledge/blob/99ae8a3c/tests/test_publication_bundle2_task.py)。

固定判断票の提出時には、運営者が実行する補助処理・隔離確認・失敗診断も可能な範囲で揃える。承認後に設置手順を新規に組み立てる仕事を残さず、実権限が必要な照合だけを運営者操作の先頭へ置く。

新しい試験基盤を先行開発する必要はない。完了版のjournal分類、backup計画、WSL全体/rollback、Task例外の既存試験を、次の更新実装へ使うことを優先する。共通部品への抽出は次の具体的な再利用箇所に限定し、保護された設置版・過去の固定包をその場で変更しない。

## 8. 減らせる作業・人間介入と最小の次工程

### 削減対象と残る負担

- **削減根拠が強い**：形式誤認2件と退避衝突1件は、既存producer・固定5パスと更新全工程の隔離試験から発見可能だった。これらに対応した3回の失敗実行、修正版包の作成/固定/再説明、再操作後の再照合を削減対象にできる。
- **回数削減は未実測**：初回から限定待機を入れれば、正常競合ごとのAI引継ぎを減らせる。sudo認証前後の競合や15分期限は残り、1回の実行で必ず終了するとは保証できない。
- **原因調査を減らせる**：PowerShell子結果が最初から残れば、権限・競合・保全比較を広く推測する作業を絞れる。直接原因不明のため、この停止そのものを防げた回数には算入しない。
- **残す**：固定対象の承認、必要なSSH/sudo、直前drift照合、実設置版の検証、復旧資材保持、通常運転確認。これらはコード上の事前検証で置き換わらない。
- **増える**：最初の引渡し前のproducer対応付けと更新全工程の隔離確認、短い導線の保守。別AIの常設レビュー、新しいデータ収集、全機能の再検証は要求しない。

確認できる7実行を「必ず1実行へ減らせる」とは見積もらない。確定不具合3件とPowerShell診断の修正4枠は、利用者入力受領〜次の引渡しの経過時間で約70分だった（ツール待ち・検証・記録を含む）。その全量が削減可能なAI実働時間ではない。最初の引渡し15:09からWSL成功返却21:11までの約6時間には運営者の不在時間も含む。待機期限15分やlock関連時間をそこへ重複加算しない。トークン削減量は未測定。

### 次に承認する最小の改善単位

**「実行版更新の参照導線・子結果保持・既存検証を使った引渡し基準の整備」一つを推奨する。** 到達点はrepo内の運用知識・開発側の限定した子結果保持と隔離確認まで。公開基盤、ロック構造、鍵/権限、稼働Taskを変える承認とは分ける。新たな更新対象がまだなければ、汎用installerを作らず、完了版からケースを確認し、子結果保持の小さい部分だけを隔離で扱う。

合否基準：

1. 新しいセッションがAGENTS→短い入口から、現在の設置状態の根拠と、各形式のproducer・既存検証へ辿れる。過去の固定更新コマンドの再実行を案内しない。
2. 同じ既存更新処理に対し、state/nonce backup/導入snapshotを受理し、未知/孤立/未完了を拒否する既存試験を使える。
3. 固定5ファイルの同名2件、新設3件、既存backup不一致、途中差戻しを、更新全工程の隔離確認で扱える。
4. Task同sourceの読取成功をsetter成功と報告しない。子例外・変更前snapshot・差戻し結果を失わず、未知失敗は自動再操作しない。共通の子処理呼出しについても、非ゼロ終了/timeout/不正JSONで後続が走らず、原例外と秘匿した出力が残ることを隔離で確認する。
5. 正常競合の待機中はロックを持たず、成功したVPS工程・署名/applyを再実行しない。ドリフト時は停止する。
6. 次の運営者依頼には未確認の実権限境界と、そこで確認する結果をまとめる。repo内の確認不足だけを理由とする再操作依頼を減らせたかを次の1案件で評価する。

この基準は既存の修正を運用へ引き継ぐためのもので、新たな大量テスト件数を合格条件にしない。完了済み更新の再実行や追加sudoは不要である。
