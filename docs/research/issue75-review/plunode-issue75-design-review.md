# Plunode 全体設計の再評価

Issue #75・確定依頼v2に基づく調査、四案比較、推奨構成と実現計画

調査基準日：2026年11月1日 JST。主調査のコードは `cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206` に固定した。以後、コード参照はこの版を指す。実機には接続せず、PC・WSL・VPS・公開KG・会員DB・共有Kev・スケジュールの状態は変更していない。既存repositoryにも書き込んでいない。実施したのは読取調査と、独立した架空fixtureのオフライン検証である。

## 最初に読む要約

**最大の関門は、根拠を確認した具体的な内容でも、既存の関係型と限定値に翻訳し終わらないと、通常の知識として保存・検索・探索へ運べないことにある。** 収集件数だけを増やしても、この境界は残る。現在の漫画収集は、書誌、対象同定、原語、巻・版を丁寧に照合する方式で、単語の有無だけで判断する粗い処理ではない。しかし扱える資料と関係を限定したプログラムであり、文脈を読んで新しい種類の関係を理解するAIの代わりにはならない。既存Roleを数個増やす改善は有用だが、作品同士の翻案、復刊への働きかけ、招待と参加の違い、時期の定まらないエピソードまで低負担で扱う全体解にはならない。

従って、**小さな語彙追加だけで済ませず、知識の正本と意味対応の境界を変える中核変更を推奨する。** 画面全体や既存Capsuleを作り直す提案ではない。既存の対象・根拠、探索UI、保存・共有、公開の安全機構を再利用し、変える箇所を知識登録・改訂・索引へ集中させる。

**推奨は、根拠付きの原主張を共通の単位として保存し、同定・共通語への対応・探索用の分類を後から加える案Bである。** 利用者は「何が、何に、どう関係したか」を自然な言葉で書く。資料の該当箇所と対象を一緒に確認し、具体的な意味を保ったまま関係図・テーマ・語検索で使う。よく使う関係は共通の意味IDへ対応させ、厳密な条件検索にも参加させる。対応していない内容を無視せず、原文に当たった候補として発見できる。ただし、未対応の同義語まで厳密に拾えるとは約束しない。そこは検索画面の説明と、需要に応じた整理で埋める。

これは、原文だけを保存して残りを将来へ送る提案ではない。最初の実装単位に、原主張の表示、根拠への往復、語検索、意味対応、訂正、保存済みCapsuleへの変更通知と明示取り込みまで含める。コードの変更が要るのは、新しい取得方式・時間の演算・描画方式などが増える場合であり、新しい関係語が一つ現れるたびではない。資料の支持や語義の判断が不要になるわけでもなく、その判断を一つのテーマにまとめ、必要な精度のところへ集中させる。

**代案Aの「事前に体系を整える」は、対象領域が狭く、同じ種類の関係を繰り返すときに最も安定する。** 動的catalogへ改善すれば、新しいRoleのたびのコード編集も減らせる。しかし知らない関係を最初に使う前の定義・対応確認は残り、開放的なテーマ追加とは衝突する。**案Cの「固定型と自由な補助形式を併存」は移植しやすいが、二つのschema制約と、その間を移る契約を保つ負担が増す。** 共通IDと単一改訂にすれば二重編集は避けられるが、どちらの形をいつ適用するかは残る。**案Dの「資料・出来事・テーマを中心にする」は、魅力ある一つの読み物を早く作る力が強い。** 一方、別テーマから同じ意味の関係を辿るには、資料から独立した主張索引とその訂正機構が必要になる。文書を正本として索引を再生成する構成も成立するが、直接の関係編集と文書の改訂の対応が要る。Plunode全体の基盤としては案B、編集する成果物としては案Dのテーマ構成を利用するのが妥当である。

**年表構想は、保存構造の選択に実際に影響する。** 現行の年月日と期間だけでは、周期や「青の時代」の区間を忠実に置けない。軸の種類・軸ID・点／区間・元の時期表現を保ち、日付へ無理に変換しない構造が必要である。非時系列の情報は人物・作品・テーマへの情報枠として保存できるが、時点や区間に関係するエピソードまで全部そこへ追い出さない。本報告では、比較はまず同軸の複数レーンと重ね合わせ、異軸は対応点を使った並置を推奨する。「2対1」も複数の構成を一つの比較対象として束ねれば可能で、元データの統合は必須でない。細かな目盛、配色、全操作、周期の初期単位は今回決めていない。

**次に作る単位は、「一つの根拠付きテーマを、登録から訂正まで完成させる機能」である。** 既存Capsuleの編集・保存・共有を土台に、未対応の関係を含む小さなテーマを取り込み、関係図・日付と期間の年表・非時系列情報を見せ、検索から見つけ、訂正を明示反映できるところまで作る。初弾の価値は「テーマを開くと面白さが分かり、自分の文脈で編集して人へ渡せること」である。共通知識へ提案しないCapsuleも、そのまま独立した成果物として成立する。

## 1. 共通の流れと、利用者が困っている点

サービスを一巡する流れは、テーマを決め、資料を集め、具体的な内容と根拠を残し、使える関係図・年表・Capsuleへまとめ、検索と共有で再発見し、後から直すことである。①〜⑥はこの流れを説明する地図として使い、承認ゲートや実行プロセスを六つに固定しない。

| 区間 | 現在の主な担当・入出力 | 推奨構成での役割 |
| --- | --- | --- |
| ①テーマ・対象を決める | 人間／ChatGPTが企画。既存テーマ・catalog・recipeの範囲を指定 | 「見せたい問い」「核になる対象」「必要な関係」「完成したと判断する例」を一つのThemeBriefへ。広い基礎収集も、この需要と接続して優先する |
| ②受付・開始 | 許可されたIssue入力を専用control branch経由でWindows／WSL Workerへ。本文やラベルだけでは実行許可にならない | UIの直接提案、Capsuleの選択部分、テーマ調査の三入口を共通受付へ。保存と調査実行を区別し、一つの操作を一つの結果へ追跡 |
| ③取得 | PythonがWikidata・NDL等の対応済み取得先へアクセス。rawとcacheは主にPC側 | 取得先固有のfetcherは残す。人／AIのWeb調査も同じSourceBundleへ出力。取得済み資料は解釈前から保存して再利用可能にする |
| ④読解・整理 | 限定された規則で対象、Role、scopeを組み立て、人が重要な意味を確認 | 人／汎用AIが文脈を読み原主張と根拠箇所を提案。通常プログラムが整合を検証。既知語への対応は同じ確認画面で行え、未対応でも原主張を使える |
| ⑤保存・共有 | hidden候補、review、判断、receipt、releaseを保存・共有。raw全体と共有資料は同じでない | 原主張・資料・版・意味対応を独立して保持。テーマの読める断面と必要な証拠を先に作り、重い整理を一括して後から行える |
| ⑥利用・公開 | 受入済みreleaseを別の公開gateで反映。Webは公開Claimを読む。Capsuleの保存・共有は別経路 | 共通知識の公開、検索索引、関係図、年表へ同じ公開版を投影。Capsuleは自分の保存版と文脈を保持し、必要な変更だけ明示取り込み |

現行の呼出しは、Windowsの毎分・ログオンTaskからWSL内の固定Python runtimeへ入り、`issue-prepare`、`collect-review`、`accept-release`等を実行する。PC停止中にこのWorkerが仕事を続けるわけではない。公開applyはCollectionWorkerの仕事ではなく、別の公開gateへ分離されている。これは現行の安全境界であり、今回の調査では触れていない。[受付と保存](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/docs/design/COLLECTION_ISSUE_INTAKE.md#L7-L49)、[実起動](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/scripts/collection-worker-task.ps1#L14-L44)、[Worker dispatch](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/scripts/collection-worker.py#L295-L341)。

利用者の負担は入力欄の数だけではない。現行で既存の型・限定では表せない関係を本線へ追加する場合、「新しい関係を見つける→既存語へ入るか調べる→入らなければ意味を定義する→catalog／schema／収集処理のどこを変えるか判断する→必要なruntime更新を扱う→検索に届く」という仕事が発生する。対応済みRoleの追加データまで、毎回再build・再配置が必要という意味ではない。これを「まず何が読み取れたかを残す→見せるために必要な対象・根拠を確認する→繰り返し使う意味をまとめる」へ変えるのが主目的である。

### 2.3 実装から分かった構成上の境界

**関係モデル。** Predicateは関係の種類を表す識別子で、現行は5種。Entityの種類は人物・作品・組織・出来事の4種で、各Predicateの端点種類が固定されている。例えば制作は人物→作品、影響は人物→人物であり、作品→作品の翻案をそのまま入れる場所はない。Claimは根拠に結び付く独立した主張で、UUID、肯否、期間、限定を持つ。この独立性と根拠への参照は有用なので残す。[Predicate定義](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/domain/predicates.ts#L1-L38)、[schemaと端点検証](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/domain/fixture.ts#L14-L62)。

**Roleの追加コストは改善済み。** 制作Roleは現在10種で、映画のDIRECTING／ACTINGも生成語彙に含まれる。Roleごとに多数の箇所を手で更新していた昔の状態として評価してはいけない。それでも型は生成済みenumに限定され、意味レビューとcatalog更新は残る。また新しい限定の種類を増やすと、型別欄、保存property、検索条件へ追加が必要になる。既存Role値の追加と、新しい関係型・限定型の追加を分ける必要がある。[生成語彙](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/generated/contribution-roles.ts#L1-L29)、[限定3型と比較キー](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/domain/qualifications.ts#L8-L34)、[Roleレビュー](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/domain/role-vocabulary.ts#L37-L55)。

**検索。** 現役Discoveryは、Entityの名前・別名と、管理されたPredicate／Role等の条件を使う。別作品を介した条件や2〜3段経路もあるため、単純な名前検索だけのサービスではない。一方、未対応の関係文を全体から探し、同義候補を整理して意味検索へ接続する索引は見当たらない。自由な表示ラベルを足すだけではこの欠落は埋まらない。[Discovery検索](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/server/discovery-search.ts#L19-L60)、[関係条件](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/domain/relation-conditions.ts#L11-L28)、[記録検索](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/server/discovery-records.ts#L17-L47)。

**プリセット・おすすめ。** コード上の編集catalogと固定の経路形は実装され、実際のDiscoveryから呼ばれている。おすすめは公開例や最近登録されたEntity／Claim等を返す。人気の実測が未接続なら編集priorityへ戻る。完成した任意テーマのGraphを運営UIで登録・更新する一般機構、自然言語だけで動く汎用プリセット、歴史的時間を並べる年表が既にあるとはいえない。[catalog](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/domain/discovery-preset-catalog.ts#L15-L39)、[経路形](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/domain/discovery-path-presets.ts#L5-L31)、[現在のHome](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/server/discovery-home.ts#L9-L44)。

**Capsule。** 現在のdocumentには独自の対象・関係ラベル・注釈・根拠と、KGから取り込んだID・版・断面がある。編集と保存、共有版は分かれ、現在KGとの差を明示的に確認して取り込める。独自関係は描画できるが、その自由ラベルがGlobalの意味検索に自動参加するわけではない。これはCapsuleが未完成な待ち箱だという話ではなく、既にある独立した編集価値へ、新しい知識基盤を接続する課題である。[document](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/domain/capsule-document.ts#L26-L64)、[明示比較と取り込み](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/components/CapsuleStudio.tsx#L287-L336)、[共有版の更新](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/server/member/sharing.ts#L113-L131)。

**時間。** 現行のPartialDateは西暦1〜9999年の年／月／日で、期間はその二端点である。Eventは特定開催回として保存される。年月日精度を保つ設計は利用できるが、周期・定性軸・任意の軸座標・軸間対応はこの型にない。描画だけの変更では足りない。[日付と期間](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/domain/dates.ts#L3-L38)、[Event](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/domain/event-participation.ts#L5-L10)。

**収集。** 現在の漫画経路は、P31・正規化名・ISBN・主書名・巻／版・言語・責任表示・人物作品catalog等を組み合わせて確認する。Source URL、原語、Role、scope、locatorも再検査する。従って「作者という語が一箇所にないだけで全て拒否する」と一般化するのは不正確である。ただし対応済みの書誌構造と有限の原語写像に依存している。書影・ページ構成・複数段落を読んで作者だと理解する一般処理や、追加URLの探索はこの経路にない。[候補とRole写像](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/scripts/collect-manga-v2.py#L145-L227)、[根拠再検査](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/scripts/collection-workflow.py#L299-L347)。

Issue #74の17 Claim／12バッチ、技術待ち6親は2026年10月30日19時の観測であり、現在件数、正式受入件数、公開増分として使用しない。親にtechnicalWaitが残ると子をまだ発行しない経路はコードで確認でき、部分的な取得成功を早く使う案の比較に影響する。ただしこの局所修正だけでは意味モデルの問題は解消しない。[Issue #74](https://github.com/isinxnisi/graph-knowledge/issues/74)、[子生成前の待ち](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/scripts/collection-issues.py#L540-L609)。

## 3. 比較に使った同じ代表例

今回の小さい検証は、実在の関係を創作しないため、人物・作品・資料をすべて架空にした。「葵の作品が、仲間と別の作品へつながった経緯」という一テーマに、次の11件を置いた。資料本文と期待する意味は人が作成した。AIによる抽出・照合の成功例ではない。

| ID | 原資料から残したい内容 | 設計上の試験点 |
| --- | --- | --- |
| s1 | 書影と著者紹介から、葵が『潮の地図』を著したと分かる | 定位置の「作者」の語に依存せず、文脈と該当箇所で支持を説明 |
| s2 | 葵が復刊を働きかけた | 既存Roleにない具体的関係。後に復刻特装版への提案だったとscopeを訂正 |
| s3 | 蓮が映画『窓』を「監督」 | 既存DIRECTINGで表現可能 |
| s4 | 蓮がスポーツクラブの「監督」 | 同じ表記の別の意味。映画の監督へ混ぜない |
| s5 | 日菜が映画『港』の「演出を担当」 | この架空資料では監督クレジットを指すと明示。異表記の同義対応 |
| s6 | 葵は上映会へ招待されたが欠席 | 招待を参加へ弱めたり、逆に補ったりしない |
| s7 | 蓮は上映会へ参加した | 人物・特定出来事・日付をつなぐ |
| s8 | 映画『窓』が『潮の地図』を翻案した | 作品→作品の関係。人物間の影響や制作Roleへ代用しない |
| s9 | 葵の「青の時代」 | 定性軸上の期間。年数や確定日を作らない |
| s10 | 毎年10月から翌2月が推敲期 | 周期の原点をまたぐ区間 |
| s11 | 見返しの海図の読み方についてのエピソード | 時期がない情報。偽の日付や架空Eventを作らない |

紹介する内容は、葵の作品から復刊をめぐる働きかけ、映画化、映画の制作仲間へと辿れることにある。年表では制作期、復刊提案の期間、上映会を読む。時期不明のエピソードは作品の情報枠へ、周期は人物の制作習慣として置く。利用者は自分の気になった関係を強調したCapsuleを保存・共有する。この体験なら、情報量の増加と「見せたいまとまり」を結び付けて評価できる。

現行モデルへそのまま入る関係の小さい部分集合はs1・s3・s5・s7の4件だった。ただし、これは今回の架空例に対してschema条件を転記したスクリーニングであり、現行アプリ実行による合否率ではない。残り7件を全部現行へ無理に入れることも、案Aなら永久に扱えないとすることもしていない。

## 4. 四つの構成案

四案はUIの入力文を変えただけの比較にしない。**利用の前に何を確定するか、何を正本として持つか、後の訂正で何を作り直すか**で区別した。どの案も根拠の保存、通常の認可、有限な実行、訂正履歴を必要とする。この共通の必要コストを、一つの案だけの欠点として数えない。

### 案A：事前に広い管理体系を用意する

主データは現在に近いEntity／Claim／Source／Citationで、Claimは事前に定義したPredicate・Role・scopeへ必ず対応する。公平な改善案として、値の正本をコードenumからデータcatalogへ移し、既存の外部語彙を調べて借り、安定した意味IDと定義から入力・検索の選択肢を作る。これなら同じ型内の新値でアプリコードを毎回変更する必要は減る。

例は `aoi --REPRINT_PROPOSED_FOR--> sea_map`、`scope=復刻特装版`、`period=2012–2013`。このPredicateの定義、端点、方向、何を含まず何を含むかを先に登録する。映画監督とスポーツ監督を別IDにし、同義の演出表記を映画側へ対応する。翻案、招待、定性区間、周期、ノートを扱う保存形式も先に設計する。

| 一巡の区間 | 同じ代表例での動き |
| --- | --- |
| 取得 | API／Web調査の両方を使用可能。AI補助を禁止する案ではない |
| 根拠確認 | s1をページ全体から確認し、同定と支持をレビュー。取得処理とは分けて改善できる |
| 登録 | s1/s3/s5/s7は既存型へ。s2/s4/s6/s8は語義の定義と対応が済むまで通常KG登録を待つ。s9/s10/s11は別保存構造を追加 |
| 表示 | 対応後は短く一貫した関係名と具体scopeで表示。未対応時にCapsuleへ原文を保つことは可能だが、その時点の通常KG利用は未成立 |
| 検索・発見 | 定義済み条件は強い。同じ意味の表記揺れも対応済みなら集約。未知の関係は検索結果に入る前に作業が必要 |
| 利用者編集 | 意図を自然文で直し、共通型との差を再確認。既存型を熟知させないUIは作れるが、裏側の対応作業は残る |
| 後の整理・訂正 | 誤った監督対応を訂正し、意味変更は新IDへ。scope訂正をClaim改訂と検索索引へ反映。保存Capsuleは旧版と差分を保持 |

**総評：限定領域では有力。今回の最優先軸には不利。** 語彙不足が同じ型の数値追加だけなら、案Aが最も小さく済む。しかしこの代表例では、新しい端点関係と時間表現が実際に出た。広い外部体系を先に採用しても、資料に書かれた意味とその定義が一致するかの確認は消えない。未知の意味も原主張のまま通常の検索・関係図へ通すよう改めれば、この案の登録前必須条件を外すことになり、案Bへ近づく。

### 案B：原主張を共通保存し、意味の対応を後から加える【推奨】

主データは、版を持つ「記録」。関係を述べる記録には対象、具体的な主張文、根拠箇所、範囲・時期を持たせる。エピソードや説明は、その対象やテーマに付ける。全記録が同じ版管理・根拠・編集・検索の経路を使い、共通語への対応だけを付加情報にする。原文を残すだけでなく、対象との接続と語検索を最初から提供する。

```json
{
  "recordId": "s2", "revision": 2, "kind": "relation",
  "subject": "aoi", "object": "sea_map",
  "assertion": "葵が『潮の地図』復刻特装版の復刊を提案した",
  "scope": {"text": "復刻特装版"},
  "time": {"kind": "calendar", "from": "2012", "to": "2013", "precision": "year"},
  "evidence": [{"sourceId": "interview-1", "locator": "第3・第5段落"}]
}
```

意味対応は別に `s2@2 → reprint_proposal` と記録し、対応の理由・担当・版を持つ。この構造例は採用推奨の責務を説明するもので、最終API名・UUID形式を確定するものではない。根拠のある具体的な主張を公開可能と判断することと、それを全領域共通の語へ整理することを、同じ必須条件にしない。

| 一巡の区間 | 同じ代表例での動き |
| --- | --- |
| 取得 | 取得直後にSourceBundleを保存。固定APIと自由なWeb調査が同じ出力へ集まる |
| 根拠確認 | s1では書影・著者紹介、s2では前後の段落を見て、主張と支持範囲を確認。必要なときだけ補足URLを探す |
| 登録 | s2を元の意味のまま保存。対象・根拠・公開範囲が確認できれば、その具体文でテーマと関係図へ。共通語が未定でも保存を止めない |
| 表示 | 「復刊を働きかけた」を辺に、対象版等を詳細に表示。s6は招待の線であり、参加にしない。s9–s11は適切な時間枠／情報枠へ |
| 検索・発見 | 全文・対象・テーマから発見できる。厳密な映画監督条件はs3/s5のみ。s4を語の一致で混ぜない。未対応の意味は本文候補として示す |
| 利用者編集 | 同じ編集器で原文・対象・根拠・scopeを直す。Capsule内の私的な説明と、共通知識への訂正提案を分ける |
| 後の整理・訂正 | 意味対応を分離／統合して索引を更新。原主張は書き換えず、s2の内容訂正は第2版。推薦テーマは更新検知、保存Capsuleは比較と明示取り込み |

**総評：今回の要求に最も合う。** 負担は「登録前に全語義を確定する」から「検索需要の高い語・意味が紛らわしい箇所を、原文に戻って整理する」へ移る。原主張のまま使えるので、この後処理を全件完了させるまでサービスが止まらない。一方、意味未対応の同義語を漏れなく厳密検索する要求には、そのままでは応えない。後述の検索表示と整理運用を初弾に含めなければ、単なる保管庫に終わる。

### 案C：既存の型を本流にして、未対応内容を別形式で併存させる

既存Claimを通常の形式とし、入らない内容だけ自由なassertionへ保存する。両者の横断検索、表示区別、後からの昇格・差し替えを作る。既存の意味検索と受入経路を早く残せる点が長所である。新しい型が必要になったときだけ定義するため、案Aより入力待ちは減る。

例ではs1/s3/s5/s7がtyped Claim、残りはfallback recordになる。改善した案Cなら、共通IDと単一の改訂履歴を持ち、typed表現をそこから作ることで二重編集を避けられる。その場合でも、どの内容がtypedの制約を満たすか、型から外れる訂正をしたときにどう戻すか、既存の厳密な条件で何を返すかという、二つのschema間の昇格・降格契約が必要になる。単純なコピー方式の欠点を、案C全体の不可避な欠点とはしない。

| 一巡の区間 | 同じ代表例での動き |
| --- | --- |
| 取得・根拠確認 | A/Bと共通化可能。ここに本質的優位はない |
| 登録 | 既存型に入るか判定して振り分ける。利用者へ判定を強制しない場合も、システム内で分類する必要がある |
| 表示 | 両形式を描画。未対応側の原文を省かない。型付き側だけを美しく見せると未対応内容が二級の体験になる |
| 検索・発見 | 厳密条件と原文索引を統合し、共通IDで重複を避ける。検索統合・ランキング・cursorの費用はBにもある共通費用。C固有には二形式の適用状態を条件へ反映する |
| 利用者編集 | 同じUIにできるが、型から外れる編集、再昇格、内容版の対応を実装する必要がある |
| 後の整理・訂正 | 共通IDの一改訂から両表示を更新できる。ただしtyped条件を満たさなくなった内容の降格、再昇格、保存条件への影響を扱う |

**総評：短期の段階導入としては可能だが、永続する全体構成として不採用。** 既存資産の互換が強い制約なら合理性が増す。今回は互換が設計条件でなく、既存Capsuleもすでに独自内容を扱える。正本を一つに改善しても、元の固定型を独立した登録資格として維持する利点より、二つのschema制約・昇格降格契約を保つ負担が大きいと判断した。案Bでも意味対応済みのtyped投影は使えるが、原主張自体の編集資格を別形式への昇格に従属させない点が違う。

### 案D：資料・出来事・テーマを正本にする

主データは資料の抜粋と注釈、出来事のカード、テーマ文書。人物・作品はそこへ参照され、関係グラフや年表はテーマから作る。例えばs6/s7は一つの上映会カードに、参加者と招待者を区別して置く。s9–s11も読み物へ自然に入る。すべての関係を二項Claimへ分解する負担を避けられる。

| 一巡の区間 | 同じ代表例での動き |
| --- | --- |
| 取得 | 資料を先に保存し、その範囲・版・抜粋をテーマへ引用 |
| 根拠確認 | 人／AIがテーマ単位で読む。段落やページ構成を保ちやすい |
| 登録 | 文書block、出来事、注釈として11件とも保存。関係の意味体系は必須でない |
| 表示 | 編集された一テーマ、年表、Capsuleは早く作れる。グラフの辺は編集者が選んだ投影として持つ |
| 検索・発見 | 全文・テーマ・人物参照で見つかる。全テーマを跨ぐ映画監督や翻案経路は、抽出索引がないと文書読解に戻る |
| 利用者編集 | 文書や出来事カードの編集に統一。知識が他の文書へ複写された場合の訂正通知が必要 |
| 後の整理・訂正 | s2の資料箇所を訂正し、依存するカード・辺・年表・推薦を更新。索引を再生成するなら生成条件と版が必要 |

**総評：テーマを見せる初速は最も強い。基盤としては関係探索の再利用負担が大きい。** 複数人物・役割・場所を持つ出来事には適しているが、作品の翻案や時期不明の影響を、すべて名前付き出来事へ変換する必要はない。文書を正本として主張索引を再生成すれば案Dのまま横断検索は成立する。違いは、文書を直した結果どの抽出主張のID・対応を引き継ぐか、利用者がGraphの関係だけを直した場合にどの文書へ戻すかという依存管理である。案Bは主張の直接編集と再利用を中心に置くため、その責務が小さい。関係探索を二次的にして編集テーマを主商品にするなら、案Dへ推奨を切り替える余地がある。

### 全体比較と不採用理由

| 判断軸 | A：事前体系 | B：共通原主張 | C：型とfallback | D：資料・テーマ |
| --- | --- | --- | --- | --- |
| 未知の関係を具体的に使い始める | 定義・対応の完了後 | 対象・根拠を確認後。意味対応前も使える | fallbackで使えるが本流との差を埋める必要 | テーマ内では早い |
| 既知意味の厳密検索 | 最も単純 | 対応済み索引で成立 | typed側は単純、全体統合は複雑 | 独立した抽出索引が必要 |
| 新語ごとのコード | 動的catalogなら減らせる | 通常の意味追加は不要 | fallbackなら不要、typed化で増える | 文書保存は不要、投影追加で増える |
| 訂正の正本 | Claim | 原主張と別版の対応 | 共通IDにできるが二schemaの適用状態を管理 | 資料・block・抽出物の依存管理 |
| 後処理の滞留 | 登録前に待ちが溜まる | 意味整理へ移る。未整理でも利用可 | 未対応側が恒久的に取り残されやすい | 横断索引化と文書間反映へ移る |
| 今回の結論 | 狭い収集経路へ部分利用 | 全体基盤として採用推奨 | 永続二系統として不採用 | テーマ編集の構成として利用、基盤には不採用 |

四案とも具体的な追加で作れる。原理的に不可能な案と結論しているわけではない。今回の要求と直接矛盾するのは、「体系へ収まらないと保存・表示・検索できない」という必須条件、および「未対応でも共通意味として厳密検索に無条件で混ぜる」という処理である。どちらもその前提を変える必要がある。案C/Dは技術的には成立するが、求める横断探索と訂正まで完成させると案Bに比べて管理対象が増えるため、全体基盤として選ばない。

## 5. 推奨構成を、登録・発見・訂正まで成立させる

### 5.1 何を保存し、何を別にするか

正本に残すものは、対象の識別、原主張、根拠箇所、範囲・時間表現、原入力と改訂、公開範囲である。意味対応は「この記録のこの版を、この文脈ではこの概念として扱う」という別の記録にする。対象の同定と関係の意味対応は同じ操作画面で確認できるが、意味として混ぜない。名前が似ているだけで人物を統合しないし、人物が同じと分かっただけで関係の意味まで受入済みにしない。

記録の基本形は、関係・出来事／エピソード・説明の少数とする。関係では主語と対象への明示参照を持ち、複数参加者を持つ出来事は参加者と役割の組を保持する。参加者の役割名は原語のまま保存できる。型のない巨大なJSONを何でも公開する構成にはしない。サイズ、参照、版、根拠の対象、時間表現の形は通常のschemaで検証する。新しい意味を追加することと、新しいデータ構造・検索演算を実装することは別である。

Entityも、安定IDと分類を分ける。現行の人物・作品・組織・出来事を初期の便利な分類として使いながら、場所などの新しい対象を保存するたびに閉じた4種enumの変更を必須にしない。未分類の対象を名前と根拠で保持し、必要な分類をデータとして加える。ただし地理検索や地図表示など、分類名を足すだけで成立しない演算・表示は別実装になる。ここでもIDの安定性は、世界の全対象分類を先に完成させることと同義ではない。

Claimの独立UUID、SourceとCitation、肯否が限定・scope・期間を含む命題へ掛かる原則は残せる。肯定と否定、予定、推測、資料にないことは区別する。例えばs6は「招待」の肯定を保存する。「欠席」の厳密検索も必要なら、同じ資料に結び付く別の限定された否定主張を作る。「欠席だった」という注記を、別の年の参加や人物の全活動の否定へ広げない。

日付不明、共通意味未対応、根拠未確認、対象未同定は同じ「未完了」ではない。利用可否は具体的に決める。根拠未確認の個人メモはprivate Capsuleで保持できる。根拠と対象を確認した具体的な関係は、その原主張でサービスのテーマへ載せられる。共通意味IDが未対応なら、厳密条件検索だけで対応済みと表示しない。この差を全部独立の承認ボタンにする必要はなく、テーマのレビュー画面で必要な項目を一度に確認する。

### 5.2 意味整理前の検索を「使えるが限界が分かる」ものにする

検索は三つの性質を分けて同じ入口から使う。

| 検索の性質 | 何を返すか | 約束しないこと |
| --- | --- | --- |
| 原文・語の検索 | 原主張、関係語、対象名、根拠の採用抜粋、テーマの説明に当たった記録 | 文にその語があることから関係の成立を認定しない。否定文・資料の引用にも当たり得る |
| 共通意味による条件 | 確認済みの意味対応、肯否、scope、期間等に一致する記録 | 未対応の同義語を全て拾うこと、同じ語を自動的に同義扱いすること |
| テーマ・関連コンテンツ | 記録や対象から結び付く公開テーマ／Capsule | Capsuleが公開されていることから各local主張を共通知識へ混ぜること |

例えば「復刊」ならs2の原文に当たる。しかし、利用者が「再出版の提案」と検索して、まだ同義対応がなければ、単純な語検索はs2を見落とす。案Bの実際の弱点はここにある。対策は、無根拠に一致扱いを広げることではなく、次の具体的な導線である。

1. 共通意味による結果には「この条件として整理済みの記録」と表示し、原文候補を別の一致種別として同じ結果画面から見られるようにする。内部のIDや処理状態を通常画面へ大量に並べない。
2. テーマ・人物等で範囲が定まっているときは、その範囲の未対応件数と「本文からも探す」を示す。全Webや全世界の網羅率を計算したような表示をしない。
3. 同義候補の検索には、まず採用済みaliasと文字列候補を使い、必要な場合だけ埋め込み・汎用AIを候補発見へ使う。近さのスコアを共通意味の確定にしない。初弾にvector基盤は必須でない。
4. 整理の優先度は、よく使われる検索語、完成させたいテーマ、衝突しやすい同形語、訂正要求から決める。未対応全件を一律に毎晩AIへ再送しない。
5. 一度「再出版の提案」と「復刊提案」の文脈付き対応を確認したら、該当候補へ再照合する。個々の資料のscopeは別に検査し、「復刊を実現した」まで同じ意味へ統合しない。

「意味整理待ちが減った件数」だけを成果にしない。テーマ内の意図した検索が通るか、整理のために利用者が書き直した回数、未対応のために発見できなかった例、誤対応の訂正件数を観測する。最初の利用者が本人だけなら、検索語と不足箇所を一つの小さい一覧で扱える。大規模な語彙管理部門や全自動ontology構築は要らない。

### 5.3 表示・プリセット・おすすめ・Capsuleの役割

**関係図は具体的な意味を保つ。** s2の線は「復刊を提案」、詳細では「復刻特装版」「資料のどの箇所か」を示す。長い文を一行に詰めるために「関係がある」へ薄めない。短い見出しは編集できるが、押すと原主張と根拠へ戻れる。意味IDが未対応でもこの経路は成立する。逆に短い見出し自体から共通の意味を生成しない。

**プリセットは条件の雛形。** 「作品→制作した人→その人の別作品」など、実行できる条件を名前で再利用する。必要な意味対応の版を記録し、語彙を分離した後に条件が勝手に広がらないようにする。条件が使えなくなったら、別条件へ黙って退避せず修正を案内する。

**おすすめは編集された入口。** 最初は完成したテーマを数件掲載し、なぜ面白いか、どこから読めばよいか、根拠と更新日を示す。多くのEntityがあっても、テーマが成立していなければおすすめにしない。個人利用の現段階では、利用ログの少ない人気ランキングや大きな推薦AIを先行させる理由は弱い。既存の公開例を、このTheme／Capsule入口へ育てる。

**Capsuleは作者の文脈。** テーマから複製・引用し、注釈、配置、独自の対象や関係を加え、そのまま保存・共有できる。共通知識への申請は選択部分に対する明示操作の一つにする。直接一件を提案する入口も同じ受付へつなぎ、Capsule作成を強制しない。保存だけでAI処理や投稿を始めない。

固定版の表示は旧仕様だから残すのではない。作者が共有した説明と、その版へのコメントの意味を守るのに適しているから残す。一方、古い事実を見つけやすくするため、共通知識の訂正があれば「取り込んだ記録に更新があります」と比較を提供する。作者が取り込むまで配置・私的注釈・本文を上書きしない。参照主体の表示名修正と、主張の内容変更、意味対応だけの修正を分ける。共有URLへ更新するのは従来どおり明示操作とし、固定掲載の版も勝手に変えない。

### 5.4 誤対応・意味分離・統合・内容訂正をどう直すか

| 変更 | 正本への操作 | 検索・おすすめへの反映 | 保存Capsuleへの反映 |
| --- | --- | --- | --- |
| 「監督」の映画／スポーツ誤対応 | s4の意味対応を失効し正しい対応を追加。原文・根拠は保持 | 映画監督条件からs4を除き、対象の索引だけ更新。関連プリセット／推薦を再点検 | 保存した本文は保持。現在の意味表示との差を示す |
| 「演出」と監督の同義確認 | この文脈に限定した対応を追加。同じ表記の全記録へ無条件適用しない | s5が映画監督条件へ入る。候補群を再照合 | 作者の原文ラベルは保持できる。共通語への表示変更は選択 |
| 一つの概念を二つに分ける | 旧概念を参照可能に残し、各記録を再評価。曖昧なものは未対応へ戻す | 旧条件を新条件へ無条件でOR展開しない。保存条件に修正要否を表示 | 古い参照と新しい候補を比較。勝手にどちらかへ振り分けない |
| 二概念を統合する | 確認した等価対応と版を追加し、記録IDは維持 | 重複結果を記録IDで除く。近義語なら統合せず関連として扱う | 内容は不変。表示語の更新は任意 |
| s2の版・scope訂正 | 同じ記録の新しい内容版を作り、旧版・理由を保持 | 現在版で再索引。全作品への無限定な関係として返さない | 旧断面と新版の差分を見せ、明示取り込み後に共有更新可能 |

対応を変えたら原文を書き換える方式や、巨大な「同義語集合」を一括で置換する方式は採らない。これにより誤りを直す単位が小さくなる。ただし分離時の意味判断は人または検証したAI支援へ残る。自動で分けられないものを未対応へ戻すと、厳密検索で一時的に見つからなくなる。この減少は隠さず、テーマ担当が必要なものから再確認する。

### 5.5 物理保存の推奨と、DBを変えない代案

論理上の核心は「原主張と改訂の正本を一つにすること」であり、PostgreSQLを選ぶだけで解決するわけではない。比較の結果、初弾の候補は、**PostgreSQLの知識専用領域にRecord／Revision／Source／MeaningAssignmentと受付状態を置き、Neo4jは公開探索用の再生成できる投影にする**構成である。会員表へ知識を混ぜる意味ではなく、領域・権限・backupを明確に分ける。

| 保存案 | 利点 | 追加負担・弱点 | 判断 |
| --- | --- | --- | --- |
| Neo4jを知識正本のまま拡張 | 現在の探索とDB運用を保ちやすい。版や原文もnodeとして表現可能 | 原主張・版・対応・submissionの更新とPG側の作者／Capsuleとの連携を設計する。一般的な訂正APIは現seedの代用では作れない | 技術的に成立。小さい改修に限定したい場合の有力代案 |
| PGを記録正本、Neo4jを公開投影 | 改訂・受付・対応・公開候補をtransactionで管理しやすく、自由な記述と検証済み欄を併存できる。Graphは元記録から再構築可能 | 投影の遅延・失敗・再構築・版切替が増える。二つのDBを一つの正本に見せない厳密な実装が必要 | 編集と訂正が中心になる今回はこちらを推奨 |
| PGだけで知識と探索 | 投影先を減らせる。小規模の隣接・固定長経路ならSQLでも候補 | 現役のNeo4j取得・経路・cursor等の移植が大きい。今回性能比較をしていない | 初弾の全面置換は見送る |

現seedは、同じIDの内容が違えば拒否し、固定fixture以外の混在を拒否する。これは凍結データ導入として妥当だが、一般の利用者訂正APIを提供しているわけではない。どの保存案でも、改訂を受け付けるwrite経路は新設が必要である。[現在の書込み境界](https://github.com/isinxnisi/graph-knowledge/blob/cd84b76ecf5b5f36009fb43ee01ffc7ac6cf9206/lib/server/seed.ts#L39-L84)。

PG→Neo4jでは、公開結果の完了通知を投影成功後に出す。正本の受入と公開版は別で、投影に失敗したら「反映待ち」として前の整合した公開版を使う。新しい公開版の対象記録・索引・Graphを検証し、一つの版参照を切り替える。cursor、プリセット、テーマの構成はその版へ束縛する。検索だけ新しいscope、Graphは古いscopeという混在を許さない。撤回は通常の遅い再構築を待たせず、対象IDを読取対象から外す小さい更新を優先し、全読取経路で同じ公開対象集合を見る必要がある。

この部分には、変更依存の一覧、再送しても二重適用しない処理、投影checkpoint、旧版からの復旧が必要になる。初弾でNeo4j正本案より工数が増える理由でもある。PG案はその費用を払って訂正の正本を単純にする選択であり、無償の改善ではない。DB容量・再構築時間は未実測なので、最初に小さい複数版データで比較し、既存運用上の負担が大きければNeo4j内の版付き記録へ替えても案Bの結論は維持できる。

## 6. 年表が今回の採否へ影響した範囲

### 6.1 保存構造に効くもの

| 論点 | 選択肢と反例 | 今回の判断 |
| --- | --- | --- |
| 日付軸と精度 | 全てを日付へ変換すれば既存型は再利用しやすい。しかし「青の時代」に日付を補うと資料にない精度を作る | 原語と精度を保持。日付表現はそのまま利用し、それ以外は別の時間表現を持つ |
| 点と区間 | 全てを一点へ置くと制作期・在籍期・時代が失われる。全て二端点なら瞬間・未知端点の意味が曖昧 | 表現上の点／区間／未配置を分ける。未記録端点を永遠・現在継続とみなさない |
| 周期 | 10月→2月を通常の日付順の二端点で検証すると逆転扱いになる | 周期長・単位・原点・跨ぎの有無を軸側に保存。必要な年へ展開するのは表示／検索の操作で、元記録を多数の偽Eventへ複製しない |
| 定性軸 | 「若いころ→青の時代→晩年」は順序があっても間隔が一定とは限らない。座標1.2〜10.3も意味未定 | 軸IDと座標の意味、順序・距離の有無を持つ。数値はピクセル位置と別。順序未確定なら無理に補間しない |
| 非時系列 | 全情報に時点を要求すると豆知識が落ちる。全部を注記にすると時期付きエピソードまで年表から消える | Entity／作品／テーマの情報枠を用意し、時点・区間に結び付くエピソードはその場所にも置ける |
| 一つの年表内の混在 | 日付の一定期間に周期や定性段階が入る。一本の数直線へ押すと意味が変わる | 主軸と補助レーン／期間内の小図を構成できる参照を保持。画面を全部同時に密集させる必要はない |

したがって、年表を現行Claim.periodの描画だけで実現する案は不十分である。案Aでも時間モデルを広げれば成立するし、案Bだから自動的に描画できるわけでもない。案B/Dは原語と期間の追加を自然に持てるが、軸ごとの比較・絞り込み演算とUIは別途必要になる。

### 6.2 比較とマージを一つの操作に決めつけない

| 操作候補 | できる体験 | 条件・トレードオフ |
| --- | --- | --- |
| 同じ時間軸での重ね合わせ | 葵と蓮の活動を同じ年で比較 | 時間参照系が合う必要。情報過密ならlaneに分ける |
| 複数レーンの束 | 葵＋蓮の二年表を一組にして、日菜の年表と2対1で比較 | 合成対象が複数laneを参照する構造で成立。原データ統合は不要 |
| 連結 | 前半と後半、世代の連続性を読む | 実際の年代順の連続と、物語上の編集順を区別。繋ぎ目と空白を示す |
| 対応点での並置 | 作品制作の段階と、暦年の出来事を比較 | 「初稿完成」等の対応点を明示。軸全体の等速変換や等距離を推定しない |
| データそのものの統合 | 同じ上映会を両年表から一件にまとめる | Entity／Eventの同一性と版・出典の判断が必要。表示合成とは別操作 |

周期軸同士でも、単位・周期長・起点が異なれば単純には重ねられない。異軸でも並べて読み、対応する資料上の点を結ぶ体験は作れる。共通尺度へ変換できないことは、比較不能という意味ではない。一方、対応の根拠がないまま「青の時代の1.2は2012年」という値を作ることはしない。

保存上は、Timelineが記録と軸配置を参照し、Compositionが複数Timeline／laneと対応点を参照する小さい構造で、2対1と連続表示の余地を残せる。任意の無限再帰、全軸の数式変換、全種類のマージ操作を初弾に実装する必要はない。比較単位と元データを分ける点だけは、最初に保持する。

### 6.3 今回詰めなかった詳細と、その理由

目盛間隔、zoomの加速、定性段階の配色、全ての周期単位、入れ子の深さ、最終的な編集ジェスチャーは四案の採否を変えないため未決とした。表示の一覧性は後続の実画面検証が必要で、保存構造の対応だけで達成済みとはしない。最初は日付・期間と未配置の情報枠を実装し、同じデータで定性・周期を保存して、簡単な専用laneへ置けるところまで検証する。精密なズームや混在表示の完成を、知識登録の開始条件にしない。

関係図と年表は別の表示モデルを持ってよい。共通の対象ID、原主張ID・版、根拠参照、訂正差分を共有すれば、人物から年表、作品から関係図へ往復できる。全ての関係をEventへ変換することも、別機能にしただけで訂正の問題が消えたとすることも採らない。

## 7. 外部の設計から採る考え方と、採らない飛躍

| 一次資料 | 再利用できること | Plunodeで別途必要なこと |
| --- | --- | --- |
| [OpenRefine reconciliation](https://openrefine.org/docs/manual/reconciling) | 元の値と照合結果を分け、候補・判断・再照合を保持する。s4の「監督」を残したまま誤った対応を直せる | 対象照合が中心。関係の語義、方向、scope、年表合成、Capsule差分まで自動的に解決しない |
| [SKOS Primer](https://www.w3.org/TR/skos-primer/) | 概念IDと表示語を分け、近い対応と厳密な対応を区別する。映画／スポーツの監督を別概念にできる | 表示語を共有するだけでは同じ関係にならない。主張の支持、端点、適用条件、分離時の再評価を設計する |
| [Wikidata Properties](https://www.wikidata.org/wiki/Help:Properties) | ID・定義・別名・datatype・制約のある広い体系を参照でき、案Aの現実的な供給源になる | 外部propertyに入らない意味を近い語へ押し込まない。外部の提案・承認手順を丸ごと採用する義務はない |
| [Web Annotation Data Model](https://www.w3.org/TR/annotation-model/) | 文書の一部をselectorで示し、引用箇所や資料版を参照する。案DやSourceBundleの根拠定位に有用 | 抜粋は関係索引ではない。複数資料を合わせて支持する場合の証拠集合と、各資料単独の支持を区別する |
| [OWL-Time](https://www.w3.org/TR/owl-time/) | 点・区間、前後・重なり・包含、時間参照系、数値／名義上の位置を区別する | 任意の定性語の順序、周期の原点と跨ぎ、曖昧さ、異軸対応、UIのマージ操作は決まらない |

SKOSのexactMatchとcloseMatchを同じ同義語リストへ潰さないことは、誤対応の伝播を防ぐ上で参考になる。ただしPlunodeでは、語彙間の厳密対応さえあればすべての記録を自動統合できるわけではない。対象・scope・期間・肯否が異なる記録は独立して残る。OWL-Timeの区間関係としての「定性的」と、利用者が考える「青の時代」という定性軸も同じ意味ではない。

外部方式をそのまま導入することより、原資料、意味対応、検索・表示の投影を区別することに価値がある。今回の案Bはこの考え方を使うが、外部標準名を採ったことで実装や意味判断が済んだとは扱わない。

## 8. 収集・AI・実行環境・費用をどう組むか

### 8.1 AIに任せる仕事と、通常のプログラムでよい仕事

| 処理 | 主担当 | 入出力・実行上の考え方 |
| --- | --- | --- |
| テーマの問いと完成像 | 人、ChatGPT等 | 問いと核になる対象からThemeBrief。紹介する価値は件数で代用しない |
| API取得、hash、cache、URL・参照・schema検証 | 通常のプログラム | SourceBundleを作る。取得元のレート制限、失敗と再試行は意味判定と分ける |
| ページ構成・前後文・複数資料の読解 | 汎用AIと人 | 原主張、根拠箇所、支持範囲、曖昧点を提案。重要な不足には補足URLを探索 |
| 同一対象・語義候補の検索 | 索引と通常プログラム、必要時AI | 名前・外部ID・文脈から少数候補を渡す。毎回全体系をpromptへ入れない |
| 限定された選択・要確認の振り分け | 検証できた範囲のKev候補 | 数個の候補から判定。新しい関係の自由抽出・根拠探しを担えるとは前提にしない |
| 主張の採用・例外の判断 | 初弾は人がテーマ単位で確認、AIが補助 | 原主張・対象・根拠・対応候補を一画面で確認。五種類の独立承認ゲートへ分割しない |
| 保存、再索引、公開投影、差分・通知 | 通常のプログラム | 安定ID・版・冪等性・公開範囲を検証。AI出力で承認済み状態を自己付与させない |

取得先ごとのadapterは必要である。NDLのXML、Wikidataの構造化応答、HTML/PDFでは取得・locatorの作り方が違う。一方、「漫画」「映画」「科学」ごとに全工程を一式作ることは必須ではない。取得形式のadapterと、関係の意味を読む処理を分離する。書誌の規則が強い領域には既存の有限parserを使い、文脈が要る資料には汎用読解を使って、同じ原主張パッケージへ出力する。

③の直後に資料を保存し、④を後でまとめて行う構成を選ぶ。例えば10資料のうち2資料が取得待ちでも、取得できた8資料の意味確認とテーマ編集は始められる。ただし「全資料確認済み」とは表示しない。資料全体の収集完了と、個々の根拠付き記録の利用可能性を分ける。既存の一つの親ジョブにあるtechnicalWaitが、無関係な完成分をいつまでも止める構造を一般化しない。

### 8.2 現在確認できた接続と、候補として残る接続

### 8.3 初テーマと次テーマで、誰の作業が何回残るか

以下は計測値ではなく、運用設計上の目標単位である。テーマ一件、資料8〜12件、候補15〜25件程度を仮定する。資料ごとの読解や例外判断は残るが、「候補25件×5つの独立承認」を求める方式にはしない。

| 作業 | 初テーマ | 同じ仕組みでの次テーマ |
| --- | --- | --- |
| 面白い問いと完成条件 | 人が1回決める。AIの候補を調整 | 1回。新しい機能定義ではなくテーマ内容の仕事 |
| 資料取得・候補抽出 | AI／人が一まとまりの調査。取得済み資料は再利用 | 1調査batch。新取得元の特殊形式ならfetcher追加が別途必要 |
| 根拠・対象・意味の確認 | テーマの1回のレビューで通常分をまとめて採用。曖昧なものだけ例外確認 | 同じ。既存対応は候補として再利用するが、資料の支持を省略しない |
| 未知の関係語 | そのまま保存。厳密検索に必要な概念だけ定義・対応 | 通常はデータ追加。新たな語ごとのアプリ修正を目標上0にする |
| 語義分離・同義整理 | 例の「監督」は2語義を1回明示し、演出対応を確認 | 既知文脈なら再利用。異なる制度・分野なら新たに判断 |
| テーマ編集と公開確認 | 1回。どの関係を見せ、何を説明するかを人が決める | 1回。自動収集が編集判断を置き換えるとはしない |
| 後の意味整理 | 小さい候補群を1batchで処理。全部完了を公開条件にしない | 需要がある語・訂正・次テーマ接続を優先し、有界に処理 |
| アプリ実装 | 共通受付、原主張索引、改訂、投影、差分を初回実装 | 通常の関係・参加役割の追加は不要。新しい検索演算、軸種類、専用rendererは実装が必要 |

一テーマの人手は、整理済み領域でもゼロにはならない。相当部分は「資料を読み、面白さを選び、曖昧さを判断する」という製品価値そのものの仕事である。削減するのは同じ意味を毎回再定義する作業、型へ入れるための書き直し、複数形式への二重登録、全件の無差別再判定である。

案Aはこのうち未知語の定義を登録前へ移す。案Cは振り分けと昇格時の対応確認が加わる。案Dは初回の読み物編集を軽くできるが、後で横断検索が必要になるたび抽出・対応が追加される。案Bは初期の共通実装が大きい代わりに、次テーマの意味追加をデータ上の仕事へ寄せる。

### 8.4 費用と処理量

今回、AI呼出しの精度、token、latency、GPU占有、実運用のthroughputは測定していない。料金・時間の数値を、検証済みの実行費用と混同しない。

API費用の感触として、公式Standard単価の短文脈リクエストを合計して入力100,000 token、課金対象出力20,000 tokenを使うと仮定する。`gpt-6.1-sol`の入力$2／出力$10（各100万token）なら約$0.40、Astraの$10／$50なら約$2.00になる。検索ツール料金、追加処理、インフラ、人手は別で、成功するテーマ数や品質はこの計算から分からない。これは新API利用の推奨発注でも、今回のChatGPT消費量の計算でもない。[公式API料金](https://developers.openai.com/api/docs/pricing)。ChatGPT Work／Codexの含有枠や追加creditsはAPIとは別であり、このドル額へ直接換算しない。[Work料金の説明](https://learn.chatgpt.com/docs/pricing)。

費用を抑える実装は、全体系を毎回送らず関連する少数候補だけを渡すこと、資料抜粋・前処理を再利用すること、失敗を無限再送しないこと、未変更の記録を再判定しないことである。AIの適用は、複数資料の読解と曖昧な候補に集中させる。Kevも電力・熱・共有資源と停止時間を使うので、無制限の無料枠として扱わない。

初弾の利用量管理は、サイト全体と背景処理を含む一つの予算台帳、jobごとの有限上限、同時実行数、再送識別を備える。実行前に見積枠を取り、終了後に計測可能な消費を記録し、timeoutで結果不明なら同じ仕事を無条件再送しない。API課金、ChatGPT枠、ローカルCPU/GPU秒は別欄で管理し、取得不能な指標を0消費と記録しない。利用者別課金・ポイント制度・複数プランは初弾に不要だが、一つの処理が全枠を占有しない小さいjob上限は必要である。

後処理の量は、未整理記録N件を毎回処理するのではなく、変更された記録Δ件と、影響を受けた意味対応・保存条件を処理する。次のテーマを追加して未対応が増えても、既に使える原主張の表示は止めない。滞留は、未対応総数だけでなく、完成待ちテーマ数、利用者から求められた検索語、最古の訂正要求で見えるようにする。

## 10. 実現順、再利用する資産、切替の方法

### 10.1 先に作る利用体験

初弾は「根拠付きテーマを作って紹介し、訂正まで行える」一巡である。関係図の全面拡張を先に全部終える必要も、年表を全部完成させる必要もない。最初は関係図と簡単な日付・期間の年表を同じ記録へ接続し、時期不明の情報は対象・テーマの情報枠へ置く。定性・周期は元の表現と軸参照を保存し、小さい専用laneで検証する。

初弾終了時に利用者へ提供するものは、次の五つをまとめた体験である。

1. URLや根拠パッケージから、既存のRoleにない関係も具体的な言葉で登録できる。
2. 原主張と根拠を見て、一つの面白いテーマを関係図・年表・情報枠として紹介できる。
3. 対象名、原文の語、対応済みの関係条件から見つけられ、未対応の限界も分かる。
4. そこから自分のCapsuleを作り、自由に編集・保存・共有できる。知識申請をしなくても価値が完結する。
5. 誤った語義対応やscopeを直すと現在検索が変わり、保存Capsuleは差分を確認して明示取り込みできる。

### 10.2 実装単位と完了条件

| 単位 | 作るもの | 完了を何で確認するか |
| --- | --- | --- |
| 1. 共通記録の一巡 | 原主張・根拠・改訂・意味対応、共通import、対象同定候補、原文検索、既存Graphへの投影 | 架空fixtureに加え、利用者が選ぶ小さな実テーマで、未知関係が保存・表示・検索できる。根拠箇所へ戻れる |
| 2. テーマとCapsuleへの接続 | 直接提案と選択部分申請を共通受付へ。テーマ紹介、日付／期間の年表、情報枠、Capsule差分 | 一件の保存・共有が完結し、共通知識へ申請しない編集も保持。s2相当の訂正で本文・配置を勝手に上書きしない |
| 3. 読解支援と実行管理 | SourceBundle、AIの候補提案、例外レビュー、総予算、job再送・反映状態、結果通知 | 支持不足、同名異人、誤対応、部分採用、PC停止、quota到達、結果不明を通し、入力を失わず再開できる |
| 4. 二つ目のテーマと公開切替準備 | 新しい分野・語、意味分離、条件と推薦の更新、投影の再構築・復旧 | 同じ関係形なら追加のアプリ修正なしで次テーマを作れる。新しい演算が必要な箇所だけ特定し、切替前後の根拠・参照を照合 |

これは四回の承認会議を要求する区切りではない。実装はPC側で、相互依存を確認しながら順に進める。クラウド側は設計・調査・根拠確認へ留めるという現在の分担を守る。初弾の外部AIは、対話で作ったパッケージの取込から始められる。自動実行の接続は単位3で実測し、既存の教育スケジュールや収集Workerを無断で置き換えない。

工数は今回未実測である。計画用の粗い仮定として、一人の実装担当とAI支援で、上の4単位をそれぞれ数営業日、合計2〜4週間程度の作業規模と置く。実DB投影の方式、年表UIの仕上げ、実資料の確認量で変わるので納期の約束にはしない。まず単位1で見積りを補正する。既存Role数個の追加より大きい一方、認証・会員・Capsule・Graphを全部再実装する規模へは広げない。

### 10.3 既存資産の扱い

| 扱い | 資産 | 理由 |
| --- | --- | --- |
| 維持・接続 | Capsule Studio／保存／共有／版付きコメント、認証・会員・community | 独立した編集体験が既に成立。知識の正本変更と再実装を結び付けない |
| 維持・拡張 | Entity ID、Source／Citation、根拠locator、原語、肯否・scope・精度の境界 | 同定と根拠を失わず改訂するために有用 |
| 小修正・再利用 | Graphの描画・選択・配置、LIMIT前の条件、cursor／公開版拘束、経路の証拠確認 | 意味対応済みの投影と原文関係を同じ操作感で使う土台 |
| 役割変更 | Predicate／Role catalog | 唯一の登録許可表から、厳密検索・表示の共通概念辞書へ。現在の定義は初期辞書として使う |
| 役割変更 | Neo4j | PG案採用時は公開探索用投影へ。DB変更が過大なら版付き記録をNeo4jに保持する代案も可能 |
| 部分再利用 | 漫画collector、通信cache、NDL/Wikidata取得、hash・review資材 | 対応済み資料では効率的。全テーマの唯一の読解経路にしない |
| 維持して再接続 | 公開gate・署名・receipt・backup／復旧・固定版の検査 | 現運用の安全資産。新payloadへの検証を追加し、調査中に無効化しない |
| 置換・新設 | 原主張の正本、一般改訂API、意味対応、原文索引、変更依存・差分 | 現在の固定fixture・typed Claimだけでは不足する部分 |

### 10.4 下位互換を必須にしない、現実的な切替

新しい知識領域を独立して用意し、保存済み根拠・受入記録・現在公開データから必要な内容を読み直す。既存のUUIDを再利用するのは参照の追跡に便利だからであり、古いAPI全てを残すためではない。意味が一致しないものを、移行成功のために自動的に丸めない。旧データから原文が復元できない箇所はその事実を明示し、既存の構造化Claimと根拠から始める。

最初のテーマと訂正を新領域で完結させ、現在の本番・βはその間も維持する。次テーマを同じ経路へ通してから、読み取りAPIと公開投影をまとめて切り替える。保存済みCapsuleの断面は保持し、旧IDと新しい記録の対応を明示比較へ使う。新形式へ移せない独自内容も、Capsule本文として残す。既存共有版やコメントを移行のために削除しない。

切替時に確認するのは、必要な対象・主張・根拠・改訂が追えること、公開範囲が同じであること、検索とGraphが同じ公開版であること、問題時に旧読取へ戻せることである。これは下位互換を永続維持する計画ではなく、現運用を壊さず新しい正本へ扱い直す作業である。実装・merge・commit/push・Issue更新・本番切替は今回実施していない。

## 11. 結論を変え得る、最小の未決事項

1. **横断関係検索と、編集テーマのどちらをサービスの中心に置くか。** 今回の依頼は両方を重視するため案Bを選んだ。今後、横断検索を従属機能へ下げ、編集された読み物を主商品とするなら、案Dを基盤にする選択が強まる。
2. **意味未対応の原主張を、根拠付きの具体文としてサービス内で利用できる範囲。** これを厳密な意味IDの確定まで全面禁止するなら案Bの主な利点は失われ、案Aへ近づく。初弾は実テーマで、原文結果と意味条件の違いを利用者が理解できるか確認する。
3. **実際の読解支援の品質・負担。** 汎用AIが資料の文脈・scopeをどの程度拾え、人がどこを確認すべきかは未測定。ここで失敗が多ければ、AI担当を狭めても案Bは成立するが、自動収集量と運用費の見積りは変わる。
4. **知識正本の保存先と投影更新の実費。** PG→Neo4jの再構築・訂正反映が既存運用に見合うか、小実装で確認する。見合わなければNeo4j内の版付き正本へ替える。原主張と意味対応を分ける結論自体は変わらない。

周期・定性軸の全操作、推薦AIの方式、全分野の語彙体系の完成は、この四点の判断を待たせる条件ではない。まず一つの具体的なテーマを、保存だけで終わらず、発見・編集・訂正まで通す。それが次のテーマを同じ低い負担で増やせるかを判断する最小の実装である。
