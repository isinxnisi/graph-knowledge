## 型の定義と観測を分ける

型は「何を発見したいか」と、それに必要な条件のまとまり。作品名・人物名・現在の件数・公開revisionを型の定義へ入れない。具体的なUUID、成立例、未発見、公開／受入／保留、APIの応答と上限は、日付ごとの観測に置く。

| ID / 定義版 | 利用者の問い | 構造・正規方向 | 必要条件と出力 |
| --- | --- | --- | --- |
| S1 / 1 | この人物が関わる別作品は？ 作品によって役割はどう違う？ | 作品 ← 人物 → 別作品 | work/person/work、CONTRIBUTED_TO、異なる作品、各Claimの肯否・Role・scope・根拠。辿る向きは逆→順 |
| S2 / 1 | 同じ作品に、どんな担当の人がいる？ | 人物 → 作品 ← 別人物 | person/work/person、異なる人物、段ごとのRoleとscope。共作・同時期参加を成立条件へ暗黙追加しない |
| S3 / 1 | この人の別作品から、次の担当者を知りたい | 作品 ← 人物 → 別作品 ← 別人物 | S1＋S2の3段。全対象を再訪しない。第1・2・3段のRole条件を別々に評価 |
| S4 / 1 | 同じ人物の記録から、別の機関へ進める？ | 機関 ← 人物 → 別機関 | organization/person/organization、AFFILIATED_WITH、異なる機関。各段の立場・期間・資料の記録限定を保持 |

いずれも代表例の成立認定には**公開済み・肯定・非デモの支持Citationあり**を使う。これは研究で採った条件であり、否定も含む現行GET経路APIの意味を変更しない。並行Claimは別記録のまま扱い、同じSourceを引用する広いClaimと限定Claimを独立証拠2件と数えない。

### 同じ形の、異なる問い

S1の「別作品を見つける」はRole無指定でよい。「両作品で著者欄に載る」は両段AUTHORSHIPが必要。「PLUTOのプロデュース担当が、別作品ではストーリー共同制作をしているか」は第1段PRODUCING、第2段STORY_CO_CREATIONが必要である。

後者を全段共通のRole集合 `{PRODUCING, STORY_CO_CREATION}` に置き換えると、逆の組合せや同Role同士も許してしまう。**RoleのOR集合と、段ごとの割当ては異なる検索条件**。今回の定義では問いの変種として残し、Role名ごとに別の型を増やさない。

S4も「接続している機関を見つける」と「ある期間に両機関に関わったか」は異なる問い。後者には、期間の精度、nullの扱い、期間重複の判定方針、受賞時点の記録等の限定が要る。未知の期間を無期限・現在継続と解釈しない。受賞年・資料公開日・記録日時を関与期間へ転記しない。

## 検索条件として残す単位

- 対象：各位置のkind、固定起点・中継点・終点を指定する必要の有無、対象の同一性と別名照合範囲。
- 接続：段ごとのpredicate、正規の主語／目的語と辿る方向、肯否、全段の完全な成立証拠。
- 限定：段ごとの制作Role／組織立場、元Claimのpublication scope、期間の値・精度・不明方針。異なる作品のISBN一致を要求しない。
- 取得：公開revision、条件版、ページング・探索予算、取得済み範囲と未取得範囲。部分取得0件を不存在へ変換しない。
- 説明：Claim→Citation→Source・locator・原表記へ戻れること。経路から共作・交流・影響・移動順・続編関係を生成しない。

機械定義とcohortの `requiredConditions` は研究用の条件記述で、実行可能DSLやAPI仕様ではない。scope=nullは全巻・全版を意味せず、役割nullは未構造化である。Citationに「Visitor」「漫画」とあっても、構造化した立場やDRAWINGを検索時に補完しない。

## 不足を切り分ける記録軸

| 軸 | 判断すること | 初回例 |
| --- | --- | --- |
| データ・同定・根拠 | 対象や命題が公開されているか、受入済みか、資料が支持するか | タッチの刊行物同定保留。小畑のDEATH NOTE作画Claimは未収録 |
| 検索能力 | 保存済みの条件を段ごとに指定・照合できるか | PRODUCING→STORY_CO_CREATIONはデータあり、段別Role指定なし |
| 取得上限 | 問いを表せても候補が切れていないか | GETは20記録/対象・24展開・128中間経路・12結果。初回の代表GETには制限理由なし |
| データモデル | 問いに必要な意味が構造化されているか | 受賞時点の所属限定はCitation.note。期間・雇用・同時在籍へ強められない |
| 表示 | 既存の意味を利用者が読み取れるか | 並行ClaimのRole・版・原語、選択経路とGraph最短経路の区別。改修は今回行わない |

公開済み、正式受入済みだが未公開、候補・保留を同じ経路集合へ混ぜない。受入票の存在だけでは現在の公開を証明しない。公開APIで見えない受入済みUUIDも、撤回・差替え・取得範囲を確認するまで「公開待ち」と断定しない。

## データが増えたときの扱い

同じ問い・形・条件の下で新しい人物や作品、Role値の成立例が増えたら、既存型の**新しい観測例**とする。群の合流や枝の追加は観測結果であり、新しい型ではない。ヒカルの碁の橋渡しとH2→MIXの作者横断は、どちらもS1として比較できる。

新しい型を検討するのは、既存型で表せない端点構造、複数経路の全称・不存在等の量化、新しい時間・scopeの意味が必要になったとき。まず問いと反例を追加し、既存型の変種で足りるか検討する。採用時は定義版を増やし、過去観測を新定義で黙って上書きしない。

頻度・件数と、探索としての魅力は別欄で評価する。初回の「役割が変わる」「別の群へ渡る」「名前以外の接点を知る」は価値仮説であり、利用者評価済みの人気順位ではない。日々の増加を追って今回の分析を延長せず、固定観測ごとに比較する。
