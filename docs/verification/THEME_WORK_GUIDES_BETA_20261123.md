# 動的作業ガイドのβ実装・受入記録

設計の基準は [動的ガイド設計](../design/THEME_WORK_GUIDES_20261123.md) の `c7c5b986`。既存の制作・見直し工程、案件進捗、実行権、登録受付と公開処理を利用する。

## APIの使い方

- `read_theme_work_guide` に `phase`、必要な `focuses`、案件に応じて `caseId` を指定する。案件の運営者・origin・環境・実phaseを照合する。共通原則と工程の安全条件を毎回返し、reviewには全体評価の必須本文、画面証拠と公開確認の契約を加える。`knownVersions` が省略できるのは任意節の既読本文。未知のfocusでは必須部分と対応キーを返す。
- 明示依頼に基づく運営者改訂では `read_theme_work_guide(management:true)` で編集可能な構造を読む。既存の構造を保持して修正した全体を `update_theme_work_guide(changes:…)` に渡す。期待版、操作依頼ID、理由も渡す。履歴は管理読取の `revision` と `historyBefore`、復元は更新の `restoreRevision` を使う。自由形式の旧版は全文を返す。構造化された版は旧API向けのMarkdownを描画する。
- 新契約は作成時の `guideContract:2` で案件ごとに選ぶ。既存案件は旧契約のまま読み書きできる。新契約の評価では対象digest、監査用の `guideRevision`、判定用の `criteriaRevision`、画面用の `evidenceRevision` を渡す。新契約の定期案件では、最新の対象・build・採取要件と一致する全証拠を当該review起動で取得する必要がある。
- 必須本文・追加必須言語／画面をサーバーが比較して版を進める。通常手順・例示・モデル補助は合否や採取の必須条件を定義する入力ではない。復元も新規revisionとして記録する。作業版・送信・公開が競合した場合は既存の読戻し、同一受付の回復と `reconcilePublished` を利用する。
- βの会員DB追加migrationは `050-theme-work-guides.sql`。旧Webへ復旧するときは、新規案件の選択を止め、構造化版を処理できる時点で必要な案件・公開intentを確定させる。旧Webの再起動前に、旧Webが読めるMarkdown版が現行となるよう、ガイドの運営APIで復元・確認する。DB台帳や旧版を直接書き換えない。

## 比較試験の引継ぎ

1. βに同じ開始データを持つ旧契約・新契約の非公開テスト案件を用意する。ルート66型の期間・見出し、Webb型の場面不一致、黒澤／Nas型の画像の選択から、複数題材を用いる。各題材で方式の実施順を入れ替え、同じモデル・資料・稼働条件で複数の独立起動を比較する。
2. 制作は規定時間内で関連作業を進め、今回の反映差分と次回の再開点を残す。両方式でprepare後・dispatch後の異なる箇所から再開し、同じ保存済み内容、同じ受付と画像ID、作業版の維持を確認する。
3. 別のWebの見直し実行で、方式を伏せた年表を通読する。重要な欠落の発見、訂正が日英の表示へ届いたか、欄外の改善だけで合格していないか、任意の磨き込みで止まり続けていないかを記録する。PCとスマートフォンのPNG受取は配信記録と実視認を区別する。
4. 1回で読者に届いた反映、重大な見落とし、中断後の重複・消失、外部待ちを記録する。単発の成功で採用を決めず、品質や成果量が繰り返し落ちる条件は原因を修正して比較し直す。ChatGPT Web側のツール一覧に新ツールがない場合はβ Appの定義を読み直す。運用移行では見直し側の新旧両対応を確認してから、制作に新規案件の選択を渡す。

## 追補 — Issue #78 の管理用読み取り

[Issue #78](https://github.com/isinxnisi/graph-knowledge/issues/78) の入力を接続済みChatGPT Webで再実行すると、`read_theme_work_guide({phase:"production",management:true})` は `{}` と報告された。同時刻のβログではツールの認証と `RETURNED`、HTTP 200が記録された。同じβ DBに対しサーバーのMCPハンドラを通すと、JSON-RPC結果に版・本文・履歴を含む非空のテキストがあった。旧管理用のテキストは制作38,285バイト、見直し39,247バイトで、制作の画像フォーカス併用時は48,159バイトだった。認証やDB取得の失敗は今回の再現に現れず、サーバーからChatGPT側へ結果を渡す境界で再現した。クライアントの内部制限や空応答を生成した箇所の詳細は確認できていない。

### 管理用取得の契約

- `management:true` の初回応答には `versions`、`content.required`、順序付きの `content.sections`、補助ルールと画面要件、`history` を含める。MCPの `structuredContent` と既存テキスト形式の両方で返す。通常の作業別取得では従来どおり必要な専門手順・技術スキーマ・必須本文を返す。
- 本文がその場に含まれず `bodyKey` がある項目は、同じツールに `management:true`、一覧の正確な `versions.revision`、`managementBody:{key,offset:0}` を指定する。次の位置は `body.nextOffset` で受け取り、nullになるまで `body.text` を順に連結する。補助ルールは連結後にJSONとして読み取る。旧全文モードでは `legacyBodyKey` に従える。履歴は `nextHistoryBefore` で続ける。改訂の入力には復元した完全な編集構造と最新の期待版を使う。
- β Appの入力定義に `managementBody` が無ければ、ChatGPT Webの設定で「Plunode資料収集 API（β）」の「ツールを更新」を実行する。ガイド改訂・復元の運用試験は管理読取の確認後に別途行う。

修正後のβ DB／MCPハンドラで制作の管理用テキストは9,733バイト、見直しは10,063バイト。作業別の画像＋登録は従来と同じ15,087バイトだった。revision 9の「独立見直し・公開確認」10,298バイトを2ページから再構成できた。revision 6の旧全文は管理の本文ページから再取得し、旧APIのMarkdownと完全一致した。`historyBefore:8` では7〜1版を返した。

β Web build `QxQxq_0J_KQh_6LMoCO54` を配備し、3200とHTTPS βの公開datasetは200。OAuthメタデータも200。制作・公開・MCP回帰58件と、配備ビルドのTypeScript検査が成功した。既存の非公開Webb検証案件は状態版13、review、`needs-changes`、leaseなし、公開版なしを認証済みβ Appから読み戻した。

ChatGPT Webの再現に使った同じチャットで、同一入力から版 `9 / 7 / 7`、必須本文、5節、履歴9件を実データとして読めた。さらに見直しの版指定と `historyBefore:8` が成功した。β Appの「ツールを更新」後も既存のチャットには新引数が現れなかった。新しい通常Chatでは `managementBody` が利用可能となり、revision 9の「独立見直し・公開確認」を2ページ取得し、最後の `nextOffset:null` を確認した。βのログでも該当呼び出しの認証・正常応答を照合した。新しい引数を使う場合は、ツール更新後に新しいチャットを開始する。今回のWeb検証は読み取りのみで、品質ガイドの改訂・復元は別途実施する。
