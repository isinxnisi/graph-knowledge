## ChatGPT Webでの実施手順

1. 対象のペアは下記のA→B順で実行する。旧方式を先に行うペアと新方式を先に行うペアを交互にした。1件ごとに新しい通常Chatを使い、先に行った実行の結果や採点基準の答えは渡さない。両方式に同じモデル・推論設定、同程度の時間、検索・API・画面へのアクセスを与える。記録用にモデル・開始終了時刻、時間上限と外部待ちを残す。
2. **制作**。指定案件を `get_theme_production` で読み、新しい `executionId` と操作 `requestId` でproductionをclaimする。新方式は作業に応じて焦点を選んでガイドを読み、旧方式は共通ガイド全文を参照する。年表・根拠・日英・画像を見て、読者にとって重要な不足から修正する。関連する仕事は同じ起動中に進める。登録は必ずprepare→dispatchで行い、受付と `read_theme` で作業版に現れた変更まで確認する。
3. 評価用に、開始版から実際に反映した変更、根拠、解消済み・未解消と次の一手を保存する。正規の制作引継ぎ条件が揃えばhandoffする。まだ不足する場合は同じphaseでsave→releaseし、次回に継続する。比較のためだけにhandoff条件を緩めない。制作の一回目と、独立見直しへ渡せるまでの総回数を区別する。
4. **独立見直し**。handoff後に制作と別の通常Chat・新しい実行IDでreviewを開始する。制作の自己評価を先に読ませず、現行の年表を通読してから、根拠と資料、画像・日英・導線を比較する。認証済みPNGをPC・モバイルと利用可能な言語で実際に視認し、画像や見出しの修正が読者画面に反映したか確かめる。対象digest、ガイド版、使用した証拠を照合し、評価と残件を記録してreleaseする。公開操作は実施しない。
5. 条件の違う回や途中で不可抗力に止まった回をペアから明示的に分ける。重要な欠落の見落とし、同じ時間で実物に届いた改善、安全な再開を並べる。API回数、字数、出来事件数や取得ガイド量は原因調査用に残し、作品品質や仕事量の代用にしない。

制作に渡す共通指示の例。案件IDと方式だけを各回で差し替える。

> βだけを使い、指定の個別案件を制作してください。年表を読者の順で読み、重要な点から調査・編集し、同じ起動で進められる範囲を実際の作業版へ反映してください。開始版と反映版、読者に届いた改善、根拠、残件、外部待ちを短く保存してください。指定された方式のガイドを使い、既存の受付と実行権を守ってください。テーマ公開・新規画像生成・共通知識の編集はしません。

独立見直しに渡す共通指示の例。

> 指定のβ個別案件のreviewを、制作とは別の起動として実施してください。先に実物の年表から読者が理解できる変化を述べ、重大な欠落と画像の配置・表現の妥当性を独立に判断してください。根拠と日英・認証済み画面を確認し、取得と視認を分けて報告してください。修正した場合は反映版で全体を読み直してください。公開はしません。

## 記録の型

| 項目 | 1回ごとに残す内容 |
| --- | --- |
| 開始条件 | 匿名ラベル、題材・回、対象版とガイド版、モデル・推論設定、実行時間 |
| 作品品質 | 年表で伝わった変化、重大な不足の発見・見落とし、画像の説明と表示、根拠・日英 |
| 反映した仕事 | 変更箇所と確認した作業版、読者に届いた改善、必要だった次回作業 |
| 再開確認 | 受付ID・内容一致、再開前後の版、重複や上書きの有無 |
| 外部条件 | Web接続・受付待ち・資料アクセス・証拠視認の未確認、費用 |
| 評価 | 必須の不足と任意の改善を分けた判定。総合判断は両ラウンドと両題材の所見を比較する |

制作・見直しの担当者にこの資料の一番下の運営判定用メモを渡す必要はない。開始原稿・資料・案件のbriefから、まず本人に不足を見つけてもらう。APIの動作上、見直し側は案件の方式を識別できる。方式を伏せた品質判定を追加する場合は、原稿または画面証拠を匿名ラベルだけで提示する。
