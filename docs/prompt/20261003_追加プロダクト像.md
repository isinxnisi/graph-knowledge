■ このサービスの中心

このサービスの中心は、

「関係性をGraphで検索・探索して遊べること」

です。

将来、

- Entity詳細
- Claim / Relation詳細
- Source
- 議論スレッド
- 会員機能
- 保存ビュー
- 設定画面
- その他のコンテンツ

等が増えても、
Graph Explorerがこのサービスの主要な体験であることを
利用者が理解できる構成を維持したいです。

詳細やコミュニティ機能によって
Graph探索が奥へ追いやられることは避けたいです。

理想的には、

Graphで探索
→ 気になる関係を選ぶ
→ Claim・Source・異説・議論を深掘り
→ 別のEntityや関係へ進む
→ 必要ならGraphへ戻る

という流れを自然に行えることを重視します。

検索画面やGraph Explorerへの導線も、
サービスの中心機能として分かりやすく保ちたいです。


■ UI / UXを全体の設計原則として重視する

UI / UXは、機能完成後に見た目だけを整える工程ではなく、
各機能の初期設計から考慮したいです。

WebをSPAに固定する意図はありません。

ページ遷移、
クライアント側遷移、
部分更新、
サイドペイン、
モーダル等を含め、
その機能と利用体験に適した方法を選択してください。

特定のUI方式を先に固定するのではなく、
利用者が探索している文脈をなるべく失わず、
自然に次の情報へ移動できることを優先したいです。

例えば将来、機能追加の積み重ねによって、

- 何でもモーダルになる
- 長い同期処理で操作を止める
- 詳細を見るたびにGraphの探索状態を失う
- 戻った際にNode位置や探索文脈が失われる
- URLや戻る／進む等の挙動が不自然になる
- Graph上へ全情報・全操作を詰め込む
- Web画面固有のstateが探索モデルそのものになる

といった状態にはしたくありません。

機能ごとに最適なUIを判断してください。

また、将来的にはWebだけでなく
モバイル等のアプリとして提供する可能性も高いと考えています。

現時点でネイティブアプリ、PWA等の方式は決めません。

ただし、

- Claim
- Entity
- 探索条件
- 開閉状態
- 保存ビュー
- Relationの表示構造

等の中核概念が
特定のWebコンポーネントだけで成立する設計にはせず、
将来別クライアントでも利用できる境界を意識したいです。

この将来構想を理由に、
今からアプリ用機能や不要なAPIを先行実装する必要はありません。


■ Graphの表現と出力

探索して作ったGraphを、
将来的に外部へ出力できるようにしたいです。

例えば、

- 画像として出力
- シンプルなデザインのGraphとして出力
- 人物画像等を含むリッチなGraphとして出力
- 表示モードをシンプル／リッチ等で切り替える
- 可能であればdraw.io等、外部で再編集できる形式へ出力

といった利用を想定しています。

具体的な出力形式、ライブラリ、ファイル仕様はまだ決めません。

ただし、

Knowledge Graph上の意味
→ 探索結果
→ 表示対象
→ Relation集約
→ presentation
→ renderer / export

のように、
意味・探索状態・表示実装を必要以上に密結合させず、
将来別の表現やexport処理を追加できる構造を維持したいです。


■ Claim / Relationを中心としたコミュニティ

将来的には、
ClaimまたはRelationを単位として利用者が議論できるようにしたいです。

議論には、

- 参考になった
- 支持
- 不支持
- その他のリアクション

等を持つ可能性があります。

ただし、
支持／不支持の多数決によって
Claimの真偽を決定することは目的にしません。

コミュニティの反応は主として、

- 注目度
- 関心
- 議論の活発さ

等を表すものとして扱いたいです。

検索結果等へ利用する場合も慎重に扱い、

検索上の関連度
出典の存在
Claimの意味
コミュニティ上の人気・注目度

を混同しないようにしたいです。

例えば将来、

「注目されている関係」
「議論が活発なClaim」

のような別の探索軸を提供する可能性はありますが、
人気がそのまま事実性や検索関連度になる設計にはしません。


■ 異説・少数説・不確かな情報も探索対象にする

このサービスは、
関係性について一つの「正解」を決めること自体を目的にしません。

存在する、

- Claim
- Source
- 根拠
- 反証
- 異説
- 少数説
- 不確かな説
- 議論
- 人々の関心

を関係性として探索できることを価値としたいです。

例えば歴史上、

「AとBは同一人物だったという説」
「別人だったという説」

が併存する場合、
一方をシステムが勝手に真実として統合するのではなく、
それぞれのClaimと根拠を辿れる体験を目指します。

不確かな説や異説が存在すること自体も、
このサービスを探索する面白さになり得ると考えています。


■ コミュニティからKnowledge Graphが育つ

議論が単なるコメント欄で終わるのではなく、

議論
→ Sourceの提示
→ 補強資料
→ 反証
→ 新しいClaim
→ 新しい関係

のようにつながり、
コミュニティ活動によってKnowledge Graphそのものが育つ可能性を持たせたいです。

具体的な投稿フローや承認方式はまだ決めません。


■ 情報の由来・provenance

将来的には、
Claim等について情報の由来を区別したくなる可能性があります。

例えば、

- Wikidata等の外部データ由来
- その他の外部import
- 運営が登録・確認した情報
- ユーザー投稿

等です。

将来的には、

「Wikidata由来の情報だけを見る」
「ユーザー投稿を含める」
「ユーザー投稿を除外する」

といった探索条件が必要になる可能性があります。

ただし現時点では、

どのprovenance区分を正式に持つか
どこまで検索条件へ使うか
品質や信頼性とどう関係付けるか

は未確定です。

重要なのは、

「Wikidata由来だから正しい」
「ユーザー投稿だから信用できない」

のように、
由来そのものを自動的な真偽・信頼度へ変換しないことです。

今の段階では、
将来provenanceを区別・表示・探索条件として利用することが
困難になるような保存構造にはしないことを意識してください。

■ 探索軸・プリセット

将来的には、

「何を見るか」

自体をシステム管理可能な探索軸として扱いたいです。

例えば、

- 広義の影響関係
- 直接的な影響関係
- 制作上の人的系譜
- 作品同士の影響
- 特定期間の関係

等です。

別predicateであっても、
ある探索軸では同じカテゴリとして扱い、
別の探索軸では区別する場合があります。

ただし、
元のClaimのpredicateを探索都合で別の意味へ潰さないでください。

正確な関係は正確なpredicateとして保持し、
探索側で必要なpredicate集合等へ解決する方向を想定しています。

現在検討済みの
predicate taxonomy、
探索条件、
システムプリセット、
保存ビュー
との責務分離を維持してください。

■ 「世界が変わったかもしれない瞬間」を残す

将来的に特に実現したい構想として、

議論や新しい資料が登場した当時のGraphや探索状態を、
後から参照できる可能性を持たせたいです。

例えば過去の議論を読み返した際に、

当時:
「この時点ではこういう関係として見えていた」

↓

議論・Source・Claim等が追加された

↓

現在:
「Graph上では別の関係も見えるようになっている」

という経緯を辿れる体験です。

これは単なるコメント履歴ではなく、

「この議論や資料によって、
世界の見え方が変わったかもしれない瞬間」

を観察できる、
このサービス独自の価値になり得ると考えています。

例えば、
評価の高い過去の議論から当時のGraph状態を開き、
現在のGraphと比較できるような体験も将来的には考えられます。

このため、

- Entity / Claim等の安定した識別
- Claim等の変更履歴
- 探索条件
- 保存ビュー
- Graph状態の保存

等について、
将来この構想を実現できなくする設計にはしないことを意識したいです。

ただし現時点で、

- イベントソーシング
- 完全な履歴DB
- Graphスナップショット
- 差分表示機能

等を先行実装する必要はありません。

■ このプロジェクトで重視する設計姿勢

将来構想が多いからといって、
全てを先回りして実装することはしません。

不要な抽象化、
汎用エンジン、
未使用の拡張ポイントを大量に作ることも避けたいです。

一方で、
かなり高い確率で必要になる機能が
基幹設計へ影響する場合は、

「必要になった時に考える」

だけで済ませず、
その関連機能を最初に作る段階で
将来追加を妨げない責務・境界を考慮したいです。

これまで、
後から必要になることがほぼ分かっていた要件を無視した結果、
後になって大きな破綻や妥協を強いられるケースがありました。

そのため、

将来必要になる可能性
×
後から変更するコスト

を見て、

今から守るべき境界なのか
関連機能の初回実装時に考えればよいのか
完全に必要になるまで後回しでよいのか

を判断する姿勢を重視します。
