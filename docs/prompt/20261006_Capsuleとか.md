## 1. Capsuleとは何か

将来的に、ユーザーがあるテーマ・事件・人物群・作品群・仮説などを、
一つの「関係図／文脈」としてまとめて名前を付け、保存・共有できる仕組みを考えています。

これを仮に `Capsule` と呼びます。

Capsuleは単なるSaved Viewではありません。

Saved Viewは、
- root
- 探索条件
- 展開状態
- layout
- pan / zoom

など「既存Global KGをどう見ていたか」を保存するもの。

一方Capsuleは、文脈自体を持つ公開・共有可能なコンテンツになり得ます。

Capsuleには例えば、

- Global Entity / Global Claimへの参照
- Capsule内だけのlocal Entity
- Capsule内だけのlocal assertion / relation
- 未確認情報
- 仮説
- annotation
- Source
- discussion
- 初期表示状態やlayout

などが混在してよいと考えています。

重要なのは、

「AさんとBさんが同じCapsuleにいる」
こと自体は
「AさんとBさんの間にGlobal Claimが存在する」
ことを意味しないことです。

Global KGを汚さずに、文脈上必要な人物・出来事・仮説等を表現できる場所でもあります。

---

## 2. CapsuleとGlobal KGの関係は一種類ではない

Capsuleには、作成目的の時点で複数の性格があり得ます。

例:

### A. Globalへの合流・マージを目的とするCapsule

調査中のEntity / Claim / Source等を整理し、
後に一部または全部をGlobal KGへ正式に受け入れることを目指す。

### B. Community / User Capsule

Global EntityやGlobal Claimを参照しつつ、
Capsule-localな人物・出来事・assertion等も含む。

このCapsule自体は公開可能で、
Global探索側から

- 話題のユーザーCapsule
- 関連するCommunity Capsule

などとして発見できてもよい。

ただし、Capsule内のlocal Entityやlocal assertionは、
Globalの通常の関係探索には自動的に混入させない。

つまり、

GlobalからCapsuleへナビゲーションできること

と

Capsuleの内容をGlobal KGへマージすること

は別概念です。

### C. UserLocal / private Capsule

個人用の調査、仮説、メモ、関係図等。
Globalへの合流を目的としない。

この分類自体を今固定する必要はありませんが、
「Capsule = Globalに入らないデータの隔離場所」
とは考えないでください。

---

## 3. 公開とGlobalへの受入は別

Capsuleはかなり自由に作成・共有できる方向を考えています。

例えばURLを知っている人が閲覧できる形で、
ユーザー作成Capsuleを公開することも想定しています。

一方、

「公開できる」
ことと
「Global KGの関係探索へ合流できる」
ことは別です。

Global KGへEntity / Claimを正式に受け入れる場合は、
より厳しいSource確認、Entity同定、意味正規化、Claim審査等を通す可能性があります。

悪意ある捏造、重大な人物情報、プライバシー性の高い内容等もあり得るため、
public CapsuleのmoderationとGlobal KGへのacceptanceは別レイヤーとして考える必要があります。

具体的なmoderation policyはまだ決めません。

## 4. Globalへの登録をすべてCapsule経由にするかは未決

将来的なUser Contributionとしては、

- Entity単体を追加したい
- Claim単体を追加したい
- Sourceを登録したい
- Capsule内の一部ClaimをGlobalへ昇格したい
- Capsule全体を調査単位として扱いたい

など複数の導線が考えられます。

ここで、

「Globalへの投稿をすべて一旦Capsuleとして扱う」

のが良いのか、

「Entity submission / Claim submission / Capsule」

を別概念として持つのが良いのかは未決です。

将来のUI/UX、審査フロー、AI処理、運用コストを見て判断したい部分です。

今の段階で一方へ固定しないでください。

## 5. User ContributionとAI

一般ユーザーへ、

- Predicate
- qualification
- Role
- scope
- period

等の内部semantic modelを直接理解させるのは難しい可能性があります。

一般向けには例えば、

「AはBだった」

というユーザー自身の主張と、
根拠となるSource URL等を入力してもらう。

その後AIが、

- Entity候補
- Predicate候補
- qualification / Role候補
- scope / period候補
- 原資料の表記
- 既存semantic vocabularyへの対応可否
- 既存Claimとの近似

等を構造化し、
人間には自然言語として確認してもらう方式が有力候補です。

ユーザーが何を主張したいのかまで完全にAIへ任せるのではなく、
主張そのものはユーザーが提示し、
AIは厳密なKG表現との間を翻訳する役割を想定しています。

一方で、研究者・専門家等のユーザーには、
Predicate / qualification / Source locator等まで直接扱えるAdvanced入力UIがあってもよいと考えています。

AIには、
「既存語彙へ正規化する」
だけでなく、

- 既存意味IDへ寄せない
- 未正規化の原語として保持する
- human reviewが必要

という判断も期待します。

## 6. User Contributionの非同期承認フロー案

これは単なるバックエンド実装案ではなく、
将来のContribution UXとして共有しておきたい構想です。

ユーザーが投稿した瞬間にGlobal KGへ反映するのではなく、

submission
→ Pending
→ queue
→ 低コストなvalidation / local処理
→ 必要なものだけLLM / JEV等
→ 必要ならhuman review
→ 結果保存
→ ユーザーへ通知

のような非同期フローを候補とします。

理由は、

- 全投稿を高価なAIで同期処理しない
- サーバー資源やAI利用料を抑える
- ユーザーを処理完了まで画面上で待たせない
- URLがあるだけの捏造や誤読を即Global公開しない
- semantic normalizationが難しいものをreviewへ回す
- AIで判断できないものを人間へエスカレーションする

ためです。

将来的な結果状態としては例えば、

- Globalへ受入
- ユーザー確認待ち
- review中
- 修正依頼
- Globalには不採用
- Capsule-localとしては保持可能

などがあり得ます。

名称・状態遷移・判定基準はまだ決めません。

この構想から、
将来UIには

- 処理中の投稿
- 要確認
- 審査結果
- 完了通知

等への導線が必要になる可能性があります。

## 7. provenanceと信頼性

system登録データとuser登録データ、
Global ClaimとCapsule-local assertion等は、
内部的にもUI上でも区別できる余地を残したいです。

将来的には、

- 誰が登録したか
- system由来かuser由来か
- review済みか
- Global受入済みか
- Capsule-localか

等を追跡できることが重要になる可能性があります。

投稿回数制限、ポイント、信用、reviewer制度等の具体的なサービス設計はまだ決めません。

## 8. Capsuleの宣言的manifest案

Capsuleが形になってきたら、
docker-compose.ymlのような宣言的フォーマットとして

`capsule.yml`

のようなmanifestでimport / exportできる形も有力だと考えています。

これにより、

- 一般ユーザーUI
- AI生成
- Advanced userによる直接記述
- Git管理
- diff / review
- import / export

等が共通のインターフェースへ収束できる可能性があります。

例えば、

自然言語 + Source
→ AI
→ capsule manifest候補
→ schema validation
→ user確認 / review
→ import

という流れも考えられます。

AIが直接DBへ書き込むより、
人間にも読める宣言形式を一度境界に置く案です。

ただし、

- `capsule.yml` という名前
- YAMLを使うこと
- schema
- Global contributionにも同じmanifestを使うか

はまだ採用仕様ではありません。

また、

- ユーザーが宣言するコンテンツ
- server側のqueue / review / moderation / AI判定状態
- presentation / view state

を安易に一つのmanifestへ混在させない方がよいと考えています。

manifestとして自然に表現できるかどうかを、
Capsuleの責務境界を確認する材料として使う案でもあります。
