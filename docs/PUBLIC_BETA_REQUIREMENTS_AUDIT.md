4. テスト `phone-explorer.ts`：詳細を開くと別paneへ入り、Graphボタンで戻る動作を期待値にする。状態保持の回帰テストとしては有効だが、下段案・詳細優先の検討履行を証明しない。
5. 工程10の完了報告：touch／読書位置／復帰の成功を示す一方、欠けた比較を未完として残さない。

ユーザーが計画全体へ「進めて」と述べたことを、この省略への個別承認とは扱えない。以前のスマホタブ方式に既存の理由があることと、memo後もその方式が最適であることは別。過去の担当者の内心は推測せず、確認できるのはこの文書・コード・テスト間のずれである。

完了前に確認するのは四点。

1. 元のmemo／対話・採用計画と差分を照合し、明示された検討案が全て「採用／不採用理由あり／未評価」のいずれかになっているか。
2. 「動く」「テストが通る」と「依頼の目的を満たす」を別に説明できるか。見た目・使い勝手の主観が未確認なら、その範囲を正直に残しているか。
3. 必須部分が未対応、または約束した比較が未履行なら、工程全体を無条件に完了とせず部分対応として報告したか。未解決を後工程へ移すなら、元工程の残りにもリンクを残したか。
4. 進捗・main実装・日常確認先・VPS・外部設定の状態を分けたか。採用範囲外の未来機能を新しい完了条件に足していないか。

この確認はユーザーに毎回承認を求める手続きではない。可逆な実装判断は担当が行い、要求から外れる置換・重要な未充足だけを明示する。今回はこの提案をAGENTS／runnerへ無断追加しない。
