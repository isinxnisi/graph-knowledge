# 自動開発の現在の進め方

2026-10-08採用、2026-10-09に設計不足と優先順位の扱いを補強。自動実行時にrunnerがこのmain側文書を読み取り専用でpromptへ加える。自動側から変更しない。

目的は、関係を発見し、自分の関心に沿ってGraphを組み立て、根拠を確認し、必要なら保存・再訪・共有できる体験を育てること。現在の読み取り探索は成立しているが、将来像に必要な導線・機能も作りながら判断する。

- 各回、今前へ進める体験と今回触れるようにするものを短く決める。大きな計画書や「使いたいと証明する」関門を毎回設けない。
- 探索中の迷い・操作・根拠確認の改善と、保存・再訪・共有等の次の体験を候補にする。特定の機能順を固定せず、現行コード・構想と期待価値から選ぶ。
- 直近と同じ種類の微調整が続いたら、それが解消する具体的な障害を確認し、次の体験を触れる小さい実装／prototypeも比較する。見た目の改善だけへ限定しない。設計済み・簡単・45分で完了することを、優先順位の代わりにしない。
- 可逆なprototypeは、その体験を試せる範囲まででよい。会員制度・汎用基盤・公開運用を一度に完成させない。人間の実データ受入をAI確認で置き換えない。
- 調査はPROJECT_CONTEXT、docsの入口、関連する現行契約・コード・直近差分から始める。毎回全archiveを読む、同じ資料を再調査する、巨大な将来設計を書くことを避ける。
- AI関連に触れる場合は、main側の [AI処理・共通Kev方針](design/AI_PROCESSING_DIRECTION.md) を読み取り専用で参照する。Kev本体は他プロジェクトとの共有資産であり、自動開発から変更しない。接続情報の共有自体はAI連携実装の承認ではない。
- 検証は変更の責務・リスクへ合わせる。新しい導線は実画面で触り、state・API・意味に触れる場合は必要な回帰を確認する。局所変更で毎回全dataset・全テストを繰り返さない。
- スマホ向けの既存6行報告を維持する。「目的」で進めた体験、「残り」で次に繋がる不足を短く示す。完成度・面白さの立証を報告条件にしない。

## 設計が足りない重要機能の進め方

設計不足は、自分で解消する開発作業として扱う。既存構想に沿う可逆な設計・実装／prototypeは、専用設計書が未作成という理由だけで人間待ちにしない。現在有効な明示禁止は守り、過去フェーズの「今回は実装しない」を永久禁止として読み替えない。

- 完了した引き継ぎの「次の候補」は提案。次の仕事を選ぶ際は、直近機能の追加改善と、未実装の製品体験を2〜3候補で短く比較する。継続中でも、優先順位が変わる理由があれば切り替えてよい。比較理由は引き継ぎに1〜2行で足り、毎回新しい棚卸し文書は作らない。
- 選んだ機能に設計がなければ、利用者の操作経路、初回の対象／対象外、意味・保存・認可の境界、既存実装への影響、検証と段階分けを短い採用契約へ落とす。関連文書を更新し、必要なら一つの専用文書を作る。技術選択・可逆な仮定は自分で決め、理由を残す。
- 設計と実装は同じ機能の引き継ぎに載せる。重要な設計判断だけで一回を終えることは可能だが、決まった点と次に実装する単位を明記する。次回はその実装へ進み、追加調査は具体的な未解決事項が必要な場合に絞る。
- 人間判断が必要なら、その判断が止める範囲を限定する。資格・料金・公開範囲・実credential・実データ受入・不可逆操作等を勝手に確定しない一方、入力確認・権限設計・ローカルで触れる導線・検証用adapter等、依存せず進められる部分は作る。未設定の認証を本物に見せたり、機能しない登録画面だけで完成扱いにしない。

## 次の製品体験の初期候補

保存・再開は今回までで成立した。次は「自分の関心で関係図を組み立て、説明し、他人へ伝える」方向へ進む。以下は現コードを踏まえた初期優先案であり、順番の固定や全仕様の承認ではない。初回が完成した候補は実装済みとして再評価し、同じ候補の細部を磨くことを既定にしない。具体的な障害を直す必要があれば優先してよいが、保存入口の整理だけを次の到達点にしない。

| 候補 | 初回に触れる体験・設計する境界 |
| --- | --- |
| **最小Capsule（第一候補）** | 既存KGの対象・主張を明示的に選び、題名と自分の説明を添えた関係図を保存して再び読む。探索途中の保存とは別コンテンツとして設計する |
| 対象・根拠へ直接入る閲覧導線 | Entity／Claimを直接開けるURLから探索・出典へ進む。表示対象と探索途中復元を分け、戻る挙動・dataset・失効を設計する。検索エンジン向けページも候補に含めるが、公開・index許可は別に扱う |
| 会員保存・Capsuleの共有／議論 | ローカル保存では成立しない体験の必要性に応じて着手。所有者・サーバー認可・安定した参照先／版・訂正／削除を最初に設計する。登録画面、PostgreSQL、スレッドはその縦経路に必要なら候補にしてよい |

### 最小Capsuleのたたき台

[Capsule構想](design/CAPSULE_AND_USER_CONTRIBUTION_VISION.md)の境界を守る初回案。例えば「研究所を介して辿った人物」や「PLUTOに関わる人物と参考資料」を、自分の説明付きで読み返せるものを作る。

- 現在表示しているGraphから採用するEntity／Claim参照を選び、題名と全体メモを添える。保存後に対象・独立Claim・Sourceを読み直せるところを最初の縦経路にする。保存数の増加や単なる保存画面の名称変更をCapsule完成とはしない。
- 初回は既存KG参照と利用者の説明に限定してよい。参照のdataset／内部ID、内容の版、明示的な構成要素を持たせる。メモは説明であり、新しいClaim・根拠・Global受入へ自動変換しない。共に配置した対象から関係や同時在籍を推論しない。
- 初回の保存先はブラウザ内privateのprototypeで成立させられる。保存ビュー／途中保存と別形式・別領域にし、既存保存を自動移行しない。現在データへの再解決、参照失効・取得失敗・上限、途中保存の互換性を検証する。将来のサーバー正本を決定したことにはしない。
- 構成要素の所属は明示して保持する。現在の `projectGraph` は開いた枝の到達性から表示を導出するため、そのままCapsuleの内容・永続形式にしない。既存Graph renderer・詳細は再利用候補だが、通信状態と表示束IDを知識の永続参照にしない。
- local Entity／assertion、投稿・Global昇格、公開共有、会員同期、discussionは初回に必須ではない。次の段階で必要になれば自分で狭い契約を設計し、実装／prototypeを進める。外部公開・実credential・課金・人間受入の境界は維持する。
- 一件の作成 → 保存 → reload → 再閲覧 → 個別Claim／Source → Explorerへ戻る、を確認する。既存の開閉・条件・再開が壊れないことも確認する。説明付きの内容を保存できれば初回として区切り、機能の完全版や毎回の利用価値証明は要求しない。

45分は一回の実行上限であり、機能全体の規模制限ではない。価値ある機能は複数回で実装してよい。専用worktreeの `docs/AUTOPILOT_HANDOFF.md` に、状態・目標・実装済み範囲・検証済み／未検証・次の一手・重要な判断を通常25行以内で残し、実装と同じcommitへ含める。次回runnerがpromptへ加える。継続中なら現コードと方針に照らして続きを優先し、完了・保留・方針変更なら短く更新する。履歴を積み上げず一件を置き換える。

終了予定時刻と締め作業開始時刻をrunnerが渡す。作業の区切りで時刻を確認し、通常は最後の5分を検証・commit・メモへ使う。機能途中でも既存動作を維持した検証可能な単位へ区切り、必要なら独立route・feature flagを使う。段階の完了と機能の完成・人間受入を区別する。安全な区切りが作れなければ変更を保持し、dirty検査で停止する。メモや時刻指示は強制中断時の正常終了を保証しない。

利用量上限は作業の不備と区別する。CLIが上限を明示したら途中変更を保持して終了し、runnerが当日の残りをスキップする。人による受入が完了した場合は、手動側の完了手順で休止を解除して次の予定で再試行する。翌日または受入後の再試行許可は利用枠の回復保証ではなく、再び上限なら改めて当日休止する。dirtyが残れば人による整理が必要。モデル切替・有料API・追加購入で回避しない。
