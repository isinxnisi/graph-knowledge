# 自動開発の現在の進め方

2026-10-08採用。自動実行時にrunnerがこのmain側文書を読み取り専用でpromptへ加える。自動側から変更しない。

目的は、関係を発見し、自分の関心に沿ってGraphを組み立て、根拠を確認し、必要なら保存・再訪・共有できる体験を育てること。現在の読み取り探索は成立しているが、将来像に必要な導線・機能も作りながら判断する。

- 各回、今前へ進める体験と今回触れるようにするものを短く決める。大きな計画書や「使いたいと証明する」関門を毎回設けない。
- 探索中の迷い・操作・根拠確認の改善と、保存・再訪・共有等の次の体験を候補にする。特定の機能順を固定せず、現行コード・構想と期待価値から選ぶ。
- 直近と同じ種類の微調整が続いたら、それが解消する具体的な障害を確認し、次の体験を触れる小さい実装／prototypeも比較する。見た目の改善だけへ限定しない。
- 可逆なprototypeは、その体験を試せる範囲まででよい。会員制度・汎用基盤・公開運用を一度に完成させない。人間の実データ受入をAI確認で置き換えない。
- 調査はPROJECT_CONTEXT、docsの入口、関連する現行契約・コード・直近差分から始める。毎回全archiveを読む、同じ資料を再調査する、巨大な将来設計を書くことを避ける。
- 検証は変更の責務・リスクへ合わせる。新しい導線は実画面で触り、state・API・意味に触れる場合は必要な回帰を確認する。局所変更で毎回全dataset・全テストを繰り返さない。
- スマホ向けの既存6行報告を維持する。「目的」で進めた体験、「残り」で次に繋がる不足を短く示す。完成度・面白さの立証を報告条件にしない。

利用量上限は作業の不備と区別する。CLIが上限を明示したら途中変更を保持して終了し、runnerが当日の残りをスキップする。翌日の再試行許可は上限解除の保証ではない。dirtyが残れば人による整理が必要。モデル切替・有料API・追加購入で回避しない。
