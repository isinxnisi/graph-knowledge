# 自動開発の設計不足・優先順位の扱い

2026-10-09。ユーザーの「設計がないため重要な構築へ進めないなら、自動側に設計させるか先回りして追加したい」という指示を反映。[現在の進め方](../../AUTOPILOT_DIRECTION.md)が次回以降の正本。今回アプリ機能は実装していない。

## 確認と変更

既存kit policyは新機能・Capsule・Contribution・sharing/discussionの設計／prototypeを既に許容しており、設計がないため停止した実ログは確認していない。直近4実行は保存・再訪を段階的に拡張しており、それ自体は有用だった。ただし完了した引き継ぎの次候補が保存入口の整理で、未設計の製品体験との比較が弱かった。

main側のAUTOPILOT_DIRECTIONへ以下を追加した。

- 設計済み／簡単／45分で完成を優先順位の代わりにせず、未設計の重要機能も候補として比較する。
- 設計不足を作業として解消し、操作経路・保存／認可／意味境界・影響・検証を小さい契約へ落とす。設計から実装を同じ引き継ぎで継続する。
- 過去のフェーズ範囲と現在有効な禁止を区別し、人間判断待ちはその判断が必要な部分だけに限定する。公開・実credential・実課金・人間の資料受入を代行しない。
- 次の初期候補は最小Capsule、直接開く閲覧URL、会員保存・共有／議論。未着手の第一候補は既存KG参照＋題名＋説明を保存して読み返す最小Capsule。local知識・Global昇格・公開を初回の必須条件にしない。
- 完成済み候補は再評価し、設計や局所改善を繰り返し続けない。6行報告と通常25行以内の引き継ぎを維持する。

最小Capsuleの初期案は同じ方針文書に短く置いた。runnerが毎回main文書を注入するため、専用worktreeへ新しい設計ファイルを同期する仕組みや、巨大な全体計画を追加する必要はない。現在のprojectGraphは到達性から表示を導出するので、そのままCapsule内容の永続形式にしないというコード上の境界も示した。具体schemaとUI方式は自動側が関連構想と実装を確認して判断する。

## 検証

- `make autopilot-test`：20件成功。排他・受入・休止解除・dirty保持等の既存運用を確認。
- kitの `tests/test-handoff.py`：4件成功。連続する段階commitとメモ注入、期限、dirty停止を確認。
- 同じ隔離fixtureのmain方針を今回の全文で置き換え、fake CLIへ実際のrunnerが渡したpromptに全文・Capsule初期案・6行報告・複数回継続・外部操作制約が含まれることを確認。source文書と開始HEADは不変。実Codex・本番の自動開発は呼び出していない。
- 文書の相対リンク・`git diff --check`を確認。アプリコード・API・DB・dataset・稼働画面・kit policy／runner・Windows予定は変更しておらず、アプリ全テスト／buildは再実行していない。

指示の輸送は確認できたが、実際に次回がどの候補を選び、適切な設計と実装へ進むかは今後のcommitと報告で確認する。自律判断の品質を機械的に保証したものではない。
