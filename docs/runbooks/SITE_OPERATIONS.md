# 小さなサイト運営画面：初期運用

2026-10-25。beta用。正式公開は別承認。[契約](../design/SITE_OPERATIONS.md)。

## 入り方

本人が通常のGoogleログイン後、共通ヘッダーの盾アイコン（PCは「運営」）またはアカウントメニューの **サイト運営** から `/operations` を開く。サイト運営入口は、サーバーで明示許可された本人だけに表示する。一般会員／コミュニティ管理者には運営権限を与えない。

## 通報の確認から対応まで

1. 運営受信箱の未対応を確認する。ページ末尾の「次」で続きへ進める。先頭ページを総件数とは扱わない。
2. 「確認・対応」を開き、対象種別・期限・版・状態を確認する。
3. 必要な場合だけ「対象を確認」。確認目的を監査理由へ入力し確定する。この通報の対象と通報理由だけを表示する。内容を確認できない場合は権限／期限／版の失効として扱い、別の私的情報を探して代用しない。
4. 根拠を踏まえ、必要な処置を選び、対象と影響・理由を確認して確定する。通報は真偽の認定ではなく、対応終了と非表示／停止は別操作。
5. 結果と履歴を確認し一覧へ戻る。通信結果が不明なら画面に残り、**同じ操作の結果を再確認**を使う。新しい内容で繰り返さない。

監査理由に投稿本文・秘密・認証情報を転記しない。実利用者への処置は運営者の判断で行う。検証は許可された検証対象だけを使用する。

## アカウント／復帰

- アカウント対応で対象IDを入力し、状態・履歴を確認する。停止／再開の影響を読んで理由付きで確定する。再開しても旧セッション・共有・参加権限は戻らない。Web実行中の本人停止は緊急CLIから扱う。
- 復帰申請は期限・状態・再受入要否を確認する。承認／却下後、本人が就任承諾し、場所を別途再開する。運営者が管理者権限やCapsule所有権を自動取得しない。
- 操作履歴は対象IDで絞れる。Webと既存CLIの記録を区別する。実行者ID、理由、日時、対象を記録し、通報本文をログへコピーしない。

## betaの設定・追加migration

秘密値は出力・Git保存しない。接続先はbeta `127.0.0.1:55433/graph_member`、コンテナ `graph-knowledge-member-beta-postgres-1`、volume `graph-knowledge-member-beta_member-data`。本番の `graph-member-postgres`／`graph-knowledge-production_member_data` とは別。

保護された `.env.public`（0600）へ次を設定する。

```dotenv
SITE_OPERATIONS_ENABLED=1
SITE_OPERATOR_USER_IDS=<確認済み本人UUID。複数はカンマ区切り>
```

本人IDはログイン済みの「届いた招待」の「招待用アカウントID」で本人に確認する。表示名から推測しない。許可解除はUUIDをリストから削除しWebだけ再起動する。全停止は `SITE_OPERATIONS_ENABLED=0`。複数Webがある場合は全てに反映する。機能停止で追加table・投稿・監査を削除しない。

008適用前に、専用0700ディレクトリへbeta PGのcustom dumpを0600で保存し、別DBへの復元と008適用・再実行を検証する。Webは旧schemaでも継続可能な追加tableだけ。適用は、明示的に設定ファイルを読む安全なローカル実行環境で以下を実行する。接続文字列はコマンドライン引数やログへ出さない。

```sh
node --env-file=.env.public --import tsx scripts/member-migrate.ts --site-operations --confirm-origin https://graph-beta.isinxnisi.com
```

その後、検証済みWebをbuildし、既存の3200起動方法でWebだけ切り替える。許可本人200、未認証401、非運営者403、feature off時404、buildとHTTP応答を確認する。flag/許可リストはserver-onlyでありNEXT_PUBLICへ置かない。

## 切り戻しと緊急経路

まず `SITE_OPERATIONS_ENABLED=0` でWebだけ再起動し、管理API/pageが404となることを確認する。必要なら直前の検証済みWebへ戻す。008は追加tableなので旧Webを妨げないが、コミュニティ失効処理を持たない本番旧版まで戻す判断とは別。新しい監査・投稿を失うDB復元／DROP TABLEを切り戻しの標準手順にしない。

既存 `community-safety`、`community-recovery`、`member-ops` CLIは継続する。Webから任意CLIやSQLを実行するAPIは作らない。緊急時の実行方法は既存コミュニティ公開手順を参照。運営CLIとWebの並行操作も期待版・lockで競合を検出する。

## 対応待ちの確認

ヘッダーの数は未読ではなく、未対応通報＋現在判断できる復帰申請。既存の30秒確認・画面復帰・処置後に共有集計を更新する。「…」は未取得、「!」は確認失敗であり0件ではない。受信箱の内訳から未対応通報・復帰申請へ移れる。期限間近は24時間以内、確認期限終了の通報も対応を終了するまでは未対応に含む。件数表示だけでは内容を開かず、内容確認は従来どおり理由付きの明示操作。

投稿の内容確認が許可された場合は、投稿者アカウントID（通報者IDではない）をコピー、またはアカウント状態確認へ進める。退会等でIDがない場合は取得できない状態を表示する。アカウント停止は別の理由・期待状態・確認を経て確定し、IDを開いただけでは処置しない。
