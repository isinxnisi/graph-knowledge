# 公開して育てるための対応プラン

2026-10-11。main `8696385`、ユーザーの `memo.txt` と直近の対話を基にした計画。同日のユーザー指示で採用し、実装へ着手した。[全24ステップの進捗](../PUBLIC_BETA_PROGRESS.md)を現在の作業範囲・完了数の正本とする。未完了の公開範囲を実装済みと扱わず、実credential設定・広告配信等は具体的な設定時に確認する。

目的と現行仕様は [PROJECT_CONTEXT](../PROJECT_CONTEXT.md)／[ARCHITECTURE](../ARCHITECTURE.md)、製品構想は [プロダクト像](PRODUCT_VISION_AND_PRINCIPLES.md)／[Capsule・User Contribution](CAPSULE_AND_USER_CONTRIBUTION_VISION.md) を正本とする。個別設計をここで再定義しない。memo原文は編集・コミットせず、SSH接続先や広告タグも転載しない。

## 1. 方針の評価

memoは、検証画面を「公開し、利用しながら変えていけるサービス」へ移すための要求として妥当。デザイン、スマホ、アカウント、英語、広告、計測は周辺の飾りではなく、入口・継続利用・運営を成立させる要素である。基盤や意味モデルの精密化だけを先に続けない。

「小さく公開する」は、公開する機能・変更単位を絞る意味とする。データを少数に固定する意味にはしない。数千Entity／Claimを扱い、見つかった問題を直して反映できる状態を目指す。両者の件数とSource／Citation件数は分けて記録し、Graphの表示上限100 Entity／200 Claimとは区別する。件数達成のためだけの弱い関係追加は行わない。

公開判断を「面白いと証明できた」「精度が十分高くなった」という無期限の関門にしない。探索・根拠閲覧・更新・復旧が実際に機能し、公開する機能のアクセス境界が守られていれば、限定的なβ公開から改善してよい。新しいデータがつながらない箇所を、推測した関係で埋めることはしない。

## 3. 精度を何のために優先するか

| 分類 | 今の優先度 | 判断例 |
| --- | --- | --- |
| 同一性・保存・認可の正しさ | 必須 | 別人への誤結合、再投入でID再発行、他人の内容の表示、保存物消失、限定リンク漏洩を防ぐ |
| Claimとしての意味保持 | 必須 | subject／object、肯否、限定、原語、Source／Citation、受入範囲を落とさない。招待から参加等を作らない |
| 公開データの根拠・利用範囲 | 必須 | 根拠のない断定や架空demoの混入を避ける。既存の受入判断は再利用し、AI確認で人間受入を代用しない |
| 基本的な操作成立 | 必須 | 起点を検索できる、線から根拠へ進める、スマホで操作できる、失敗から再試行できる |
| 性能 | 問題に応じて対応 | 実データ量・高次数Nodeで操作が待ち続けるなら先に直す。架空の将来負荷のための分散化は行わない |
| 検索関連度・網羅性 | 原則、公開後も改善可能 | 曖昧検索、推薦、順位最適化、網羅的なRole付与を公開前の条件にしない。既知名・別名から辿れない問題は基本操作の不具合として対応 |
| 表現の完成度 | 基本の読みやすさは優先、細部は後 | 白紙・読めない・操作場所不明は直す。全配置の最適化、全ラベルの自然さ、全画面の演出完成は待たない |
| AIの判定精度 | 現時点で公開の依存にしない | Kevの用途別検証は、候補整理へ実際に導入するときに実施。汎用スコアの改善を製品開発の中心にしない |

不確かな資料の内容が併存することと、誤読・誤結合・誤変換は別。前者は出典と範囲を示して扱えるが、後者を「精度改善は後でよい」で放置しない。完全な真偽判定、全件再審査、Source信頼度ランキングを公開条件に追加しない。

新しい資料群を大量に取り込む際は、資料・property・変換規則・限定保持・例外隔離を収集単位でレビューする方式も検討する。現行の人間受入契約を自動解除せず、件数に応じた受入方法をその収集フェーズで決める。過去の凍結版を毎回最初から審査し直す必要はない。

### アカウントメニューの初期案

既存機能の整理を優先し、探索へ戻れる共通の入口を作る。

- 未ログイン：登録／ログイン。匿名探索とブラウザ内保存は継続。
- ログイン後：自分のCapsule、共有リンクの管理、自分の投稿、設定、ログアウト。
- 設定：表示名、表示言語、外観、全端末ログアウト、退会／削除の案内。外観の端末設定とUser設定の同期範囲を実装前に決める。
- ブラウザ保存・探索途中保存：会員保存と所在を分け、ログインだけではアップロードしない。未実装の会員同期をメニューで約束しない。
- 将来の投稿候補・審査状況・通知・課金：配置先の考え方は残すが、機能がない間は空メニューを並べない。提供に必要になった時に追加する。

運営操作はこの一般メニューへ混ぜない。現状、本人撤回や所有者の会話停止だけでは運営非表示を代用できない。公開する会話機能に対応する停止・削除・問い合わせ経路を小さく決める。運営画面全体が未完成なら、公開する書込機能を限定し、探索まで停止させない。

## 5. 推奨する実施順序

一直線に基盤を完成させてからUIへ進む計画にはしない。下記AとBを並行できる単位に分け、Cで実環境へ接続する。順序は推奨であり、未実装の全項目を一括着手する指定ではない。

| 段階 | 達成すること・主な作業 | 区切りと次の一手 |
| --- | --- | --- |
| **A：更新できる共通KGと本番起動の土台** | 漫画v2＋Event（科学v2を含む）の受入済み内容から公開用データを作る。新しい安定dataset領域、ID対応、生成・検証・差分適用・復旧、本番build起動を整える | 既存pilotを変更せず、一つのWebで漫画・科学・Eventを検索・探索できる。同じ入力の再適用は無変更、追加・訂正・撤回と参照維持を実DBで確認 |
| **B：公開する画面の体験** | デザインルール・ヘッダ／アカウント入口、スマホのGraph／詳細／隣接一覧、読み取り・会員画面間の戻り方を整える。広告枠の場所も仮配置で確認 | PC／スマホの代表経路が自然に使え、探索状態が失われない。大量データや実Googleの準備を待たず、既存データで進められる |
| **C：VPS上のβ公開** | memoのVPSの既存サービス・RAM／diskを調査し、domain確定、単一Web＋Neo4j＋必要ならPG、HTTPS、起動復帰、更新・backup／restoreを実環境で確認 | 外部のPC／スマホから検索→Graph→根拠が使え、コード／データを更新・復旧できる。匿名探索だけでも先に区切れる |
| **D：会員機能を公開可能にする** | A/Bと並行して実Google、設定、会員保存と共有の往復、本人の削除・問い合わせ、公開書込に必要な運営操作を仕上げる | 登録→保存→別ブラウザ再訪→共有→失効／削除が実認証で成立。準備済みならCへ同梱し、credential待ちで匿名β全体を止めない |
| **E：データ拡充・英語・計測・広告** | データはAの更新経路へ段階追加。英語UIはBから並行して進める。最小計測はCに合わせ、広告実配信はC後の短い単位で接続 | 数千規模でも問題箇所を測定・修正して更新可能。英語主要経路、集計画面、広告枠の有無によるGraph／スマホの使いやすさを確認 |

EはすべてをC後まで待つ意味ではない。先にできる翻訳、収集、広告枠の検証を進め、実データ更新先・公開origin等への依存だけ待つ。匿名βを唯一の最終目標にせず、会員・共有・英語・収益化へ続く計画を維持する。

### Aで先送りしない最小契約

1. **安定した参照領域**：公開用datasetのIDは更新版ごとに変えない。投入release／manifestの版を別管理し、Capsule・URLの参照先を維持する。旧pilot参照は旧領域のままで、暗黙に公開用へ付け替えない。
2. **ID対応と重複**：既存内部IDを可能な限り維持。Eventに複製済みの科学データを二重投入しない。同ID・異内容や外部ID衝突は検出し、人が対応を確認する。同名や同一SPOだけではEntity／Claimを統合しない。
3. **更新単位**：生成元の管理範囲と入力版、変換版、変更前後を記録する。新規・訂正・撤回を明示したmanifestとdry-runを作り、入力にないという理由だけで一括削除しない。機械検証と資料の受入は別。
4. **訂正の意味**：表記・書誌の訂正と、subject／object／predicate／肯否／限定が変わる主張の差替えを分ける。後者を同じClaim IDへ黙って上書きしない。既存参照には撤回・置換を確認できる最小記録を残す。Entity統合の一般解は不要。
5. **再実行・失敗**：初期は排他した一括適用とDB transactionでよい。入力検証後に適用し、同releaseの再実行は無変更とする。Web公開中の適用／短時間のメンテナンス、cursorの失効・再取得方法は採用契約で決める。途中失敗やデータ更新で新旧ページを黙って混在させない。
6. **復旧と所有データ**：KG更新と会員PG migrationを分ける。参照不明は不明として示し、ユーザーのCapsule・コメントを巻き戻してKGを合わせない。KGの版と復旧可能なbackup、適用結果を残す。完全な過去Graph再現基盤は不要。

検証用の凍結seedは維持し、公開用の更新処理を別入口で作る。既存ポートguardを削除したり、DB全走査で「fixture以外は異常」とする契約をそのまま本番更新へ流用したりしない。

### データ拡充と公開構成

- データ量の上限を少人数に固定しない。まず既存受入データで更新経路を通し、その後、扱えるpredicateと資料群を限定した実在データを段階投入する。
- Entity数・Claim数・Source／Citation数・高次数Entityを別々に記録。検索、neighbors、overview、Claim詳細を数千規模で実測する。合成データは性能試験に使っても実在資料として公開しない。
- 新しいPredicate／限定を増やすことを件数増加の前提にしない。既存契約で表せない情報は元資料へ残し、保留する。モデル追加は必要な具体例が出た時にレビューする。
- 本番の論理構成は `HTTPS → reverse proxy → Next.js → Neo4j／PostgreSQL` を初期案とする。DBをブラウザへ公開しない。会員未公開ならPGの稼働はその機能に合わせる。安価なVPS一台での同居可否は実容量と測定で判断する。
- 六つの検証Webを本番へ移さない。通常は一つの製品入口、別に必要時の回帰・比較環境を使う。公開用Graphでも分野をまたぐ関係は資料に明示される場合だけ登録する。

## 6. 多言語・広告・計測を後付けで壊さないための境界

多言語は既存の必須設計前提を維持する。UI localeをラベル関数まで渡し、英語辞書を用意する。locale変更で起点・条件・cursor・枝・座標を変えない。現Entityの単一name／aliasesは別の制約であり、UI英訳のために人名やSource原文を自動翻訳して上書きしない。台帳に保持済みの原語・言語情報を捨てず、名称の言語別モデルは公開データ更新の初回設計で保持方法と将来移行を確認する。完全な名称モデルが不要でも、英語表示で日本語名へfallbackする状態は正直に扱う。

広告はPCの300×250／728×90／160×600、スマホの320×50／320×100／300×250というmemoの候補寸法を設計材料にする。実タグなしの枠で可読性・Graph面積・スクロールを先に確認し、初回は一枠・非固定から始める。広告未配信時に大きい空白だけが残る構成や、広告到着でGraph座標・選択が飛ぶ構成は避ける。配信条件とCSP等は接続時に確認する。[AdMax公式](https://www.ninja.co.jp/admax/)は候補の確認元であり、適用可否や配信実績を今回確認したわけではない。

GA4は公開探索の利用把握に限定した初期候補。検索実行、探索開始、Node展開、関係詳細、根拠リンク等の少数イベントから始め、本文・検索語そのもの・会員識別情報・限定リンクを送らない。GA4の通常page_viewはページ読込／履歴変更に対応し、URLが既定のpage_locationとなるため、SPAでの二重計測・送信範囲を明示的に設定する。[公式ページビュー仕様](https://developers.google.com/analytics/devguides/collection/ga4/views?hl=ja)（2026-10-11確認）。

`SharedCapsule.tsx` は共有tokenをURL fragmentから読み、headerでAPIへ送っている。GA4標準page_viewの既定URLはfragmentを除外するが、同一ページで動く第三者scriptからfragmentが読めないわけではない。したがって初回は会員・認証・限定共有ページへ広告／analytics scriptを置かず、公開Explorerだけに範囲を限定する。`noindex`や`no-referrer`をscriptへのアクセス制御と誤解しない。実配信・計測前に説明・必要な同意の扱いを提供地域と利用設定に合わせて確認する。独自analytics基盤や全画面のタグ導入は不要。

## 7. 後回しにするものと、再評価する条件

- 検索順位の高度化・推薦・AIの高精度化：具体的な検索失敗や対象タスクが出たら対応。公開・更新経路の前提にしない。
- 新ontology／全分野taxonomy／万能qualification：現データで表現できない意味が継続的に出た時に、既存レビュー手順で検討。
- 完全な履歴Graph・無停止大規模更新・自動Entity統合：初期の排他・版記録・明示対応で足りなくなった時。
- 一般ユーザーのGlobal KG投稿・自動受入：今回は既存の会員Capsule・共有と分ける。Source支持・同定・受入を省略して件数を増やす手段にしない。
- 大規模管理画面・権限エンジン・多provider・課金：実際に公開する操作から必要になった範囲だけ追加。
- 検索エンジン向けページ：外部閲覧とindex許可は別。公開データの訂正経路・URLと露出範囲を確認後に着手し、会員／限定共有は引き続き対象外。

## 8. 次の一単位と、必要な利用者判断

**次の実装単位はA「更新可能な公開用KGの初回」を推奨する。** 新しい大量収集やUI全面刷新まで含めず、既存受入済みの漫画v2＋Eventを新しい一つのデータ領域へ構成し、追加・訂正・撤回・再適用・参照維持・復旧をローカル実DBで通す。これができれば、凍結検証版を増やすことから離れ、データを増やしながら直せる。並行できるBの最初の単位は、共通ヘッダ／アカウント入口とスマホ詳細配置の実画面比較とする。

実装前の短い契約で、公開用dataset識別子、Claim差替えと旧参照の扱い、データ更新時のcursor、初期rollback範囲を決める。全更新方式の一般解は作らない。コード変更ごとに責務に合うunit／実DB／代表E2E、必要なtypecheck／lint／buildを行い、設計書だけを毎回増やして止まらない。

利用者判断が必要なのは公開サブドメイン、実Google設定、広告／計測アカウントと適用範囲、初回公開に会員・会話を含めるか。現時点ではこの回答を待つためにローカル実装全体を止める必要はない。実公開・外部設定の操作前には対象を具体化して確認する。
