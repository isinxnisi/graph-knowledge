# 成熟したサービスのプロダクト像と設計原則

2026-10-03。構想と設計原則の保存。直近の実装要件・着手順・API契約を追加する文書ではない。多言語対応は採用済みの設計前提。将来機能は実現意向が強い方向と未確定の事業候補を区別し、具体方式は関連機能の設計時に決める。

目的の基準は [PROJECT_CONTEXT.md](../PROJECT_CONTEXT.md)、現行仕様は [ARCHITECTURE.md](../ARCHITECTURE.md)。今回の依頼原文は [追加プロダクト像](../prompt/20261003_追加プロダクト像.md)。探索、操作、プリセットの詳細は既存設計を維持する。

## 1. プロダクトとしての目標

中心は「関係性をGraphで検索・探索して遊べること」。資料を調べる価値と、自分の関心に沿って関係を絵として組み立てる楽しさを両立する。Entity一覧や議論ページが増えても、Graph Explorerと検索への導線を主要な体験として保つ。

Graphで探索 → 関係を選ぶ → Claim・Source・異説・議論を深掘り → 別のEntityや関係へ進む → 必要ならGraphへ戻る、という往復を自然にする。深掘りに全情報をGraphへ詰め込む必要はない。

一つの正解を決めること自体を目的とせず、根拠・反証・異説・少数説・不確かな説をそれぞれ辿れることに価値を置く。「AとBは同一人物という説」も、その説を主張するClaimであって、Entityを統合する指示ではない。対象の同一性の管理と、同一人物説の内容を分ける。

UI/UXは各機能の初期設計から考える。SPA、ページ遷移、部分更新、ペイン、モーダルのどれかを一律に採用せず、探索文脈、応答性、URL、戻る／進む、フォーカスの自然さで選ぶ。長い処理で全操作を止めたり、詳細を見るたびに位置や枝を失ったりする構成を避ける。

## 2. 実現意向の強い将来機能

次は成熟したサービスで実現したい方向。提供時期・最小仕様・実装方式は未決定であり、現在の実装済み機能とは区別する。

| 方向 | 目指す体験 | 維持する境界 |
| --- | --- | --- |
| 探索軸とプリセット | 影響、人的系譜、作品、期間、由来などから「何を見るか」を選ぶ | 正確なpredicateを保存し、探索側で集合に解決。taxonomy・条件・プリセット・保存ビューを分ける |
| 保存と共有 | 組み立てた探索や条件を再利用し、人に伝える | 条件ビューと途中のワークスペースは別。公式更新に保存条件を黙って追従させない |
| Graph表現と出力 | 画像、シンプル／リッチな表現、可能なら外部再編集形式 | 意味と表示を分け、rendererとexportを追加可能にする。draw.io等の具体形式は未選定 |
| Claim / Relation単位の議論 | 関係の根拠や異説を深掘りし、Source提示から新Claimへ繋ぐ | コメント、リアクション、知識への登録・審査を分ける。人気で真偽を決めない |
| 情報の由来による探索 | 外部import、運営、ユーザー投稿等を区別して見る | 登録・取得の由来と、主張の根拠であるSourceを分ける。由来を信頼度へ自動変換しない |
| 過去と現在の見え方 | 議論・新資料の登場時のGraphを開き、現在との違いを辿る | 当時の知識内容と当時の探索状態を分ける。保存条件だけで過去を再現したとしない |
| Web以外のクライアント | 将来モバイル等でも探索できる | 中核概念をWebコンポーネントだけに閉じ込めない。ネイティブ／PWA等は未選定 |

多言語は任意の将来機能ではなく、これらすべての設計前提。現状の日本語実装を入口として段階導入する。対応言語、翻訳運用、Entity名称・別名のモデル移行時期は未決定。

## 3. 未確定のサービス・事業上の選択肢

会員限定保存、投稿、調査・情報追加リクエスト、有料会員機能、共有範囲、広告、アフィリエイトは検討対象。保存や共有への実現意向と、会員資格・課金方式を採用したかどうかを混同しない。

これらの提供資格・料金・件数制限はサービス／アプリケーション層で扱い、Claimの意味やpredicateへ埋め込まない。調査リクエストや支払いから、関係が成立するClaimを直接生成しない。運営・課金・広告の具体方式は必要になるまで選ばない。

## 4. 現在から守るべき設計上の性質

- **独立した知識**：Entity / Claim / Citation / Source、期間、肯否、方向を保つ。表示Relationへの集約は保存Claimの統合ではない。
- **評価の分離**：検索関連度、根拠の存在、Claimの内容、コミュニティの関心・人気は別の尺度。支持／不支持リアクションはClaim.polarityやCitation.stanceとは別。
- **探索と表現の分離**：取得条件・受理範囲・開閉意図・表示対象・Relation集約・ラベル／配置・rendererを区別する。ReactやCytoscapeの状態を探索モデルの唯一の定義にしない。
- **探索文脈の維持**：詳細への移動、テーマ・言語変更だけで枝や座標を捨てない。URLで指定する対象と、探索途中の状態を同一視しない。
- **言語から独立した意味**：安定IDと意味を表示文字列から切り離す。知識データの多言語名称、原資料の言語、UI翻訳は別の責務。
- **由来を失わせない**：取り込み時に元識別子・取得時点・変換規則等を扱う余地を保つ。QIDの存在だけをClaimの取込由来や出典の代わりにしない。
- **履歴への余地**：安定した識別を維持し、公開投稿の更新・削除を設計する時には過去参照の必要性も評価する。現在のupdatedAtだけで過去内容を再現できると想定しない。
- **運営と知識の責務**：議論・権限・審査等は運営データ、知識GraphはNeo4jの正本。非表示やロックを真偽判定と扱わない。
- **段階的な実装**：将来必要になる可能性と変更コストで判断する。境界を守ることと、未使用の汎用エンジン・拡張機構を先に作ることを分ける。

処理の考え方は「知識の意味 → 条件付き取得 → セッションと受理範囲 → 表示対象 → Relation集約 → presentation → renderer / export」。一つの共通表示中間形式を今すぐ実装する指定ではない。時系列やexportに必要な粒度は異なるため、各表現が独立Claimへ戻れるようにする。

## 5. 関連機能の初回実装時に先送りしない判断

| 着手する機能 | 最初に決めること | 先送りした場合の影響 |
| --- | --- | --- |
| 投稿・編集・実データimport | Claim同値性と更新、元statementと版、由来の粒度・複数由来、変換規則、訂正・統合時の参照、履歴保持の範囲 | 根拠・由来・過去版を失うと後から復元できない |
| 議論 | Claimの参照対象版、Relationへの永続参照、対象削除・統合時の扱い、提示資料を登録・審査へ渡す流れ | 現在の表示Relation IDは永続IDではなく、投稿先として無条件に利用できない |
| リアクション・注目軸 | リアクションの意味、集計と不正対策、露出と関連度の区別、サーバー認可 | 注目度が真偽・通常検索順位へ暗黙に混ざる |
| 条件付き探索・プリセット | predicate集合、LIMIT前評価、条件キーとcursor、不明値、由来条件、全Claim詳細との範囲差 | 後付けの表示非表示だけでは対象を十分取得できない |
| 保存ビュー・ワークスペース・共有 | 条件／途中状態の区分、schema版、共有認可、現在データへの再解決、URLと復帰の契約 | 期限付きcursorやUI内部stateを永続化すると再開が不安定になる |
| ページ・モーダル・別画面 | 文脈を保持する寿命、直リンク、戻る／進む、選択・座標復帰、非同期処理とフォーカス | UI方式の積み重ねで探索が失われる |
| export・別renderer | 表示対象と部分取得の明示、独立Claim・出典参照、位置／ラベルの受渡し、形式の制約、画像の利用条件 | Graph画像だけでは根拠や編集可能な意味構造が残らない |
| 多言語の実装拡充 | locale解決・フォールバック、名称／別名検索、原資料言語、翻訳と意味の版の区別 | 名前や翻訳文が識別子になり、言語変更で探索の同一性が壊れる |
| 過去Graphの参照 | 再現する範囲、知識の版／基準時点、探索条件・受理範囲・表現の版、当時と現在の閲覧制限 | 保存したIDを現在DBで解決するだけでは当時のGraphにならない |
| 公開投稿・議論の運営 | 表示、検索露出、投稿、リアクション、議論の各制御、サーバーでの権限検証、訂正・削除・公開範囲 | 現在のpublished / hiddenだけでは別々のロックを表せない |

過去再現への意向は、履歴機能の着手まで何も考えなくてよいという意味ではない。書き込み・更新機能を初めて作る時点で、失ってはいけない情報と保持方針を決める。ただし今ここでイベントソーシングを採用しない。

## 6. 必要になるまで先行実装しないもの

ネイティブアプリ／PWA、アプリ専用API、exportライブラリと形式、リッチ表示の画像基盤、イベントソーシング、完全な履歴DB、Graphスナップショット、差分画面、汎用query DSL、全分野のオントロジー、翻訳管理システム、モデレーションエンジン、課金・広告・アフィリエイト連携を先に作らない。

「何もしない」は現在の境界や関連機能の初回判断まで不要という意味ではない。具体的なテーブル、クラス、プラグイン接続点を用途なしに増やさないという判断。

| predicateキーと日本語labelは別、name / aliasesは単一言語 | 多言語を妨げる識別方式ではない。翻訳解決・言語付き名称と検索は移行設計が必要 |
| ClaimのcreatedAt / updatedAt、静的fixture seed | 過去内容を再構成する仕組みではない。seedは差異を拒否するデモ投入処理であり、将来の編集履歴やimport更新処理を代用できない |
| APIはpublishedを読む一段階・Claim UUIDページング | 現デモとして適切。由来・時間・taxonomy条件やスナップショット読取を現在APIが扱えるとはしない |

今すぐ構造変更が必要な矛盾は見つかっていない。基幹に影響するのは、投稿時の由来と履歴、議論の永続参照、条件と受理範囲、保存・復帰の寿命、多言語の意味分離。色・具体renderer・export形式・課金連携は、この境界を保てば後段で選択できる。

概念上の注意は三つある。第一にRelationは現在表示中Claimの集合であり、議論対象の永続的な関係概念とは同一ではない。第二に人気、Source件数、由来の種別は真偽の代替にならない。第三に「当時見えたGraph」は当時の知識全体とも現在の保存ビューとも異なり、部分取得・条件・閲覧範囲を含む。

既存の「履歴・ワークスペース等は後回し」という判断は、具体機能を先行実装しない点で維持する。今回追加した高い実現意向を踏まえ、関連する書き込み・保存・議論機能の初回設計では上表の判断を先送りしない。現在のUI、API、DB、fixture、探索開閉契約は変更しない。
