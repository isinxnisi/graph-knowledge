# サイト運営画面 初版

2026-10-25。実beta限定で有効化する。コミュニティ管理者の権限とは別。本番反映は別承認。

## 体験と境界

`/operations` に受信箱・アカウント対応・運営復帰申請・操作履歴をまとめる。PCは左メニュー、スマホは見出し右のハンバーガーから右側へ重ねるドロワー。本文を押し動かさず、Escape・閉じる・移動先選択で閉じ、元のボタンへフォーカスを戻す。フィルター・ページ・選択案件は同じタブ内のメモリで保持する。

- **受信箱**：未対応／対応終了／対応不要／全状態。日時・分類・対象種別・確認期限・版のみを一覧。理由付きの「対象を確認」で、既存の通報対象だけを監査付きで取得する。親の私的題名、他の投稿、メンバー名簿は取得しない。7日は確認権限の期限であり、保存期間ではない。
- **処置**：投稿のサイト非表示／解除、コミュニティ停止／アーカイブ状態への復帰、通報の対応終了／対応不要。通報の終了で投稿や場所の状態を暗黙に変更しない。解除は別のコミュニティ管理者非表示を解除しない。停止解除だけでは場所を活動中へ戻さない。
- **アカウント**：IDで一人を特定し、有効状態と更新時刻を確認。メール、個人Capsule、全会員名簿は提供しない。停止はセッション・参加世代・既存共有等を失効させ、再開は旧権限を復活させない。実行中の本人停止はWebでは拒否し、緊急CLIを残す。
- **復帰申請**：申請と現在状態を確認し、理由付きで承認／却下。必要な再受入は別途チェックして明示する。承認だけで管理者就任・コミュニティ再開はしない。本人承諾と再開は既存契約のまま。
- **履歴**：Webの操作記録と既存運営CLIの記録を時系列でページング。主体ID・日時・処置・理由・対象IDを確認する。対象／案件から絞り込める。投稿本文、認証情報、通報理由の自動複製はしない。

公式連絡先は **plunode@gmail.com**。管理受信箱にメールを自動収集しない。通知配送、AI判断、C2、担当者割当、保存期間・対応時間の新しい約束は追加しない。

## 認可とAPI

既存のBetter Auth DBセッション＋activeを使用する。`SITE_OPERATIONS_ENABLED=1`、`COMMUNITY_ENABLED=1`、`SITE_OPERATOR_USER_IDS` の明示UUID許可リストをすべて満たす本人だけを許可する。壊れた許可リストは全拒否。表示名、コミュニティrole、送信されたactorでは決めない。プロフィールの `siteOperator` は入口の表示情報だけで、各APIの認可を省略しない。

- `GET /api/site-operations/session`：運営権限の確認。
- `GET /api/site-operations/reports?status=open&cursor=…`：通報メタデータ。
- `GET /api/site-operations/recoveries?status=pending&cursor=…`：復帰申請メタデータ。
- `GET /api/site-operations/account?id=UUID`：必要最小限の本人以外の状態（本人参照も可）。
- `GET /api/site-operations/history?target=UUID&cursor=…`：対象フィルターは任意。
- `POST /api/site-operations`：strictなkind別入力。requestId・対象ID・期待版／期待状態・理由を必須とする。復帰のreadmit、アカウントの既存理由分類を追加する。actor/caseReferenceはサーバー生成。

全APIがセッション・active・許可リストを検証する。書込みは同一Originと期待本人ヘッダーを必須とする。処置前の認可と、応答前の認可を同一transaction内で行う。User/sessionの共有lockと、既存処置のUser→Community→対象lockを維持する。競合は成功に見せず再取得を要求する。全応答no-store、ページnoindex/no-referrer。画面URLに対象本文・理由を載せない。

ページングは既存の署名付きcursor（本人・用途・フィルター・limitに拘束、15分有効、標準20／最大50）を再利用。全件に進めるが、先頭ページの件数を総数とは表示しない。状態変更中は固定snapshotの全内容を保証する仕組みではないため、再取得で現状を確認する。

## 共通処置と再送

`operateCommunitySafety`、`decideCommunityRecovery`、`operateMember` に内部PoolClient指定を追加し、CLIとWebで同じ処置を使用する。CLIの既存引数・dry-run・緊急経路は維持する。

008で追加する `site_operation_request` は、運営者ID＋requestId一意、入力digest、処置、対象、監査理由、最小結果のみ。処置とreceiptを一transactionで確定し、同時の同一requestをadvisory lockで直列化する。内容の異なるrequestId再利用は409。通信結果不明は同じ入力とrequestIdで再確認する。本文・通報理由はreceiptへ保存しない。

inspectの再送は保存済み本文を返す方式ではなく、現在の確認期限・通報者のactive／世代／audience・対象hash／版を毎回再検証する。同じrequestの監査は重複記録しない。期限切れ・権限失効・版の変化では内容を返さない。

画面は既存の共有表示用認証状態を使い、認証確認中／未ログイン／通信失敗／運営拒否を区別する。別Userでメモリを消し、非表示・復帰時は内容を隠して再認可、遅着応答を破棄する。私的内容・草稿・セッションをブラウザ永続保存しない。再読込を跨ぐ処置草稿・再送keyの復元は初版の対象外。結果不明のまま画面を離れた場合、履歴と現状を確認してから判断する。

## 配置・指定・解除

[運用手順](../runbooks/SITE_OPERATIONS.md)を参照。008は明示migrationだけで適用し、起動時やリクエスト中には実行しない。既存000〜007を改変しない。運営機能を止めてもreceiptと利用者データは保持する。

許可対象の追加・削除は保護されたサーバー設定を編集しWebだけを再起動する。全インスタンスの反映まで確認する。権限取消後は各APIで拒否し、画面も再確認時に内容を消す。ユーザーのactive停止・session失効もDBで検査する。許可された画面を閲覧できることは、任意の利用者内容へ処置する承認ではない。
