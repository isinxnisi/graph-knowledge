# コミュニティC1b：招待・再参加・継続運営

2026-10-23。C1aと`abb26f5`を継承する。第1弾の人間向けコミュニティ基盤。実装はfeature flag内、適用は隔離DBのみ。

## 招待

初回は相手がアカウント画面で共有したUUID宛てのアプリ内招待。メール検索・メール配送・外部通知は行わない。UUIDはbearer tokenではなく、別Userが知っても承諾も閲覧もできない。アカウントの招待一覧で宛先本人が承諾／辞退する。

管理者は1／7／30日（APIは1〜30日）の期限を指定できる。取消は即失効。同じ相手への再発行は旧pendingを取り消して新しい招待を作る。招待自体はmember roleへの提案であり、管理者昇格は既存の別の本人承諾を使う。

招待には発行者の参加世代・宛先の現在世代を固定する。承諾時に発行者が現役管理者か、宛先が同一Userか、期限・取消・場所の状態・世代が変わっていないかをtransaction内で検査する。発行者の退出・降格、宛先の退出・除外・停止でpendingを失効させる。発行時は発行者／宛先Userを固定順でSHARE lockし、場所をUPDATE lockする。停止と発行がすれ違って未参加者の招待だけ残ることを防ぐ。

有効な招待は、宛先本人に場所の名前と招待情報だけを見せる例外であり、会話・名簿の閲覧許可ではない。失効した招待からprivateの現在の題名を返さない。履歴・cursorにも本文を保存しない。

## 再参加と役割

自主退出は公開の場へ自由に再参加できる。限定の場には新しい招待が必要。除外／参加停止後は、現役管理者が明示的な再受入を指定して招待を発行し、本人が承諾する。停止中Userは対象にできない。サイトによる停止解除・再ログインだけではmember statusは復活しない。

承諾は常に新しい世代となる。昔のcommunity_audience_memberは書き換えず、過去の限定会話を復活させない。参加権・管理権・Capsule所有権・編集権は別。

管理者の追加は依頼＋本人承諾。依頼取消、他管理者の降格、自分の辞任も明示操作。最終管理者が辞任／退出するとアーカイブ。別の管理者を自動選出しない。

## 管理者不在からの復帰

1. 現参加者、または元管理者が、アカウントの参加履歴から申請する。User自体の停止中は申請できない。除外・参加停止から戻る元管理者は明示的再受入を必要とし、運営者は通常のapproveだけでは承認できない。
2. pendingとして保留する。申請だけでは名前・会話の閲覧権や管理権を増やさない。退出後のprivateな場所は履歴で現在の名前を伏せる。
3. サイト運営者が外部caseで本人性・運営継続の妥当性を判断し、CLIでapprove/rejectを記録する。本文の読取や強制所有移転は付与しない。
4. 承認後7日以内に申請者が就任を承諾する。その直前にも現在のUser・membership世代・管理者不在・アーカイブを再検証する。
5. 退出・除外・停止から戻る場合は新世代となり、現参加者なら現在の有効な世代を保って管理者となる。場所はアーカイブのまま。「再開」は別操作。過去に失効した限定会話も自動復活しない。他の保留中申請は取り消す。

申請は30日期限。本人取消、運営却下、承認後失効、停止・除外で終了する。複数申請が同時に承諾されても場所のlockで一人だけが成立する。

運営判断の実行例（接続環境は別途明示。今回は隔離検証だけ）：

```sh
node --import tsx scripts/community-recovery.ts approve REQUEST_UUID --revision 1 --actor operator --case CASE-123 --origin ORIGIN
# 上はdry-run。審査と結果を確認してから同じ引数へ --apply --confirm REQUEST_UUID を追加する。
```

除外・参加停止からの元管理者を再受入する判断には、case確認のうえ `--readmit` も明示する。承認は `recovery-readmit-approve` として監査する。通常会員を勝手に元管理者として扱わず、適合する申請者がいなければアーカイブを維持する。

`community_operation`に申請ID・operator・case参照・判断を保持する。通常会員向けHTTPに運営承認routeは作らない。自動的に権限を取得する方法も設けない。

## ページング・戻る

コミュニティ、スレッド、名簿、投稿、自分の投稿、招待、参加履歴、復帰申請にkeyset cursorを使用。既定20、最大50。認可をWHEREで評価した後にLIMITする。非公開の存在を総件数や空ページの予告から漏らさない。

C1aのスレッド・投稿の累計200件上限は解除し、200件を超える継続利用と全ページ取得を検証する。スレッド作成60件/時、投稿5件/分、招待60件/時という人間向けの操作上限は保持する。

cursorはHMAC署名、15分期限。User・一覧用途・filter・ページサイズ・上端時刻へ結び付ける。招待・復帰の期限判定はDB時刻を使う。cursorの時刻はPGのmicrosecondsを保持し、同時刻はUUIDで順序を確定する。新規追加は最初の上端時刻で区切る。場所内の一覧はpolicy revision変更で409。次ページでも現在の認可を再評価する。

画面は前後のcursorと選択タブをrouteに持ち、scroll位置はメモリ内で記録。スクロールごとのReact state／History snapshot更新はしない。本文cacheや名簿を履歴に入れない。認証変更・非表示・失効時は内容を破棄し、遅い応答を採用しない。タブ切替は履歴を置換、ページ移動は追加し、ブラウザBackも成立させる。

## 追加schemaと境界

006にInvitation／Recovery、operator監査fieldを追加。005以前のchecksumと意味は不変。明示migrationだけで適用し、起動やAPIからは実行しない。

```sh
node --import tsx scripts/member-migrate.ts --communities --confirm-origin ORIGIN
```

既存の会員migration呼出は従来どおり。005／006がないDBでも既存会員の停止・退会を維持する。通常の3200／betaではCOMMUNITY_ENABLEDを無効に保つ。3275／graph-comは架空データの接続試作のまま。C2、AI、KG、会員DB本番適用は別工程。
