# 共有・議論・投稿を小さく進める設計

2026-10-09採用。最小Capsule・会員保存・特定版の限定リンク共有まで実装。現行契約は[会員Capsule](MEMBER_CAPSULES.md)と[限定リンク共有](CAPSULE_LINK_SHARING.md)。短いスレッドは[版別コメント契約](CAPSULE_DISCUSSION.md)として実装。投稿候補・一般公開・運営対応は未実装。構想の正本は[Capsule・User Contribution](CAPSULE_AND_USER_CONTRIBUTION_VISION.md)、Userの境界は[アカウント設計](ACCOUNT_AND_OWNERSHIP_DESIGN.md)を参照する。

## 到達点と進め方

最初のコミュニティ体験は「説明を添えた関係図を他人へ渡し、その内容について話せる」。人気・信用点数・推薦・大規模moderation制度は初回に必要ない。

| 単位 | 触れる体験 | 最初に必要になるもの |
| --- | --- | --- |
| 自分のCapsule | 作成した説明付き内容を会員として保存し、再び読む | User、owner、private保存、現在KGへの参照 |
| 限定リンク共有 | 特定の版をリンクで渡し、別ブラウザで読む。止めたい時は失効できる | 内容の版、閲覧token、読取認可 |
| 一つのスレッド | 同じCapsuleについてログインUserが文章を投稿し、元の内容へ戻る | 安定対象、投稿者、参照版、撤回／非表示 |
| 投稿候補の提出 | Source付きの狭い事実を提案し、処理状態／結果を確認する | provenance、候補と受入の区別、review経路 |
| 一般公開・発見 | 公開URL・検索可能な内容から閲覧／探索へ入る | 公開操作、index方針、通報・運営対応 |

これは実装を選ぶ初期順序であり、五つを一度に完成させる計画ではない。最小Capsuleのブラウザprototypeはaccountなしでも進められる。会員保存・共有が必要になったらaccountと一件の内容をつなぐ。各単位を複数回の自動実行へ分割してよい。新しい画面だけ増やして前後の導線を未接続にしない。

## Capsuleの内容・所有・版

初回はtitle、利用者の説明、明示的に選んだ既存KGのEntity／Claim参照を対象にする。参照はdataset／内部UUIDを保持し、現在の権限とデータへ再解決する。DisplayRelation IDやGraphの到達性で内容の所属を決めない。Sourceへは独立Claim／Citationから戻れるようにする。

サーバー上の参照中心Capsuleでは、Capsule ID、ownerUserId、現在revisionと、内容revision ID／schemaVersion／作成時刻を持つ案とする。**公開・共有した内容revisionは上書きしない**。編集は新revisionを作り、共有対象を更新する操作は明示する。KG本文そのものの歴史版を保存したことにはならず、参照先更新／失効は読み取り時に示す。

参照と説明を持つCapsuleの正本はPostgreSQLに置く。これはUser所有のコンテンツであり、Global KGの二重管理ではない。将来のlocal Entity/assertion、注釈線、完全manifestの物理保存方式を決定したことにはしない。初回は現行KG参照中心のschemaに限定する。

ブラウザprototypeから会員保存する時は明示コピーとし、server側でID・ownerを付ける。保存ビューや途中保存をCapsuleへ自動変換しない。内容の版と、探索座標・pan/zoom・cursor・通信世代は別にする。

## 公開範囲を小さい操作へ分ける

| 状態・操作 | 読める人 | 初回の扱い |
| --- | --- | --- |
| private | 本人 | 既定。一般認証Userでも他人の内容は読めない |
| 限定リンク | 有効なリンクを持つ閲覧者 | 特定revisionの読取だけを許す。一覧・検索・indexへ出さない |
| public | 公開閲覧者 | 次の公開フェーズ。公開設定と検索露出を明示して導入 |
| 運営非表示 | 運営と必要な本人確認経路のみ | 公開／リンク経路から本文を隠す。Claimの肯否を変えない |

owner、公開範囲、検索露出、moderation、スレッドの書込可否、Global受入、課金資格は別の判断である。一つの巨大なstatusに詰め込まず、その操作で必要な判定をserverへ置く。private内容を運営が見る場合も、運営権限・目的と操作記録を必要とし、一般のmoderator画面へ自動公開しない。

限定リンクはCapsule UUIDが推測しにくいことだけに頼らず、独立した十分な乱数tokenを発行しDBにはhashを保持する。失効・再発行でき、tokenでowner編集や新revisionの非公開内容を読めない。初回は同時に有効なリンクを一つに絞ってよい。URLはcredentialとして扱い、ログ・Referer等へ不用意に残さずnoindexを付ける。noindexは認可の代替ではない。

共有URLは一つの受理済み内容revisionに結び付ける。共有を更新するなら新リンクを発行し、古いリンクの継続／失効を明示する。privateへ戻す操作と運営非表示は既存リンクからの読取も止める。公開範囲だけを変えたことでKG ClaimがGlobal受入済みにならない。

閲覧者のKG読取権限をそのまま適用する。ownerが読めた非公開KGやlocal資料の本文を、共有参照から勝手に公開しない。現datasetのpublished読取は、将来のすべての共有内容の許可を意味しない。

## 最初のスレッド

初回対象は**Capsule IDに一つの平坦なスレッド**。短いplain textの投稿と日時・表示名で成立させる。返信階層、リアクション、ランキング、添付、feed、email通知は初回に必須ではない。

投稿には安定UUID、authorUserId、作成時刻、本文、投稿時に読んでいたCapsule revision IDを残す。User表示名はプロフィールで解決し、privateメール・外部identityを出さない。新規投稿は有効なUserと対象の読取／書込認可を必要とする。限定リンクは読取を可能にしても投稿者の匿名な書込許可にはしない。初回は本人と有効リンクを持つログインUserが投稿できる案とする。

スレッド自体はCapsule IDへ結び、各投稿のcontextRevisionIdが同じCapsuleに所属することを検証する。内容更新後も過去の投稿を新しい内容への評価として見せず、「以前の版についての投稿」とその版への導線を示す。共有tokenしか持たない閲覧者へ非共有revisionを見せない。読めない旧版の本文・注釈・投稿は隠し、その理由を一般表示に留める。すべての関連版を自動公開する設計にはしない。

版ごとに別スレッドを作る案は参照が明快だが会話を分断しやすい。初回は上記の対象固定＋投稿時版を推奨し、実際の会話量で再評価する。

Global Claimについてのスレッドは別の次段階とする。Claim UUIDは安定していても、現実装には知識本文の歴史版・訂正時の参照契約がない。初回Capsuleスレッドをそれに依存させず先に成立させる。後からClaimスレッドを追加する際は対象種別・dataset・UUID・参照時点／版を定める。SPOの表示束IDを永続議論対象に使わない。

## 訂正・撤回・運営

初回の投稿は追記中心にしてよい。作者は自分の投稿を撤回でき、内容を伏せた記録と時刻を残す。編集を入れるなら更新競合と編集履歴を同時に設計する。他人の投稿をCapsule ownerが書き換えることはできない。ownerはスレッドを閉じられるが、他人の投稿を運営非表示にする権限まで自動付与しない。

通報対象と理由、処理状態、運営の非表示／解除／スレッド停止についてactor・時刻・理由を記録する。最初は管理CLI等でも運用でき、全管理画面の完成を必須にしない。頻度／本文長／対象への投稿上限を初回に明記する。一般公開する前には対応経路を持つ。ローカルの2 User検証を、その公開運用体制待ちで止めない。

削除・退会時の個人情報処理と、会話・auditの保持は別に決める。撤回表示だけで法的・個人情報上の削除要求を完了したことにしない。内容の非表示／撤回がSource支持やClaim.polarityを変更することもない。

通知はthreadが使えるようになってから必要に応じてin-appの未読から始められる。email／push／外部サービス契約は初回の依存にしない。

## 投稿候補とGlobal受入は別経路

Capsuleの説明、スレッドの文章、公開共有、投票、AI抽出をKG Claimへ自動変換しない。投稿候補を提出する時は原文／言語／Source／locator／scope／period／狭い意味を別の候補記録へ残し、型validationと人間の意味受入を分ける。

初回Submissionは実装対象を選んだ時に一種類へ絞る。すべての投稿をCapsule経由にすることも、全候補を一度に処理することも未採用。submit→pending→確認／修正→結果の往復を設計し、provenanceと操作権限をserverが付ける。User入力から「Global受入済み」「review済み」を自己付与させない。

reviewerの受入権限はowner・通常moderatorと区別する。Globalへの書込は現行seedを転用せず、資料確認と受入範囲・元候補版を追える専用の経路が必要。その初回設計までKG自動書込は行わない。共有とスレッドはこの昇格機能なしで実装できる。

Kev・Job Queue・外部LLMは必須ではない。AI処理を選ぶ時に[共通Kev方針](AI_PROCESSING_DIRECTION.md)を読み、公開APIと人間の意味判断の境界を守る。

## 実装時に作るもの・作らないもの

初回accountでは認証と一種類のprivate保存に必要なテーブルだけを作る。共有時にrevisionとlink、議論時にthreadとpost、運営対応時にreportとauditを追加する。九種類の空テーブル・万能permission frameworkを先行導入しない。

UIはExplorerから作成／保存内容へ入り、内容→個別Claim／Source→探索へ戻る導線を維持する。共有閲覧ページとスレッドを探索画面へすべて押し込まない。戻ってきた時の起点・条件・開閉・pan/zoomの保持は既存snapshotでできる範囲を再利用し、永続完全復元を約束しない。表示文字列はlocaleで解決できる境界を持つ。

APIはUserと対象の認可、公開範囲、revision、一貫したエラーを持つ。認証ライブラリに任せる部分と、Capsule/threadの製品認可は別責務とする。公開KG読取とprivate運営機能の障害を分離する。

## 初回の検証条件

- User Aのprivate内容をB／匿名が読めず、owner偽装、更新、削除が拒否される。
- 有効リンクで指定版だけ読める。失効・private戻し・運営非表示後は読めず、内容が検索／index／cacheへ漏れない。
- 新revisionで共有内容が黙って変わらない。投稿時の旧版と現在版が区別され、非共有の旧版は漏れない。
- ログインUserは許された対象へ投稿でき、失効session／書込停止／他人の投稿変更が拒否される。
- 説明・コメント・公開・非表示を行ってもKG Claim／Citation／Source・肯否が不変。
- 別ブラウザで共有内容から根拠へ進み、Explorerへ戻れる。元の条件・開閉・復帰が壊れない。

これで一つの「共有して話す」経路が触れれば初回として区切る。Capsuleの完全版、ユーザー投稿全体、信用制度、完全なontology、課金を先に完成させる必要はない。反応を証明するための際限ないUI調整も完了条件にしない。

## 後回しと人間判断

共同編集、フォーク、follow、feed、評点、推薦、階層返信、資料添付、通知配信、paid entitlement、投稿からGlobalへの昇格は別フェーズ。安定した対象・owner・版・認可の境界を今回決めておけば後から追加できる。

外部公開、実provider設定、料金、実在データの意味受入はユーザーへ必要な範囲を相談する。投稿データのライセンス、privacy／削除・保持、公開moderation対応は一般公開前に具体化する。これらの未決を理由に、private account／限定共有／2 Userのローカル議論prototypeまで回避しない。
