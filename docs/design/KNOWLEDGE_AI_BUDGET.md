# 外部AIの提供側制限とサービス側上限

## 2026-11-08 本番・βの配分を確定

ユーザー回答により、本番300回／日・β100回／日を採用。二つの会員DBに同じprojectの台帳を持つため、両方へ400回を配らない。正式AI処理を起動する前にβ側を先に切り替える。現在は本番未起動のため、稼働中βの400回設定は維持し、切替候補をprivate領域に準備している。

| 上限 | 本番 | β | 合計 |
| --- | ---: | ---: | ---: |
| 回／日 | 300 | 100 | 400 |
| 回／月（31日分） | 9,300 | 3,100 | 12,400 |
| RPM | 9 | 3 | 12 |
| 入力TPM | 150,000 | 50,000 | 200,000 |
| 日次入力・出力token（それぞれ） | 1,500,000 | 500,000 | 2,000,000 |
| 月次入力・出力token（それぞれ） | 46,500,000 | 15,500,000 | 62,000,000 |

用途別上限は各環境の全体上限の内数とする既存ルールを維持する。実際の切替時はβのWeb・対象Workerを止めて、同じprojectの既存消費と送信不明分を再確認する。切替前のβ消費が新配分を超えていた場合、その分を無視して本番へ満額を追加しない。該当期間の残枠へ本番側を抑えるか、通常の次期枠を待つ。台帳削除・project変更・provider待機解除で調整しない。

準備時の実台帳はprovider基準日2026-11-07で5回、2026-11月で412回。回数台帳は温存し、新設定のschemaと合計を検査する。これはGoogle側の残量を直接確認した値ではない。以下は配分前の共通上限の説明。

2026-11-06。Google側の無料枠と、Plunodeが設定する処理上限を区別する。80回／日は初期設定の据置きで、Googleの無料枠が尽きたという根拠ではなかった。

同日、実Googleログイン済みAI StudioのplunodeプロジェクトでGemini 3.1 Flash Liteの無料枠を確認：RPM15、入力TPM250,000、RPD500。表示された7日間の最大使用量は、現在の残量ではない。課金設定やAPI keyは変更しない。

## 今回のサービス設定

| 対象 | 上限 |
| --- | ---: |
| 全用途合計 | 400回／日、12,400回／月 |
| 収集系（全体の内数） | 133回／日、4,133回／月 |
| 翻訳系（全体の内数） | 66回／日、2,066回／月 |
| 開発評価全種（全体の内数） | 100回／日、3,100回／月 |
| 全体の送信速度 | RPM12、入力TPM200,000 |
| 日次入出力の処理量 | 入力・出力それぞれ2,000,000 token |
| 月次入出力の処理量 | 入力・出力それぞれ62,000,000 token |

GoogleのRPD500に対し100回の余裕を残す。月次回数は31日分のサービス側上限で、Googleに同じ月次枠があるという意味ではない。収集・翻訳の既存配分は全体上限に比例させ、開発評価には独立した1/4上限を追加する。collection-evaluation／translation-evaluationは用途と評価の両方に計上し、評価だけで全体を使い切らない。投稿確認と取込は全体の残りを利用する。

旧設定から回数だけを増やしtoken上限が実質的な低い回数制限にならないよう、日／月の処理量も調整する。原子的な予約、結果不明分の保持、同一projectの共有、providerの429／停止待ち、項目別再試行上限は維持する。台帳を削除・リセットせず、別keyや有料fallbackで迂回しない。

## 表示と設定の反映

サービス上限による待機には「このサービスの本日のAI利用上限（400回）」等と表示する。token処理量による待機と提供側の429を区別し、「無料枠を使い切った」と断定しない。

設定変更時は既存projectのdigest照合と旧設定backup後、同じ台帳を保ったまま新設定へ更新する。旧サービス上限によるquota待機だけを再開対象とする。外部AIのRetry-After／project pause、項目別の送信上限は解除しない。通常の投稿ごとに管理者操作を要求する機能ではない。
