## 1. 結論と問題の整理

推奨は、**正確な関係語彙の意味契約を小さく管理し、Claimの限定、閲覧分類、探索条件、表示上の束ね方を分ける**こと。世界全体のontologyや大分類ツリーは必要ない。分類を作るだけでは、同義語の増殖も意味の変質も防げない。

語彙追加時には「既存概念の別名」「既存関係の役割・限定」「近いが異なる関係」「閲覧分類」「本当に新しい概念」を判別する。判別の結果と具体例を版管理し、機械は参照・制約・変更を検査、人は意味と根拠を審査する。この二つを組み合わせる。

現在の考え方の問題は、分類軸が足りないことよりも、**意味を判断する定義が短く、表示集約のキーが将来の命題の同一性にも使えるように見えること**。UIでまとめることには価値があるが、それを同義性や矛盾判定へ流用しない。

現行4語彙はASSISTANT_OF（person→person）、INFLUENCED_BY（person→person）、CONTRIBUTED_TO（person→work）、AFFILIATED_WITH（person→organization）。同じ端点種別は意味の同一性を示さない。CONTRIBUTED_TOは作者を特定せず、AFFILIATED_WITHは雇用・所属を断定しない。アシスタントから師弟、作品への影響から作者への影響を推論しない。

パイロットは5人物・3作品・9 Claim。制作関与8件と人物間の影響1件で、役割・巻・版の限定は台帳とCitationに残る。既存の保留判断は重要な実例で、原作由来や組織の協力をCONTRIBUTED_TOへ押し込めなかった。凍結版の注記を今回自動変換しない。

## 3. 分ける最小の概念

| 概念 | 問い・責務 | 混同しないもの |
| --- | --- | --- |
| Predicate | 主体と対象について何を主張するか。意味、方向、端点の許容組を固定 | UIカテゴリ名、翻訳、役割名 |
| Claimの限定 | その主張は何の役割・期間・対象範囲についてか | 単なるSourceの説明文、Entityの恒久的な属性 |
| 閲覧分類（taxonomy） | どの関係語彙を一緒に探しやすくするか | 同義性、論理的な上位関係、自動推論 |
| プリセット | どの具体的な条件・表現を選択するか | 新しい知識上の意味 |
| 表示集約・束 | 取得済みの関係をどう簡潔に見せるか | 保存Claimの統合、正しさの評価 |

各概念のID空間とlocale別labelを分ける。「同じ日本語だから同じ概念」「翻訳が違うから別概念」と判定しない。言語情報は設計前提であり、辞書の説明・別名・順逆表現も対象とする。資料の原語・原表記は翻訳リソースとは別に保存する。

「キャリア」「経歴」「実績」「活動歴」は、まず分類やビューの候補として目的と収録条件を比較する。特定の二者間で何を主張するかを定義できない語を、そのままpredicateへ追加しない。完全同義なら一つのIDと別名、範囲が違うなら違いを明文化する。異なる分類軸の多重所属は許容できる。

「好き」「尊敬」「影響を受けた」「参考にした」は、似た表現でも違う命題になり得る。同じ分類に入れることと同じ意味として保存することは別。語感で統合せず、それぞれを区別する資料上の例を確認する。

### 既存taxonomy案との差

閲覧分類であり推論体系ではない、複数所属を許す、公開プリセットは具体的predicate集合へ固定する、という既存案を維持する。今回加えるのは、**分類が語彙追加審査の代わりにならないことと、分類変更ではPredicateの意味を変更できないこと**。対象kindは整理の一軸で、唯一のツリーの根にする必要はない。制作、態度、組織的関与などの軸も、具体的な選択需要が出てから少数導入する。

既存プリセット文書のwork→workのINFLUENCED_BYは未実装の将来例。端点許可を増やすだけで実現済みにせず、人物の影響と作品の影響の意味・根拠が同じ契約で扱えるかを先に審査する。

## 4. 制作関与と役割の推奨

CONTRIBUTED_TOを制作関与の命題として維持し、作画・脚本・監督・監修・プロデュース等は、**Claimを限定する管理された役割**として扱う案を推奨する。役割は人物の全般的な肩書きではなく、その人物とその作品の関与についての値。役割ID、定義、適用predicate、locale別labelを持ち、原資料の役割表記と正規化判断を別に残す。

将来の概念例（現行schemaではない）:

```text
A -- CONTRIBUTED_TO(role=作画) --> W / affirmed
A -- CONTRIBUTED_TO(role=監修) --> W / denied
```

この二つは両立する。polarityは限定を含む命題全体にかかる。初期の役割対応は一Claim一役割を推奨し、複数役割を列挙したClaimの否定が「全部を否定」か「同時成立を否定」か曖昧になる構造を避ける。複数役割を資料が示す場合は、それぞれ根拠のある独立ClaimとCitationを作り、Sourceを共有できる。

役割なしは「役割不明または特定していない制作関与」であり、すべての役割を肯定する意味ではない。役割限定の否定も制作関与全体の否定ではない。限定なしの否定との比較は期間・対象範囲も確認する必要があり、自動矛盾判定は導入しない。

巻・版の限定も命題の解釈に影響する。役割を型に載せる際は、全作品・全期間の担当へ一般化しない契約を併せて決める。直ちに汎用scope言語を作らず、今回の資料で必要な限定を保持し、扱えないものは保留する。

現在の凍結Claimは広い制作関与のまま残す。注記のregex解析や元クレジットの機械的な別名置換で、より強い役割付きClaimへ変えない。将来の別版で、元表記・資料の限定・根拠を人が再確認して正規化する。「著」や一般的な制作クレジットから作画等を推定しない。

### 新predicateに分ける場合との比較

| 案 | 利点 | 負担・適用判断 |
| --- | --- | --- |
| 制作関与＋役割限定（推奨） | 共通関与と具体的担当を分離し、語彙の増殖を抑える | 限定込みの肯否・比較・条件取得を設計する必要がある |
| 作画した・監督した等を各predicateにする | 各命題を直接選べる。役割機構が不要 | 多くの共通定義・翻訳・条件が重複。役割ごとの差が関与の限定以上なら候補 |
| Citation.noteだけで保持 | 現行の凍結版に適切。原表記を失わない | 役割で取得・比較できない。恒久的な意味モデルには不足 |
| 制作参加・制作イベントのNode | 場所、組織、複数参加者等を一つの出来事として表せる | 今の二者間パイロットには過大。多項関係が必要になった時に検討 |

すべての関係を役割で表す方針ではない。好きな作品は態度、批判したは発言・行為、代表作や出世作は評価者・基準・文脈を伴う可能性がある。制作役割とは分け、根拠と必要な限定が確認できるまで新語彙を確定しない。この例から新predicateを採用したことにはしない。

## 5. 語彙の意味契約と追加ルール

当面はGit管理の既存辞書と文書でよい。意味の正本をコードと管理DBに二重化しない。各predicateの最小契約は次の内容とする案:

- 安定ID、規範的な意味説明、主体と対象が担う意味、許容端点組、保存方向。
- 含む例・含まない例・判断が割れやすい境界例。近い既存IDとの違い。
- 必要な限定と、資料から許される変換・禁止する推論。
- locale別label / reverseLabel / 説明・別名。意味契約と翻訳変更を区別する。
- 導入記録、状態（使用中・廃止等）、意味に影響する変更の判断記録。

ASSISTANT_OFに師弟を含めない、CONTRIBUTED_TOから作者を認定しない、AFFILIATED_WITHから雇用を認定しない、といった現在の制限を先に基準化する。短い既存説明に新しい意味を足す作業ではない。曖昧な箇所は既存Claimと受入例を照合し、矛盾する解釈を黙って採用しない。

追加提案には次の比較票を必須にする:

1. 何を登録・探索したいのか。実資料の例と、採用してはいけない反例。
2. 追加対象はpredicate、役割、分類、翻訳別名、プリセットのどれか。
3. 最も近い既存IDと比較し、同義・限定・部分的重複・別概念のどれであるか、その理由。
4. 既存語彙では表せない差異。端点、方向、期間、限定、肯否への影響。
5. 既存Claim・探索条件・翻訳・表示への影響と、受入判断者・判断日。

少数の語彙では全件比較で十分。増えたら同じ端点組・共通語・別名・役割を使って比較候補を提示する。自動的な意味同一判定はしない。候補提示と、比較票が未記入なら公開を止める検査で、注意力だけに頼る状態を減らす。埋め込み検索やAI審査基盤は必要条件ではない。

### 使用開始後の意味を守る

同義の新表現は同じIDのlocale別名とする。近いだけなら同義別名へ登録しない。別名自体にも対応概念の審査が必要で、翻訳の変更による意味の拡大もレビュー対象。

**使用済みIDを別の意味へ再利用しない。** 意味の変更が必要なら新IDと差分・廃止方針を記録する。旧Claimや保存条件を自動置換しない。説明の明確化と意味変更の区別は人が判断し、差分確認を必須にする。旧語彙を読み取れる定義を残す。

まずGitの基準版と収集・変換版から定義を辿れるようにする。意味が不変のIDを前提とすれば、全Claimへ意味版番号を追加する必要は直ちにはない。同じIDで複数意味版を運用する案は全読取・比較・条件解決に負担が広がるため推奨しない。定義のhashは変更検出には使えても、意味が同じかの証明にはならない。

## 6. 構造・validator・人間判断の境界

以下は今後の最小カタログ整備で導入する候補。現行validatorが全て実装済みという意味ではない。

| 項目 | 機械で担保・検出できること | 人間に残ること |
| --- | --- | --- |
| ID・参照・namespace | 重複ID、未知参照、別名循環、型の混同を拒否 | 二つの概念が本当に同じ意味か |
| 端点・役割・限定 | 許容組、適用predicate、必須値、日付を検証 | 元資料からその関与・限定を読み取れるか |
| 定義・追加票 | 必須欄・比較先・例・判断記録の欠落を拒否 | 比較と例が十分か、境界が妥当か |
| 類似語 | locale別に正規化した重複label / alias、共通端点等を警告 | 同名別概念・誤訳・同義・近接の区別 |
| 意味変更 | 基準版との差分、削除・端点拡大・別名変更を検出しレビューを要求 | 互換な明確化か、別IDにすべき変更か |
| 分類・プリセット | 参照整合、採用する階層の循環、条件解決の固定を検査 | 分類の有用性、所属の妥当性 |
| 契約例 | レビュー済みの受入・拒否例と検証規則の回帰を確認 | 新資料の事実性、文脈、微妙な意味差 |

表示名の重複は一律エラーにしない。同名別概念や言語固有の語彙があり得る。曖昧な名称を内部ID解決に使わず、候補の説明で区別する。文字列が似ていない同義語も、似ている別概念もあるため、lintに意味の完全性を約束させない。

Sourceの存在、支持Citation、型検証の成功は真実の保証ではない。矛盾する主張や少数説を排除する検査は導入しない。

## 7. 将来のユーザー投稿

利用者は承認済みpredicate・役割から選択し、独立Claimと根拠を提案する。新しい語彙は提案として受け付け、即座に正規語彙として公開しない。自由記述・原表記は保持するが、未承認文字列をpredicateとして本番Graphへ増殖させない。

運営も同じ比較票と検証を通す。投稿Claimの審査と語彙追加の審査、翻訳提案を分ける。既存語彙で表せない資料は保留できるようにし、投稿できるようにするための意味の拡張を避ける。認証・管理画面・提案テーブルは今回設計しない。

## 8. 保存方向・探索視点・UI表現

保存は人物（関与者）→作品（対象作品）の意味方向を維持する。作品起点ではOBJECT側から同じClaimを取得する。探索方向は取得する隣接関係の条件であり、保存方向の変更ではない。

人物側の「作品の制作に関わった」と作品側の「制作関係者」はlocale別の順逆表現。逆向きの知識Claimを重複登録しない。現在のGraphは正規方向の矢印を維持し、一覧・詳細の文は視点に合わせられる。役割を表示する場合も「作品が作画した」のように主体の意味を反転させない。

将来対称関係が必要なら、その語彙の契約で決める。両方向探索や双方向矢印だけから対称性を推論しない。時系列の配置方向も知識上の矢印とは別。

## 9. Claim比較・Relation集約・表示束の責務

将来の処理境界:

```text
独立Claim（役割・期間・肯否・Citation）
  → 条件付き取得・受理範囲・到達性・表示対象
  → 現行の三つ組によるDisplayRelation
  → 必要になった時だけ、表示用のRelation束
  → locale別ラベル・配置・renderer
```

現行DisplayRelationは粗い関係概要として再利用できる。しかし役割追加後の命題比較にはsubject / predicate / objectだけで不足する。正規化した役割と限定を比較に含める必要がある。期間は現行どおり異なる主張を並べる軸として残し、同内容・比較候補・表示同居を一つの同値キーで処理しない。

現在の「異説あり」は取得済みの同じ三つ組に肯定・否定があることだけを示す。役割の違う肯否まで対立と見せるのは危険。役割対応時には、同じ限定の比較と全体の肯否混在を区別し、後者は必要なら「肯定・否定の主張を含む」など内容を記述する。時期差だけでも両立し得るため、同じ限定であっても真偽の自動判定はしない。

現在のrelatedClaimIdsは広い比較候補として維持可能だが、役割導入時に返却の対象範囲・詳細の区分を明記する。既存APIに役割がないため、役割付き命題を本当に導入する時はDB・投入・API・条件・詳細を一緒に設計する必要がある。今回API変更は不要。

さらに異なるpredicateを一本に束ねる場合はpresentation層に置き、束にrelationIdsとclaimIdsを保持する。束の選択では意味別Relationと個別Claimへ戻れなければならない。一つの代表ClaimのrelatedClaimIdsだけでは、別predicateを含む全内容を取得できない。

「制作（作画・監修）」という概要は、正規化済みで取得・表示対象にある役割だけから作る。注記から推測しない。好き・批判・制作を同じ「制作」に束ねない。端点が同じだけの概要なら「複数種類の関係」とし、方向の異なる関係を一本の一方向矢印で誤表現しない。束ねる設定は自動的な意味分類ではなく、明示した表示規則とする。

表示束によってClaim単位のページング、上限100 Entity / 200 Claim、受理範囲、開閉・復元・条件を変えない。Graphが一本でも取得した主張は独立に数える。Graphの概要は部分取得、詳細の関連Claimはより広い範囲、という現在の違いも維持する。表示束のIDは知識の永続IDにしない。

## 10. 今決めること・後回しにすること

**UIをさらに作り込む前に合意する境界**は、使用済みpredicateの意味を不変にすること、役割をClaimの限定として扱うこと、分類・プリセット・表示集約で意味を変更しないこと、限定込みの肯否を区別すること、言語から独立したIDと正規方向を維持すること。特に役割追加と「異説あり」の扱いを別々の改修で進めない。

役割の物理schema、正規化キー、APIの具体型、限定の最小項目は役割対応フェーズの着手前に確定する。新しいデータを追加する前に、旧い広いClaimの保持と役割付きClaimの扱い、収集版・定義への参照も決める。現在の凍結版は変更しない。

後回しにできるのは全領域の分類体系、意味推論エンジン、役割の全辞書、制作イベントNode、管理UI、ユーザー投稿、PostgreSQLカタログ、全文検索による類似語審査、全面翻訳、複数predicateの表示束。安定IDと分離を守れば、必要になった時に追加できる。多言語の前提そのものを後回しにする意味ではない。
