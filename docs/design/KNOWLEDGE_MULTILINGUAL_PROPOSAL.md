# 知識データの原語・翻訳・訂正を分ける案

2026-11-05。ユーザーの継続指示により、**原語保存の第一段階を採用・実装。** 現行の到達点は[原語保存の契約](KNOWLEDGE_ORIGINAL_LANGUAGES.md)を参照する。以下の翻訳版・自動翻訳・訳文訂正は後続の設計案であり、全実装済みではない。 多言語を必須の設計前提とする既存の[アーキテクチャ](../ARCHITECTURE.md#多言語対応の設計前提)を、共通原記録と投稿へ具体化する。本メモだけでmigrationや外部AI翻訳を開始しない。

## 現行の到達点と不足

表示UIの日英辞書、言語に依存しないID、内容版・資料pin・Capsuleの保存断面は既存資産として使える。一方、共通Record／Theme／Evidenceには言語別本文・原文と翻訳の対応がない。Entity／Sourceの単一languageも既定jaのまま保存する経路があり、元資料の実言語として信用できない。訂正者の記録・表示はあるが、翻訳者や訳文訂正者の対象・版・言語は管理していない。

主な確認先：`lib/domain/knowledge-foundation.ts`、`lib/domain/knowledge-submission-selection.ts`、`lib/domain/knowledge-submission-capsule.ts`、`lib/server/knowledge-collection-plan.ts`。旧KGでは原本payloadを保持する一方、表示用の日本語文を生成している。画面の英語化を知識本文の翻訳済みと扱わない。[現行UI言語の契約](UI_LOCALE.md)とも区別する。

## 1. まず言語の意味を分ける

| 言語 | 何を示すか |
| --- | --- |
| UI言語 | 操作・案内の表示設定 |
| 投稿文の言語 | 投稿者自身が書いた本文・具体関係・補足の原語 |
| 資料の言語 | 読んだ原資料の本文言語 |
| 引用の言語 | 個々の原文抜粋の言語。多言語資料では資料全体と異なり得る |
| 翻訳先言語 | 別に生成・提出した訳文の言語 |

国籍・アカウント設定・UI言語から原語を確定しない。本人の明示、機械の推定、不明を由来として区別する。古いja既定値を「本人が日本語と確認した」と読み替えず、不明／混在も扱う。

フォームは項目の近くに小さな言語指定を置く案がよい。推定値を候補として出し、必要な時に修正できるようにする。引用は投稿文と別の言語を保持する。すべての欄に大きな言語設定を並べない。具体的な必須条件と自動判定の採否は次の実装時に決める。

## 2. 原文と翻訳は別の版にする

日本語で書いても英語で書いても、その入力を原文として保存する。翻訳は「対象の種類・安定ID・原文内容版・対象項目・訳先言語」を指す別の追記版にする。対象項目は既知の本文・名称などに限定し、任意のJSON位置を書き換える権限を作らない。

翻訳には本文・翻訳版・作成者／作成方法・訂正理由・原文hashを保持する。AI由来なら処理参照、model／prompt等の版も持つ。原文が更新されたら旧翻訳は旧版の翻訳として残り、新しい原文の確定訳へ付け替えない。原文へ戻れる表示を用意する。

### 対象ごとの扱い

- **Entity**：同じIDへ言語付き名称・別名を結び、正式名・別名・翻訳名・転写を区別する。対象名が一致することだけでは同一Entityとしない。現行name／aliasesは移行時の原文・fallbackとして保護する。
- **関係・出来事・背景**：assertion／relation／scopeの原語と表示訳を保持する。関係語の翻訳、意味分類への対応、関係の方向・限定の変更は別操作。訳語を識別キーにしない。
- **Theme**：title／descriptionも原文と翻訳を分ける。題名の翻訳でTheme ID、記録の選択、年表構成を変えない。
- **Source／Evidence**：原題・原文抜粋・locator・資料pinを保つ。引用の参考訳を原資料の原文として照合しない。正規化した照合用テキストと、入力／取得した原文の区別も保持する。

検索は原名・別名・訳名から同じ対象へ到達する。画面の言語切替だけで探索条件やGraphの位置を変えない。

## 3. 訂正対象を先に明示する

別言語で投稿されたことだけでは、「事実の訂正」か「訳文の訂正」かは分からない。操作対象で区別する。

| 操作 | 更新するもの | 保持するもの |
| --- | --- | --- |
| 事実・原文を訂正 | 同じ正本IDの次の内容版 | 元の投稿・原文・根拠・旧翻訳の履歴 |
| 訳語・ニュアンスを訂正 | 指定言語の翻訳の次版 | 正本の内容版・原文・根拠 |
| 引用・記載箇所を訂正 | 指定Evidenceを含む次のRecord版 | 旧引用と資料pinの履歴。資料版の差替えは別に明示 |

例：日本語原文の英訳が不自然なら、日本語原文はそのままで英訳だけを直す。事実自体が誤っていて英語で訂正されたなら、訂正文を英語の原文として次の内容版に保持できる。旧日本語は履歴に残すが、新しい事実の日本語訳としては使わない。逆翻訳で投稿者の日本語を作り直して、本人の原文とすることもしない。

投稿者・事実の訂正者・翻訳者・訳文訂正者を対象と版に結び、元の作者を置換しない。既存の人物Badgeと本人／匿名の公開規則を使う。匿名でも内部の投稿者はログインアカウントに紐づける。

なお現行の引用訂正が重複処理に吸収される回帰は、この設計案の採用とは独立した不具合として今回修正する。[修正検証](../verification/KNOWLEDGE_QUOTE_CORRECTION_20261105.md)。多言語対応の実装完了とは扱わない。

## 4. Capsule・共有は採用した訳文も固定する

保存時に、原記録pinに加え、表示に採用した翻訳版と本文を固定する。原文・訳文の訂正で、保存済みCapsule・共有版・コミュニティ固定掲載を暗黙に差し替えない。現行の明示的な取得元更新・共有反映を使い、原文更新、翻訳更新、Capsule独自の編集を別に比較する。公開停止の確認は既存どおり別に行う。

## 5. 自動翻訳は段階導入する

まず原語の保存と、原文訂正／訳文訂正／引用訂正の対象を分ける。その後、日英の名称・短い関係文・Theme見出しなど、効果の見える範囲から表示訳と訂正を接続する。全量の事前翻訳や全言語対応を先行完成の条件にしない。

翻訳は投稿審査とは別用途のjobとし、既存のproject利用枠・予約・実使用量・失敗／再試行管理へ接続する。原文版／hash・項目・訳先言語・必要な周辺文脈／用語集の版・翻訳条件を再利用キーにし、閲覧ごとに再推論しない。変更箇所と必要な文脈を送り、無関係な私有Capsuleや会員情報を外部へ送らない。

資料が主張を支えるかの審査と、訳が原文と同じ意味かの評価は分ける。否定・時期の曖昧さ・役割・範囲・固有名詞を評価に含める。未翻訳／枠待ち／失敗でも原文を読める。現在の既存budgetが、翻訳専用用途・cache・多言語精度まで実装済みという意味ではない。

## 次に合意・実装する範囲

推奨する次の単位は、原語情報と翻訳参照の保存契約を確定し、「日本語原文＋英訳だけの訂正」「英語による事実訂正」「原文引用だけの訂正」の三経路を分けて通すこと。最初の翻訳対象、開始方法、AI訳の表示条件、共有時の訳の選択は、その実装前に短く決める。U6のEntity同一性・Chat取込でもこの分離を踏まえたschemaを選ぶ。
