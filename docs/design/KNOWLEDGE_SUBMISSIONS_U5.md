# U5：利用者の知識投稿（着手・未完了）

2026-11-03。[採用済み統合計画](PLUNODE_PRODUCTION_INTEGRATION.md)のU5を進める。今回できたものは、実AIの小さい比較評価と、公開原記録から隔離した投稿データ層。**利用者向けの投稿画面・認証付き投稿API・自動審査・受理・通知は、まだ利用できない。** [評価・検証・現在の環境](../verification/KNOWLEDGE_SUBMISSIONS_U5_20261103.md)参照。

## 維持する判断

- 利用者投稿の受付・審査中・修正依頼・部分結果・取消・本人通知を残す。運営収集の全件管理者承認の省略と混ぜない。
- 未受理の投稿を公開Recordへ登録しない。投稿待ちの訂正で既存の公開版を差し替えない。
- 草稿は根拠なしでも保存する。公開Recordの根拠必須schemaは緩めない。根拠なしを虚偽・荒らしと同一視しない。
- AIは提示された抜粋の支持・投稿の適否を別々に判定する。抜粋を資料本文と照合したこと、事実の正しさ、公開受理とは別。
- AI停止・混雑・未評価の接続は待機理由とし、不受理や未チェック公開へ変換しない。

## 今回の投稿データ層

`lib/domain/knowledge-submission.ts`、`lib/server/knowledge-submissions.ts`、追加migration `003-submissions.sql`。既存001／002を変更しない。003の適用は今回は使い捨てテストDBだけ。3200／β／3276の保存DBへは未適用。

| 保存物 | 意味 |
| --- | --- |
| submissions | サーバー認証から受け取るowner UUID、現在の内容版、状態版、draft／queued／cancelled |
| submission_revisions | 元入力JSONと正規化した内容、内容digest、時刻。内容版は追記し上書きしない |
| submission_receipts | 提出した内容版とdigest。後の編集を過去の提出へ付け替えない |
| submission_requests | ownerとrequest IDごとの操作応答。同じ操作の再送は同じ応答、異なる内容なら409 |

`save`は内容版を進めて草稿へ戻す。提出済みの古い版は保持する。`submit`はその版をqueuedへ、`cancel`は取消へ進める。取消済みの投稿は復活させず、やり直しは新しい投稿として扱う。`expectedVersion`は内容変更・状態変更の双方を検出する。再送が返すのはその操作時の応答であり、クライアントは最新状態を別途取得する必要がある。

内容には複数項目、具体的な関係語、対象・資料、観測した既存対象版、訂正先の観測版、複数の時間注釈・根拠を保持できる。今回の上限は20項目／128KB、ownerごと取消済みを除く100投稿。型で保証することと、資料の支持・対象同一性の審査を分ける。

**これは内部repositoryであり、本人認証を実装したWeb APIではない。** `ownerId`をクライアント本文から渡すadapterを作らない。現在は外から呼べるrouteもworkerもない。一般投稿にcollection権限を渡す経路や、公開原記録の変更処理は追加していない。

## AI評価から得た判断

既存Kev 0.8Bの公開APIと、ユーザーが一時停止を承認した既存4B NF4実験を使用。共有Kevのソース・設定・ネットワーク・モデルを置換せず、評価後は0.8Bへ復帰した。

- 0.8Bは今回の二形式で正常な投稿と荒らしを安定して分けられず、自動受理の候補から外す。
- 4Bの二択形式は開発用20件で投稿適否が20/20。限定された一次判定の候補として継続評価する。実運用の誤検知率を測れた意味ではない。
- 根拠の支持は両形式とも18/20。二択形式では宣伝文・罵倒文を支持ありとする誤りがあり、投稿適否では両方を除外できた。支持判定だけで受理しない。
- 正常な引用・書籍名を含む少数の仮想ケースであり、独立holdout・長文・多言語・本物の資料取得／抜粋照合・実会員入力の評価は残る。確率を事実の信頼度や校正済みの受理閾値へ読み替えない。
- `knowledgeReviewAutoAcceptance.enabled`はfalseを維持する。4Bの採用・常駐切替・全件人手審査への変更を決定したものではない。

このPCのGPUでは既存手順が0.8B／4Bの同時常駐を避けている。**投稿のたびに共有0.8Bを自動停止する実装はしない。** 当面は4Bが利用可能な評価窓に有限バッチを実行する接続を候補とし、通常運用の利用時間・他サービスとの共存は先に詰める。今回は単発評価の許可であり、定期停止や恒久変更への許可へ広げない。

## 次の実装（U5を完了するために必要）

1. 実会員の直接入力／所有Capsuleの選択部分を、同じ投稿内容へ変換する。Capsuleの保存版・選択・元入力をサーバーで捕捉し、本文や共有範囲を変更しない。Origin、owner、現在session、会員停止・退会に伴う取消と私有入力消去、連投制限、履歴／一覧を接続する。この段階まで未接続のrepositoryをβの完成機能と扱わない。
2. 非同期job／試行／lease／送信結果と利用量を分離する。版変更・取消・古い応答・送信済み応答喪失を通し、推論の無条件再送を防ぐ。4B停止中は待機の理由を返す。日次／月次／一仕事の予約・精算はU6と共通に使える必要部分だけを実装する。
3. 未見ケースと実資料で、荒らし・引用・根拠不足・矛盾・意味変更・資料中の指示を評価する。受理方針はサーバーに固定し、AI出力・閾値だけで自由に公開できるようにしない。認証済みの受理結果と共通原記録・操作receipt・投影依頼を同じ知識DB transactionへ接続する。既存`execute()`をuserからoperatorへ偽装して呼ばない。
4. 修正依頼／意味が変わる補助の本人確認／一部受理・残件理由／受理先ID／通知／公開投影を接続し、βの実Googleで一巡する。運営者の例外確認を、収集全件の管理者承認へ流用しない。

残り指示回数の推定は**基本2〜3回以上**。次の一回は実会員の投稿画面・受付APIと、取消／停止／退会の境界。その後は実AIの有限処理・利用量・受理結果とβ総合確認。4Bの通常運用や実資料評価で不成立が見つかれば追加が必要で、U5完了予定を固定しない。

推奨担当は通常実装を引き継げるSol 6.1高。AIの共存・受理方針が既存契約で成立しない具体的な点だけ横断設計へ戻す。U6の運営収集、U7の移行受入、U8の本番公開は今回完了していない。
