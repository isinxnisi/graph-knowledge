## 維持する判断

- 利用者投稿の受付・審査中・修正依頼・部分結果・取消・本人通知を残す。運営収集の全件管理者承認の省略と混ぜない。
- 未受理の投稿を公開Recordへ登録しない。投稿待ちの訂正で既存の公開版を差し替えない。
- 草稿は根拠なしでも保存する。公開Recordの根拠必須schemaは緩めない。根拠なしを虚偽・荒らしと同一視しない。
- AIは提示された抜粋の支持・投稿の適否を別々に判定する。抜粋を資料本文と照合したこと、事実の正しさ、公開受理とは別。
- AI停止・混雑・未評価の接続は待機理由とし、不受理や未チェック公開へ変換しない。

## 本人の受付と保存先

入口は `/member/submissions`。アカウントの活動・履歴「知識の投稿」、または本人の保存済みCapsule下部「知識を投稿」から入る。Capsuleからは別タブで項目を選び、最大20件を草稿へ取り込む。本文・具体的な関係・範囲・肯否・時期・根拠を編集し、草稿保存または「保存して受付」を選ぶ。草稿だけなら根拠なしでも保存できる。

受付後の編集は新しい草稿になり、以前の受付対象版へ付け替えない。取消は確認後に行い、取消済みの内容を勝手に復活しない。読み直しただけで日時・並び順を変えない。今回のβでは「受付済み・AI処理の接続待ち」と表示し、まだ審査／公開が動いているように見せない。

### 会員DBを非公開投稿の保存先にする

追加migrationは **`db/member/020-knowledge-submissions.sql`**。会員DBの専用schema `member_knowledge` に保存する。認証から得たownerのuser行を同じtransactionでlock・再確認し、停止・退会・同時保存の境界を一つのDBで成立させる。受理前の本文を公開正本へ置かない。

| 保存物 | 意味 |
| --- | --- |
| submissions | owner FK、内容版、状態版、draft／queued／cancelled。本人userの削除でcascade |
| submission_revisions | 元入力、正規化した内容、digest、選択したCapsuleの取得断面。内容版は追記 |
| submission_receipts | 受付時点の内容版・digest。後の草稿へ付け替えない |
| submission_requests | owner＋操作IDごとの応答。同じ送信の再試行は同じ結果、内容変更なら409 |

`lib/server/knowledge-submissions.ts` のmemberStoreを、`lib/server/member/knowledge-submissions.ts`の認証付きadapterから使う。従来の知識DB用003・prototype modeは先行の隔離試験の再現用であり、βの保存先に使わない。適用済み003は書き換えず、βの知識DBへも適用しない。

保存上限は20項目／128KB、取消済みを除く100投稿、100内容版／投稿、ownerの保存容量と操作回数を有界にする。短時間の操作制限中でも取消は可能。退会は本文・取得断面・再送応答をFKで削除する。停止はDB triggerで草稿／受付を取消し、再開しても旧受付を復活させない。受理後の公開原記録まで退会cascadeで消す設計にはしない。

### 認可とCapsuleの捕捉

- APIは `/api/member/knowledge-submissions`（本人一覧／操作）、`/[id]`（本人読取）、`/capsule?capsuleId=`（候補）を使う。Origin、現在session、active user、表示中のX-Member-User、本文stream上限を確認。owner・公開権限・受理状態を本文から指定できない。他人の有無は404へ揃える。
- CapsuleのID・保存版・選択keyだけを受け、同じ会員DB transactionで本人の現在保存版を再取得する。別版なら409で選び直す。クライアントのsnapshotを信頼して取り込まない。
- 選んだ記録と必要な両端・資料だけを捕捉する。選ばなかった自由メモ・関係・Capsule全体の私有説明は含めない。元のCapsule・共有範囲を変更せず、共有版を新規発行しない。
- 原記録ID・取得版は保持し、既存記録なら訂正候補のpinを添える。作者の具体語・本文・肯否・範囲・時期を保ち、未知語を旧ENUMへ落とさない。共通資料の版はsourcePinsで固定する。
- KGの保存済みcitation・Capsule独自資料の題名／URL／箇所を再利用するが、**引用ではない作者noteを原資料の抜粋へ昇格させない**。原note・元のKG詳細は取得断面に保持する。抜粋が未取得なら空のまま補足できる。
- この捕捉は本人の非公開草稿であり、参照の真正性・現在公開可否・Entity同一性の受理ではない。公開時の原本照合・権限再確認と受理transactionは次工程へ残す。

## 本人依頼からAI結果まで（追加021）

会員DBの追加 `021-knowledge-review-jobs.sql` は適用済み020を変更しない。受付版・項目key・digest・送信確認の版を固定したjobと、送信試行・privateなwire／応答・project利用枠を分ける。通常保存、従来の受付、過去の投稿からjobを自動で起こさない。本人が画面で送信対象を確認したときだけ、認証付き `review` 操作で冪等に作る。

現在は日本から利用する18歳以上の指定β検証協力者に限定した無料APIの試験接続。サーバーのuser ID許可リストを使い、一般ユーザーへ一括解放しない。画面で公開予定の知識と根拠だけをGoogleへ送ること、機密・個人情報を含めないことを確認し、Google側の改善利用／人による確認の可能性を送信前とprivacyで案内する。[Googleの条件](https://aistudio.google.com/docs/terms)に合わせ、一般提供時の年齢・地域条件と送信対象の管理はU8前に別途確認する。Geminiへ会員ID・名前・メール・共有tokenや、捕捉断面全体を渡さない。

Workerは既存Web保存と独立したlocal processで、既存launcherから再開する。DBのuser→submission→jobを短くlockし、HTTP中はlockを解放する。lease失効は消費の可能性を残して120秒以上の間隔で再試行する。受信済みの応答を保持できていれば再推論せず、その応答から状態更新を再開する。送信は1job最大3回。通信・接続設定・未評価モデルは内容の不受理と分ける。取消・新しい草稿・停止で古いleaseを無効にし、遅い結果を現在版へ付け替えない。

projectのminute／day／monthと仕事の送信回数をDBで予約し、取得できた実使用量で精算する。出力・推論量が欠測なら出力予約を保持する。日付はproviderのAmerica/Los_Angelesで区切り、429のRetry-After・project停止・枠待ちを尊重する。既存評価63送信も同じ台帳へ一度だけ取り込み、同projectの旧online評価CLIを止める（offline再採点は可能）。新しい課金・別keyへの切替・未評価providerへの自動fallbackはない。上限は今回の保守的なPlunode側制限であり、Googleが保証する残量の表示ではない。

本人画面には項目ごとに待機／接続再試行／補足依頼／AI確認済みを示す。5秒の結果更新はprivate入力やdirtyな草稿を作り直さない。`reviewed`は提示した抜粋とのAI整合確認であり、原資料と一致した証明や公開完了ではない。次工程で原資料・参照・同一性を確認して通常分を自動受理へ進める。全件人手承認へ戻すための状態ではない。

Kevは草稿の項目ごとに任意のヒントとして公開local APIを呼ぶ。保存済み版だけが対象で、失敗・警告・無視をGeminiの判定材料へ加えない。4回／10分の本人制限と15秒の応答期限を設ける。共有Kevの設定・起動停止・モデルは変更しない。

## 採用する自動化の方針（2026-11-03更新）

ユーザーの補足に基づき、**通常分はAIの確認から自動受理・公開へ進み、全件の人手承認を挟まない。** 完全な無誤判定を待って停滞させず、小さい実評価、版と根拠の確認、利用量制御、訂正・取消・例外救済を実装して進める。運営収集の管理者承認省略とは別の投稿処理である。

| 段階 | 利用者の体験・権限 |
| --- | --- |
| 機械検証 | 必須項目・容量・権限・連投等を確認。単語の部分一致だけで作品名・引用を禁止しない |
| Kev 0.8Bの任意助言 | 送信前の気付きとして表示。ユーザーは修正しても、そのまま進んでもよい。停止・失敗も送信を妨げない。指摘の無視を不利な審査材料にしない |
| Geminiの非同期確認 | 提示された根拠と主張の整合、投稿適否を確認。正常かつ全体が支持される内容を通常の自動受理対象とする |
| 補足・拒否・例外 | 不足・曖昧は理由を添えて自動修正依頼。荒らし等は自動不受理と救済導線。誤判定の異議や運営処置だけ必要に応じて例外対応 |
| 通信失敗・利用枠待ち | 内容への判定と分けて待機・再開。未チェックの公開や、全件の人手確認へ置き換えない |

0.8Bは先行評価で自動受理の判定器には不十分だった。コードでも `kevReviewAuthority` を非阻止の助言とする。4Bは単発実験で改善したが、共有0.8Bを投稿のたびに止める案は採らない。4Bの常駐切替・追加停止はしない。

### Geminiを通常処理の候補として採る根拠

既存の無料プロジェクトと `gemini-3.5-flash-lite` で、先行20件と別の40件を評価した。正常20件中18件が自動受理候補。不適切・根拠不足・矛盾等の40件を誤って自動受理した例は0。最終59/60件で有効な回答を得た。事前に決めたこの小さい評価の接続基準を満たし、**Geminiによる通常自動受理へ接続する実装を進める**。実運用の誤受理率ゼロを保証する結果ではない。

残りは正常な引用の差し戻し1件と応答不明1件。支持の4分類は47/59件で期待値と一致し、`unclear` と `contradicted` の取り違えもある。AIの説明を真偽確定として表示せず、「資料の補足・確認が必要」という提案として扱う。詳細・失敗・token・固定hashは[実測記録](../verification/KNOWLEDGE_GEMINI_U5_20261103.md)に残す。

### 実装した接続部品と、まだ接続していない境界

- `lib/server/gemini-knowledge-review.ts`：固定HTTPS先への1回の送信、構造化結果、終了理由・実行ID・モデル・usageの検証。AIに公開権限や外部ツールを渡さない。
- `lib/domain/knowledge-review-outcome.ts`：通常の `legitimate + supported` を `accept`、不足を `request-changes`、荒らしを救済可能な `decline` とする純粋な結果ルール。取消・古い内容版・参照不可は破棄し、応答待ちを不受理にしない。**受付から明示依頼したAI jobまで接続。公開処理は次工程。**
- `scripts/evaluate-gemini-knowledge-review.ts`：仮想評価専用の有限CLI。project単位のローカル台帳、送信前予約、取得できた実使用量、応答不明の予約保持、途中再開・offline再採点を備える。評価CLIは本番の永続job queueではない。βのjobとDB利用枠は別実装で、導入後は旧CLIの同project online送信を拒否する。

受理時には同じtransactionで会員状態・投稿の現在版・利用できる参照・AI結果の対象hashを再確認する。AIの `accept` だけで公開するrouteや、クライアントが `assessedProfile` を指定するAPIは作らない。根拠抜粋と原資料の一致は別の自動工程として接続し、取れない資料は補足・別資料の指定を返す。今回の評価は入力された抜粋との整合までで、元URLを取得した実証ではない。

### 無料枠・再試行・差し替え

- 利用回数・token・送信結果をモデル実行と分け、用途・project・日次／月次／仕事ごとの予約と精算を記録する。無料枠の実値は環境から確認し、固定の恒久上限としない。
- 429はRetry-Afterとproviderのリセットを尊重する。通信結果不明は消費ゼロにせず記録を残し、待ち時間と回数上限を持つ新しい試行へ進む。再推論しても公開のreceiptは重複させない。
- 枠切れ時の基本経路はqueueでの待機・翌枠再開。利用者は編集・取消できる。無断課金や別キーでの枠迂回はしない。
- provider固有の送信・応答と投稿の結果ルールを分ける。将来、同じ評価を通した別AIへ差し替え可能にする。今回は有料fallbackも未評価モデルへの自動切替も有効化しない。
- Gemini無料APIのデータ条件に合わせ、実投稿を送る段階で対象データ・ユーザー範囲を定める。今回の送信は非機密の仮想データのみ。私有Capsule本文や会員情報を送っていない。

## 受付から後工程へ渡す際の注意

- `source_capsule.captured` は取込時の由来を説明する記録であり、後から草稿で外した項目も初期断面に残り得る。AIへ送る対象・受理する対象は、受付receiptに固定された**現在のcontent.itemsとそこから到達する資料・対象だけ**とする。捕捉断面全体を一括送信・一括公開しない。
- 捕捉したKG由来の型付き限定・役割等は原断面にも残る。具体的な関係名だけへ平坦化して受理しない。訂正候補の原記録版・両端と資料版を照合し、既存の意味を失わせない。
- 根拠の抜粋欄の入力や既存データは、原資料との一致を検証した証明ではない。URL／箇所からの照合、引用と要約の区別は次の原資料工程の責務とする。
- 取消済みの試験投稿を、後からqueueを有効にした際のbackfill対象にしない。現在のstateと版・会員状態をjob作成／受理時の両方で確認する。
- 会員DBの私有投稿と共通知識DBの公開正本は別DBであり、両者を単一SQL transactionで更新できるとみなさない。次工程では会員状態・取消・内容版を確定する側と、公開正本／公開receipt／投影outboxを確定する側を分け、固定decision ID・再送・途中停止からの収束を実証する。一般公開の経路はこの境界の検証まで有効化しない。

## 次の実装（U5を完了するために必要）

1. 原資料の取得・抜粋との照合、同一性と参照の現在認可を接続する。取れない／一致しない資料は、理由を添えて別資料・抜粋の補足へ戻す。通常の自動受理を全件人手承認へ置き換えない。

残り指示回数は**あと1〜2回程度**の推定。次の主工程は原資料照合と通常自動受理・公開の接続で、総合確認と不具合修正の量で増える。U6収集、U7移行受入、U8正式公開は別工程。
