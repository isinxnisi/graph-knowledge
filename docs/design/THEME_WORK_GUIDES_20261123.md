**既存の2工程を保ち、ChatGPTが選んだ作業に応じて、共通原則・その作業の判断基準・必要な技術契約をまとめて読めるようにする。** 一つの起動で年表の構成、根拠の確認、改稿、翻訳、登録まで進めてよい。サーバーの責務は現在の事実を返し、書込み・公開の条件を保証すること。作品の何が弱いか、次に何を深めるかは編集者が判断する。

## 2. 案件状態・作業ループ

| 何を表すか | 正本と使い方 |
| --- | --- |
| 担当と案件の状況 | 現行のworkflow、phase（production／review）、status。scheduledは既存の逐次選択、manualは明示caseId。handoffで制作のleaseを解放し、別の起動がreviewをclaimする |
| 誰が今書けるか | 起動ごとに一つのexecutionId。claimで得たleaseTokenと最新expectedVersion。既定15分、期限前にrenew。busy・担当外では待つ。期限切れで仕事を完了扱いにしない |
| 何に集中するか | 現行のbrief・scope、artifactsのreaderOutcome・proposedArc・workLoopを使う。focusの値は案内のヒント。任意の補足として「確認に使った対象版／成果物参照／次に確認する差分」を記録。旧形式・欠落でも現物から再開できる |
| 何が残るか | 必須で実行可能な仕事はunfinished、外部条件が要るものはblockersに理由と再開条件。任意の磨き込みは必要なものだけartifactsに残す。資料・外部指示・過去の自己評価は証拠または引継ぎ情報として読む |
| 何を送信・反映したか | submissionId、保存済みwire、登録requestId、受付状態とreadback。結果不明では同じ受付を照会・回復。prepared／acceptedは反映の証拠にならない。画像生成のautomationIdも独立に追跡する |
| 何を評価・公開したか | evaluationTarget・whole-theme assessment・公開intent・実際の承認release・公開言語の到達確認。完了の履歴はそのreleaseに結び付け、後日の公開版やガイド改訂で完了案件を再び定期枠に戻さない |

**1回の流れ**。本番接続を確認→該当工程を取得・claim→未決送信・競合・確定済み公開を照合→読者に約束した内容と実物を比較→いま価値があり着手可能な仕事を選択→必要なガイドを取得→関連する調査・編集・反映・確認をまとめて実行→まだ進めるなら同じ起動で次の仕事へ。ガイドを読むだけでは案件状態を変えない。制作はhandoffでその回を終え、見直し専用起動は年表を単体で読むところから始める。見直し側で必要になった追加調査・修正はreview内で行える。

**保存するタイミング**は復旧コストで決める。外部送信前には既存prepare、応答後には安定した参照、長い調査の区切りには次回が利用できる原稿・根拠、待機時には具体的な残件を保存する。フォーカスを変えるたびの書込みは不要。現行saveはprogress全体置換なので、最新値を読んで既存キーを保持する。送信の操作IDと内側の登録IDを区別し、ページングした未決受付を含めて回復する。期限を失った後に書けなかったメモは保存済みと扱わない。

**やり直す単位**。資料の訂正で出来事の日付が変わったら、年表の並び・期間、該当Recordのピン、関連するStory・日英訳・画像の場面を点検する。画像だけを差し替えたら、該当行・詳細・拡大・alt・クレジットを確認する。無関係な資料の再調査は不要。どちらも対象digestが進めば、合格前に最新の画面とテーマ全体を再評価する。通常編集が並行公開された場合は、旧公開版・現公開版・作業版を照合し、正確なrevision／releaseIdでreconcilePublishedを送る。単なる再試行では解消しない。

**停止と再開**。1件の素材待ちでも他の独立作業が可能なら続ける。進められなければ同じ案件・phaseでsave／release。後続回は実物、受付、待機条件が変化したかを確認し、結果不明の生成を繰り返さない。同一阻害が続く場合は阻害の原因と運営判断点を一度示す。回数による自動合格・自動放棄は設けない。見直しでは年表の重要な欠落はneeds-changes、任意の改善は公開後の候補。必須の未確認をexceptionsへ移すだけでpassにはできない。

## 4. 本番App経由のAPI・版管理契約案

1. **取得**。`read_theme_work_guide({phase, focuses, caseId?, profile?, knownVersions?})` を追加する。案件作成前の選定にも使える。caseId付きなら運営者・環境を照合し、実phaseとの不一致を返す。応答は契約版、共通原則と必要な節（安定したkey・revision・本文）、該当する技術契約、適用した補助、評価基準の識別子、関連作業を示す。必須部分はサーバーが加える。履歴・全案件・全操作schemaは通常応答に含めない。同じ起動で既読の版は識別子だけを返せる。別の起動や本文を失ったクライアントは本文を再取得する。独立見直し開始時は年表と読者への約束を先に提示し、制作側の結論を合否の初期値にしない。未知のfocus・契約版では対応キーと全文取得先を返し、必須基準を落として続行しない。
2. **改訂**。`update_theme_work_guide({expectedRevision, requestId, reason, changes | restoreRevision})` は複数節を一つのトランザクションで改訂する。運営が明示的に依頼した通常Chatから実行できる。保存→別読取で確認する。対象版が違えば競合として再読し、同じID・入力だけを再送可能にする。変更箇所、操作者、理由、影響区分、復元元を保存する。版指定読取・履歴ページング・過去版を新しい版として復元する方法を本番Appに提供する。フォーカスと節の対応や補助ルールの停止もこの管理対象。入力schemaそのものはコードの版管理に残す。
3. **最小の保存単位**。環境内に一つのガイドIDを維持し、版ごとに節の順序と参照を持つ目録を保存する。節はkey・種類（必須基準／手順・例示／モデル補助）・本文・適用範囲・内容の版を持つ。必須基準は全テーマ共通を初期仕様とし、手順内に追加の合格要件を隠さない。モデル別補助は観測理由・見直し日・無効化も持つ。評価・証拠の一致確認にはサーバー計算の識別子を使う。案件・評価には読んだ版の参照だけを残し、ガイド全文を複製しない。
4. **旧APIとの互換**。`read_theme_quality_guide` と `get_theme_authoring_guide` は従来の全文と単一revisionを返し続ける。一つの保存内容から旧形式を組み立てる。旧版のMarkdownはそのまま読める。旧 `update_theme_quality_guide` の全文更新・復元も保つ。新旧書込みは同じ期待版・受付台帳・ロックを使う。**旧APIから節に対応づけられない自由形式全文が保存された場合**、勝手に自動分割せず、その全文を当該版の正本として新旧双方へ返す。旧補助や旧節を混ぜない。影響不明は必須改訂として扱い、運営がAPIから再整理するまで全文モードで継続する。旧本文のサイズ制限を含む従来契約を壊す保存を避ける。
5. **改訂の効き方**。監査用の「本文全体のrevision」、合否用の「必須基準の版」、採取用の「必要な画面・操作の仕様版」を分ける。必須本文の変更はサーバーが必ず基準版を更新する。誤字・例示・モデル補助の変更で基準を変えたくなければ、該当する補助・例示領域だけを直す。編集者が任意に「軽微」と付けて必須改訂を回避できるAPIにはしない。全体revisionはどの場合も進む。復元も新しい監査版とし、失効した古い合格が自動復活しない設計にする。

| 変化 | 進行中案件・合否 | 画面証拠 |
| --- | --- | --- |
| 補助・例示・通常手順だけ改訂 | 次の該当作業で新版を取得。対応版の評価は維持 | 再採取不要 |
| 必須の編集基準が改訂 | 次の境目で変更点を取得。未確定の公開は最新基準で独立全体再評価。調査済み資料と原稿は保持 | 対象・build・採取要件が一致する既存PNGは再利用可。そのreview起動で再読・視認 |
| 画面の必須操作・対象言語条件が変化 | 評価に新しい証拠が必要。最終評価を更新 | 必要な画面を満たす新しい一式を採取 |
| テーマのdigest、公開元、Web buildが変化 | 内容変更は現行digestとworkDigestで全体再評価。後発公開は既存の調停手順。build変更は表示を再確認 | digestまたはbuild変更時は再採取・再視認 |

更新影響の判定は取得APIだけに置けない。**評価保存、complete、未確定intentのactivation、証拠の採取・取得、再送回復で同一契約を使う**。改訂と公開が重なる場合はガイドの必須版の確定と承認確定の順序を直列化する。既に承認されたreleaseは過去の証明を保持する。公開後確認に失敗したらURL・言語・版・失敗種別を残し、公開処理をむやみに再実行しない。公開待ちの再送は既存の正確なretryCommandだけを使う。

## 5. 画像を扱う例

**黒澤明の名誉賞**。年表で重要なのが「世界の映画人との関係が授賞の場に現れた」点なら、候補は授賞の行。まず何を読者に見せたいかを決め、人物・場所・役割を資料で確かめる。利用条件が合う式典写真があれば来歴と指定クレジットを保存する。象徴的な写真を読者が知っている場面では、似ていない疑似報道写真にも、元写真をそのままなぞった絵にも違和感がある。独自構図・色彩の再現画に編集価値があり、権利と事実表現を説明できる場合に選ぶ。再現である旨は画像外の日英の説明に置く。確信が持てなければ文章で届ける。

**Nas『Illmatic』**。発売の行で見たいものが「あのジャケットそのもの」なら、権利未確認のジャケットやそれらしく描き直した顔を採用しない。一方、「複数のプロデューサーが異なる曲で一つの作品を形づくった」という制作の行なら、根拠のある曲と人物の対応を短い固有名で示す図解に固有の価値がある。発売と制作は別の出来事なので、入手できた図を発売行へ移す理由にはならない。いずれも実写真・オマージュ・図解・画像なしに採用比率を設けない。

**実行のつなぎ方**。選んだRecordの正確なid・revision、対象言語、見せたい内容、権利と代替案を引継ぐ。生成を選んだ場合は原則3:2横長、画像内の文章は極力省き、必要な固有名・関係だけを短くする。生成指示の中心は被写体・出来事・構図。詳説・日英alt・クレジットは画像外に置く。既存imageIdや未決automationIdを確認し、必要時に一度だけ生成を依頼する。readyのimageIdを、既存のprepare→dispatchで対象言語の同一Recordへ紐付ける。サーバーガイドにはgeneratedImage.targetがあるが、今回Codexに公開された本番Appツール定義にはtargetがなかった。利用側の定義を確認し、正式imageIdを各言語のpresentation.recordsに指定する既存経路も案内する。登録、読戻し、年表行→詳細→拡大、クレジット、日英・PC／スマホの観察を分ける。回復可能な入力エラーは元の受付を修正し、登録失敗を理由に再生成しない。

## 6. 互換移行と復旧

1. **比較基準を保存**。実装時点でもう一度、2予定の原文・本番ガイド・公開されているツール定義を読み、どの指示を起動指示・必須原則・作業ガイド・技術契約・補助へ移すか対応表を作る。既存の約束を削除しないことと、二重に保存しないことをレビューする。
2. **βで読取・編集契約を先行**。現行全文を固定版として保持し、旧予定はそのまま使う。新旧ガイドを同じ案件から読み、その時点で必要な判断が新しい応答からできるか比較する。編集・競合・再送・復元を、専用のβデータでChatGPTから往復する。原文の整理とサーバーの安全条件・証拠契約の試験は並行できる。
3. **完了条件の切替は案件単位**。既存案件・評価・保存済みintentは旧契約のまま精算する。バージョン未記録は旧方式と解釈する。新方式は対応クライアントが明示した新案件から有効にする。既存のworkLoop v1は無変換で読める。caseの方式は後続のreviewも引き継ぐ。旧式の書込みでは新方式の合格条件を省略できない。両予定が対応するまで新方式のscheduled案件を作らない。
4. **本番は追加配備→ツール読み戻し→両予定の移行**。本番Appで対象ツール・契約版・入力schemaと旧APIを確認後、ユーザーとChatGPTが両予定の文章を更新・読み戻す。見直し側を先に新旧両対応とし、制作側が新方式を開始する。予定時刻・既存資料収集・通常Chatの運営編集は独立。旧予定に戻す場合も新規案件の方式選択を止め、開始済み新方式の案件は対応版で完了させる。未確定公開を戻す目的で古いpass・新規案件・通常公開を使わない。
5. **運用完了**は、新方式の一つの案件が制作予定から独立見直し予定へ渡り、実画面と最新評価を照合できた時点。公開した場合は日英の正規URL・提供版・canonical等を確認する。要修正の案件は継続し、通信成功だけで移行完了にしない。旧方式で公開済みの完了案件が後の訂正・ガイド改訂でも次回制作を塞がないことを確認する。
