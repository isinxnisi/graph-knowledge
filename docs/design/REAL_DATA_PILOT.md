# 少数実データパイロットの設計案

2026-10-03。条件付き探索の実装後、実在の関係で探索の価値を検証するための提案。**対象候補と受入契約の設計までで、採用確定・収集完了・データ投入完了ではない。** コード、API、Neo4jモデル、demo fixtureは変更していない。

[現在地点](CURRENT_STATE_AND_NEXT_PHASE.md)の「実データ投入前に決めること」を具体化する。現行契約は[ARCHITECTURE](../ARCHITECTURE.md)、目的は[PROJECT_CONTEXT](../PROJECT_CONTEXT.md)を優先する。

## 推奨範囲

**浦沢直樹の作品と制作関係者を中心に、まず人物4名・漫画作品3件・関係8件程度から始める。** 同じ作品から別の人物へ移り、その人物から別の作品へ辿れるまとまりを優先する。人数を埋めるために根拠の弱い関係を採用しない。

| 段階 | 提案する規模 | 意図 |
| --- | --- | --- |
| 最初の受入候補 | 4人物 / 3作品 / 8関係・8 Claim / 3 Source以上 | 小さな連結成分で、検索・作品経由の探索・根拠確認を試す |
| 同じパイロット内の追加候補 | 合計6〜8人物 / 5〜7作品 / 15〜25独立Claim / 5〜10 Source程度 | 最初の操作から足りない経路を補う。必達件数ではない |
| 組織 | 初回0、必要なら最大2程度 | 出版作品のクレジットだけから人物の所属を推測しない |

「関係」はsubject/predicate/objectが同じ表示Relation、「Claim」は期間・肯否を含む独立主張。出典追加だけなら同値ClaimにCitationを追加でき、関係数・Claim数・Citation数・Source数は一致しない。上記8件は候補の全件を受け入れた場合の見積りであり、投入結果ではない。

### 根拠を確認できた最初の候補

2026-10-03に出版社の商品情報を確認した。まだ個々のQID確認・保存用データ作成・最終受入審査はしていない。

| 漫画作品 | CONTRIBUTED_TO候補 | 確認した資料と限定 |
| --- | --- | --- |
| PLUTO | 浦沢直樹、長崎尚志、手塚眞 | [小学館・第1巻](https://shogakukan-comic.jp/book?isbn=9784091874313)。制作クレジット、プロデュース、監修を確認。原作由来は別扱い |
| MASTERキートン | 浦沢直樹、勝鹿北星、長崎尚志 | [小学館・完全版第1巻](https://shogakukan-comic.jp/book?isbn=9784091841612)。当該版の制作・脚本クレジットを根拠にする |
| BILLY BAT | 浦沢直樹、長崎尚志 | [講談社・第4巻](https://www.kodansha.co.jp/r/comic/product?item=0000014047)。著者とストーリー共同制作の記載を候補根拠とする |

作品Entityは漫画作品全体を表し、巻・版・ISBNは引用対象の書誌情報として区別する。「この漫画に制作関与した」という限定的な主張にし、「全巻の作者」「同じ役割で全期間関与した」とは読まない。当該巻・版にしか成立しない内容を作品全体の関係へ一般化する必要がある場合は保留する。漫画とアニメ、続編、再編集版は同じEntityとしない。作品QIDへ特定の巻のISBNを外部IDとして付けない。

PLUTOに手塚治虫のクレジットがあることだけで、手塚治虫→PLUTOの現行「制作に関わった」を作らない。原作・翻案の由来を表す適切な関係が今回はないため保留する。手塚プロダクションの協力も、現行person→workのpredicateへ無理に変換しない。こうした未採用のクレジットは収集記録に保持する。

追加候補は[小学館のパイナップルARMYシリーズ情報](https://shogakukan-comic.jp/book-series?cd=16896)で確認できる工藤かずや・浦沢直樹の制作関与など。最初から全作品一覧を収集しない。

## predicateの受入方針

| predicate | 初回の扱い | 根拠・禁止する推論 |
| --- | --- | --- |
| CONTRIBUTED_TO | 主軸。人物→漫画作品 | 公式制作クレジット等。脚本・作画・監修・プロデュースの原表記を残す。現行辞書は役割を区別せず、作者を自動推定しない |
| INFLUENCED_BY | 追加で1〜3件を目標、資料を確認できた場合のみ | 人物→人物の明示的な本人インタビュー等。「作品に影響された」をその作者への影響へ置き換えない |
| ASSISTANT_OF | 初回必須にしない | 当事者の証言・公式経歴など制作補助を明示する根拠。「師匠」「親交」「同じ職場」から推定しない |
| AFFILIATED_WITH | 初回必須にしない | 人物と組織の具体的関与を示す資料。出版社が本を出しただけで著者の所属・雇用にしない |

全predicate、否定、異なる期間、複数出典を実データに無理に揃えない。初回の制作関与だけでは条件選択の実用価値を十分比較できないため、明示的な人物間の影響関係を探す小さな追加調査を行う。それでも確認できなければ「制作経由の探索の価値だけを検証した」と報告する。taxonomy、新predicate、work→work影響は別フェーズ。

## Sourceと根拠

初回の公開Claimは、少なくとも1件の、主張を支持すると人が確認したCitationを必須にする。検索結果の断片や出典不明の転載だけで受け入れない。出典未確認・受入保留は収集記録に残し、公開Claimにはしない。検索・クレジットだけで否定を作らず、deniedは否定を明示する資料がある場合だけ独立登録する。

- Sourceは実際に確認した資料。出版社Webページならkind=web、ページタイトル・発行主体・URL・判明する公開日を保存する。書籍の商品ページを読んだだけでkind=bookや「書籍本文を確認済み」にしない。
- Citationは資料中の参照箇所と、そのClaimに何を示すか。クレジット欄・巻・版、役割の原表記、読み取った内容の短い要約、確認日を保持する。ページ番号は実際に確認したときだけ保存する。
- 巻のISBN、商品発売日、ページ公開日、関与期間、取得日時を別項目として収集記録に保持する。発売日をSourceのWeb公開日やClaim.periodへ転用しない。関与期間が分からなければfrom/toはnull。
- Source.isDemo=false。資料が複数Claimを裏付ける場合は同じSourceを共有し、Claim別Citationを付ける。別資料を同じSourceに潰さない。
- 同じ関係でも期間・肯否・主張内容が違えば別Claimとして保持する。GraphのRelation集約は表示だけ。登録順、Source件数、資料の著名さで真偽を順位付けしない。
- 保存は書誌情報・参照箇所・自分の要約を中心とし、表紙画像・記事全文・出版社HTML一式の再配布をパイロットの対象にしない。引用が必要な場合の範囲と利用条件は資料ごとに確認する。

訂正窓口はローカル検証では管理する人への報告で足りる。対象・根拠・変更理由を版管理に残す。一般公開するなら、公開前に訂正連絡先と対応担当を別途決める。私人・家系・センシティブな推測は今回扱わない。

## Wikidataの利用範囲とprovenance

**初回は外部ID・名称・同一性の確認に限定する。GraphのClaimは人が確認した資料から作る。** 選定したEntityだけ、QIDを確認して個別取得する。Dump、再帰的な取得、広域SPARQL、Wikipedia全文解析はしない。

WikidataはEntityの個別JSON取得を提供する。qualifierやreferenceを落とす簡略化取得は使わず、取得したEntityの原JSON・revision・取得時刻・URL・内容hashを記録する。[Wikidata Data access](https://www.wikidata.org/wiki/Help:Data_access)

| 情報 | 保存するもの | ClaimのSourceになるか |
| --- | --- | --- |
| 名前・外部IDの取得由来 | 提供元、QID、revision、取得日時、取得URL、名称の言語、採用判断 | それだけでは関係の根拠にならない |
| 出版社等で確認した関係 | Source・Citationと確認箇所、受入判断、変換規則の版 | 確認した資料が根拠 |
| 将来Wikidata statementから採用する関係 | statement ID、property、値、qualifier、rank、references、対象revision、変換・判断 | Wikidata由来と、そのstatementが挙げる原資料を区別。原資料の確認有無も別に記録 |

原資料を読んでいない場合に「原資料を確認済み」としない。Wikidataしか根拠が確認できない関係は今回は公開対象から外す。rankはサービスの信頼度ではない。未対応qualifier、somevalue/novalue、精度外の日付を黙って通常Claimへ落とさない。[Wikidata Data model](https://www.wikidata.org/wiki/Wikidata:Data_model)

Wikidataの構造化データはCC0だが、そのreferenceが指す記事・本の利用条件までCC0にはならない。提供元と確認元を記録し、資料のライセンスを混同しない。[Wikidata Licensing](https://www.wikidata.org/wiki/Wikidata:Licensing)

## ID・言語・取り戻せない情報の保存

内部UUIDを最初に割り当て、版を跨いで固定する。QIDはnamespace=wikidataの外部ID。同名や表記一致では統合せず、職種・作品・生年等の確認材料を人が照合する。QIDがなくても登録でき、判明したら対応候補として審査する。衝突・QIDの統合やredirectは収集記録に残し、自動的なEntity統合や内部UUID変更をしない。

日本語の表示名を優先し、根拠のある日本語別名、原語名、英語等の名称を**言語タグ付きで保持**する。原語名は英語labelと同義ではない。原表記、採用元、名称種別、表示用優先名を分け、手塚／手塚等の表記差を取得段階で消さない。推定読み・機械ローマ字を公式別名にしない。検索用のNFKC正規化は表示用・原名称とは別扱い。

現行Entityはname / aliasesの文字列だけで、Sourceに専用ISBN・言語欄、Claimに取得provenanceや役割qualifierはない。strictなfixture validatorも未知項目を受け入れない。**現行JSONへ追記すれば保存できる、とは扱わない。**

初回は小さな版付きファイルパッケージを推奨する。名称・由来の情報を自由文だけに押し込めず、内部IDを参照する構造化収集台帳と、そこから作る現行schema互換の投入用JSONを分ける。

| パッケージの部分 | 保持内容 |
| --- | --- |
| manifest | dataset ID・版・作成日・担当・対象範囲・変換規則版・ファイルhash、Entity/Claim/Source/Citationの固定UUID対応 |
| 名称・同一性台帳 | 内部Entity ID、確認したQIDと対象粒度、言語タグ付き原名称・別名・出所・採用判断、未確定対応 |
| 主張・引用の台帳 | 内部Claim/Citation/Source ID、資料内locator、書誌・ISBN・版・役割・原文の短い必要箇所または要約、確認日・受入／保留理由、外部statement情報があればその識別と限定条件 |
| 原取得記録 | Wikidataの取得JSON・revision・取得時刻・hash。Web資料はURLと確認箇所・確認記録を中心にする |
| 投入用JSON | 台帳から人が確認して作る、現行validatorに適合するEntity・Claim・Citation・Sourceの投影 |

ファイルは収集・変換の証跡であり、別DBに第二の運用Knowledge Graphを作るものではない。投入用JSONを別途手で更新して台帳と食い違わせない。ID参照・必要項目・出力との整合を投入前に検査する。将来のオンライン更新では運用側の名称・provenanceモデルへの移行が必要になるが、保持した構造から移せる。

これは少数の凍結パイロットに限る暫定境界。収集台帳は今回まだ作成していない。UIではSource/Citationから根拠を確認できるが、言語付き名称や詳細な取り込み履歴をAPIで閲覧できるようになるわけではない。全言語UI・provenance検索を先行実装しない一方、受け入れるデータの元情報は収集時から残す。

## 再取得・再投入・更新

検証期間中はdataset版を凍結する。現行cursorはデータ版に結び付かず、複数ページや画面キャッシュの更新整合を保証しない。ライブ同期は行わない。

1. 同じ元データの再取得は、取得記録を追加し内容hashで差分を確認する。再取得時刻だけで新Claimを作らない。
2. 同じ確定版の再seedは固定UUID・固定内容で冪等にする。現在のseedは差異を拒否するため、更新処理として使わない。
3. 元資料に変更があれば新しい候補版を作り、人が差分を確認する。値・意味が同じならIDを保ち、根拠追加はCitationを追加。意味が違う主張は別Claim。トリプルだけで同一Claimと判定しない。
4. 元statementの消失・ページ削除は否定の根拠でも自動削除指示でもない。保留・訂正・公開から外す判断と理由を残す。削除前の確定版・原取得情報を保持する。
5. 新版は専用DBを作り直して検証し、切替時は探索セッションを再開始する。同じDBを閲覧中に書き換えない。一般的な差分import・履歴DB・過去Graph再現は作らない。

この方法で過去ファイルは追跡できるが、旧Graphをサービス画面から再現できる機能を提供するわけではない。

## demo fixture・検証環境

fixtures/demo.jsonと既存テスト期待値を維持する。架空データは同名・denied・複数Claim/Source・孤立・循環・ページング等の回帰ケースであり、実データへの置換や混在をしない。実データを件数目標のために架空Claimで補わない。

実データは別Neo4jインスタンス・volume・接続設定にする。現在のCommunity構成で同一インスタンスの複数DBを当然に使えるとは考えない。composeの固定portの衝突も分離時に調整する。API統合テストはDB停止・一時データ書込みを行うため、パイロットDBを向けた状態で既存テストを動かさない。別インスタンスと実行前の対象確認を準備する。

回帰テストは固定demo・外部ネットワーク不要を維持。パイロットには台帳／投入用JSONの整合・意味・ID衝突・引用必須の検査を追加し、主要経路の読み取り確認を別環境で行う。出版社やWikidataの現在の応答を毎回のテストの正解にしない。

## 先に表面化する制約と最小準備

| 制約 | パイロット前／今回の対応方針 |
| --- | --- |
| 架空デモと決め打ちされたヘッダー | 実データ専用モードでは「少数の確認済み資料によるパイロット・網羅的ではない」と分かる表示が必要。実データとdemoを明確に分ける |
| 孤立・関係なしの受け取り方 | 「登録範囲内では該当関係なし」とし、実世界で関係が存在しないとは表現しない。条件内ゼロと未登録も混同しない |
| CONTRIBUTED_TOの役割が広い | Citationに役割・版・限定を明示。共通作品を介した接続は、人物同士の直接関係や同時期の協働を証明しない |
| 名前・aliasesに言語なし | 台帳に構造化保持、既存APIには確認した表示・検索名だけ投影。ロケール切替や多言語検索の実装済みとはしない |
| seed CLIがdemo固定・差分更新不可 | 次の準備ではデータセットの明示選択と誤投入防止が必要。更新importへ拡張せず、凍結版の投入に限定 |
| 詳細のrelatedClaimIdsが無制限・全並列取得 | 少数版の件数分布を確認。まず同一RelationのClaim数・Citation数を計測し、極端に多い対象は初回範囲を見直す。隠れた切捨てはしない。増量前に取得予算を設計 |
| 検索personのみ・最大20件・続きを取得不可 | 初回は4〜8人物で困らない。作品はGraph経由。作品起点検索は観察後に判断 |
| 日付と作品粒度 | 不明期間はnull。巻の発売日を関係期間にしない。近代漫画に絞り、未対応の日付・限定条件は保留 |
| Graph密度・100 Entity / 200 Claim上限 | この規模なら上限拡張は不要。長い実名・題名、作品のハブ、役割を読めるかを実画面で観察。再配置や専用レイアウトは必要性が出てから |

**読み取りAPI契約や知識モデルの大きな変更は初回パイロットに必須ではない。** ただし台帳・投影・対象環境・表示モードの最小準備なしに、現在のdemoへそのまま流し込むことは推奨しない。これらは次の実装範囲の案であり、今回は実装していない。

## 検証する体験と区切り

例：浦沢直樹を検索 → PLUTO → 長崎尚志 → MASTERキートン → 勝鹿北星。別枝でBILLY BATから浦沢直樹へ戻り、合流・循環・閉じる／復元を試す。関係を選び、制作関与の内訳と引用した巻・版を確認する。追加で明示的な影響関係を採用できた場合は、制作関与／影響を切り替えて経路の違いを試す。

まず3〜5人程度に10〜15分ずつ操作してもらうか、同等の短い探索セッションを行い、手動で観察記録を残す。認証・アクセス解析基盤は不要。

- 自発的に別人物・別作品へ移り、知らなかった繋がりを見つけたか。
- 根拠を開いて関与の役割・資料の限定を理解できたか。共通作品経由の繋がりを直接の師弟・親交と誤読しなかったか。
- 閉じる・再開・条件変更が探索の整理に役立ったか。
- データ不足、操作の問題、表示の問題を分けて記録できたか。

受入検査、seed冪等性、demo回帰、パイロット主要経路確認、観察結果と次の判断を記録したところで区切る。興味を持てない場合に大量取り込みで解決すると決めつけず、対象群・関係の種類・根拠の見せ方を見直す。

## 今決める／後回し

提案する今の決定は、制作関与中心の小さな対象群、資料を確認したClaimだけの受入、作品と版の分離、QIDと内部UUIDの分離、言語・provenanceの構造化保持、凍結版と環境分離。採用後、個々のQID・Claim・資料の限定を確認し、必要最小限の投入準備へ進める。

大量import、Wikidata property全対応、taxonomy・プリセット管理、役割の汎用モデル、完全な履歴DB、公開編集、認証、全画面翻訳、時系列、作品検索は後回し。全面的な基盤を完成させることではなく、根拠を失わず実データで探索の価値を確かめることを完了基準とする。
