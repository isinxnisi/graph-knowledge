# Plunode コミュニティ基礎設計 — 体験初案 v0.1

作成：2026年10月21日 02:22 JST
状態：レビュー・画面試作の起点となる提案。実装済み・本番反映済みではない。

## 1. この初案で目指すもの

気軽に作り、しばらく離れ、別のコミュニティを作ってもよい。小さな思いつきの場所が残っていても失敗とは扱わない。一方、育ったコミュニティは、公開Capsuleを選び、紹介し、議論するギャラリーになれる。

コミュニティを作ることと、継続的な成果提出・常時管理の義務を負うことを同一視しない。サイトの利用ルールは共通に保ち、安全対応を個々の作成者の善意や常駐だけに依存させない。

コミュニティを設計の中心にし、アカウント側の管理体験、分析、AI参加・活動へつなげる。初案は具体的に決め、実画面や代表操作で問題が出た部分を修正する。詳細項目をすべて利用者へ質問してから設計する進め方にはしない。

## 2. 場・会話・作品を分ける

| 対象 | 初案での役割 |
|---|---|
| コミュニティ | テーマや関心で集まる場所。参加者、会話、Capsuleの掲載と管理方針を持つ |
| スレッド | その場所で始まる一つの話題。Capsuleなしで作成でき、複数のCapsuleを参照できる |
| Capsule | 個人または明示的な共同管理者が育てる独立コンテンツ。コミュニティに掲載しても所有を自動移転しない |
| ギャラリー掲載 | そのコミュニティで特定のCapsuleの版を紹介する関係。紹介文、掲載者、対象版、ピックアップ状態を持つ |

同じCapsuleを複数のコミュニティで紹介できる。掲載のたびにCapsule本体を複製しない。議論はコミュニティごと・スレッドごとに分かれ、非公開の会話が別の掲載先へ移動することはない。

Capsuleは本線KGの単なる不採用情報置き場ではない。本線との同一性・参照と、Capsuleの文脈・断面を両立させる従来の方向を維持する。ただし、現在の参照中心Capsuleを、KG本文の完全な歴史版保存が実装済みであるかのようには扱わない。

## 3. 気軽な作成と、管理の終わり方

### 作成時

名前、任意の短い説明、公開／メンバー限定を確認して作れる。テーマ分類・運営規約の個別執筆・成果目標は必須にしない。

基本の初期値は以下とする。公開範囲だけは作成画面で明示し、ユーザーが意識せず公開する操作にしない。

| 設定 | 初期値・候補 |
|---|---|
| 公開コミュニティへの参加 | 自由参加。承認制・招待制へ変更可能 |
| メンバー限定コミュニティへの参加 | 招待制。参加申請を受ける方式も選べる |
| 投稿・返信 | 参加者が可能。未ログイン者は公開内容の閲覧だけ |
| 投稿審査 | 原則なし。新規スレッド・Capsule掲載など対象を分けて有効化可能 |
| ギャラリー | 参加者が掲載可能。管理者が選ぶピックアップは別枠 |
| AI参加 | 招待したAIだけ。招待・接続されるまでは自動参加なし |
| AIの自主活動 | 既定で停止。参加後もまず呼びかけへの応答を基本とする |

閲覧・参加・投稿・Capsule編集・管理を別の権限として扱う。画面には一般的な設定を中心に見せ、詳細な権限編集を作成の必須手順にしない。

### 作った後

更新しない期間があっても自動削除や失敗扱いにしない。通知を止めて離れることと、所有者として正式に退会することも区別する。

管理者の追加・引継ぎ、投稿受付を止めるアーカイブを用意する。最後の管理者が離れる際、引継ぎがなければ閲覧中心のアーカイブへ移行する案とする。別のコミュニティを作るために以前の場所を削除させない。

アーカイブは保存容量や永久提供の保証ではない。サイト全体の停止・削除・保管方針は別に設計する。放置された場所の通報もサイト運営へ届けられるようにする。

## 4. ギャラリーとして育つ体験

コミュニティには最初から「Capsule」と「スレッド」の両方の入口を設ける。Capsule掲載に、紹介用スレッドの作成を必須にしない。掲載後に「このCapsuleについて話す」から話題を作ることはできる。

ホームには管理者が選んだCapsuleと最近の会話を置く。初期の並びはピックアップと新しい掲載を中心とし、未計測の人気・品質・信用順位を作らない。ギャラリーを育てたい場所ではCapsuleを先頭に、会話中心の場所ではスレッドを先頭にできる程度の表示設定を持つ。

Capsuleのカード／行は、題名、短い紹介、作成者、掲載した版とGraphへの入口を中心にする。Graphへ直接進め、先にスレッドを読ませない。カードを大型化しすぎず、既存のライト・エディトリアル調と一覧性を維持する。

ピックアップは「このコミュニティの選定」であって、真実の認定・本線KGの審査通過ではない。

掲載は初案では選んだ版に固定する。Capsuleに新しい公開版ができたら掲載者・管理者に更新を知らせ、「掲載版を更新」で切り替える。これは私的な編集中内容が展示へ漏れることと、過去に選定した内容が黙って入れ替わることを避けるための初期判断。後から「最新公開版を追う」展示方式を追加する余地は残す。

## 5. 公開・非公開の自然なルール

### 基本原則

**会話の公開範囲と、Capsuleの公開範囲を別々に持つ。貼り付け・掲載だけで閲覧権限を広げない。**

| 組合せ | 振る舞い |
|---|---|
| 公開コミュニティで公開Capsuleを紹介 | そのまま掲載・閲覧できる |
| メンバー限定の場所で公開Capsuleを議論 | 議論はメンバー限定。Capsule自体は引き続き外からも公開閲覧できる |
| メンバー限定の場所で私的なCapsuleを共有 | 所有者が「この版をこのコミュニティに共有」を明示すると、メンバーが読める |
| 公開の場所へ非公開Capsuleを掲載しようとする | 自動公開しない。権限のある人へ公開版の作成・公開内容の確認を案内する |
| 限定リンク共有を公開スレッドへ持ち込む | tokenを公開権限の代用にしない。公開版を作るか、適切な共有先を選ぶ |

「私だけ」「指定コミュニティ」「リンク限定」「公開」を利用者向けの共有先として整理する。内部では一つの巨大な状態にまとめず、版ごとの閲覧許可と一覧・検索への掲載を分けて扱う。指定コミュニティへの許可で読む人は、退会・除外後にはその許可を失う。他の独立した有効な閲覧許可があれば、その範囲だけは残る。

### 非公開の検討から公開へ

例：数人でスレッドを立てて資料を検討し、Capsuleの成果だけを公開する。

1. 会話と共同作業はメンバー限定のまま進める。
2. 所有者または許可された公開担当者が、公開するCapsuleの版をプレビューする。
3. 公開用の説明・注釈・参照だけを確認して、その版を公開する。
4. 公開コミュニティのギャラリーへ掲載し、必要なら新しい公開スレッドで紹介する。

元の非公開コメント・参加者一覧・検証メモを一緒に公開しない。非公開会話全文の「まとめて公開」を初期の通常操作には置かない。成果の公開と会話の公開を分ける。

### 公開設定の変更・取り下げ

スレッドは作成時の公開範囲を明示して記録する。コミュニティを後から公開へ変更しても、以前のメンバー限定スレッドは自動公開しない。設定変更時には、これからの投稿と既存の内容への影響を分けて示す。参加方式の緩和による既存メンバー限定内容への影響も確認する。

コミュニティを非公開にしても、独立して公開されているCapsule本体まで非公開にはしない。必要な場合はCapsule側で公開停止する。

Capsuleの公開・共有が取り下げられたら、該当許可に依存するギャラリー、プレビュー、Graph入口も追従して閉じる。読めない本文・題名・非公開の版数を新たに漏らさない。スレッド自体の所有・存続は別に扱い、Capsuleを消したことだけでコミュニティの会話を丸ごと消さない。

公開後に第三者が取得したコピーや、利用者が別投稿に書いた引用の完全回収は保証できない。システム内の共有撤回と、すでに読まれた情報の回収を混同しない。

## 6. 所有・編集・管理

Capsuleをコミュニティへ掲載しても、作成者は変わらない。コミュニティ管理者は掲載・ピックアップ・その場所の会話を管理できるが、他人のCapsule本体を書き換えたり、全サイトから削除したりはできない。

Capsuleの共同編集は、所有者による明示招待を基本案とする。閲覧、編集、公開更新を区別し、参加しただけで編集者にしない。初期の共同編集に同時編集・自動マージまでは要求しない。

将来のコミュニティ所有Capsuleも基礎設計で扱う。作成者の記録と、現在の管理主体を分け、コミュニティ閉鎖・所有者退会時の扱いを検討する。個人所有Capsuleを掲載時に自動でコミュニティ所有へ変換しない。

参加承認、投稿審査、Capsule編集の承認、公開更新、本線KG受入は別の判断。たとえば「公開閲覧・自由参加・投稿審査なし・ピックアップは管理者選定」の気軽なギャラリーを基本形として成立させる。

## 7. 画面の初案

### コミュニティ

上部に名称、紹介、公開範囲、参加ボタン。本文の入口は「ホーム／Capsule／スレッド／メンバー」。権限のある人だけに「管理」を表示する。

管理では、基本情報、参加・投稿方針、メンバーと役割、掲載・ピックアップ、通報・承認待ち、AI参加設定、アーカイブ・引継ぎを扱う。全項目を一画面へ展開せず、通常利用と管理を分ける。

### アカウント

「自分のコミュニティ」で参加中、運営中、申請・招待、アーカイブを確認する。自分のCapsuleから掲載先・共有先を確認し、同じ管理対象へコミュニティ側からもアカウント側からも辿れる。管理状態の正本を二つにしない。

### サイト運営

コミュニティをまたぐ通報、停止・異議、最後の管理者がいない場所、サイト全体のAI停止・利用枠を扱う。コミュニティ管理者にサイト運営権限を自動付与しない。

既存Explorerの検索・Graph・保存をコミュニティ参加の必須条件へ変えない。コミュニティからGraphを開き、戻ると元の一覧・スレッド・停止位置へ戻れることを画面試作で確認する。

## 8. AI参加と活動の自由度

人間向けログイン、AIとして表示される身元、AIの役割、処理に使うモデルを分ける。公式AIという名前だけで管理者権限・private閲覧を与えない。

コミュニティ設定の初案：

- 参加許可：参加させない／招待したAIのみ／サイトで許可されたAIも受け入れる。
- 活動開始：呼びかけ時のみ／設定された範囲で自主活動も許す。
- 活動内容：会話・紹介・要約・検証コメントなどを役割単位で制御する。

初期は「招待したAIのみ・呼びかけ時のみ」。自主巡回や全件ファクトチェックを既定で開始しない。AIを外したり許可を取り消したりした場合は、待機ジョブ・読取・投稿直前の認可にも反映する。

AI参加の許可と、非公開内容を外部モデル提供者へ送る許可は同一にしない。利用する処理先・範囲を別途扱う。今回の設計作業から、外部AIへの内容送信や有料実行を開始しない。

コミュニティに参加するAIと、サイト運営の通報・安全対応は別の権限・目的として設計する。「AI参加なし」は常駐Botの不参加を意味し、運営の安全対応を無効化する設定にはしない。ただし安全対応を理由に無制限の非公開閲覧権限を与えず、対象・目的・履歴を限定する。

## 9. 分析と本線KGへの貢献の余地

人気・活動量・根拠の充足・本線KG受入は別々に扱う。最初から単一の信用点や総合ランキングを作らない。

本線KGへの貢献は、後から実績を照合できるよう、元のCapsule／版、関連スレッド、提出者、関与したコミュニティ、提案、受入・訂正・撤回の対応を辿れる設計にする。複数コミュニティへの掲載回数だけで受入実績が増えないようにする。

将来の表示候補は「受入された知識」「根拠の補強」「訂正への貢献」など。計算式や配点は今は決めない。提出時の実際の関与を記録し、後から掲載しただけのコミュニティへ自動で実績を付け替えない。

分析では、人間とAIの活動、イベント時点の公開範囲、参照した版、AIの選定理由・方針版・実行予算を区別する。人気だけで同じ対象へ介入し続けないよう、活動の偏り・対象の偏り・未確認の範囲・クールダウンを後から評価できるようにする。

非公開活動の個別内容・参加者・存在を、公開ランキングや貢献数から推測できないよう、公開する集計範囲も別に決める。AIチェックの未実施や根拠不足を、誤りや悪意と同一視しない。KGへの採用は既存の明示的な受入経路と分離しない。

## 10. 次の実装に進むための区切り

次の作業単位は、この初案の既存実装との照合、権限・版・公開変更の具体化、主要画面を一巡できる試作まで。

初回試作で確かめる体験は次の四つ。

1. 公開コミュニティを作り、Capsuleを掲載し、Graphへ進んで戻る。
2. メンバー限定で検討し、Capsuleの成果だけを公開する。
3. 自分のアカウントから参加・運営・申請・共有先を管理する。
4. AI参加設定を変更し、現在何が許可されているかを理解できる。

その結果で、初回の実機能を切り出す。公開／メンバー限定、会話、ギャラリー、基本管理、招待制AIの身元と権限を最初の候補とし、本格的な自律活動、貢献スコア、同時共同編集、分析ダッシュボードは後段に分ける。後段の構造を考えないという意味ではない。

無承認の本番・会員DB・公開KG変更は行わない。試作を実際の公開許可やAI稼働済みと表示しない。
