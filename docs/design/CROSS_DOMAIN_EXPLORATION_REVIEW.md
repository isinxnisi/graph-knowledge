# 複数分野の探索文脈・入口・起点切替のレビュー

2026-10-04。**起点切替・直前復帰はPhase 08で採用・実装。別分野追加等は未実装の提案**。以下はPhase 07完了後を基準にしたレビュー時点の記録。レビュー時の変更は設計文書とdocs入口だけ。DB・API・UI・schema・dataset・fixture・語彙は変更せず、新しい実在データの収集も行わない。

## 結論

知識は分野別の閉じたGraphへ分けず、共通の内部Entity IDと独立Claimを持つ**一つの論理的Knowledge Graph**を推奨する。ただし一つの物理DBを永久に使うという判断ではない。分野・時代・文化運動の分類を、そのまま保存境界や取得制限へ変換しない。

入口は検索と、将来の任意の開始例・テーマ案内が共存する形。探索テーマは利用者の関心を説明し、実際に取得を制限する条件とは分ける。名前を知っている人に分野やプリセットの選択を必須にしない。

Nodeのクリックは従来どおり選択・展開・開閉。別の対象を主題にしたくなった時は明示的な起点切替を使う。**「この対象から広く見る」と「同じ条件でこの対象から見る」を分ける**案を推奨する。前者は関係・Role等の追加条件を解除する新しい探索、後者は確定条件を維持する新しい探索。分野を自動判定して条件を切り替えない。

次の1フェーズは、一般Entity検索や新分野データより先に、**既存Nodeからの明示的な起点切替と、直前の探索へ戻る最小経路**を成立させる案を推奨する。この契約を決めれば一般Entity検索は安全に続けられ、taxonomy・プリセットの完成を待つ必要はない。

| --- | --- | --- |

## 2. 分ける概念

これは概念境界の提案であり、同数のテーブル・クラス・画面を今作る指定ではない。

| 概念 | 例・意味 | 知識・取得・表示との関係 |
| --- | --- | --- |
| 知識 | Entity、predicate付きClaim、限定、Citation、Source | 入口や探索セッションから独立した正本 |
| 分野・歴史的文脈 | 映画、科学、ルネサンス、産業革命 | 同じ種類の分類とは限らない。複数への関連を許し、対象を一つのworldへ排他的に所属させない |
| 入口 | 名前検索、将来の開始例、テーマ案内、共有されたビュー | 対象・任意の条件を選ぶ導線。入口ラベルから暗黙の取得制限を作らない |
| 探索テーマ | 「映画から見た影響」「研究者と大学」「ルネサンスの交流」 | 関心を説明する文脈。候補起点や条件案を案内できるが、それだけで検索・Graphを制限しない |
| 探索軸 | 影響、制作、家族など、どの繋がりを見たいか | 人間の意図。対応済みpredicate集合等へ明示的に解決する |
| 探索条件 | 正確なpredicate IDs、制作Role。将来の期間・端点条件等 | 実際に取得対象を変える値。LIMIT前評価、条件キー、cursorへ反映する |
| 現在の起点 | 手塚治虫、作品、研究機関の内部ID | 展開の到達対象を導く始点。検索語や選択中Node、入口テーマとは別 |
| 探索セッション | 起点・確定条件・受理範囲・開閉・現在選択 | 現在組み立てている探索。テーマの出自と表示設定を関連付けられるが、その名称を条件キーにしない |
| 表現・操作設定 | 自由Graph、将来の時系列、配色、pan/zoom | 同じ知識をどう眺めるか。表現変更だけで追加条件を変えない |

「ルネサンスを眺める」は、案内テーマから出発するのか、厳密な時代内の対象だけを取得するのかで異なる。前者は小さな編集済み開始例で成立する。後者には関連の根拠、対象粒度、年代、不明値、境界を跨ぐ関係の扱いが必要で、テーマ名だけでは実装できない。

歴史的文脈自体について主張する必要が出た場合には、知識上の対象としての同一性・粒度を別途決める。運営が作った「ルネサンスを探索」カードを、そのまま知識Entityや「属する」Claimへ変換しない。

## 3. 一つの論理Graphを推奨する理由と代替案

同じEntityを映画版・漫画版・科学版として複製すると、外部IDの一意性、Claimの出典共有、横断経路が分断される。現行のEntity＋Claimモデルには分野分割を要求する制約はなく、両方向取得も共通の内部IDを前提にしている。

| 案 | 利点 | 負担・今回の評価 |
| --- | --- | --- |
| 分野ごとに独立DB・独立Entity | 各分野の運営・性能を分離しやすい | 同一性・横断クエリ・出典参照・同期の負担が増える。分野のためだけには非推奨 |
| 共通知識＋入口／テーマの案内 | 同一対象を共有し、横断探索が自然 | テーマと取得範囲を混同しないUIが必要。今回の推奨 |
| 単一worldタグを必須化して検索・近傍を制限 | 表面上は分かりやすい | 分野／時代／運動の意味が混ざり、境界のEntityを排除する。非推奨 |
| 後で物理分割し、アプリで統合する論理Graph | 規模・認可・運用の要件に対応できる | 横断照会とID解決の設計が必要。具体要件が出るまで導入しない |

公開範囲・権利・運営組織・性能に実際の分離要件がある場合は、認可や物理配置を再評価する。テーマ名を認可境界の代用品にしない。demo／凍結pilotの保護は維持し、横断検証のために既存環境へ別データを混ぜない。将来の統合検証では新しい専用dataset版を用意し、同じ実在対象の内部IDを再利用する受入方針を決める。

## 4. 探索途中と起点切替

ユーザーが示した「映画関係者→影響を受けた→手塚治虫」は以下の操作例の仮定であり、その実在Claimを確認・収集した記録ではない。

### そのまま辿る

手塚治虫をクリックすると、現在の条件で近傍を展開する。映画側の起点・枝・適用条件は維持する。作品や別分野の対象へ到達しても、自動リセットしない。これは既存Node操作の責務。

映画という入口が単なる案内なら、最初から漫画側のClaimも取得対象にできる。明示的な「影響だけ」等が設定されていれば、その条件は跨いだ先でも適用する。将来の「映画関連だけ」という実際の対象条件がある場合には、その外側が出ないことを示し、条件解除の操作を提供する。境界の外を自動取得したり、無表示を「関係なし」と断定したりしない。

### 主題を変える

Entity詳細等から次の明示操作を提供する案。常時確認ダイアログや起点切替ごとの軸選択は要求しない。

| 操作の意図 | 新起点 | 追加条件 | 元の文脈 |
| --- | --- | --- | --- |
| この対象から広く見る | 手塚治虫 | predicate／Role、将来の期間・対象制限等を解除 | 映画テーマは有効テーマから外す。元の探索への戻り先として出自を保持 |
| 同じ条件でこの対象から見る | 手塚治虫 | 確定した実効条件を維持 | 継続中の関心・テーマを維持できる。ただし「映画内」と誤表示しない |
| 別の軸でこの対象を見る（将来） | 手塚治虫 | 選んだ軸を解決した条件 | 新テーマへ切替。未対応条件は拒否し、無条件へ黙って代替しない |

広く見る場合もpublished、認可、dataset範囲、取得件数・表示上限は維持する。「無条件」は登録済みの閲覧可能な関係に追加条件を指定しない意味であり、全知識を一括取得することではない。手塚治虫の分野を推測して「漫画」の条件へ自動変換しない。現在のCONTRIBUTED_TO／Roleから職業や所属分野を認定しない。

二つの操作の追加条件が同じなら、余分な選択肢を出さず共通の起点切替へまとめられる。条件がある場合は「広く見る」を主題変更の主導線、「同じ条件で」を補助導線とする案。条件要約を近くに示す。Node再クリックやダブルクリックには割り当てず、選択・開閉の既存契約を守る。

### 現在の検索からの起点変更との整合

検索結果の候補選択は、現行どおり確定条件を維持する。条件を先に決めてから人物を選ぶPhase 07の経路を壊さない。「広く見る」は別の明示意図として導入する。検索結果への同じ補助操作が必要かは、一般Entity検索の結果設計時に判断する。

新しい起点への遷移は起点と条件を**一度に確定**して新しい世代を開始する。既存changePredicatesの後にchooseRootを呼ぶだけでは旧起点への不要な再取得を生む可能性がある。旧通信を無効化し、cursor／受理ページ／open意図を引き継がず、新起点を選択して一段階取得する。新しい主題では初期配置を作り、元の座標へ無理に押し込まない。

同一起点で条件だけ変える場合は、現在の共通Node座標・pan/zoom維持の契約を使う。同一起点・同条件で単に選択し直す操作と、枝を捨ててやり直す操作も混同しない。

### 元の探索へ戻る

起点切替は、誤操作の取消だけでなく、枝を眺めて元へ戻る体験を持つ。「戻る」で元の起点だけを再検索する案では、組み立てたGraphの開閉・受理範囲・座標を失う。

初回は**直前1件の画面内復帰**を推奨する。起点、実効条件、出自／テーマ、受理済み範囲、開閉意図、選択、Node座標、pan/zoomを一時保持する。GraphCanvasのrefは別途取り出せる境界が必要。検索語・検索結果は同じ画面の検索状態として扱い、復帰で勝手に書き換えない。適用中draftは起点切替へ持ち越さない。

これは未実装の提案であり、現在の休止枝復元で代用できない。進行中要求・AbortController・旧loading状態を保存して再開しない。戻る時にも新しい世代番号を使い、旧応答を排除する。受理済みページだけを同一dataset・同じデータ版・認可の範囲で復元し、中断ページは明示的に再取得する。条件変更後のページを別条件へ流用しない。

直前記録は次の別起点遷移で置き換え、一段の復帰後は消費する案。連続した履歴・タブ・永続保存・ブラウザBack／Forward・共有URLは今回の小さいフェーズへ広げない。通信復帰、dataset／認可変更、キャッシュ予算400 Entity／800 Claimと復帰用保存の合計上限、保存できない場合の事前案内を、実装開始前に具体化する。保存不能なのに「元のGraphへ戻る」と約束しない。

## 5. 初期画面／途中／切替と「見たい軸」

| 場面 | 主な役割 | 任意に使う探索軸 |
| --- | --- | --- |
| 初期画面 | 名前検索と、将来の少数の開始例／テーマ案内から起点を見つける | 見たいものが決まっている人だけ条件やpresetを選ぶ |
| 探索途中 | 起点を保ち、枝を辿り、必要時に見る関係を調整する | 同一起点に別条件を明示適用。既存世代切替を使う |
| 起点切替 | 到達先を新しい主題にする。条件維持／解除を意図で分ける | 既定は広く見る導線。軸選択は必須にせず、将来候補として提供可能 |
| 保存テンプレート | 再利用したい条件を明示的に記録する | 公式preset・個人テンプレート・対象付き保存ビューを区別 |

「制作を見る」はpredicate集合等への解決、「歴史的文脈を辿る」は起点候補や将来の取得制限も含み得る。どちらも同じpreset解決境界を使えるが、同じ意味の条件とはしない。

presetは版付きのアプリケーション層テンプレートという既存提案を維持する。入口・途中・起点切替から共通の解決処理を使い、確定条件をセッションへ渡す。テーマカードがpresetを参照することはできるが、テーマ＝preset＝taxonomyではない。preset由来でも利用者が条件を変更したら「調整済み」と扱い、元の名前だけで現在条件を説明しない。ID／版・名称のlocale・実効条件を分ける。

Phase 07の「条件なしでまず辿る」は維持できる。ただし高次数では一段階・Claimページング・上限付きの部分取得である。分野が増えたら対応predicateのチェックを初回に大量列挙せず、必要時の編集・任意の小さい軸案内を維持する。

最初から全分野の選択を要求する入口と、検索だけで名前を知らない人を置き去りにする入口の間に、任意の開始例がある。テーマ候補数、カード配置、どの入口が有用かは複数題材で観察して決める。人気・Source件数を根拠の信頼度へ変換しない。

## 6. 一般Entity検索のタイミング

上記の概念境界と起点切替の意図を先に決めれば、一般Entity検索を実装しても作り直しリスクは小さい。大きなtaxonomy・テーマカタログ・preset管理を先に完成させる必要はない。

今回の推奨順は、既存Graph内の人物／作品／組織で起点切替と復帰を検証 → 既存kindの一般Entity検索 → 小さな別分野パイロット。作品／組織の入口を直ちに検証したい場合は、一般検索と最小起点切替を同じ小さいフェーズへまとめる代替もあるが、復帰契約と検索契約を同時に増やす負担がある。

一般検索の初回判断は、kindの結果表示、同名・別言語・組織名の判別、検索対象条件と探索条件の独立、limit、現在の人物検索APIとの互換性。人物の職業をRoleから生成しない。テーマ内検索を追加するなら「候補を探す範囲」と「Graphで辿る範囲」を別に表示する。

## 7. 小さい別分野Vertical Sliceの提案

**一つの大学・研究機関を介した、近代の研究者の人的ネットワーク**を第一候補とする。具体的な実在人物・機関・Claimの採用は資料確認前なので未決定。この文書では資料収集や事実の確認を行っていない。

| 候補 | 何を揺さぶるか | コスト・限界 |
| --- | --- | --- |
| 同じ漫画題材の人物間の影響を増やす | 非制作の軸、双方向の人物探索、条件維持と解除 | 既存predicateで可能。別分野の入口や機関起点までは検証しない |
| 漫画題材で家族関係を追加 | 制作と独立した近い人物関係、関係方向、同名・家系 | 親子・養親・配偶・家族の粒度を決める必要。少人数でも新predicateと受入判断の費用がある |
| 映画の制作クレジットを追加 | 別分野の名称、長い作品名、別Role | 現在の制作モデルと似ており、上位構造の検証力は相対的に低い |
| 研究者と大学・研究所 | organizationを中心に複数人物へ進む、移動・合流、人物を新起点にする。制作Roleなしで成立 | AFFILIATED_WITHの広い意味を守れば最小化可能。制度上の所属、共同研究、師弟を厳密に表現する検証にはならない |
| 産業革命・ルネサンス全体 | event、期間、運動・文脈、複数分野の境界 | 題材が広く、eventへのpredicate、文脈所属、歴史日付を同時に増やしやすい。初回の最小案にはしない |

### 最小範囲・受入条件

- 目安は人物5〜6名、機関2〜3件、Entity計7〜9件、Claim8〜12件。二つの機関を介した合流と、人物間の関係があれば十分。件数のために未確認関係を採用しない。
- 初回はAFFILIATED_WITHを主にし、明示資料があれば人物間INFLUENCED_BYを1〜3件。機関に関係したという広い命題の資料限定・原表記をCitation／台帳へ残す。雇用・所属・師弟・共同研究へ自動変換しない。
- 大学・研究機関の公式沿革、人物紹介、アーカイブの該当記述をSource候補とする。影響は明示の証言等が確認できた場合だけ。資料が具体的関与を示さなければ保留する。
- 論文・著書の制作関与、研究Role、新しいevent・taxonomyを初回の成立条件にしない。科学の「助手」を漫画のASSISTANT_OFへ無審査で対応させない。
- 19〜20世紀程度の題材なら現在の日付表現の範囲内から選びやすいが、年月日・関与期間は資料で確認した範囲のみ。不明を機関創設日やSource公開日で補わない。
- QID・内部ID・名前の言語・原資料の表現・版・取得由来は既存パイロットと同じ受入規則で残す。対象が別分野に現れても同一性を確認して一つのEntityを参照する。

想定経路は「研究者A→機関U←研究者B→明示された影響の相手C→機関I←研究者D」。これは構造を示す架空の説明で、実在データの採用候補を確認した結果ではない。同じ機関へ関わったことから、同時在籍・面識・共同研究を推論しない。期間が違っても機関を介した探索経路として示し、詳細に戻れるようにする。

この題材は制作中心への偏りと機関起点を揺さぶるが、event・時間条件・家族・作品間関係を検証したことにはならない。また現在の漫画pilotと繋がる実在Claimを保証しない。実際の分野横断は確認できる橋渡しClaimが見つかった段階で新datasetへ追加する。起点切替の横断UXだけなら、先にHTTP mockの架空例で検証できる。

### 同じ世界での非制作系検証

最初は漫画題材のINFLUENCED_BYを小さく増やす案。好き・尊敬・参考だけでは受け入れず、明示された人物間の影響を確認する。影響条件で到達 → 広く見るで制作等へ進む → 同じ条件では影響を保つ、の違いを検証できる。

家族は次の意味検証候補として価値があるが、初回の別分野検証と同時に増やさない。扱うなら「家族」という包括語で急いで登録せず、具体的な関係一種類、方向、生物学的／養子等の限定、時期、資料の記述を先に決め、既存語彙との比較手順を通す。対称関係ならsubject/objectを逆にした重複Claimを作らない規約も必要。これらは今回採用・追加する新predicateではない。

## 8. 今決めることと後回しにすること

| 今、契約として先に決める境界 | 実データ・需要を見てから決める具体方式 |
| --- | --- |
| 分野を排他的なEntity同一性・保存境界にしない | 全分野カタログ、分類ツリー、運動・時代の正式モデル |
| テーマ案内と実際の取得制限を区別する | テーマ内／外の対象をどう定義・編集するか |
| 選択・展開・起点変更を区別し、広く見る／条件維持を明示する | 複数起点、タブ、履歴、ブラウザ復帰、共有・保存 |
| 起点＋条件は原子的に切り替え、旧応答・cursorを混ぜない | 多条件キャッシュ・スナップショット・汎用探索DSL |
| 元の探索へ戻る際に何を復元するか | 多段の復帰履歴や永続ワークスペース |
| presetは実効条件へ解決し、出自とlocaleを分ける | 管理画面、会員保存、推薦・人気順 |
| 新題材のEntity粒度・外部ID・関係の意味・限定・Sourceを投入前に決める | 科学Role、研究イベント、多項関係、作品間影響 |

新しいpredicateが必要ならPhase 05の意味契約・比較票・validatorを使う。既存IDの端点や意味を黙って広げない。taxonomyは新predicateの意味を保証せず、入口テーマを作るためだけには不要。

## 9. 次の1フェーズと受け入れ基準

推奨：**既存Entityからの明示的な起点切替・直前探索への復帰**。

1. 広く見る／同じ条件で見るの表示と、無条件時の共通操作、同一起点時の扱いを具体化する。復帰の寿命・予算・失効・失敗表示を先に固定する。
2. 起点と条件を一度に扱う遷移を既存hookの小さい境界へ加える。既存検索の条件維持は変更しない。
3. 選択Entity詳細から実行し、新起点の一段階取得を確認する。作品／組織も既存Graph内から起点にでき、一般検索APIは不要。
4. 直前1件を画面内で復帰する。GraphCanvasの座標・pan/zoom受渡しを最小化し、永続保存基盤を作らない。
5. 無条件／predicate／Role空集合・部分集合、通信途中、起点取得失敗、共有・循環、上限、元の選択・座標、途中の条件変更をテストする。条件解除で新起点だけへ一回取得し、元の探索へ不要な通信をしない。

全て提案であり実装開始の承認ではない。完了後、一般Entity検索で作品・機関から直接始める入口を追加し、その次に少数の研究者・機関パイロットを受け入れる。プリセット・taxonomyの完成を待たず、実在資料でテーマや開始例の必要性を観察する。
