## 4語彙の境界

具体例は語彙解釈用であり、実在する出来事の新規Claimではない。完全な例・理由・全件比較はcatalogに収録する。

| Predicate・正規方向 | 含む例 | 含まない例 | 境界例・判断 |
| --- | --- | --- | --- |
| ASSISTANT_OF：補助した人物→補助された人物 | アシスタントとして制作補助したとの明記 | 師匠という呼称だけ、同じ仕事場だけ | 「手伝った」だけなら制作補助・アシスタントとしての関与を確認し保留 |
| INFLUENCED_BY：影響を受けた人物→対象人物 | 本人が対象人物から絵のタッチに影響を受けたと述べる | 好き・尊敬だけ、作品への影響を作者へ変換 | 「参考にした」が影響の主張なのかは文脈審査 |
| CONTRIBUTED_TO：関与人物→作品 | 脚本・監修・プロデュース等の制作クレジットを、資料の限定内で扱う | 原作由来だけ、好き・代表作という評価だけ | 「著」から作画を認定しない。一巻から全巻の担当へ拡張しない |
| AFFILIATED_WITH：人物→組織 | 資料が編集部への協力等の具体的な関わりを述べる | 出版社が作品を刊行したことから人物の所属を認定 | 曖昧な交流表記は内容を確認。雇用・所属・契約形態を推定しない |

ASSISTANT_OFとINFLUENCED_BYは同じperson→personでも独立。CONTRIBUTED_TOの制作参加だけでは人物への影響やアシスタント関係を示さない。AFFILIATED_WITHと作品への参加も独立。各語彙は他の既存3語彙との比較理由を持つ。未登録を否定の根拠にしない。

## コマンドと変更検出

```bash
npm run vocabulary:check
npm run vocabulary:check -- --hashes
# 複数コミットを含む変更の審査には、変更開始前の信頼できるcommitを指定する
npm run vocabulary:check -- --base-ref <変更開始前のcommit>
npm run vocabulary:check -- --hashes --base-ref <変更開始前のcommit>
```

既定のGit比較先はHEAD。作業中の変更を検出する。**変更をすでにコミットした場合、変更開始前のcommitまたはPRのbaseを明示する。** HEADだけではそのコミットで基準版まで書き換えたかを判別できない。将来CIを導入する時もPRの信頼できるbaseを渡す。現在リモート／CI／ブランチ保護はなく、今回導入しない。

固定baselineとの比較は常に実施。指定したGit版にbaselineがある場合はその書換えを拒否し、承認済み比較票の変更・削除も拒否する。Git参照が存在しない場合は失敗し、比較を黙って省略しない。初回導入に限り、比較版にbaselineがないことを明示する。

npm run lintとnpm testの先頭でもチェックを実行する。警告は正常終了、エラーは非ゼロ終了。アプリのbuildやAPI起動を語彙審査の代用とはしない。

## 機械が拒否するもの

- 未知フィールド、不正ID、重複ID、未知・自己・重複した比較先、比較理由や必須事項の空欄。
- 含む・含まない・境界例の欠落、定義言語の表現欠落。
- 実行辞書に契約がない、契約と端点・表示・説明が異なる、関係選択labelの不一致。
- 使用済みIDの削除、端点kind・主体／対象の意味の変更、廃止IDの再利用。
- 新規predicateに全既存語彙との比較または一致する承認済み比較票がない。
- 変更前後のhashに一致する承認済み比較票がない。同義と記録した概念を別predicate IDで増やす。
- 明示的な意味変更を既存IDのまま承認する。意味契約の変更を翻訳だけの修正として処理する。
- 役割・分類という判断結果を、新predicateの追加承認として利用する。
- 承認者・判断日の欠落。Git比較先にある基準版・承認済み比較票の書換え。

hashはオブジェクトのキー順に依存せず、配列の内容・順は保持して変更を検出する。基準版から複数の承認を経た明確化はhashで結んだ履歴として確認する。Git比較では直前の契約との差も確認する。承認済み票を無効な旧hashのまま使い回せない。

## 警告と人間審査

機械はlocale別の正規化したlabel / aliasの重複、同じ端点組、同じ定義文、基準版からの変更を警告する。表記の正規化はNFKC・前後空白・小文字化で、意味を解析しない。近いが文字列の違う語彙の自動発見は保証しない。

同名別概念はあり得るため、名称重複だけで拒否しない。現在の通常チェックの1警告はASSISTANT_OF / INFLUENCED_BYの同一端点組。これは故障ではなく比較確認の対象。

人は実資料の解釈、同義か近接か、限定か新命題か、例の十分性、翻訳が誤解を招かないかを判断する。**「clarification」と記入した変更が実際には意味を広げているかを機械だけでは見抜けない。** hash、比較票の必須化、明示的な端点変更の拒否は、その判断を見える形にする仕組み。

審査時は票の記入だけで承認せず、before / afterの契約差分、全既存語彙との比較、原資料例・反例を確認する。status=approvedは審査結果の記録であり、承認者の本人確認・権限制御ではない。リポジトリを変更できる人がvalidatorや基準版も意図的に改変することは、Gitレビューや将来のCI・保護設定で扱う。意味の完全保証・真実認定・セキュリティ境界ではない。

## 新predicateを1件提案する手順

1. [TEMPLATE.json](../../vocabulary/reviews/TEMPLATE.json)をもとにrecordsへdraftを追加する。テンプレートはチェックの承認対象ではない。TODOを具体的な内容に置き換える。
2. 実資料例・反例を示し、predicate / role / classification / alias / presetのどれが適切かを判別する。現在の4語彙すべてとの比較を記入する。
3. 同義なら既存IDの別名、制作役割なら限定として保留・別フェーズへ。必要な新命題の場合だけ新IDと契約・包含／除外／境界例を追加する。既存IDの意味を広げて代用しない。
4. predicateを実際に追加する場合、実行辞書・型のキー・関係選択labelにも整合する定義を追加する。条件/APIに必要な変更はその追加フェーズで別途評価する。
5. --hashesで追加対象のafterHash（beforeHash=null）を取得し、比較票に記録する。既存語彙の更新ならbefore / afterを記録する。
6. 人が資料・差分・全件比較・Claim／条件／翻訳／表示への影響を審査する。必要な新predicateならkind=predicate、outcome=new-predicateで承認者・日付・理由を記録する。draftのままでは公開変更のチェックを通らない。
7. 語彙チェック、契約テスト、既存テストを通す。審査開始前のGit版とのチェックも実施し、レビュー記録と一緒にコミットする。

新しい語彙が増えた後の追加では、Git比較版に存在する全語彙との比較も要求する。既存の契約を新語彙追加のたびに書き換える相互比較は要求しない。新しい側の比較票と契約で全件を比較する。

意味を保つ明確化・翻訳修正も同じ変更チェックを通る。意味が変わるなら新IDが必要。旧IDと旧定義を保持し、旧Claimや保存条件を自動置換しない。

## パイロットと将来Roleの確認

テストは凍結台帳の8件をIDで参照し、原表記（プロデュース・監修・脚本・著・ストーリー共同制作等）、資料の巻・版の限定、広いCONTRIBUTED_TO、Claimにroleがないことを確認する。原作由来と組織の協力が保留されていることも確認する。原資料から意味を自動分類するテストではない。

契約には「役割なしは全役割の肯定ではない」「将来の役割限定の否定を制作関与全体の否定へ変換しない」を含める。作画affirmedと監修deniedは両立し得るという境界を維持する。今回はRoleのvalidator・Claim型・矛盾判定器を実装していない。

Role対応前に決めること:

- 最初の役割集合、資料の原表記からの正規化、役割なしの解釈、一Claim一役割。
- 期間・巻・版等の限定、肯否がかかる命題、比較候補と同一内容の区別。
- DB・投入・APIの具体型、条件のLIMIT前評価とcursor、relatedClaimIdsと詳細の区分。
- 「異説あり」が役割の違う肯否を対立と見せない表示契約。
- 新しいデータ版での根拠付き受入、現在の広いClaimの保持。凍結版の自動移行は行わない。

これらを確定してから限定されたRole対応へ進む。今回のチェックだけで、Role対応やUIの新しい集約が実装済みになったとは扱わない。
