# 探索画面の入口・探索軸・条件提示のレビュー

2026-10-04。Phase 06完了後のコード・現役docsを基準にした設計レビュー。推奨範囲を承認され、**Phase 07で採用・実装済み**。[実施記録](../archive/phase-07-exploration-entry/IMPLEMENTATION_EXPLORATION_ENTRY.md)を参照。本文の現状分析はレビュー時点の状態。一般Entity検索・開始例・プリセット等は引き続き未実装の提案。

## 結論

人物起点のVertical Sliceは妥当だった。現在の問題は、その検証用の操作面が一般的な探索の入口を兼ね、検索・辿る範囲・制作役割を初回から同時に判断させていること。データや探索エンジンを作り直す必要はない。

**対象を探す → 選んだ対象からまず辿る → 必要なら見る関係を調整する**、を既定の流れとする案を推奨する。見たい関係が決まっている人は起点選択前にも条件を設定できる。同じ画面・同じ探索セッションを使い、自由探索／条件探索の別モードを先に作らない。

検索、適用中の探索条件、条件の編集を役割で分ける。詳細な条件編集は段階的に提示するが、適用済み条件は常に確認できるようにする。「Roleを隠す」こと自体を目的にせず、制作関与の追加条件として発見・変更・解除できる位置へ戻す。

## 1. 実際の構造と暗黙の前提

暗黙の前提は「名前を知っている人物がいる」「関係タイプを選べる」「制作役割も最初から検討したい」「条件を変更すると枝を捨てて再取得することが分かる」。それぞれ単独では技術検証に適するが、初回利用者に同時に求めると入口が制作検索に偏る。

初期画面には空Graph、Entity／Claim／Relationの0件、未選択、線の集約の説明、操作凡例も出る。探索前の情報より内部動作の説明が目立つ。v2の「制作Role」badgeも検証目的の表示として正しいが、サービスの主目的を説明する文言とは分ける必要がある。少数実データ・非網羅の表示は維持する。

コード上で全てが混ざっているわけではない。検索stateとGraph stateは別で、候補のkindに関係なくEntitySummaryを起点へ渡せる。混在の中心は画面上の優先度と、条件編集部品に集約された操作の見せ方である。

## 2. 分ける概念

| 概念 | 利用者の問い | 扱うもの・分離するもの |
| --- | --- | --- |
| 検索対象 | 何を探すか | 検索語、任意の対象種別、将来の検索言語。候補発見の条件であり、Graphの辿る範囲ではない |
| 探索の起点 | どこから始めるか | 選択したEntity内部ID。検索結果の選択で決まる。検索語や現在選択中Nodeとは別 |
| 探索軸 | どんな繋がりを見るか | 利用者の関心。現在は正確なpredicate集合として指定できる。将来プリセットが条件・表現へ解決するが、軸という概念とプリセット機能は同一ではない |
| 関係に付く絞り込み | その繋がりをどこまで限定するか | 現在は制作関与のRole。将来の期間等は未対応。検索候補の絞り込みやEntity属性とは別 |
| 適用中の条件 | 今、何を辿っているか | 正規化されたpredicate／Role集合。編集draftと分け、画面の要約はこの値から作る |
| 探索途中の状態 | どの枝を開き、何を確認しているか | 開閉・受理ページ・cursor・現在選択・座標。条件設定や検索語と同一視しない |
| 表示・操作設定 | どう眺め、操作するか | 配色、条件編集の開閉、将来のペイン幅等。取得条件キーに入れない |

概念を分けることは、7個のペインや汎用schemaを作ることではない。利用者には「探す」「見る関係」「必要な追加条件」程度のまとまりでよい。

例：作品を検索して起点にしても、人物との制作関与を取得できる。検索対象を「作品」にしたことからGraphのpersonを除外しない。保存方向person→work、作品側の探索、作品視点の説明も別であり、逆向きのClaimを追加しない。

## 3. 推奨する入口と情報の順序

### 初期状態

主操作は対象の検索。検索対象種別やプリセットを先に選ぶことを必須にしない。将来の一般検索では人物・作品・組織を一つの入口で探し、結果に種別と区別情報を示し、必要なら対象種別で絞る案を推奨する。ただし現在の人物専用APIでは、人物を探すと正直に示す。「人物・作品を検索」という未対応の約束を先に表示しない。

名前が決まっていない利用者には、収録範囲内の少数の開始例を任意に提示する案がある。これは入口の補助であって新しい軸のカタログではない。現時点の人物例は実行可能だが、作品から直接始める例は別の起点選択手段が必要。人気・信頼度の順位や大量の推薦機能は不要。開始例が必要か、件数や位置は操作観察で決める。

Graph領域は「対象を選ぶと周囲の関係を辿れる」という次の行動を案内し、空の凡例・集約説明・未選択詳細を常時並べる優先度を下げる。少数実データ／架空データの区別は残す。条件の入口には「見る関係：制限なし」のような短い要約と編集導線を置く案とする。ここでの「制限なし」は対応済みの公開Claimに追加条件を指定しない意味で、全世界の知識・全件取得・上限なしを保証しない。

### 起点選択後

既定の無指定条件で一段階取得し、Graph操作と詳細確認を主役にする。関係条件の要約をGraphの文脈に近い場所へ置き、条件の編集を開けるようにする。三列を維持する場合、左は対象検索、中央上部は起点・適用条件・条件編集の導線、右は選択対象の詳細という役割が自然。具体的なポップオーバー／開閉領域／ペイン等は実装時に画面高・キーボード操作・Graphの占有面積で判断する。

GraphのNodeをクリックしただけでは起点を変更しない。現在の即時選択、必要な一段階展開、選択済みNodeの再クリック開閉を維持する。「起点」と「選択中」を区別し、別の対象から始める操作は新しい探索として明示する。

見たい関係が決まっている利用者は、検索前でも条件編集を開いて設定できる。この場合は起点選択時に確定した条件で取得する。起点の選択を条件編集のロック解除条件にしない。

### 文脈が決まってから見せる情報

- 関係を調整したい時：既存4 predicateの正確な意味に対応する選択。初期全件のチェックリストを毎回読み終える必要はなくす。
- 制作関与を調整する時：「制作の役割で絞る」等の追加操作からRole編集へ進む。制作関与が有効なだけで全Roleを自動展開しない。
- Roleを指定した後：適用要約にRoleとその作用対象を必ず残す。編集を閉じても有効条件を隠さない。
- Relation／Claim選択後：個々の肯否・期間・制作役割・刊行物限定・Citation／Source、広い主張との比較。複雑な意味はここで説明する。
- 未取得ページ・上限・エラー発生時：その状態と次の操作。条件編集の説明で覆い隠さない。

条件欄の露出を、選択中Entityがpersonかworkか、現在取得済みのRoleがあるかだけで決めない。制作関与は両端から辿れるし、未取得・条件外・未構造化のデータもある。その判定でRole編集を隠すと、必要な条件を選ぶ入口まで失う。

## 4. Roleと関係条件の位置づけ

現在の「辿る関係」は探索全体の条件を編集するもの。選択Nodeだけの絞り込みではない。UI上で位置を変えても、この作用範囲を維持する。Roleはそのうち制作関与にだけ掛かる条件で、人物や作品の共通属性フィルタへ持ち上げない。

関係編集の中で制作関与の追加条件としてRoleを配置し、全関係を対象にする時も任意に指定できる案を推奨する。制作関与だけを選んだ時しかRoleを設定できない構成にしない。

役割指定の操作は「役割で絞らない」と「役割を指定する」を区別し、後者でRoleの複数選択を提示する案が分かりやすい。全件という項目と個別Roleを同格のチェックボックスとして並べる現在の方式では、意味の異なる操作が同じに見える。具体的な部品はまだ固定しない。

| 利用者向けの意味 | 現行内部値 | 維持すべき違い |
| --- | --- | --- |
| 制作関与を役割で絞らない | Role=null | 役割を限定していない広いClaimも含む |
| 選んだ役割の主張を見る | Role=[指定ID] | OR条件。役割が未指定のClaimは対象外。否定Claimも取得対象 |
| 全4 Roleを個別に選ぶ | Role=[4 ID] | 構造化された4 Roleだけ。nullとは異なる |
| 役割指定だが0件を選ぶ | Role=[] | 制作関与だけ対象なし。他の有効predicateの関係は残る |
| 関係を0件選ぶ | predicates=[] | 全関係が対象なし。孤立Entityとは別 |

0件を自動的に無指定へ補完しない。Role指定で選択0件なら、適用前に「制作の関係は表示されません」と説明する案を推奨する。全関係を外した場合は「関係を表示しない」と明示する。現在の空集合契約を変える必要はない。

例：「影響＋制作（プロデュース）」なら人物間の影響はそのまま、制作関与はPRODUCINGだけ。画面全体を「プロデュースのみ」と要約しない。「監修」も肯定された担当だけという意味にせず、詳細で肯定／否定を区別する。初期UIにpolarity enumやnullを表示する必要はないが、Role条件が否定の主張も対象にする説明は編集時に短く残す。

制作関与を取得条件から外して適用した時は現行正規化どおり有効Role条件も解除する。再び制作関与を選ぶ時は役割無指定から始め、古いRoleを黙って有効化しない案を推奨する。編集中の一時的な保持はdraft内に限り、確定値の解除／再適用と混同しない。

## 5. 条件変更・編集表示の契約

**編集UIの表示変更と、探索条件の変更を別操作にする。** 編集を開く／閉じる、ペインを広げる、要約を表示するだけでは通信・世代・cursor・開閉意図・選択・座標を変えない。

適用時の探索挙動は既存契約を維持する。draft中はGraphを変えず、明示適用で新世代・旧通信abort・受理範囲／cursor／開閉意図をリセットし、同一起点から再取得する。条件変更の直前には「同じ起点から取得し直す」ことを説明する。座標・pan/zoomは可能な限り維持するが、以前の枝が自動復元されるとは約束しない。同じ実効条件なら再取得しない。

検索候補の取得／将来の検索対象種別変更は、現在のGraphを変えない。結果の選択で起点を変更し、適用中条件は維持する。新しい起点でも条件要約を見える位置に残す。条件draftがある時に候補を選んでも、未適用draftを勝手に適用しない。

条件編集を閉じる時のdraftについては、次フェーズではキャンセルを明示し、再度開く時は適用値から初期化する案を推奨する。閉じた編集欄に見えない未適用条件を残す方式は避ける。条件解除は編集取消と別操作で、実効条件が変わるため再取得が必要。未来の履歴／戻るで枝を復元する機能まで約束しない。

UI構造を変える際はdraftの同期を小さく整える必要がある。現在RelationFilterはuseStateの初期化でpropsを読むだけなので、将来外部の条件解除やプリセット適用で有効値が変わるとdraftが古いままになり得る。適用値・draft・編集開閉の境界を一箇所で管理するか、編集開始時に確定値へ揃える。Graphの世代変更だけに頼って部品を再マウントしない。

## 6. 自由探索と軸による探索の共存

自由探索は追加条件なしという既定値。軸による探索は同じセッションへ条件を与えるものとする。現在の4 predicate選択を、汎用taxonomyや保存プリセットに見せかける必要はない。

将来プリセットを入れた場合も、解決された条件を同じ要約／編集へ渡す。プリセット名と具体条件の出自は分け、個別変更した条件を元プリセットそのものと表示しない。preset名・locale・編集欄の開閉をcursorや取得キーに入れない。

「作品と作者の影響を時系列で見る」は探索軸の意図として自然だが、現在はwork→workの影響predicate、時系列表現、複数起点が未対応。制作Roleを選ぶだけでその要求を満たせない。現在の「影響を受けた」はperson→personのみで、制作関与から作者を推定しない。未対応の軸は実行可能なメニューとして出さない。

## 7. 既存実装の再利用と変更が必要な境界

| 対象 | 入口整理での扱い |
| --- | --- |
| neighbors API／Cypher | 関係・Roleの正確な取得条件とLIMIT前評価をそのまま利用。UI折り畳みのためにAPIへvisible等を追加しない |
| 正規化・conditionKey・cursor | そのまま利用。無指定／空集合、Roleの作用範囲、dataset／起点／条件の一致を維持 |
| GraphState／projectGraph | そのまま利用。編集欄の開閉はGraphStateへ入れる必要がない。多条件キャッシュを先行導入しない |
| useGraphExplorer | chooseRoot、changePredicates、展開・閉じるを再利用。名前の見直しや引数の整理が必要でも挙動は変更しない |
| GraphCanvas／DisplayRelation | そのまま利用。Role条件は集約前、詳細は個別Claim。条件のUIから新しい表示束を作らない |
| Claim詳細API／比較 | 全公開の同三つ組を比較し、条件外／未表示を説明する方針を維持。選択時に条件を自動変更しない |
| SearchPanel／人物検索 | 次のUI整理では現在の人物検索を利用できる。一般Entity検索は別途検索APIの入力・kind・結果label・上限・テストを決める必要がある |
| RelationFilter／Explorer | 主な整理対象。条件要約とdraft編集、Roleの文脈表示、検索と起点／選択の言葉を整理する |
| 詳細ペイン | 条件編集を右に移してさらに狭くしない。深掘りは条件設定とは別の読み取り領域として確保する |

近傍APIは現在もwork／organizationを中心に両方向取得でき、Graphの中では作品・組織を辿れる。検索だけが人物限定である。作品起点の追加では知識モデル・Claim方向・ページングモデルを変える必要はないが、検索APIの人物専用契約は変更が必要になる。単に同じ左列へ作品検索と組織検索のフォームを積むと、どの結果がどのGraphを開始し、条件が何に掛かるかがさらに不明確になる。

## 8. 代替案とトレードオフ

| 案 | 利点 | 負担／判断 |
| --- | --- | --- |
| 現在の全操作を常時表示 | 慣れた利用者には一覧性がある | 初回に判断が多い。Role等が増えるほど画面と主目的が偏る。既定の入口には非推奨 |
| 検索対象→軸→条件を必須の順に選ぶ | 条件を厳密に指定しやすい | 関心が未確定の自由探索を始めにくい。現在は独立して指定できるものを不要に直列化する |
| 独立ホームで対象／軸の入口を分ける | 起点未定の人へ説明しやすい | 画面遷移と探索の復帰を設計する必要。少数パイロットで先に増やす根拠が弱い |
| 選択Nodeや取得Roleに応じ自動で条件を出す | 一見、関連情報だけに絞れる | 制作関与の両端・未取得Role・有効条件を見失う。選択が変わると設定UIも揺れる |
| 同じ探索画面で検索を主入口、条件を段階提示 | 起点を知らなくても知っていても始めやすく、既存エンジンを使える | 編集の発見性と有効条件の可視性を検証する必要。今回の推奨 |

新しい分類体系を導入して「制作」等へ既存predicateを勝手に再分類する必要はない。利用者向けの言葉を平易にしても、意味契約と語彙レビューの境界を守る。安定IDとlocaleによる解決を前提とし、文言をconditionKeyへ使わない。

## 9. 今決めることと後回しにできること

今は、検索条件と探索条件の独立、起点と選択の区別、自由探索の既定値、関係条件の全体作用、Roleの制作関与限定、条件要約の可視性、編集開閉と条件適用の違いを決める。ここが曖昧なまま作品検索・期間条件・プリセットを積むと、条件の保存先と部品ごとの状態が増え、後で全体を作り直しやすい。

右ペインの寸法やRoleチェックの部品選定は、この責務分担を踏まえて行う方がよい。先に幅だけ広げても条件の露出順は変わらない。一方、既にある長いラベルのはみ出し等、明確な可読性問題を全て将来設計まで止める必要はない。意味を変えず局所改善できるものは別に扱える。

後回しにできるものはホームの有無、プリセットカタログ、taxonomy、検索ランキング基盤、時系列、複数起点、期間条件、会員保存、URL／履歴復帰、可変幅／全画面詳細の具体方式。多言語自体は後回しの任意要件ではなく、今から表示文字列の境界を守り、翻訳追加や切替UIの時期を後で決める。

## 10. 推奨する次の1フェーズ

**「既存機能を使った探索の入口・条件提示の再構成」**を推奨する。対象は人物検索の現行能力を正直に示す入口、適用条件の要約、必要時に開く関係／Role編集、Graphと詳細の役割整理。プリセットや作品検索のAPI変更を同時に必須化しない。

実装を承認された場合の順序：

1. 初期・探索中・条件編集中・詳細確認中の4状態の小さい画面案を作る。Graphの表示領域と条件編集の発見性を確認する。
2. 適用条件とdraft／編集開閉を分ける。既存取得・条件世代・開閉を維持し、解除／空集合／起点変更の挙動を固定する。
3. Roleを制作関与の追加条件へ位置づけ、無指定と個別役割の違いを操作に反映する。適用中のRoleは要約で常に確認可能にする。
4. 詳細の読取領域を確認し、必要な範囲で幅・縦配分を調整する。Source／刊行物限定／条件外Claimへ必ず戻れるようにする。
5. demoと凍結v2で操作観察と回帰検証。検索候補から無条件探索、条件先行、Roleの発見・混合条件、閉じた編集欄の有効条件、キャンセル、空条件、条件適用、開閉／復元／ページングを確認する。

完了基準は、条件を決めていなくても探索を開始でき、必要な時に関係・Roleを調整でき、その作用範囲と現在の条件が見失われないこと。条件を編集するだけで探索が消えず、明示適用の再取得だけが既存契約に従って起きること。条件UI整理でDB・dataset・predicateの意味を変えない。

その後、作品／組織から始める需要を確認し、同じ入口へ一般Entity検索を足す小さいフェーズが自然。名前が未定の人がなお始めにくいなら開始例、軸を指定したい人が増えれば小さいプリセットを検討する。今回これらの機能を採用済みにはしない。
