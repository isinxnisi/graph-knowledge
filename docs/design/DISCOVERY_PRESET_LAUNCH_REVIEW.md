## 結論

現状の主導線は「再利用できる探し方を選ぶ→開始対象を名前で指定する」に寄っており、今回目指す「プリセットを選ぶ→実際のつながりが現れる」と整合していない。実装側で**再利用可能であることと、先に対象を選ばせることを結び付けた**のが直接の原因。APIが名前入力を必須にしているわけではない。

推奨は、既存の「PLUTOで試す」等が使う直接実行を主導線へ移し、任意の対象指定を補助操作へ移す小さい修正。プリセットの汎用性はそのまま保ち、公開KG上の代表的な開始対象から毎回実際の記録・経路を取得する。対象を内部で選ぶ方式と、開始対象なしで全KGの経路を列挙する機能は別物である。

## なぜ名前検索へ移るのか

### UI

`components/DiscoveryPresetBrowser.tsx` は、固定対象なら「探索する」、再利用可能なら「対象を選んで使う」を主操作として `onSelect(preset)` を呼ぶ。直接実行する `onSelect(preset, true)` は「PLUTOで試す」等の別操作になっている。

`components/DiscoveryExplorer.tsx` の `selectCatalog` は `execution.type === "template" && !example` の場合に、経路APIを呼ばず `catalog.mode = "names"`、`pending = preset.id`、名前入力を空にして終了する。このため既に適合する対象を選択済みでも、名前検索へ移り、別途「PLUTOを使う」等を押す必要がある。betaでこの追加ステップを再現した。

### API

- `/api/entities` は名前・別名検索。`q`が必要で、今回の選択画面はこのAPIを使う。
- `/api/discovery/entities` は**空欄＋kind／関係／制作Roleから候補対象を取得できる**。今回のプリセットの対象選択には未接続。
- `/api/discovery/claims` は対象未指定の一段の記録検索に対応している。
- `/api/discovery/paths` はUUIDの `anchor` を一つ必要とする。有界な2／3段探索であり、「ユーザーが名前を入力しないと実行できない」という契約ではない。

経路APIからanchorを省略すると400。PLUTOを組織開始のinstitution-bridgeへ渡しても400。名前入力を省くには、UUIDをUI側の代表入口や候補選択処理が決めればよい。既存API全体が対象未指定検索に未対応という説明は誤りになる。

### プリセット定義

`lib/domain/discovery-preset-catalog.ts` は、固定対象に `anchorId`、再利用可能なものに版付き `path` と `exampleId`／`exampleName` を持つ。後者にもすでに入力なしで使える開始対象がある。これを主操作に接続せず、再利用を「先に対象指定」として表現したのはUI実装上の判断だった。

## 3件以外の対象・適合性

3件の表示は `prototypeSeeds` の固定配列を対象選択にも流用したもの。候補対象をKGから網羅取得した一覧でも、許可対象リストでもない。作品開始ではPLUTO以外の2件はkind不適合、人物開始では3件ともkind不適合で無効になる。betaで取得完了後も人物用の3ボタンがすべて無効になることを確認した。初期のおすすめプリセットと、任意対象の選択候補を混同させている。

名前を入力すれば3件以外も取得できる。UIは `pendingPreset.kind` とEntityのkindで適合性を判定し、不一致の実行ボタンを無効にする。経路APIも開始kindを再検証し、各段のkind列・正規方向・predicate／Roleを検証する。**kind適合は経路の存在保証ではない。** 分野タグはカタログ用で、任意対象を暗黙に分野分類して制限しない。

## 推奨する最小修正案A：代表入口から直ちに実行

**利用者の流れ：プリセット検索→「つながりを見る」→実際の記録／経路一覧→個別経路・根拠・Graph。名前検索は必須にしない。**

1. 再利用可能な5件の主操作を、現在の直接実行分岐に接続する。「対象を選んで使う」を主操作から外し、「つながりを見る」等にする。固定対象3件の動作は維持。
2. 開始対象を「PLUTOから」等と事前／結果の両方で分かるようにする。代表的な入口であり、全対象・全KGの網羅結果ではないことを表示する。現在の `exampleId` を再利用すれば、定義の大改造も不要。
3. 任意指定は「対象を変えて使う」等の補助操作として残す。初回の開始対象はプリセットの明示した代表入口にそろえ、過去のContextから予想外の別対象を黙って優先しない。現在の対象を使う場合は利用者が明示して選べる。
4. 補助の対象選択画面に入ったときだけ、初期おすすめ3件を対象候補として繰り返し表示するのをやめる。必要なkindと「公開KGの任意の作品／人物／組織を検索できる」ことを明示する。例を表示する場合はそのkindに適合する補助例と明記する。初期カタログのおすすめ3件はそのまま残す。
5. 取得失敗・版変更・0経路・取得上限による未発見を区別する。自動的に名前検索へ戻したり、Roleを外して結果を作ったりしない。代表入口が使えない場合はその理由と再取得／別対象への任意操作を示す。

変更箇所は主に `DiscoveryPresetBrowser` の主／補助操作、`DiscoveryExplorer` の開始分岐とpending時の対象候補表示、対応するブラウザー試験。必要な短い説明文以外、絞り込み・ソート・アイキャッチ・デザイン細部・他2タブを変更しない。任意対象の候補をkindで絞る改善も、既存名前APIへkindを渡す小さい接続変更で可能だが、主導線の直結に必須ではない。

**API・Cypher・Graph codec・公開データの変更は不要。** 汎用の経路定義、Context／Undo、catalogの絞込・並び順・戻り位置、現在の記録／経路表示、Graphの版付きviaと全段再検証を再利用する。再利用可能な探し方を固定対象だけの機能へ変更するわけではない。

## 対象未指定の自動発見を広げる案B：後続候補

公開KGから対象候補を取得して、成立する経路を少数提示する方式も可能。名前なしの `/api/discovery/entities` を今回確認した結果、CONTRIBUTED_TOに接続する作品は10候補、人物は7候補、AFFILIATED_WITHに接続する組織は371候補（初回20件・続きあり）、AUTHORSHIPに接続する作品は6候補だった。いずれも**一段の関係条件による対象候補数であり、複数段が成立する対象数ではない。**

候補APIの順序は名前等の安定順で、経路の成立や発見の面白さによる順位ではない。候補応答のrevisionへ経路要求を束縛し、途中で版が変わったら結果を混ぜず再取得する必要がある。

これらの候補から必要kindの対象を少数選び、既存経路APIで形・Roleに合った経路が成立するか確認できる。新検索エンジンやDSLは不要。ただし、候補対象と完成経路の違い、候補を何件試すか、全体の取得時間／展開数、同じ経路の逆向き重複、取得途中・空振り・再試行、候補ページの巡回、revision単位の結果保持を扱う入口選択処理が追加で必要。既存APIの単純な一回呼出しにはならない。クライアントでの調停／サーバー集約の選択は後続の規模に応じて決められ、現時点で新APIが必須とはしない。

初期は編集側が指定する少数の代表Entity IDを入口として使い、経路やClaimそのものは保存しない方式を推奨する。将来はプリセットの実行条件と `entryTargets` のような複数の入口候補を分離できる。公開revisionごとに生存・kind・成立経路を検証し、未公開r0003を混ぜない。最小案Aの段階では複数候補機構や自動選択サービスを実装する必要はない。

## 対象未指定での制約とGraph再利用

- ユーザー未指定でも、現行経路APIの内部実行には具体的な開始UUIDが必要。anchorなしの全KGの2／3段検索は未実装。Aは代表入口の選択でこの前提を満たし、Bは候補の自動選択で満たす。
- 各対象20記録、全段24対象、128中間経路、12結果、2／3段という現在の制限を維持する。複数の開始対象を試す際は一対象ごとの上限に加え、処理全体の予算が必要。組織371件へ一斉に経路要求を送らない。
- 0経路でも未取得の記録があれば不存在とは扱わない。代表対象の全候補でも、他の対象や知識世界全体の全候補ではない。対象候補のページ件数と経路件数も合算しない。
- 世界をDB分類へ変換しない。段別Role、期間の共通部分、肯定のみの条件等は今回の既存経路機能にない。プリセットの目的を満たさない別Claimの条件を合成しない。
- 既存 `discoveryPathHref` は具体的な端点列・各段のClaim IDとrevisionからGraphへ渡せる。`rebuildExplorationUrl` は各段の再取得と版・記録を検証する。開始対象をユーザーが入力したかシステムが選んだかには依存しないため、AでもBでも個別経路のGraphはそのまま使える。
- Bで複数対象の経路を同時に列挙する場合は、各結果に開始対象・実行条件・部分取得範囲を持たせる追加の表示／状態整理が必要。候補全部を一つの巨大Graphに自動展開することは今回の最小案に含めない。
