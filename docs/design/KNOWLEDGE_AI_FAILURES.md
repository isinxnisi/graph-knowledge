# 確認サービスの一時障害と自動再開

2026-11-05。利用者の知識投稿を確認する既存Gemini無料接続に適用する。モデル・API key・利用枠・有料fallbackは変更しない。通常の一時障害を、投稿者の内容不備や管理者の個別承認待ちへ変えない。

## 判断根拠と状態

Google公式は503を一時的な過負荷／停止とし、指数バックオフとjitterを推奨する。[APIエラー](https://aistudio.google.com/docs/api-errors)／[再試行の指針](https://aistudio.google.com/docs/troubleshooting#retry-strategy)。利用者提示のAI Studioには当該projectの503が表示されていた。ただし過去3試行の正確なHTTP statusを後から復元した証拠にはしない。

| 結果 | 投稿確認の扱い |
| --- | --- |
| HTTP 408 / 500 / 502 / 503 / 504 | 一時障害としてretry。内容への不受理判定をしない |
| DNS／接続／TLS／timeout等で応答不明 | 消費・送達が不明な試行を保持。0消費にせず、間隔を空けてretry |
| HTTP 429 | quotaとして、Retry-Afterと既存の無料利用枠に従って自動再開 |
| 認証・権限・不正な要求等 | attentionで設定確認。一時障害として無限に再送しない |
| 正常応答だが形式不正・対応モデル不一致 | 従来の検査を維持。支持確認・公開を省略しない |
| 内容の補足が必要・不受理・取消 | それぞれの状態を維持し、自動で受理／再開しない |

## 待機・消費・公平性

永続queueで1回ずつ送る。HTTPクライアント内の隠れた再送は増やさない。基準待機2分→4分→8分→16分→32分→最大1時間にjitterを加え、Retry-Afterが長い場合はそちらも尊重する（最大24時間）。project共通の待機にも反映し、別項目が直ちに同じ障害先へ送信することを防ぐ。

1項目はquota日付あたり最大8送信。到達後は次の利用日に自動再開する。Google無料project全体の日／月／分・token・用途配分の既存上限も毎回予約・照合する。応答不明は実token量null・予約分確保とし、消費0と偽装しない。資格の切替や課金有効化で上限を迂回しない。

待機中に投稿を訂正・取消したり会員を停止／削除した場合は、現在版・同意・資格を再照合して止める。復帰後も原資料照合・現在参照・重複・最終受理を通し、同じreceiptと既存のidempotencyを使う。

## 診断と過去の停止

会員privateのreview_payloads.responseに、成功のprovider応答か、kind=attempt-failure / version=1の診断を保存する。HTTP status・分類・正規化Retry-After、許可した通信error codeを保持する。API key・header全体・URL・原文・providerエラー本文・生の例外messageは診断へ保存しない。Workerのログにもattempt IDと同じ非機密の分類だけを出す。成功応答の復旧は従来通りattemptのreceived状態を必要とし、失敗診断を成功応答と誤認しない。

旧「3回試しました」でattentionとなった投稿は、旧一時障害停止の固定理由・resultなし・最後の試行種別・現在の受付内容と会員状態を照合してretryへ戻す。内容への判断・設定エラー・取消・別版を一括で再開しない。送信上限は過去の実試行を含めて数え、直接DBで成功状態を作らない。

追加migrationなし。既存のprivate payloadは退会時の削除対象のまま。共通HTTPクライアントは通信の診断を返すが、今回この再開policyを接続したのは**利用者投稿の確認queue**。収集読解・翻訳生成・原資料取得に残る各3回上限まで変更済みとは扱わず、再計画の共通化残件へ引き継ぐ。
