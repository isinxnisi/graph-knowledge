| 誰が | 本運用初版でできること |

## 2. 収集とユーザー投稿を分ける

### 運営収集の経路

`対象・任意のテーマ・範囲を指定 → 取得／読解／整理 → 機械的な整合確認 → 登録・公開反映 → 必要な部分を後追い管理`

- 同じ収集結果への全件人手承認、毎バッチの個別署名、公開のためだけの再承認を、新経路の必須操作にしない。収集依頼や通常の運営設定で対象範囲・予算・登録先を決めることと、結果を一件ずつ審査することを分ける。
- 不完全な一件で独立した完成分まで止めない。「12件反映・2件要対応」のように示し、取得失敗、識別の衝突、参照欠損、反映待ちを区別する。未知の関係名・外部IDなし・意味未対応だけでは失敗にしない。
- 対象の同一性が決まらない場合は既存対象へ推測統合せず、識別未確定の候補を保持する。独立した対象として記録可能な場合と、関係の端点自体が決まらない場合を分ける。
- 管理画面は全件消化を要求する承認待ち箱にしない。入力元、直近変更、疑義、訂正依頼、根拠、確認履歴で探し、確認・訂正・非表示・復帰ができる。未確認件数を減らすこと自体を運用目標にしない。
- 資料の支持、対象同定、意味対応の確度は由来とともに保持する。機械検証やAI処理の成功を、人間が事実確認した証拠にはしない。

### ユーザー知識投稿の経路

`直接入力／Capsuleの選択部分 → 受付 → AIによる一次チェック・必要な補助 → 審査中／修正依頼 → 受理・一部受理・不受理 → 本線反映と結果通知`

- このワークフローを初版に残す。収集側の承認を省く方針を転用して、投稿を無条件に本線へ流さない。
- AIは荒らし、無意味な入力、スパム等を確認する。単語だけを禁止して作品名・資料引用・専門用語を弾く方式にはしない。根拠候補の整理・入力の不足や明白な不整合の検出も支援するが、投稿適格性と事実判断を一つの「正しい確率」にしない。
- **推奨する初版の処理は「AIで通常分を自動審査し、判断できないもの・異議申立てだけ運営確認」**。全件人手審査を必須にしないが、自動受理の対象・判定条件は実データ評価で絞る。この受理方針は今回の提案であり、ユーザーがワークフロー削除を承認したという意味ではない。
- 迷惑投稿チェックの通過だけで資料不足を解消した扱いにはしない。提供資料から支持する箇所を得られなければ補足依頼・保留にし、AIの内部知識を取得済み根拠として作り込まない。根拠の評価をすべて人手へ戻すこととも区別する。
- 審査対象は投稿時の内容版。AI補填は原入力と別に示し、意味が変わる補填は投稿者が確認する。部分受理では残った項目・理由・受理先IDを返す。元Capsuleの本文・公開範囲は変更しない。
- 入力は任意の資料URL・書誌を添えられる。資料が不足する場合、初版では提供資料内の候補整理・補足依頼までを確実に実装する。自由なWeb検索で根拠を必ず見つける機能は後続に残す。根拠なしでも草稿や確認依頼を保存できるが、見つからないことを虚偽認定しない。
- AI停止・上限到達・判定不能は「チェック待ち／審査中」として保存し、待つ理由と編集・取消を示す。AIの障害を投稿拒否にせず、未チェックの投稿を公開へ迂回させない。訂正候補が待機しても、既存公開版を勝手に差し替えない。
- 状態・結果通知はまずサイト内の本人一覧と既存通知の仕組みに接続する。メール・Push通知の新サービスは初版の条件にしない。

### 共通化するもの／しないもの

| 共通にする | 登録元ごとに分ける |
| --- | --- |
| 原入力・資料・根拠・対象・具体文・時期のデータ契約 | 運営収集の処理状態と、利用者投稿の審査状態 |
| ID・版・再送照合・訂正・公開投影・監査 | AIの判定目的と、その判定でどこまで進めるか |
| 原記録を検索・図・テーマ・Capsuleへ渡す仕組み | 登録権限・収集範囲・公開方針・例外の担当 |
| AI実行履歴・利用量台帳・有限の非同期処理 | 人への通知文・次の操作・処理の優先度 |

入口の区別はサーバー側の権限で決める。利用者がJSONに `source: collection` と書いて審査を迂回できる形にしない。一般投稿のAIチェックを、そのまま運営収集の必須待ち工程にもしない。既存のCapsule保存・限定共有・コメント全体へのAI必須化は本計画の対象外。

公開済みRecord／Entityに対する一般利用者の訂正も、観測版を持つ投稿ワークフローへ通す。元記録が収集由来でも訂正者の権限を継承しない。記録の由来と今回の変更主体・処理方針を別に持つ。運営者の後追い訂正、許可範囲を限定したWorkerの更新、本人のprivate草稿編集はそれぞれの認可で扱う。

| P3：有限収集と後追い整理を接続 | 本番相当APIをWorkerがpollし、少なくとも一つの実読解経路で通常結果を管理者の逐次承認なしに登録。停止・再開・送信失敗・予算不足・後追い訂正が扱える | 独立検証後にβの専用データへ。既存の漫画Workerと新Workerの書込先を区別し、検証中に旧運転を切り替えない |
| P4：本運用の受入 | 異なる二つの実テーマ＋テーマなし登録を実際の入口で通す。Graphと年表の往復、共有、投稿、収集、管理の全経路と登録負担を確認。別DB復元・全件移行照合・公開世代切替をリハーサル | 検証済み固定SHA／資材を3200・βへ揃え、ユーザーが一連の体験を確認できる状態にする |
| P5：正式公開 | 同じ利用経路がplunode.netで使え、既存会員・共有・コミュニティ・通常探索を保全。停止・復旧と日常運用も確認 | 計画採用後の実装・公開指示に従って正式切替。事前backup、追加migration、現行設定継承、配置後確認、記録までで完了 |

P1は価値のある中間成果だが、推奨ゴールBの完成ではない。P2とP3はP0の契約が固まれば一部並行可能。P1の往復UXを最後まで後回しにせず、各段階で実ブラウザ・スマホ幅を確認する。mainへ入れるたびに未完成機能を全員へ露出しない。細切れのPRごとにユーザーの再承認を要求する計画ではない。

本番切替はP4の固定版を基本とする。中間公開を選ぶ場合は「運営登録のみ」「投稿受付は未公開」等、利用者に提供した範囲を別に記録し、全体完成と呼ばない。今回の計画作業ではmain・3200・β・正式サイトを更新しない。

## 5. データの分け方と原本

三つの登録入口――テーマなしの関係まとまり、関係図中心のテーマ、関係図だけでは表しきれない年表中心のテーマ――を、相互排他的な保存型にしない。

| 保存するもの | 初版の境界 |
| --- | --- |
| Entityとその版 | 安定ID、名称・別名・分類・説明・言語。外部IDは任意。既存対象の明示選択・対応と、識別未確定の候補を区別。同名だけで統合しない |
| Recordとその版 | 関係、出来事／エピソード、説明。具体文・関係語・対象・肯否／不確実・scope・時期・根拠。テーマ所属を必須にしない。独立した相反主張は別記録、同じ記録の訂正は新しい版 |
| Source／資料版とEvidence | 資料自体、URLまたは書誌・識別子・取得版を、各記録の参照箇所・抜粋・支持／反証／背景から分ける。同資料でも箇所や支持を無条件コピーしない |
| 入力原本・取得artifact | 入力payload・hash・由来・取得日時・資料参照を追跡。取得できた原応答はprivateな永続volumeへhash付きで保存し、DBには参照を置く。資料全文の公開・永続取得保証はしない。利用条件上保持しない全文はURL・版・必要箇所と理由を残す |
| 意味対応 | 内容版に対する概念ID／概念版・対応理由・確認状態。登録の前提にせず、後から修正・解除。内容訂正時に旧対応を無条件で確定扱いしない |
| Theme／Timeline構成 | 何を紹介するか、記録の選択参照・順序・初期表示。年表の軸・配置・明示した関連を別構成として保持。収集batchとThemeを同一視しない |
| Capsule | 読んだRecord・Entity・意味・根拠・年表構成の断面、編集前baseline、作者の編集文書、初期表示。取得元の現在版とは独立 |

個人草稿、利用者投稿の審査対象版、公開原記録は別の読取範囲。公開テーマ・検索へprivate草稿を混ぜない。公開テーマは公開した構成版を固定し、原記録の訂正を一覧で確認してまとめて反映できる。通常探索は現在の公開世代を読む。Capsuleとコミュニティ掲載は従来どおり固定断面を読む。

原本は正規化前の入力・資料由来を指し、後に訂正できない「真実」を意味しない。入力の再現性、変更者、変更理由、AIの補填を追えることが目的である。

### 物理保存の判断

| 案 | 利点・負担 | 推奨 |
| --- | --- | --- |
| Neo4j正本を拡張 | 既存の探索側へ寄せられる。一方、新しい版・入力原本・投稿状態・PGの会員保存との整合を追加する必要がある | 代案。収集の人手承認を省く分、以前より比較価値は高い |
| PostgreSQLの知識領域を正本、Neo4jを公開探索投影 | 編集・版・入力結果・投稿状態・投影依頼を一つのtransactionで扱い、既存の経路探索資産を残せる。投影遅延・再構築の運用が増える | **推奨**。審査が多いからではなく、訂正と複数の読取先を同じ原記録から維持するため |
| PGだけで全探索 | 管理する読取系が減るが、既存近傍・経路探索・cursorの移植と性能評価が必要 | 初版での全面置換は選ばない |
| 3276のJSONB一行をそのまま拡大 | 小規模実装が容易。テーマ内所有・全件走査・全体ロックが残る | 本番基盤には採らない。各版のpayloadにJSONBを使うことは妨げない |

現在の[ARCHITECTURE](../ARCHITECTURE.md)はNeo4j正本である。上記は明示的な契約変更案で、添付レポートをそのまま確定事項にしたものではない。P0では新方式で代表的な旧Claimと新記録の登録・訂正・非表示・再送・再投影を実証し、容量・応答・復旧の成立を確認する。現行VPSで並行世代を保持できない、または初版の経路を大幅に作り直す必要が判明した場合に限り、Neo4j正本案へ戻して比較する。実測前に費用・性能優位を断定しない。

既存PGインスタンスの独立した知識DB／権限を第一候補とし、会員DB全体の再構築はしない。新たな検索SaaS・ベクトルDB・クラウド保存契約を初版の前提にしない。

## 6. 検索、年表、Capsuleの接続

**意味未対応でも、具体的な関係名・具体文・対象名・範囲で探せ、関係図に具体名で現れる。** 「関係がある」へ薄めて旧ENUMに通すことを禁止する。厳密な意味条件は対応済み記録だけを対象にし、語検索との一致理由を分ける。同義語や同表記の別義は版付きの意味対応で後追い整理する。AIを検索のたびに必須にしない。

公開検索は公開版の索引・安定したページングを持つ。PGの文字列／部分一致索引等を第一候補に、日本語・別名・新しい関係語を実測する。Neo4jは近傍・複数段経路を担当する。検索結果、Graph、テーマ読取に公開世代を渡し、異なる世代を黙って混ぜない。投影中は「登録済み・探索へ反映中」とし、失敗時は再登録を求めず再開する。

公開世代は現在の配信・探索の整合単位であり、Theme／Capsuleが固定した内容参照版とは別である。保存した版を明示して読むことは、現在検索とGraphの世代混在ではない。固定版から現在の通常探索へ進むときに、その切替を分かるようにする。

年表では、出来事の点、継続期間、発生時期の候補幅、開始／終了境界の不確かさを維持する。表示単位に収まる時期を点で示しても原データの精度・曖昧さを失わせない。暦・周期・定性軸、時期のない説明を保持し、年表示でも月日や前期後期等の原情報を捨てない。初版で対応する入力は画面とパッケージから扱え、未対応をJSON専用の隠れ機能として完成扱いしない。時刻等の現未実装項目は対象形式と受入例をP0で確定し、任意の自然言語時刻の自動解釈までは含めない。

「青の時代」のような期間のためにEntityやGraphの辺を捏造しない。その期間中の出来事を自動所属させない。関係の記録は年表行に両端の対象と関係を示し、同じ関係図の辺へ焦点を移せる。説明・期間だけの記録はそのまま年表に置く。対象を通じた探索の導線は保つ。

テーマと年表を同一単位にしない。時間注釈へIDを与え、同一記録を別テーマ・別の年表構成で使えるようにする。初版の描画が一記録一時期を基本にしても、それを原記録の永久制約にしない。年表同士の比較・マージ、2対1、異軸対応は構想として保持し、今回直ちに検証しない。現型で将来の全比較を保証したとは言わない。

既存Graphの入口を維持し、関連テーマから同じ対象を引き継いで年表へ入る。画面内の関係図／年表／並列切替で焦点・選択・図の位置を保つ。スマホは二面を狭く押し込めず、同じ焦点を持つ切替を基本にする。紹介文・絞り込み・補助説明を初期画面の大部分にしない。現3276ページ全体を正式デザインとして採用した扱いにしない。

本番Capsuleには新しい原記録originと版付き断面添付を加え、既存の会員保存・共有・会話へ接続する。Graphが空でも年表だけで成立させる。作者の `initialView` と閲覧者の一時切替を分け、「並べて読む」を再訪・共有先でも再現する。OGPも共有断面から図または代表的な時点・期間を構成する。年表を架空Entityへ変換して既存OGPへ押し込まない。

## 7. AI・Worker・後追い整理

[共通Kevの方針](AI_PROCESSING_DIRECTION.md)に従う。Kevは限定判定、文脈読解用LLMは資料読解・抽出、人は必要な例外・意味判断を担当する。Kevの既存稼働実績を、投稿審査や根拠読解の品質実証として流用しない。公開APIだけを用い、Kev本体・他利用者の設定を変更しない。

```text
運営：収集／意味整理の依頼 ──→ job ──→ ローカルWorker ──→ 収集結果・機械検証 ─┐
                                    └→ Kev／許可した読解器                 │
利用者：直接／Capsule選択 ──→ 投稿版 ──→ AI一次審査・補助 ──→ 受理方針 ────┤
                                                                            ↓
                                      共通原記録・版 → 公開投影 → 検索／図／テーマ
                                            ↑                         ↓
                                       後追い訂正                 Capsuleへ断面保存
```

AI処理とネット取得は同期Web要求から切り離す。Workerは本番APIへoutbound HTTPSで問い合わせる。権限はjob取得・必要資料読取・結果送信に限定し、DB直書きや任意shellの実行権限を渡さない。入力資料を実行命令として扱わない。APIの投稿者・収集者の識別は本文の自己申告ではなく実認証に基づく。

job・試行・lease世代・checkpoint・結果送信を分ける。古い試行の遅着、ACK喪失、PC再起動、取消を通して二重登録を防ぐ。結果送信だけの再試行で取得やAI読解をやり直さない。待機理由は「PC側の処理待ち」「資料の取得待ち」「審査中」「反映中」等、次の行動が分かる言葉で示す。

job開始時の対象範囲・登録先・許可処理・予算・方針版はサーバー側で固定し、再開やWorkerの結果本文から拡大できないようにする。変更は権限を持つ運営者の明示操作とする。これは結果ごとの承認・署名を復活させるための工程ではない。

後追いの意味整理も同じjob実行基盤を使う。原記録を書き換えず、意味対応の候補とその適用履歴を残す。初版は登録済みの知識データ全体を小さい単位で継続的に巡回し、整理候補の生成・根拠確認・適用条件を満たす結果の反映まで自動で進める。人が毎回記録群を選ぶこと、候補を一件ずつ承認することは通常運用の必須工程にしない。現U6c/U6dの人手による選択・確認画面は任意の介入手段であり、この自動化の完成を代替しない。

巡回対象の網羅と、個々の判断を必ず成功させることは区別する。判定不能な項目は根拠・不足・再評価条件を残し、他の項目の処理を止めない。名前一致だけで同一とみなさず、具体語・原語・限定・旧版・Capsule断面を維持する。全データを一度のAI入力へ詰め込む必要はなく、予算・checkpoint・公平な順序で一巡と更新追従を成立させる。全体の概念体系を再編する構想と巡回を一括で後続扱いしない。具体的な不成立があれば、その対象と理由・代案・影響を提示し、無断で範囲を小さくしない。

ChatGPT側はテーマ相談・資料URLと情報の作成・package提出を担当し、Plunode側の認証付き取込APIを第一候補とする。直接配送が成立しない場合の代替はGitHub Issue等で、Workerが同じpackageを共通受理へ流す。Web貼付は任意入口として残す。送信側からの認証・定期実行・再送・失効は実接続で確認し、既存AI教育のGitHub outboxの実績だけで成立済みと推測しない。未確認を理由に手動取込だけで自動連携完成とせず、今回の取込要件を後続へ落とさない。既存AI教育・日次予定そのものは変更しない。

### 利用量管理の初版

- 新しい投稿審査・入力補助・収集・後追い整理を共通台帳へ入れ、全体の日次／月次上限と、一仕事の入力・出力・試行数上限を持つ。投稿審査用の枠を任意の読解処理が使い切らないよう用途別に割り当てる。利用者別の課金・ポイント・財布は作らない。連投・同時実行制限は受付で行う。
- 外部送信前に枠を原子的に予約し、実際の応答で精算する。provider／model・用途・request ID・入力／出力／キャッシュ／推論tokenの取得可能な内訳・単価版・回数・時間を保存する。推論tokenが出力に含まれる場合の二重加算を避ける。取得できない値は推定または不明とする。
- timeoutを消費ゼロとせず、結果不明の予約を保持し、照合してから再送する。勝手なモデル変更・有料fallback・無制限リトライはしない。実績超過は記録して次の実行を止める。provider側の課金上限まで未確認なのに絶対超過しないと保証しない。
- ローカルKevは回数・処理時間・失敗・待ちを記録する。API課金ゼロと資源消費ゼロを混同しない。Chatの定額利用や取得不能な使用量は別表示とし、ゼロとして合算しない。
- 既存AI教育・別サービスをこの工程で改造せず、既存用途の観測可能範囲と未接続消費を一覧へ明示する。「サイト全体を測定済み」とは、未接続が残る間は表示しない。

投稿チェックは正常な短い名称、問題語を含む作品名・資料引用、無意味な入力、スパム、表記崩し、資料中の命令文を含めて実モデルで評価する。判定は対象内容版とhashへ結び付け、変更後の古い通過判定を再利用しない。修正・再チェック・取消・例外確認を通し、誤拒否と見逃しを別に測る。収集用の根拠読解とは評価セットも公開方針も分ける。

Kevで成立する処理は実測して採用する。広い読解等が不足する場合は、許可された一つの外部読解器を比較する。新たな課金サービスはこの計画で有効化しない。利用許可や品質が不足してP2/P3を完了できない場合、手動のみへ黙って縮小せず、未達の工程と費用を抑えた代案を提示する。

### 移行と復旧

1. 現行データ・receipt・由来・権限・保存断面を取得し、別DBで復元確認する。適用済みmigrationを書換えず追加する。3276の仮想データやβの会員・秘密値を本番へ混ぜない。
2. 旧KGのEntity IDは確認済み同一性を保って利用する。旧Claimの不変命題を新Recordの最新版へ黙って付け替えず、`legacyClaimId → recordId + importedRevision`を保持する。旧Capsuleは保存断面を読む。全APIの完全互換維持を初版条件にはしないが、保存済み内容の意味を変えない。
3. 3276は `(themeId, localId)` を起点に移し、同名だけで統合しない。テーマ専用原記録の複製を共通参照と称さない。持ち込む実テーマは選定し、仮想ケースは検証用のままにする。
4. 新探索投影を別世代／独立領域で構築し、検索・近傍・経路・根拠・年表・Capsuleを照合する。PGの登録版と投影依頼を同時に記録し、検証済み公開世代へ切り替える。途中失敗は旧公開版を維持する。
5. 正式切替時に旧publisherの書込先・停止境界を明示し、同じ知識へ旧新の二重書込をさせない。新方式が読むdataの読取先を切り替え、移行中の追加書込も漏らさず追随する。
6. 新形式の書込後は、読めない旧Webへの機械的rollbackや古いdumpでの全上書きをしない。新形式を読める保守版、公開世代の切戻し、投影の再構築を準備する。

旧Workerの未完了job・保存cache・未受理成果・受入済み未公開releaseも切替前に棚卸しする。旧経路で継続、新経路へ由来付きで引継ぎ、保留のいずれかを記録し、成果を取り残さない。新経路へ移す場合は元成果と新操作IDの対応を残し、新旧両方で取得・登録しない。旧承認を新形式の承認へ読み替えず、新経路の処理方針で実行したことを記録する。

通常の訂正・取り下げは旧Capsule断面を自動改変しない。一方、運営による閲覧停止は別操作とし、参照を持つ公開Graph・年表・共有断面・OGPを対象に直ちにアクセス制御できるようにする。元snapshotを消さず、必要箇所の非表示または掲載停止をreader側で適用する。内容の独自コピーすべての自動検出までは保証しない。版保持を公開停止不能の理由にしない。

## 9. 本運用初版の受入条件

| 観点 | 実際に通す操作・判定 |
| --- | --- |
| 三つの入力 | テーマなしのまとまり、関係中心テーマ、関係図だけでは伝わらない年表テーマ。テーマ専用コードや語彙コード追加なしで登録する |
| 実テーマ二つ | AdaとWebbは既存比較材料として利用できるが、準備済みJSONの再投入だけで合格にしない。異なる関係・資料形式を含み、次の担当が画面または公開した取込経路で一巡する |
| 登録負担 | 資料探し、読解、同定判断、入力、補足、再試行の回数・人の実作業時間・機械待ち時間を別に測る。同資料で複数関係、複数資料で一関係、2件目の根拠だけ訂正、別テーマで再利用を含める |
| 入力元の差 | 同じpayloadでも一般投稿を収集扱いに偽装できない。利用者の審査中・修正・部分結果・通知が成立し、収集は通常結果の全件承認を要求しない |
| 実AI | 投稿の適格性と、収集の根拠読解を別々に評価。実model・入力・結果・失敗・待ち・費用を記録。fixture応答だけで完了にしない |
| 意味・検索 | 新語でも具体文と関係名が検索・Graphへ残る。同表記別義、異表記同義、否定、不確実、意味未対応を区別する |
| 保存・訂正 | 同一記録を二つのテーマで参照。対象・記録・意味の訂正→影響確認→Capsuleへ明示取込→同URLへ反映。独自名・配置・説明を保つ |
| 年表と共有 | 年表だけのCapsule、並列の初期表示、期間と同日の出来事、曖昧時期、子軸、時期なし説明を保存・再訪・共有。旧版コメントと固定コミュニティ掲載を保持 |
| 処理と停止 | PC再起動、取得失敗、結果送信後ACK喪失、旧lease、取消、予算不足、結果不明、部分成功、再投影、緊急非表示を通す |
| 全データ巡回・自動整理 | 人が対象を毎回指定せず、旧KG由来を含む知識データ全体を走査し、候補生成・確認・適用・公開反映を進める。ページ上限を超える一巡、追加・訂正への追従、枠切れ後の再開、未解決項目に他項目が妨げられないことと管理者必須操作数0を確認する |
| 本番品質 | PC・スマホ幅、実Google、通常探索との往復、OGPのmeta・画像、共有停止、公開範囲、旧保存読取、移行・復元。SNS表示成功はサイト側meta成功と分ける |

現在の194単体試験・39 HTTP項目・実ブラウザ確認は3276の成果として活用するが、認証・公開投影・実AI・人の登録負担の受入には代用しない。新しい入力語のために毎回コード修正が必要、根拠や具体性が消える、正常分が無関係な失敗や管理者承認で滞留する場合は、初版の目的を満たしたとしない。

所要日数・登録時間の見積値は現時点で置かない。P1/P3で同じ課題を人と実行器に通し、旧経路との必須操作・介入回数を記録する。テーマの紹介価値は件数とは別に、運営者が関係や期間の発見を説明できるか、閲覧者が次の対象へ辿れるかで確認する。

## 10. 今回の計画に含めないもの

初版で後続へ残すのは、年表同士の比較／マージ、任意の軸間自動変換、自律的なテーマ推薦・無制限Web調査、多providerの自動最適化、全員の共同テーマ編集、利用者課金・ポイント制度、大規模検索基盤の先行導入。いずれも構想を否定せず、実需要・能力・運用負担が確認できた時に取り組む。ChatGPT側成果の受け渡しは今回の採用方針でAPI／代替配送を実証するため、以前の「スケジューラ直結は後続」を一括の除外理由にしない。旧記載の「全件自動のEntity統合・概念再編」も、全データ巡回や根拠付きの通常の自動整理まで除外する根拠にしない。概念体系の全面再編は巡回とは別の判断事項であり、未決を自動整理全体の縮小に使わない。

今回の計画採用だけで、共有Kev本体、AI教育・既存日次予定、管理Connector、他プロジェクト、新たな課金を変更しない。新旧収集・公開pipelineの切替はP5の明示的な対象であり、現行運転を今変更する許可ではない。

## 11. モデルと次担当への引継ぎ

**この統合方針を採用した後は、Sol 6.1 高へ移行してよい。Astra Ultraで実装全体を続ける必要はない。** 最初はP0の一まとまりを担当させ、保存・移行・公開の契約をレビューしてからP1へ進む。既存の「次は名称訂正だけ」という順番は、この統合計画を優先する。

モデル間の同条件比較はしていない。推奨は、今回の横断判断を具体的な契約・受入例へ落としたので通常実装を分担できるという作業上の理由による。Astraを再度使うのは、正本選択が実証で崩れる、ユーザー／収集の審査責務が衝突する、または年表の表現能力を削る変更が必要になった等の限定した設計局面。まず高で論点を絞り、Ultraを常用しない。

実装単位・依存関係・そのまま渡せる依頼は[実装引継ぎ](PLUNODE_PRODUCTION_HANDOFF.md)。この計画を採用する前には着手しない。採用後も、最初のP0依頼からmain・本番まで無条件に進む意味にはしない。
