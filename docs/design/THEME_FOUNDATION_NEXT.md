## ユーザー評価の範囲

「並べて読む」は**関係図と年表を同じ記録から読む表現**として推したいという評価を受けた。現ページ全体、テーマ一覧・登録画面・既存Graphとの遷移まで採用されたわけではない。

年表同士の比較／マージ（重畳・複数レーン・連結・2対1・異軸対応）は構想として保持し、今回着手しない。関係図と年表の並列表示の成功を、この比較の検証成功へ読み替えない。比較で原記録の同一性、出所、各表示の選択範囲を失わず、見た目・同名・同時期だけで統合しない。共通尺度への換算は必須にしない。現在の1記録1時期・1軸の型だけで全構想を保証しない。

## 現状判断

案Bの「根拠付き具体文→表示・検索→任意の意味対応→固定Capsule→明示訂正」は独立初版として成立している。年表の時点・継続期間・発生候補幅・境界の不確かさを分け、説明を関係図へ自動転記しない変更もこの方針と整合する。土台を捨てて全改修する根拠は見つからなかった。

ただし、サービスとしての完成と、低負担の実証は別。AdaとWebbは各6対象・初期5記録、Webbの後追加1件を同じ経路で通したが、資料探し・読解・翻訳・入力パッケージの準備はCodexが補った。テーマ専用アプリコード0件という成果と、運営者が自力で登録しやすいという評価を区別する。記録済みの数秒は用意済み文章を自動入力した時間で、人間の作業時間ではない。

3276は単一利用者・localhost限定の評価環境。テーマ所有権、Google認証、コミュニティ、正式OGP、KGとの明示同定、公開版検索、移行・復旧の統合が必要であり、localhost制限を外して公開できる状態ではない。JSONB1行の直列化と全件検索は小規模確認の選択。二重DB／Neo4j投影は規模・経路要求を計測して判断する。

## 登録の入口と収集Chatのルート（方針と未実装範囲）

ユーザーが挙げた三つは、登録したい内容を考える入口として扱える。3は「既存関係グラフ表示上だけでは表せない年表構成を前提にした『テーマ』という概念を持つデータまとまりで登録」という意味であり、関係情報がないデータに限定するものではない。

| 登録の入口 | 扱いたいまとまり | 表示・編集の考え方 |
| --- | --- | --- |
| 1. テーマを持たない関係データ | 既存の関係図で表せる、根拠付きの対象・関係のまとまり | 紹介したい問いやストーリーを先に決めなくても登録できる方向にする。時期付きの関係も保持し、後からテーマや年表で使える余地を残す |
| 2. テーマを持つ関係データ | 何を見せたいかという編集意図があり、関係図で主題を表せるまとまり | 関係と根拠に、選択範囲・紹介文・読み始める場所を加えてテーマとして見せる |
| 3. 年表構成を前提にしたテーマ | 既存関係グラフ表示だけでは伝えきれない、期間・時期の曖昧さ・出来事・説明を含むまとまり | 関係情報も含め、時間上の構成と合わせて読む。関係図・年表・並列表現は内容に応じて利用する |

これらを相互排他的な保存型や、テーマごとの固定rendererにしない。**根拠付き記録、テーマとしての編集意図、年表の構成は別の軸**である。関係中心のテーマにも説明やエピソードがあり、年表中心のテーマにも二者間の関係がある。時期情報付きrelationは年表設定の有無にかかわらず保存できる。期間内にあるという理由だけで、その期間への所属関係・因果・出来事の包含を生成しない。

**現実装との差**：3276の登録APIはthemeを必須とし、entities／recordsをテーマ内に保持している。テーマ意図のないデータをテーマ名なしで登録する入口や、テーマ間で共通の原記録をID参照して再利用する経路は未実装。現時点で「テーマと独立した共通知識の正本が完成した」「同じ原記録を複数テーマで参照できる」と説明しない。テーマなし登録を可能にするのは後続方針であり、現在のフォームへ仮のテーマ名を付ければ解決したとは扱わない。

### Chatから収集する場合の概念ルート

次は将来の入力・運用を考える案であり、既存の収集WorkerやChatの自動処理へ接続した実績ではない。

1. **集める対象と範囲を決める。** 関係データの拡充なら対象・資料範囲・欲しい関係を指定し、紹介テーマがあるなら問い・見せたい価値も添える。Chatは必要に応じてテーマ案を提案するが、テーマ作成を毎回の必須作業にしない。
2. **一回の収集仕事として資料と候補をまとめる。** 取得資料・根拠箇所・具体文・対象候補・時間表現・判断が必要な点を保存する。収集バッチは再開・再送・処理上限のための運用単位であり、テーマと同じ存在ではない。一バッチから複数テーマの候補が生じる場合も、複数バッチで一テーマを育てる場合もあり得る。
3. **共通の入力経路で確認・登録する。** 手入力、根拠パッケージ、Chatの候補で原文・根拠・同定・意味対応を同じ契約に揃える。通常分をまとまりで確認し、曖昧な箇所だけ個別に補う。AIの候補を支持確認・対象同定・意味確定・公開許可の全てを済ませた事実として扱わない。
4. **紹介する構成を必要に応じて作る。** 登録した記録の選択に紹介意図を加えてテーマにし、時期・期間・説明の構成が重要なら年表を組む。Capsuleの独自編集・保存共有・訂正の明示取込へつなぐ。テーマへ採用されない関係データも、保存・検索・後の編集に使えることを目指す。

入力の共通化と同時に、**原記録をどこに所属させるか、安定ID・版・対象参照をどう持ち、複数テーマの選択・並び・説明をどう分けるか**を次の横断設計で決める。テーマ間の複製を共通参照と呼ばず、原記録の訂正がどのテーマ・Capsuleへ影響するかも明示する。既存GraphのKG IDとの対応、私有候補と利用可能な記録の公開範囲、移行時の旧テーマ内IDの扱いを含める。これは現在のJSONBを独立正本化済みとする追認ではない。

この整理は[共通Kevの接続・責務と検証方針](AI_PROCESSING_DIRECTION.md)に従う。資料を横断する読解、限定された判定、人の確認を分け、処理の実行場所・再送・利用上限は実タスク評価後に選ぶ。今回この文書の追加でAI処理を起動せず、既存Worker・共有Kev・AI教育や日次予定・課金設定も変更しない。

## サービス設計の次の判断（方向案、画面構成の採用ではない）

推奨する接続は、通常のGraph探索とテーマ入口を両方保ち、**対象の同一性を確認できる箇所で往復する**こと。同名だけで別対象を結び付けない。テーマを「独立した読み物」として紹介しながら、同じ対象・関係の別の読み方へつなぐ。

| 場面 | 推奨する体験案 | 実装前に固めること・受入 |
| --- | --- | --- |
| 初めてテーマを開く | タイトルだけでなく「何を発見できるか」と代表的な関係／期間を示す。作者の勧める初期表示から始め、関係図・年表・並列をその場で切替 | 作者の初期表示と利用者の表示選択を区別。切替で読んだ行・選択・図の位置が消えない。スマホで紹介文が主内容を押し下げない |
| Graphの対象から年表へ | 対象詳細に関連テーマを少数提示し、選んだ対象を引き継いでテーマ内の記録を見つけられる | KG ID／テーマ対象IDの明示対応。戻る操作で元の探索条件・開いた範囲・位置を復元。未同定なら同名候補として明示 |
| 年表から対象の関係探索へ | 関係行は対応する辺へ、対象は対象詳細／探索へ。説明行は図の辺を捏造しない | 選択した記録と対象の違い、出所、保存版か現在版かを明示。編集草稿を失わず戻れる |
| Capsuleとして持ち帰る | 読んだ範囲を選択し、図の独自編集と原記録の断面を保つ | 元テーマの訂正は比較して取り込む。通常保存・共有反映・コミュニティ固定掲載の意味を維持 |

次にAstraへ依頼するなら、この3つの入口／往復を既存Graphの画面と並べて小さな案にし、戻り方・状態保持・対象対応を決める。今の評価ページ全体をそのまま正式画面へ移植する作業から始めない。新しい見せ方の数を増やすより、一本の往復で年表の価値が伝わるかを判断する。
