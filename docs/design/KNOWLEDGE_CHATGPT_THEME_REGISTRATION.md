## 登録と公開

1. 運営者本人のChatGPT接続から `submit_theme` へ、安定したrequestId、テーマ名・説明・原語、初期表示、根拠付きpackageおよび／または既存の公開Record版を渡す。
2. 原記録の追加は既存の永続取込・原資料照合・意味重複確認・共通AI予算を通す。受付と公開は別で、送信成功だけで完成扱いにしない。
3. 確認が終わった項目の公開Record版を、テーマの構成として固定する。拒否・補足待ちの項目は含めず、除外keyと項目別理由を残す。確認待ちの間に未確認の図を公開しない。
4. `get_theme_registration` で同じ受付の状態、項目別結果、作成したテーマのURLを返す。作成後の変更はChatから `read_theme`／`update_theme` で直接行える。定期収集も必要な場合に限り、別の任意経路として既存の収集計画へテーマを指定する。

package内の新しいEntityは、名称と分類（name／kind）を基本にする。共通取込の初回作成ではaliasesは空、descriptionは空にし、説明・背景などの事実を根拠付きRecordへ置く。構造schemaで表現可能なフィールドと、取込の受理条件は同じとは限らない。名称訂正・訳名などは既存の専用操作を使う。

テーマ内に置くのは共通原記録の参照で、テーマ専用の記録コピーを作らない。既存RecordはIDと内容版を明示する。package内の選択はitem keyで指定し、受理した実Record IDへ束縛する。既存同義Recordを再利用した場合もそのIDを使う。明示した年表配置の新規項目は `recordId: item:KEY` で指定し、既存IDと混同しない。受理できなかった記録の配置を公開しない。省略時は既存の年表自動構成を使う。同一Recordの異なる内容版を一つの構成へ黙って混在させない。

タイトル・説明は運営者が依頼した編集値。知識・関係の原文／根拠と混同しない。一般ユーザーのテーマ作成画面・一般会員への作成権限は追加しない。

## 権限・耐久性

- `missions:collect` は既存の5収集操作のまま。新しい運営テーマ作成は別scope `themes:compose` と本人の運営資格を要求し、同意画面にも明示する。古い接続の権限を黙って広げない。
- 送信者の会員が有効で運営資格を維持していることを受付・処理・読取で確認する。外部資料やpackageに書かれた自己申告から権限を得ない。
- 追加migration `036-theme-registration.sql` でテーマの受付原本・hash・状態・項目receipt・完成先を保存する。適用済みSQLは変更しない。
- 同じrequestId／同じ内容の再送は再利用し、違う内容と別所有者の流用は拒否する。原記録受付とテーマ構成の間、または共通DB commit後の応答喪失も再開できる。
- 取消は未完了のテーマ作成と未反映項目へ作用し、既に公開した共通知識を削除しない。作成済みテーマを取消と偽らない。
- 1運営者の新規作成30受付／日・直接更新200受付／日・同時未完了10件。原記録のAI処理は既存の利用量・再試行・停止を共用し、テーマ構成だけに追加のAI呼出しは使わない。
- 現在公開でないRecordや依存先を、古い受付・完成先リンクから公開しない。既存Capsuleの保存断面と共有は変えない。

## Chatからの直接更新（2026-11-08是正）

- `get_theme_authoring_guide` が登録・更新の完全なschemaと資料URLの例を返す。URLは `package.sources[].content.url` へ保存し、事実・引用・箇所と結ぶ。URLだけを根拠確認済みの知識と扱う意味ではない。
- `search_themes` → `read_theme`（IDまたは当該環境のテーマURL）で構成・原文・資料URL・取得版を読む。共通Entity／Record／Sourceの再利用・根拠追加・訂正には公開参照の検索・読取操作も使える。未公開・停止済み情報を開示しない。検索は共通原本と取得済み旧KGを対象とし、未取得の旧KGまで検索済みと偽らない。
- `update_theme` は取得した `{id, revision}` を対象に、新しい根拠付き項目・既存Recordの追加／版選択、タイトル・説明・原語・初期表示・年表構成、掲載解除・順序を変更する。省略した値と掲載項目は保持。同じテーマIDに新しい内容版を作り、別テーマの新規作成へ置き換えない。
- `removeRecordIds` はそのテーマへの掲載解除だけ。共通知識・別テーマ・既存Capsule・過去の共有断面を削除しない。期間配置は掲載解除した項目のものだけを外す。明示した年表の不整合を推測で修正しない。
- 根拠付き項目の通常確認と意味重複処理を再利用。テーマ自身への出来事・背景は対象テーマの取得版へ結び、共通Recordの受理時に構成だけ先に更新しない。確認済みの構成を最後に適用する。
- 受付／処理／最終適用の各段階で運営権限と公開範囲を確認。対象版が変わったら競合を返し、新しいテーマ版へ勝手に付け替えない。共通DB commit後のACK喪失は同じreceiptから回復する。
- 会員038は受付対象の一意制約を見直し、一つのテーマに複数の作成・更新受付を残す。036／037等の適用済みSQLは変更しない。知識DBの追加migrationは不要。

直接更新に収集計画・定期実行の設定・運営画面操作を要求しない。継続収集は別の任意経路であり、直接更新の代替説明にしない。検証・配置前に是正完了とは報告しない。


## Chatからの訳文登録・訂正（2026-11-09）

テーマ作成／更新と同じ運営者向け `themes:compose` 接続に、次の4操作を加える。収集計画や運営画面操作を前提にせず、接続App・origin・認証主体を維持する。収集専用の古いtokenへ機能を追加しない。

1. `read_theme` で公開テーマと原本のID・内容版を取得する。
2. `read_theme_translation` にテーマの固定参照、原本の `target`、訳す言語を渡す。原文・言語・既存訳文・`expectedRevision`（未登録なら0）・文字数上限を返す。
3. `submit_theme_translation` へ同じテーマ参照と原本参照、訳文・言語・明示した `expectedRevision`、UUIDの `requestId` を渡す。登録と訳文だけの訂正を同じ操作で扱う。
4. `get_theme_translation_submission` で当該会員の受付と確認・公開結果、再試行／利用枠の待ち理由を見る。受付成功は公開完了ではない。未完了の取消は `cancel_theme_translation_submission`。既に公開済みの訳文は取り消し・削除せず、最新の訳文版に対する新しい訂正を使う。

対象は読んだ公開Theme断面に含まれるEntity／Record／Sourceと、そのTheme自身。Entityはname／description／aliases（aliasIndex指定）、Sourceはtitle／bibliography、Recordはassertion／relation／scope／excerpt／locator（根拠の2項目はevidenceId指定）、Themeはtitle／description。任意のJSONパスを許可しない。BCP47の言語tagを使い、原語と異なる言語の訳文として扱う。

訳文の登録で原文やTheme構成の内容版を更新しない。原文の版／hash・否定・範囲・時期・方向と公開文脈を固定して、既存の会員投稿→同値性確認→訳文公開の経路を共用する。既存Capsuleと共有版の訳文は、その断面のまま保持する。利用者が明示して取得元の更新を取り込むまで勝手に差し替えない。

同じrequestIdの再送は、会員IDと操作段階から導いた一意IDを使って既存の永続受付を再利用する。同じIDで異なる文面／対象／テーマ／公開名を送ると競合。応答喪失で草稿だけが保存された場合、状態照会は送信を始めず、同一内容の再送で続きから処理する。後から編集された草稿や取消を、古い再送で提出し直さない。別会員の受付や非公開／停止済みの原本は返さない。

投稿者は認証済み会員に紐付け、`attribution:profile` を既定とし、既存の寄与者表示・活動履歴・結果通知を使う。`anonymous` は公開表示だけ匿名で、内部所有者は保持。確認先とデータ方針はguideのdisclosureで提示し、既存の送信同意版と一緒に記録する。

1呼出しは1原文項目・1言語。既存会員投稿の20受付／時間・同時保存100件、既存の共通AI予算と再試行を共用する。新しい別枠・課金・Worker・DB migrationは追加しない。元の作成packageへ訳文を混ぜるとRecord掲載やTheme版と混同するため、公開した原本の参照を受けてから別操作で届ける。新規テーマ作成時も、その公開結果を読んで同じ会話から訳文を続けて登録できる。


### 年表の文章も訳文へ含める（2026-11-09是正）

テーマの年表見出し・軸の説明・子軸見出しを`axisLabel`／`axisOriginLabel`／`insetLabel`（`axisId`必須）、記録の時期ラベル・周期／定性の軸名・周期単位・段階の意味・開始終了の段階名を`timeLabel`／`timeAxis`／`timeUnit`／`timeCoordinateMeaning`／`timeFrom`／`timeTo`（`timeId`必須）として既存の訳文APIへ含める。`read_theme.translationTargets`は存在する原文と正確なselectorを返し、Chat側が内部のJSONパスを推測する必要をなくす。

日付・数値座標・比較順序のキー・原資料の表記／引用は翻訳で書き換えない。定性の段階名は表示値だけを訳し、配置・グループ・順序は原本座標を使う。範囲の補足（scope）も公開済みの訳文を年表に反映する。既存のtop-level訳文IDは保持し、新selectorがある対象だけidentityへ識別子を追加する。

受付・同値性確認・公開可否・原文hashと版の照合・寄与者・利用量・明示的なCapsule取込は従来と共通。DB migrationは不要だが、新対象のschemaを処理するWebと知識Workerは同じsourceへ更新する。原語の資料引用を残すことと、年表用の説明文が翻訳対象から抜けていることを混同しない。
