# 共通原記録・接続契約 U1

2026-11-02。ユーザーの統合計画採用後の最初の実装。[本運用計画](PLUNODE_PRODUCTION_INTEGRATION.md)のP0／U1を対象とし、独立worktree・3276・専用PGだけで確認する。

## 操作できる範囲

`/themes/records`でテーマなしの記録を追加し、対象・資料を明示再利用できる。複数のテーマから同じRecordの版を選び、元記録や対象名を訂正した後に差分を見て、選んだテーマだけ更新する。記録の内容と表示停止は別に管理する。

この操作面はlocalhostの運営者確認用。会員認証を模したロール選択や、利用者投稿を収集扱いで通す入力欄は設けない。実ユーザー投稿、AI審査、既存会員Capsuleへの新断面添付、公開検索全体は後続U2〜U6の実装である。

## 正本と版

旧`theme75.state`を変更せず、同じ専用PostgreSQLに独立schema `knowledge75`を加える。単一stateを更新する方式から、各Entity／Source／Record／Theme／Mappingの安定IDと追記版へ分ける。各オブジェクトのheadだけを更新し、過去の内容版は保持する。

- Entityは名前・別名・分類・説明・言語を持つ。同名は同一性の根拠にせず、再利用はIDと観測版を明示する。
- Sourceは資料名・URLまたは書誌・言語を持つ。EvidenceはRecord内で、その資料の版・参照箇所・抜粋・stanceを保持する。
- Recordは具体文、関係名、肯否／不確実性、範囲、端点、複数の時間注釈、根拠を持つ。期間や説明だけの記録は対象を必須にせず、架空のEntityを生成しない。
- MappingはRecordの内容版とConceptの版へ対応する。元の具体文や根拠を上書きせず、内容訂正後に旧対応を確定した意味として使わない。
- ThemeはRecordの選択版とEntity／Source／Mappingの観測版、年表構成、初期表示を保持する。同じ原記録を二つのThemeで選べる。

SourceはEvidenceの`source.id@revision`が引用先の正本。資料の新版ができても、既存Evidenceを同じ箇所で支持されたものとして付け替えない。資料の新しい版は差分として知らせ、引用先を変更するにはRecordの明示訂正を要する。ThemeのSource pinだけを変えてこの境界を迂回することを拒否する。

Themeを解決するときは保存した全pinから断面を再構成する。元記録の訂正はその断面を変えない。`refresh-theme`は差分を確認した明示操作であり、対象Themeだけを次版へ進める。現在検索・新規図が使う内容と、保存版を読む操作を区別する。

## 操作主体と公開状態

主体はサービス呼出元が渡す。HTTPの確認APIではサーバー内でlocal operatorに固定し、Host・Origin・専用DBを検査する。本文の`actor`や`source: collection`による権限選択は受け付けない。

| 主体 | U1の書込契約 |
| --- | --- |
| operator | 登録・訂正・Theme編集・確認状態・表示停止を操作できる |
| collector | 信頼したサーバー呼出元からの新規bundle登録だけ。既存記録の直接訂正は許可しない。実job認証・有限範囲の拘束はU6 |
| user | 共通知識への直接書込を拒否する。収集由来の記録への訂正でも同じ。投稿受付・審査ワークフローはU5で接続する |
| reader | 公開記録と公開依存先だけを読む |

`visibility`、`confirmation`、内容版は別。内容が未確認でも運営収集の通常分を人の承認待ちへ置かない。確認状態の更新で内容版やThemeの差分を増やさない。一般利用者の変更には元記録の収集権限を継承させない。

公開読取ではRecordだけでなくEntity・Sourceの現在の表示可否も検査する。過去版を読むときも運営の表示停止を迂回しない。運営者は停止内容を履歴として確認できる。既存の会員共有readerへの同じ停止境界の接続はU4以降であり、U1を全サイトの公開停止完成とは呼ばない。

## 保存・競合・再送

一回の操作は原入力、内容版、操作結果、投影依頼を同じtransactionで保存する。request IDは操作主体と照合し、同じ入力の再送は同じ結果を返す。異なる入力で同じrequest IDを使った場合や古い期待版は409を返す。フォーム入力は成功するまで保持する。

既存対象の再利用は観測したEntity版を照合する。Themeの作成も観測したRecord版・Entity版を受け取り、別タブの更新内容を未読のまま採用しない。更新単位ごとのロックとDB制約を用い、全テーマを一つのJSON行に集めない。

追加DDLは`migrations/knowledge-foundation/001-records.sql`。ledgerにchecksumを記録し、再適用は無変更、checksum相違は拒否する。既存会員migrationや旧theme75のDDLは書き換えない。

## 旧KGとNeo4j投影の実証

既に公開済みのKG artifactから少数のClaimを抽出し、typed限定、scope、期間、根拠・資料・対象、元payloadとhashを保持して取り込む。新しい自由関係だけで成立を判断しない。旧Claim IDは、取り込んだRecordの固定版へ対応させ、後の訂正で最新版へ付け替えない。

投影は既存Neo4jと分離したコンテナ・volumeへ作る。PGの公開断面から世代を構築し、完成した世代だけをactiveにする。途中失敗で旧世代を保ち、訂正・非表示・再投影を実DBで確認する。これはU2の公開検索・経路API全体の実装ではない。

全量移行の性能保証はしない。代表データの所要時間・容量・復元結果を検証記録へ残す。Neo4j正本からPG正本＋投影へ進む判断は、この成立を確認して次単位の契約へ引き継ぐ。

## 現段階のUIの制限

小さい登録画面は一つの根拠と暦の時点／期間を入力する。APIは複数根拠・周期・定性・複数時間注釈を保持する。画面で未対応の入力を完成済みとはしない。編集画面は具体文・関係語・対象名・表示状態までとし、資料版の訂正や高度な時期入力は後続UIへ残す。

保存版を読む操作面の最小実証であり、既存会員Capsuleの作者編集との新origin差分取込・同URL共有更新・年表OGPの統合はU4に残る。旧3276のCapsuleと共有断面はそのまま保全する。
