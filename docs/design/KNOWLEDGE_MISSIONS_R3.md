# R3 テーマに沿った定期収集

2026-11-07。R3b完了、R3c実装・検証中。R3はa（計画・配送API）／b（予定実行の実接続）／c（差分更新・通し確認）まで。全体はR6まで。通常の管理者承認を追加せず、設定したテーマ・範囲・上限に沿って資料探しを継続する。

## 体験と責務

運営の「資料の収集」に定期収集の計画を置く。テーマまたは核となる対象、調べる問い、資料のサイト、頻度、1回の資料・項目上限を一度設定する。計画・次回予定・配送待ち・受付結果を同じ欄で読めるようにし、設定フォームは必要なときだけ開く。既存のURL指定による単発取得も残す。

ChatGPT側が公開資料を探し、原文の引用と具体的な事実をpackageへまとめる。Plunodeは計画に限定した配送を受け、既存の取込・原資料確認・意味重複・自動受理・公開・Theme追記を使う。資料本文の指示は命令や権限にしない。外部Chatの取得不能なtoken量は未計測とし、Plunode側のGemini無料利用量は既存台帳で管理する。別の検索API・新規課金・共通Kev変更を前提にしない。

## 計画と配送

- 会員DBの追加033で計画・実行・配送checkpointを永続化する。既存migrationを書き換えない。計画の版と、実行時の公開Theme／対象の観測版を分ける。
- 運営の本人認証・site operator権限で設定する。外部送信者には専用の配送資格だけを渡す。計画・権限・原本を自由に変更するAPIにはしない。
- Workerは期限付きleaseで1計画を取得する。再起動後も同じ実行IDを使い、期限後の旧世代からの配送は拒否する。計画ごとの上限と次回時刻をサーバーで評価し、溜まった予定を一度に全て実行しない。
- 計画の核につながる情報と指定した資料サイトに限定する。取得した引用は既存の安全な取得器で別に照合する。送信者の「確認済み」は受理根拠にしない。
- payloadを保存してから共通取込へ渡す。ACK喪失時は同じpayload・package ID・receiptを回収し、検索・推論を再実行する理由にしない。空振りも結果として記録する。
- 停止・計画変更は新しい探索と旧版の未反映分を止める。公開済みの原記録や旧Theme／Capsuleを削除しない。再開は新しい計画版で実行し、以前止めた未反映分を復活させない。

R3aでは追加・根拠追加の配送を成立させ、明示訂正・取得済み本文hashとの比較・入力経路の拡充はR3cで接続する。これは初版要件の除外ではない。R3aだけで定期実行の実接続完了とは報告しない。

## R3bの接続方式

このPCのデスクトップアプリで、独立した予定実行「Plunodeのテーマ資料を収集」を使う。毎時に配送clientで取得可能な対象を確認し（アプリ設定は毎時20分）、保存した計画に従ってWeb検索・原資料読取・package配送を行う。[探索・配送手順](../runbooks/KNOWLEDGE_MISSION_RESEARCH.md)を実行ごとの共通指示とし、テーマ専用コードは作らない。1回の実行は最大2計画・20分、1計画の探索は15分・候補10ページを実行側の上限とする。サーバーは計画ごとの資料・項目・直近24時間の回数を独立して守る。

外部Chatの定額利用と、PlunodeのGemini無料APIの利用枠を分ける。外部Chatの取得できないtoken量を0と扱わず、通常の下流確認は既存の利用台帳を使う。PC・アプリ停止中は予定実行されず、復帰後の次の予定でサーバーが許可する仕事から再開する。作業用private directoryと配送checkpointを公開checkoutから分け、予定実行にDBの直接操作やソース変更をさせない。

編集・再開で新しい計画版になっても、直近24時間の実行数はリセットしない。次回の表示・保存値は、その頻度で次の枠が空く時刻以降に揃える。取消・空振りも探索に使った回数として数え、頻度変更では新しい頻度の上限で再計算する。

## R3c：資料の変更と明示訂正

会員034で、計画・実行に属する資料の取得版をprivateに保持する。専用clientのobserveは公開HTTPS・指定host・転送先host・資料数・現在leaseを照合し、サーバー側で取得した原文の圧縮body、本文、各SHA256、抽出方式、前の取得IDを保存する。外部Chatが申告したhashを証明にしない。初回／本文変更／HTMLのみ変更／同一本文を区別し、差分は変更箇所の抜粋であることを明示する。本文は通常の公開APIや履歴一覧へ露出させない。

実行時のsnapshotは公開Recordの固定版・本文・根拠URLを含む。Themeを指定しない計画も、核となる対象につながる公開記録を最大200件取得する（全体検索の結果とは扱わない）。Themeだけの背景はEntityを捏造せず、aboutThemeと追加先Theme版を指定する。

correct-recordは実行snapshotの記録版・about参照・理由を明示し、使う資料をその実行でobserveしてから配送する。差分検知だけでは既存Recordを上書きしない。引用の再取得照合、意味重複、現在の公開範囲・対象版、計画停止・予算は共通取込が再確認する。元のRecord／Source／Theme／Capsule版を保持し、現在Themeへの追記・訂正だけを新しい版にする。本文と翻訳は別であり、異言語の訂正を翻訳更新と読み替えない。textLanguagesの明示値をそのまま保持し、過去のunknownを推測で書き換えない。

## R3c：運営Web貼付

「資料の収集」に折り畳んだ「パッケージから登録」を置く。JSONを貼付→内容確認→明示受付→同じ欄の受付結果・公開リンク、未反映分の取消へ進む。通常の定期収集に管理者操作を追加する機能ではなく、外部Chatなどで用意したpackageの任意の入口。専用bearerはブラウザへ渡さない。

実Googleの運営資格・Origin／現在sessionで受付し、ownerと元namespaceから衝突しない内部namespaceを作る。元JSONとそのhash、変換後payload、receiptをprivateに保持する。同じ操作の再送は同じreceipt、異なる内容は409。owner全体の受付を200package／2000item/24hに制限し、AIの利用量は別の既存プロジェクト予算で守る。これは受付の滞留防止で、AI無料枠の数値ではない。受付履歴は自分の直近10件、停止・権限変更は未反映分の最終確認にも作用する。会員一般の知識投稿・帰属の経路は変更しない。

R3cの配置・実資料・画面確認の成否は検証記録へ残す。R3bの実予定実行と、R3cで未確認の経路を混同しない。
