## まず判断してほしい案

**40名の中心候補と、その作品でクレジットされる9名を対象に、96作品の入口を作る。その中で「池上遼一―稲垣理一郎」「小畑健と複数の原作者」「赤坂アカ―横槍メンゴ」を重点的につなぐ案を推奨する。**

既知の作品に入れる広さと、作り手を介して知らなかった作品に出会う深さを両立する。40人を一律に人気順で選んだ案ではなく、児童・ギャグ・少女漫画・SF・スポーツ・青年漫画・現代の共同制作を混ぜた編集案である。作品が一つしかない起点も入口として残す。

この96作品・49人は**候補枠**で、全件の資料受入が済んだ件数ではない。中心40名中21名は、今回の公式資料確認または既存公開資料で一部作品の接点を確認した。残る19名は個別資料未照合。確認済みの作家でも全作品・全巻・全役割を確認したわけではない。候補と確認範囲は[候補一覧JSON](../research/famous-manga-creators/20261016/candidates.json)に分けて保存した。これは取込台帳・fixture・公開データではない。

今回行ったのは公開資料の調査、既存KGの読取照合、企画案と次版草稿の作成。テーマ承認・収集ジョブ実行・候補自動受入・KG更新はしていない。

## 何を、どの粒度で収集するか

初回の主役は**人物―漫画作品―別人物／別作品**。単に一作家一作品の名簿にせず、複数作品と共同制作者を一緒に収める。人・作品の名前、確認された日英別名、外部ID、出典、役割の原語、確認した刊行物を最低限とする。英語別名はWikidataや正規版の実表記を優先し、自動翻訳で作らない。

| 情報・単位 | 初回の扱い | 既存モデルとの関係 |
| --- | --- | --- |
| 人物 | 同一人物の確認済み筆名はaliasとし、資料中の名義も保持 | person／ExternalIdentifier。共同筆名から個人を推測しない |
| 漫画作品 | 作品として同定する。必要なら漫画版・特定部・特定初出版を名称で明示 | workを利用可。ただし「同じtitle＝同じ作品」ではない |
| 特定巻・版 | ISBN、巻表示、版表示、言語と原資料URLを記録 | 制作Claimのpublication scopeとSource/Citationを再利用。ISBNを作品全体のIDへ付け替えない |
| 人物→作品 | 制作の関与を、資料が支持する範囲で候補化 | CONTRIBUTED_TO。資料に具体RoleがなければroleId=null |
| 著者／作／作画 | 明示された語と対象範囲を照合 | AUTHORSHIP／CREATION／DRAWING。原作をCREATION、著者をDRAWINGへ自動変換しない |
| 原作／漫画／原案／構成 | 原語・参照箇所を台帳へ保持。支持される制作関与は広いClaim候補 | 現行7Roleへ無条件には写せない。具体Roleが必須なら別の意味レビューが必要 |
| 脚本・監修・プロデュース・共同ストーリー | 資料が既存Roleの意味を支持する場合のみ | 残る4制作Roleを再利用。原作＝脚本とはしない |
| 連載と掲載誌 | 初出・媒体の資料情報は必要に応じて保持するが、独立した関係の投入は初回に含めない | 連載単位、掲載関係、雑誌／号／期間は新たな意味判断が必要 |
| 単行本・再編集・完全版 | 出典となる刊行物として区別 | 巻ごとのEntity量産や作品―版―巻の新関係は今回作らない |
| アニメ・映画・ゲーム | 漫画と別の作品。発展先として資料候補だけ残す | adaptation／原作作品間関係をCONTRIBUTED_TOで代用しない |
| 出版社・編集者 | 初回は書誌・資料発行者として使う | 出版社名だけで作者のAFFILIATED_WITHを作らない。編集担当も期間・役割の根拠と範囲が必要 |
| 影響・助手経験 | 面白い発展先だが初回の新規Claim範囲外 | 既存INFLUENCED_BY／ASSISTANT_OFの意味に合う資料は、別テーマで審査できる |

publication scopeは「その刊行物で確認した担当」を限定するもの。第一巻の書誌から全巻・全版・全連載期間へ担当を広げない。刊行年を制作期間に使わない。具体Roleが十分な新規候補で、同じ資料から広いClaimまで必ず二重に新設する必要はない。既存の広いClaimは保持し、同一SPOでも意味・scopeが違うかを既存契約で確認する。

### 同一性の重点確認

- ワンパンマン：ONEのWeb版、村田版、TVアニメを分ける。
- 火の鳥：シリーズ入口、COM版黎明編、漫画少年版黎明編を分ける。
- ジョジョ：全シリーズ・部・巻を分け、初回は第1部を候補にする。
- 藤子不二雄：共同名義とF・Aを分ける。既知の現在名義から初期の共同制作を再解釈しない。
- 武論尊／史村翔：同一人物の資料があるが、原資料上の担当名義を失わない。
- 【推しの子】：漫画、ノベライズ、特典小説、アニメの責任表示を相互転用しない。

## 収集方法と利用条件

**Wikidataを有力な構造化取得元にし、NDLの許諾条件が明確な書誌APIで刊行物を照合し、出版社・本人の資料で具体クレジットを確認する組み合わせを推奨する。** 出版社サイトを一括でクロールする計画にはしない。

| 資料 | 取得に向く情報 | 確認できた利用可能性と残る条件 |
| --- | --- | --- |
| Wikidata | 外部ID、日英label/alias、作品同定の候補、構造化された関係と参照先 | [公式Data access](https://www.wikidata.org/wiki/Help:Data_access)は構造化データをCC0で提供。User-Agent、少数並列、429の待機等を守る。各候補のQID・property・rank・qualifier・referenceは実収集で確認。P50等を既存Roleへ自動同一視しない。画像・Wikipedia本文はこの条件で一緒に取り込まない |
| NDLサーチAPI | ISBN、書名、責任表示、出版者、巻・版・典拠への参照 | [API提供元一覧](https://ndlsearch.ndl.go.jp/help/api/provider)でNDL蔵書 `iss-ndl-opac`／全国書誌 `iss-ndl-opac-national` のメタデータはCC BY互換と確認。今回の一件検索も成功。ただしNDLサーチ全件が同条件ではなく、JPRO等の提供元やコンテンツは別条件 |
| NDLの運用 | 取得頻度・出典表示 | [API利用説明](https://ndlsearch.ndl.go.jp/help/api)では広告収益のある利用は営利に当たる一方、目的を問わず許諾済みのデータは申請不要と区別する。提供元・ライセンスへの表示を維持し、継続利用の連絡協力依頼も確認する。申請や連絡は今回行っていない |
| 出版社公式書誌・発表 | 原語のクレジット、ISBN、特定版・巻の情報 | 集英社、小学館、スクウェア・エニックス、KADOKAWA等で代表例を確認。HTMLに読めることは自動収集／再配布の包括許可ではない。[小学館の利用案内](https://www.shogakukan.co.jp/picture/)などを確認し、あらすじ・本文・画像の転載は計画から除外。機械取得の方法と条件は実行版の前に確定する |
| 本人・権利者の作品解説／回想 | 同一性、作品単位、本人が担当したことの明示 | 手塚公式・原哲夫公式・著者プロフィール等に実例あり。事実確認の参照と本文複製を分ける。インタビューや回想の全文を素材として一括取得する案にはしない |

NDL／Wikidataのメタデータ取得は技術的に実現可能で、既存の資料・台帳・fixture生成へ接続できる。**このテーマ用の新規取得adapterは未実装**であり、今の `run` が収集を始められる状態ではない。資料の存在、APIの応答、利用条件確認、意味の受入を別々に記録する。

初回は各作品について代表刊行物1点を選び、必要な場合だけもう1資料で具体Roleや同一性を確認する。資料が欠ける作品・担当は保留し、推測で件数を埋めない。取得済みのmetadataと判断の台帳を凍結してから既存fixture検証へ進む。技術検証は人間受入の代用にしない。

## 初回方針の比較

以下は企画段階の規模案。新規追加件数や必要時間の確約ではない。

| 案 | 対象の目安 | 探索の楽しさ／行き止まり | 既存データとの接続 | 収集・検証負荷 |
| --- | --- | --- | --- | --- |
| 広く浅く | 60〜80人、120〜160作品。担当はまず基本クレジット | 有名作品に入りやすく、同作者の別作へ進める。一作家一作品や原作者の欠落が残ると星形の小群で止まる | 浦沢・手塚群以外に独立した入口を多く作る | 書誌の定型照合は増えるが、版・名義・例外の審査も対象に比例して増える |
| 狭く深く | 10〜15人、25〜40作品。共同制作を重点確認 | 少数群では役割・別作品の違いを楽しめるが、知っている作品が見つからない人が増える | 池上→稲垣群を優先すれば既存探索の先が伸びる | 件数は少なくても、本人資料・役割・時期を読む負荷が高い。編集・影響まで入れると別テーマへ拡大する |
| **広さ＋重点補充（推奨）** | **40中心作家＋9共同制作者、96作品、115人物作品組の候補** | まず広く見つけられ、共同制作者を介した複数の出口を持つ。全作品を一つの巨大連結群にすることは目標にしない | 既存6人・10作品・17組を再利用し、池上群を確実な足場にする | 定型的な書誌確認と、少数の共同制作・同一性審査へ作業を分けられる。19中心作家の資料照合はまだ必要 |

推奨案で、潜在的に追加する組98に、既存の役割補充や複数scopeが加わる。**新規Claimは100〜140程度を計画見積**とするが、Role追加の方式や資料次第で変わる。1作品につき全巻・全版を集めず、資料確認はおおむね作品数の1〜2倍から始める。実行版では正確な対象リスト・取得上限・出力上限を改めて固定する。

初回で全候補が受入にならなくても、裏付けのある接続群と広い基本カバーを先に前進させる。保留理由を残し、一件の未解決Roleや雑誌モデルを理由に全候補を無期限に止めない。逆に、予算枠を埋めるために弱い関係を追加しない。

## どんなGraph探索を期待できるか

矢印は記録する人物→作品の方向。探索操作では逆方向にも辿れる。以下の**追加部分は未収録・未受入**で、全区間が現在のPlunodeで実行できるという紹介ではない。

1. **既存の信長 ← 池上遼一 → トリリオンゲーム ← 稲垣理一郎 → Dr.STONE**。既存群の先から、別世代・別の作画担当へ渡る。新しい3組のクレジットを今回資料で確認した。
2. **Dr.STONE ← 稲垣理一郎 → アイシールド21 ← 村田雄介 → ワンパンマン（村田版） ← ONE → モブサイコ100**。原作者と描き手の組み替わりを辿る。モブサイコ100への最後の組は個別書誌照合が残る。
3. **DEATH NOTE ← 小畑健 → ヒカルの碁 ← ほったゆみ**、さらに小畑→バクマン。→大場へ。同じ作り手でも相手が違い、資料上の役割語も比べられる。これらの人物作品組は公式書誌で確認したがKG未収録。
4. **サンクチュアリ ← 池上遼一／史村翔**から、史村翔と武論尊が同じ人だと分かり、北斗の拳→原哲夫→蒼天の拳へ。筆名の同一性と作品の関与をそれぞれ別資料で判断する。北斗の拳の武論尊担当と各刊行物scopeの最終照合は次の作業。
5. **BASARA ← 田村由美 → 7SEEDS**、**NANA ← 矢沢あい → ご近所物語**。作家を知らなくても既知作品から別の世界へ進める。SFや音楽の作中テーマは企画上の説明で、実在の科学者や音楽家とのClaimを作らない。
6. **PLUTO → 手塚周辺 → ブラック・ジャック／火の鳥の特定版**。既存の制作・影響の線を保持し、資料で確認した新作品への出口を増やす。同じ著者だから作品同士に直接の影響関係があるとはしない。

収集後の評価は作品名検索→作者→別作品、共同制作者→別作品、原資料への到達を日英で試す。制作Roleの取得・検索UIでの絞り込み対応・世界別の検索網羅性を別々に評価する。ジャンルをまたぐ面白い経路があることと、ジャンル検索できることは違う。

また、現在の[Discovery Search](DISCOVERY_SEARCH.md)の「漫画とつくり手」はPLUTO・浦沢直樹・長崎尚志から公開関係を最大2段辿る集合で、漫画全体の分類ではない。今回の独立した作家群や遠い接続先を追加しても、この入口へ全件が自動で入るわけではない。公開後は既存の名前検索からGraphを開始する経路をまず確認し、広い知識世界からの発見はDiscovery Model側の後続判断として残す。収集テーマIDをそのまま検索タグへ追加する案にはしない。

## 人間が決める必要があること

1. **対象の広さ**：推奨の40中心作家・9共同制作者・96作品で進めるか。現代の控え4名を追加／入替するか。全候補を一律に人気順へ並べない方針は維持する。
2. **具体Roleの優先度**：「原作」「漫画」等は原語を残す広い関与で先に進めるか。Graphでも具体Roleを初回から出すなら、必要な新Roleの狭い意味レビューを別途行うか。今回の企画承認では新Roleを承認しない。
3. **作品の単位**：火の鳥はCOM版黎明編、ジョジョは第1部、ワンパンマンは村田版とする案でよいか。より広いシリーズ入口が必要なら、同じ名前を一個へ潰さず別の設計事項にする。
4. **初回の除外**：新規の師弟・影響・編集担当・掲載誌・出版社の関係・アニメ化を別テーマへ分けるか。今回には基本クレジットと同作品の共同制作者までを含める案。
5. **資料運用**：Wikidata＋条件が明確なNDLメタデータを取得の主経路とし、公式サイトは個別照合に使う案。営利利用の条件、必要な出典表示、継続利用連絡と取得上限を実行版で確認する。
