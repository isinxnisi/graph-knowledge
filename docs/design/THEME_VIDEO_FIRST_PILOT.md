# 初回の企画と試作手順　初代ウォークマンの二つの端子

2026年11月24日・再検討後の作業票。[チャンネル方針](THEME_VIDEO_CHANNEL.md)を試す最初の問いは、**人が選んだ題材と根拠から、観客が自分で面白さを見つけられる一本を脚本・映像にできるか**。初回はウォークマンを選び、車中の回想も人が補っている。テーマから見どころを探す作業の自動化は、別の公開テーマから始めるときに確かめる。

## 脚本担当に渡す企画

**仮題「初代ウォークマンには、隣の声を聴くボタンがあった」**。サムネイル案は一台から二組のヘッドホンへ延びるコード。編集の問いは、同じ曲が二人に届いたとき、隣の人の声はどう届くのか。二人で一台を使う楽しさと不便が、初代機の操作部に結びつくところを描きたい。どこから入り、何を語り、何を観客が見つける余地として残すかは脚本担当が考える。

カセットを知らない人には、一組のヘッドホンで一人が両耳を使って聴くことが伝われば入れる。初代機を知る人には、盛田が友人と出かけたときの記憶がある。語り・画面・音を含む大筋と下書きを一案作り、肝心な主張には表の根拠を添える。累計販売台数や歴代機種は今回の問いの外に置く。

## 編集者が比較用に持つ場面見本

前案の四場面を、同じ資料から成立する一通りの読みとして残す。特に試したいのは二場面目。二本の線を目で追えた直後、隣の人が話そうとする。何が起きるかを先に全部言ってしまうと、図を観る楽しみが消える。横長では同じ画面に二人を残せる。観客が視線を片方からもう片方に移す時間を取れるかが、見本と初稿のどちらにも問える。

| 場面 | 仮の語り | 見せるもの・聞かせる順序 | 視聴者に残ってほしいこと |
| --- | --- | --- | --- |
| 一台、二人 | 「1979年の初代ウォークマン。ヘッドホンを、もう一組つなげます。」 | 既につながった一組を見せ、本体を画面に残したまま二本目の線を延ばす。先端を目で追う間、次の説明を待つ。 | 左右の耳用の端子が別々なのでなく、二人が一組ずつ使える。 |
| 二人で聴いてみると | 「盛田昭夫は、友人と車で音楽を聴いた日のことを書いています。」二人の動作を見せ、間を置いて「話すたびに外すのは不便だった、と盛田は振り返ります。」 | 「盛田昭夫の回想をもとにした図」。二人に同じ曲が届く。片方がヘッドホンに手をかけたところで語りを待つ。実際の車中音声・演奏を再現した印象は与えない。 | 同じ曲は届いている。この人が隣の人に話しかけるならどうするだろう。 |
| 声の通る道 | 「初代は、録音のできない再生専用機です。でもマイクはあります。このボタンを押すと、いま隣で話す声が、ヘッドホンに届きます。」 | 二本のコードを残す。ボタンとマイクの関係を順に示し、声が二人に届くところまで見る。ボタンに「ホットライン」と添える。音を使うなら説明用の短い自作音。録音の再現と受け取られる台詞や当時の曲は要らない。 | 「ホットライン」はその場の声を聴くための仕組み。曲を録る機能ではない。 |
| 最初の一台をもう一度 | 最後の説明の後は語りを休める。 | 二人がつながった模式図をしばらく残す。実物写真に戻す案なら本体全体を見せる。どちらでも、見えない端子を指さす指示は出さない。 | 写真では一台の姿を、図では二人との関係を見直せる。何を面白く感じたかは観た人に委ねる。 |

友人にその妻のピアノを聴いてもらうところから入る構成も成り立つ。この話には「なぜその二人が同じ曲を聴いていたのか」への答えがある。機能を知ったところで興味が途切れた場合に、初めてこちらの入口を比較する。人物を紹介して尺を埋める用途には使わない。[回想の車中のくだり](https://bunshun.jp/articles/-/5676)

## 企画から脚本、脚本から映像へ

| 工程 | 次の担当に渡すもの | 何が起きたら戻すか |
| --- | --- | --- |
| 題材を選び、大筋を立てる | 今回は人が選んだ企画を出発点にする。将来テーマから選ぶ段階では、公開版の記録、使える根拠・素材、関係をたどる面白さのそろう候補を比べる。 | 題名への答えを言うと先に観たいものがなくなるなら、題材内の別の関係へ。 |
| 語りと画面を一緒に下書きする | 意味のまとまりごとに、仮の言葉、実際に見えるもの、見る順序、音・字幕、主要な言明の根拠を対応させる。素材が仮なら明記する。 | 絵が音声の飾りになっている区間は、画面で何に気づけるかまで戻る。図にする価値が薄い場面は声だけにしてよい。 |
| 狙いを伏せて読み、改稿する | 別の読み手には観客に届く言葉と絵だけを渡す。初稿を残し、感じたことと該当場面を聞いた後で、編集者が企画・根拠・見本と照合する。 | 狙いと違っても魅力のある箇所は残す。話が正しくても惹かれないときは要点・筋へ、根拠のない描写は資料へ、読みにくい箇所は文や画面へ戻る。 |
| 清書し、映像担当へ渡す | 改稿後の確定稿そのもの、読み方、字幕、素材とクレジット、図の意味、同期の合図、前の画面から残すもの。参照は採用した版に固定する。 | 代替素材で証拠の意味が変わる、新しい断定が要る、同期に無理がある場合は、元の場面を改稿してから渡し直す。 |
| 仮動画を等速で通して観る | 実際に確認した映像・音声・端末条件と、残った問題。意味・根拠を変える修正は確定稿にも反映する。 | 誤読、音量差、見切れ、字幕と図の競合は該当箇所へ。映像にしてなお発見が弱い場合は、尺の調整を続けず企画へ。 |

引き渡しの具体例は「『もう一組』で二本目が現れ、一組目は残る。二本の行き先が見えるまでマイクの話を始めない」。声の実測尺に合わせた秒数や描画方法は映像側で決められる。完成画面で字幕がヘッドホンを隠すなら、位置や間を変える。声を消して字幕だけにした場合も、語りだけを聞いた場合も、どこで誰が何をできるかを追えるか試す。図の違いは色に加えて線種・ラベルでも表す。

この題材で音を足す価値があるのは、「同じ音楽を聴く」ことと「隣の声が聞こえる」ことの違いを耳でも感じられる場合だ。音で示す区間は解説の声を休ませる。仮音が実機の録音や中村紘子の演奏のように聞こえると場面の意味が変わるので、説明用と分かる短い音で試す。図と間だけで十分なら、その静けさを生かす。

添付原案の要点整理から清書までの十工程は、このように戻り先のある仕事にまとめた。複数回の評価にはそれぞれ異なる問いが要る。資料の正確さは原資料で確かめ、初見の理解は狙いを見せずに確かめ、間や抑揚は実際の音と映像で確かめる。AIによる疑似初見の指摘は改稿候補として扱い、実視聴の記録と区別する。

## 次回、一案を通して何を確かめるか

初稿の出典を照合し、必要な改稿を経て、一案だけを仮声と静止画・模式図で最後までつなぐ。前後を通して初めて、声の説明が図を追い越したか、面白さが途中で尽きたかが分かる。初見の人には編集意図を伝えず、「何か印象に残りましたか。特になくても構いません」から始める。具体的な感想が出たら「どの場面でそう感じましたか」と聞く。題材を知っていたかは後で聞く。少人数の反応は、一人ずつ理由をたどって次の修正を選ぶために使う。

| 初見で起きたこと | 次の編集判断 |
| --- | --- |
| 「二つの端子が気になって、もう一度本体を見た」。盛田の名は出ない | 本人がどこを見直したかを聞き、発見として残す。こちらが期待したあらすじを言わせる追加質問は要らない。 |
| あらすじは正確に言えたが、途中から退屈だった | 興味が止まった場面を特定する。用途を知って話が終わったなら、聴かせたい相手の存在が効くか、企画・大筋へ戻って比較する。 |
| ボタンで録音したと思った／二本目の線を見失った | 初稿の時点で誤解を招くなら語り・図を直す。初稿にあった二人の姿や見る時間が仮動画で消えたのなら、表示の保持・字幕・同期を直す。 |
| 端子の実物を見たかった／次も観たいと言った | 前者には端子を読める写真が要る。後者は次作への期待として受け取り、再訪は別の機会に実作が選ばれるかで確かめる。 |

紙芝居で判断できるのは、話の筋、注意の行き先、模式図から伝わる使い方まで。実物の細部を見分ける体験は適した素材で、本編のテンポや発音は実際の音声と字幕を重ねた等速再生で確かめる。初稿・代表的な修正理由・予想外に良かった箇所を残す。根拠と体験上の問題を直せて、以降の修正が言い換えに終始するなら、その稿を比較の基準にする。

公開後にYouTubeを使う場合、維持率の落ち込みや繰り返し再生が出た区間を、同じ場面への自由回答、字幕・端末条件と照合する。再視聴は見どころの再観察でも、図を読み取れなかった結果でも起こる。異分野の回への実際の移動と、Plunodeに原資料を探しに行く行動には、それぞれ別の意味がある。[YouTubeによる視聴者維持率の読み方](https://support.google.com/youtube/answer/9314415?hl=ja)

公開後にテーマの該当記録が訂正された場合は、固定版と場面の対応から影響を受ける語り・画面・題名を特定する。中心の発見を変える訂正なら動画自体を改訂し、補足で足りる場合は該当箇所と出典が分かる訂正を添える。

## 別案件のソースから持ち帰る判断

参照したのは2026年11月24日に共有された手元の `5.auto-summary-news`。ファイルとGitの追跡状態を読んだ時点の所見で、音声生成・描画の動作は未検証。

- **実音声の長さを受け渡す処理。** `n8n-auto/media-api/app/main.py` は台詞から生成した音声または既存の音声を扱い、ffprobeで得た尺を `voiceSec` として渡す。ffprobeが使えず推定値になる場合もある。Plunodeで後に確かめたいのは「語り終えた後にも、二本の線をたどれる時間が残るか」。声の実測尺と、絵を残したい長さをそれぞれ扱えることを転用判断の基準にする。
- **設定を探す場所。** `n8n-auto/remotion/app/ns-video` は内側の独立したGit作業ツリー。`public/data/common/defaults.json` は追跡されている一方、`public/data/projects/newslab-kagaku-long-0001/parameter.json` など8案件の同名設定は手元にあり、内側Gitの追跡対象外だった。`src/project-entry.tsx` と `src/JsonVideo.tsx` にも内側のHEADとの差分がある。後日挙動を調べる際は「Gitの版」と「手元の案件設定を合わせた状態」を識別する。個々の設定値の転記は不要。
- **必要になった処理だけを照合する。** 旧案件には会話の左右配置や場面間の処理もある。Plunodeでは先に「何を残して見せたいか」を脚本に書き、その意図を実現するための音声計測・素材解決・描画を個別に検討する。初回には人が補った資料、素材選び、聞き直しと修正の手間も控える。二題目でも繰り返す作業が見えてから、`isinxnisi/ns-auto-video` を含む実装候補と照らす。配信頻度や縦長版の構成はその後に判断できる。
