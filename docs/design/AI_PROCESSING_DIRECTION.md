# AI処理：接続・責務と検証方針

2026-11-03更新。2026-10-08／09のKev第一候補の検証を経て、U5ではユーザーの補足と実評価に基づき、**0.8Bの任意助言と、Geminiによる通常分の自動受理を分ける**。[U5の現行契約](KNOWLEDGE_SUBMISSIONS_U5.md)と[実Gemini評価](../verification/KNOWLEDGE_GEMINI_U5_20261103.md)を参照する。

共通Kevの変更管理・公開API境界は第7節を維持する。以前の「外部LLMは読解用途のみ」「queue／provider接続は今回作らない」はAI導入前の段階方針で、現在のU5／U6を止める制約ではない。未評価の任意モデルや追加課金を許可した意味でもない。

| 担当 | U5の役割 | 保持する境界 |

## 2. 精度評価と自動化

判定対象・期待結果・受理ルールを先に固定し、正常な短い名称・問題語を含む作品名・引用・表記崩し・根拠不足・矛盾・限定の逸脱・資料中の指示を通す。開発用セットと別の未見セットを分け、モデル識別・入力／promptの版とhash・応答・失敗を保持する。

今回のGeminiは60件中59件で有効回答、正常20件中18件が自動受理候補、非受理期待40件の誤自動受理0件。これは通常分の自動化へ実装を進める判断材料であり、実世界の誤りゼロや多言語・長文・原資料取得までの証明ではない。完全無誤判定を待って全件保留へ戻さない。

AIの分類・確率は事実の信頼度や資料の代用ではない。原語・locator・具体的意味・時期精度を保持し、不足には補足依頼、誤判定には救済を用意する。受理判定のpolicyとprovider/model・入力版を記録し、取消・内容変更の古い判定を再利用しない。

## 3. 非同期処理と無料枠

Webの投稿保存とAI処理を分離する。利用者は処理中も状態・待ち理由を読み、編集・取消できる。U5の投稿状態とU6の収集状態は同じworkflowに潰さず、job試行・lease・送信結果・利用量の必要な共通部分だけを共用する。

外部送信前にproject／用途／仕事の枠を原子的に予約し、取得できた実使用量で精算する。回数、入力・出力・推論・cache token、時間、失敗を区別し、欠測を0としない。quotaは実projectから確認する。今回確認した無料枠の値を将来の恒久値と扱わない。

429・停止・枠切れはqueueで待機して再開する。応答不明は消費済みの可能性を残し、元試行・予約を保ったまま、待ち時間と回数上限を持つ新試行へ進む。結果送信の再試行とAI再推論を区別し、公開receiptは重複させない。有料自動fallbackやキー切替による枠迂回はしない。

provider固有の送信・応答を業務の受理ルールから分け、同じタスク評価を通した別AIへの追加・差し替えを可能にする。初版で多providerの最適化基盤を先行完成させる必要はない。評価CLIのローカル台帳に加え、βの会員DBへ永続job／利用枠台帳を接続済み。本番VPSのWorker接続はU8。

### 公開APIの使い方と制約

`/v1/systemone`は`state`と、質問名をキーにした`questions`を受け取る。質問型は`choice`（選択肢）、`noul`、`score`。例えば分類では、資料の必要部分を`state`へ渡し、`choice`の`instructions`と`criteria`に判定基準・候補を指定する。これは限定された判定APIであり、自由な文章生成や任意個数のEntity／Claim抽出が既に可能と扱わない。

```json
{
  "state": "確認対象の資料抜粋",
  "questions": {
    "reviewNeed": {
      "type": "choice",
      "instructions": "資料の明示性を分類する。事実の最終受入は行わない。",
      "criteria": {
        "explicit": "対象の関係が明示されている",
        "needs_review": "解釈や限定の確認が必要",
        "not_stated": "資料に記載がない"
      }
    }
  }
}
```

これは入力形式の例であり、グラフ用途の採用済み判定基準ではない。応答には質問ごとの`answers`（型に応じた確率等）と、通常の`/v1/systemone`では配備情報`kev`が付く。OpenAPIの成功応答schemaは詳細未定義のため、将来のクライアント実装時は実応答を確認・検証する。確率はClaimの真偽・信頼度や人間レビューの不要性を保証しない。`/separate`・`/permute`も存在するが、現時点でグラフ側に利用方式を固定しない。

現行のサービス側制限は本文64KiB、最大8質問、質問のcriteria最大16項目、合計入力4096 token、permute最大8回。モデルカード／OpenAPIの上限よりサービス側の制限が小さい箇所があるため、両方を確認する。超過入力は拒否され、勝手な切り詰めを前提にしない。

推論は直列処理で、実行中＋待機中の受理枠は最大2件。過負荷は`429`＋`Retry-After`、本文超過は`413`、schema／token等の不正は`422`。停止・通信失敗・timeoutを判定結果へ置き換えない。接続を中断しても受理済み推論のキャンセルは保証されず、枠は処理終了まで占有されるため、timeout後の無条件再送を既定にしない。共有サービスに永続業務Job Queue・利用プロジェクト間の公平な配分は未実装。
